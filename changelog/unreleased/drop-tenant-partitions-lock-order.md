### Fixed

- **`nexus.drop_tenant_partitions` no longer deadlocks with a search, and gives up cleanly when it cannot get its locks.** It detached and dropped a tenant's leaves one at a time, holding each ACCESS EXCLUSIVE lock to commit, while a search enters through the root `nexus.chunks` and locks partitions after it, so the two could wait on each other (engine 0.1.199, 2026-11-20: `deadlock detected`, the drop's `DETACH PARTITION` the victim). The function now reads the tenant's leaves first (none: returns 0, locks nothing), then takes every lock the teardown needs up front, ACCESS EXCLUSIVE, in one attempt: the manifest, topic-assignment, orphaned-at and collection tables, the two roots (`ONLY`), and the tenant's own model partitions and leaves. It never locks another tenant's leaf, so an index build or vacuum elsewhere does not stop it (changeset `vectors-063-1`, a function redefinition: no data effect, no wire change). No single lock order matches both searches (root, then manifest) and manifest writers (manifest, then root), so the bound is what keeps either safe: each lock is waited for at most 500 ms, below `deadlock_timeout`, and it tries five times with a 0.2 s x attempt backoff, then raises `lock_not_available` (55P03) naming the tenant ("a search, a manifest write, an index build or a vacuum on this tenant's partitions held a lock it needs; rerun, after index builds finish if one is running"). The call is one transaction, so a failed call changes nothing and a rerun finishes; teardown code should retry on 55P03 as well as 40P01. Searches and writers that arrive while it waits queue for at most 500 ms. Once it holds the locks they stay held until the caller's COMMIT, so run it as one autocommit statement (the tenant-removal runbook now says so); a NOTICE reports the attempt taken and the hold to function return.
