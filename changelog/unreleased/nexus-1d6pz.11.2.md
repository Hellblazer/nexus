### Fixed

- **A board notice's read returns the posts it announces** (nexus-1d6pz.11.2; client only, additive). The single-post notice said only "Read it with tuple_rd on that subspace", and a batch notice with no earlier post to anchor on printed `tuple_rd(subspace, n=count)` and called it the newest rows; `tuple_rd` with no `since` reads the OLDEST rows, so a read of `board/ci/nexus-develop--done` returned the morning's rows instead of the post just announced. `tuple_rd` gains `from_created_at` + `from_id`, which start AT a named row, and `through_created_at` + `through_id`, which stop at one, both inclusive (pairs; `from` never with `since` and never parks; `through` only with `from`; a start or end row no longer in the subspace is an error, not the next row). The engine's cursor is exclusive and it has no read by id, so the client starts the cursor at the row's `created_at` with the smallest id and drops what precedes the row; no engine change, so it works on the deployed engine. A single-post notice, and `nx tuple wait`'s, prints `tuple_rd("<subspace>", n=1, from_created_at=..., from_id=...)`; a batch notice prints the read from its first post through its last (`n=300`), because the announced posts need not be consecutive: a post that committed late, or that the announce skipped as claimed or dead, can sort between them and is returned too, while the notice meta's `tuple_ids` names the announced ones.
