### Changed

- An index rebuilt by hand is now seen by the engine. `REINDEX INDEX CONCURRENTLY` carries an index's anchor (its comment) across the swap, so the anchor kept describing the old build, and the deletes-since-build rule, the bulk-delete baseline and the 24 h floors counted from it. The anchor now records the index's `pg_class.relfilenode` as an optional, additive field (the version stays `"nexus_pci":1`, so an older engine reads the text and ignores the field), read on the writing session right before the COMMENT. A pass that finds an anchor whose relfilenode differs from the index's re-anchors the index as built now (current rows and bytes, `built_at` now, origin `built`), starts its bulk-delete baseline over at those rows, and logs `event=pci_anchor_rebuilt_detected` with the old and new relfilenode; a leaf's own HNSW index is handled the same way. An anchor written before the field existed stays valid and is stamped once with the relfilenode, keeping its `built_at`, rows, bytes and origin (`event=pci_anchor_relfilenode_stamped`), so a hand REINDEX of an existing index is seen from then on. The write is refused if the index was rebuilt again between the read and the COMMENT, and an index whose own REINDEX left its anchor owed is not mistaken for a hand rebuild. Nothing for an operator to do: no recipe step, no hand-written anchor.
