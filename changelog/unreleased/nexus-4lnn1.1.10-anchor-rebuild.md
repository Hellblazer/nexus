### Changed

- An index rebuilt by hand is now seen by the engine. `REINDEX INDEX CONCURRENTLY` carries an index's anchor (its comment) across the swap, so the anchor kept describing the old build, and the deletes-since-build rule, the bulk-delete baseline and the 24 h floors counted from it. The anchor now records the index's `pg_class.relfilenode` as an optional, additive field (the version stays `"nexus_pci":1`, so an older engine reads the text and ignores the field), read on the writing session right before the COMMENT. A pass that finds an anchor whose relfilenode differs from the index's re-anchors the index as built now (current rows and bytes, `built_at` now, origin `built`), starts its bulk-delete baseline over at those rows (a bulk delete still owed its REINDEX is no longer owed), and logs `event=pci_anchor_rebuilt_detected` with the old and new relfilenode; a leaf's own HNSW index is handled the same way. An anchor written before the field existed stays valid and is stamped once with the relfilenode, keeping its `built_at`, rows, bytes and origin (`event=pci_anchor_relfilenode_stamped`), so a hand REINDEX of an existing index is seen from then on. The write is refused if the index was rebuilt again between the read and the COMMENT, and an index whose own REINDEX left its anchor owed is not mistaken for a hand rebuild. Nothing for an operator to do: no recipe step, no hand-written anchor.
- A red recall canary that a REINDEX did not cure no longer triggers another REINDEX every day. When a red-canary REINDEX is re-measured and is still red, the engine writes the index's anchor again with an additive `red_unfixed` field and logs `event=pci_red_unfixed_recorded`. The field holds the index's relfilenode, the collection's row count at the red, and the ids (16 hex digits of each query's digest, at most ten, sorted) of the queries that read red (each with a top-1 miss or a mean recall below 0.99), not the whole window of the newest ten. The red-canary trigger skips the index while all three hold: the index has that relfilenode, every query reading red in the canary's latest run is one of the recorded ones (so a red set that only shrinks, because the oldest red query left the window, keeps the hold), and the collection's rows have grown by less than 10% since (the count the deletes rule also uses, retaken at least every 24 h). A rebuild (an engine or hand REINDEX), a red query that is not among the recorded ones, or growth of 10% or more lifts it with no write; a green canary run clears it (`event=pci_red_unfixed_cleared`). So an outlier that stays red keeps the hold while new queries that read green enter the window. The size, deletes-since-build and bulk-delete triggers ignore the field. It lives in the anchor, so it survives an engine restart; the 24 h floor and `red_after_reindex` are unchanged.
