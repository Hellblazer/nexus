### Added

- **The engine reindexes a per-collection index when it has degraded, not on a timer** (nexus-4lnn1.1.10, RDR-230 Phase 2; engine only, rides the next engine tag). After each pass's drops and builds, the engine that holds the builder lock runs `REINDEX INDEX CONCURRENTLY` on at most two indexes, one at a time, largest first, when one of four events has happened: its bytes per row reached 1.4 times the build's (for an adopted index, 1.4 times the install's median for its dimension, or 8.2 KB per row at 1024 dimensions when no index was built here); deletes since the build reached 25% of its rows; its row count fell by 10% since the engine's previous check (which is followed by `VACUUM (ANALYZE)` of the leaf); or the recall canary is red on ten ring queries (a red on fewer is shown and triggers nothing), at most once a day per index. The old index serves until the swap and keeps its name, so the router never loses the collection. After each REINDEX the index gets a fresh anchor and the canary measures it again, with the red run's own queries when there were some; a re-measure that is still red is logged as `red_after_reindex`; a later green run clears that flag, and the 24-hour floor from the index's anchor holds either way. A failed REINDEX gets the build backoff; one cut off by a migration is not charged. Pure ingest never triggers it. The thresholds are constants in `PciReindexPolicy`.
- **`NX_SEARCH_PCI_REINDEX`** (`1`, the default, or `0`; any other value refuses boot) stops REINDEX and the post-delete VACUUM alone: builds, drops and the canary continue. `NX_SEARCH_PCI=0` stops all of it.
- **`GET /v1/status` `per_collection_indexes.this_engine.maintenance`** now reports the REINDEX half: `reindex` (`on` or `off`), `reindexing` (`"in_flight"` while one runs, else null; the index name is not on this unauthenticated route), `last_reindex_at`, `reindexes`, and a new `unanchored` count (leaf indexes whose size rule has no install reference). [additive]

- **A leaf table's own HNSW index is reindexed too, and its REINDEX leftovers are dropped** (nexus-4lnn1.1.10, RDR-230 P2.3). Each leaf's own HNSW index (one per embedding column) gets the size rule at 1.5 times the install's reference for its dimension, read from the leaf's live row estimate; a dimension with no reference reports `unanchored` and the rule stays off. It shares the two-per-pass limit with the per-collection indexes, largest first. A REINDEX that fails or is cut off leaves an invalid `_ccnew`/`_ccold` copy of a leaf index, which the next pass drops through the same path as the per-collection leftovers (the lock timeout protects one still running).
- **`GET /v1/admin/chunks-leaves` `canary_indexes[]`** (operator-only) gains `red_after_reindex` (boolean) and a `trigger` value `after_reindex`. [additive]
