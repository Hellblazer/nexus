### Changed

- **The per-collection route's lexical leg runs its text-gate probe once for all the request's collections instead of once per collection** (nexus-bbtc2; engine only, no client change; rides the next engine tag). The trigram and tsvector GIN indexes are per leaf (tenant x model), so each one-collection probe rebuilt the leaf-wide bitmap for the pattern before it ANDed it down to its collection: about 65 ms an arm for an identifier, 120 arms. The engine now runs one statement over every collection of the request as the first fan-out task, overlapping the vector arms: `nexus.text_gate_probe_by_collection_<dim>` (changeset `vectors-060-1`, three functions, same posture as the existing probes) returns the chashes per collection, or marks a collection dense when it holds 5,001 or more gated rows. Each collection's lexical arm ranks its chashes with `text_gated_search_by_chash_<dim>` and skips its own probe, and a dense collection ranks HNSW-first as before. The function gathers the gated rows (at most 2,000,000; past that it raises SQLSTATE 54000) with a plan the planner may run in parallel, then applies the liveness test and the per-collection cap; it sets `jit = off`. Every arm ranks exactly the rows its own probe would have returned, in the same order. The probe is bounded to half of what the fan-out and request budgets have left when it starts. If it runs past that, or hits the 2,000,000-row ceiling, or fails, every lexical arm runs its own probe with the rest of the budget, as before; the fallback is logged with its reason. A request with one collection, or with `chash_allow`, shares nothing. `NX_SEARCH_ROUTE_SHARED_PROBE=0` turns the sharing off. `NX_SEARCH_ROUTE_PROBE_WORKERS` (default 2, `0` serial) sets the parallel workers the probe's statement may use; the workers come from the cluster pool the engine's arm permits do not count, so a cloud engine should measure before raising it. `NX_SEARCH_ROUTE_LEXICAL` stays opt-in: this entry does not change that default. The request's `event=search_per_collection_lexical` log line gains `shared_probe=<per_collection|fallback|not_started|off>`, `shared_probe_ms` and `shared_dense`; its `slowest_arm_ms` includes each arm's wait for the probe.
- **Measured, one request on an idle 8-core box over a synthetic 414,000-row leaf of 120 collections (nine timed runs each, median, route against `/hybrid-search`):** the two-word query `advisory lock` (D) 5.24 s against 6.22 s and the identifier `resolve_active_session_id` (E) 3.77 s against 4.78 s, both faster with non-overlapping ranges; the single word `serialization` (C) 4.53 s against 4.37 s, tied (overlapping ranges, Mann-Whitney p about 0.9). D's gain needs free parallel workers: with `NX_SEARCH_ROUTE_PROBE_WORKERS=0` the shared probe alone took 8.7 s and D lost, 9.95 s against 6.59 s; E and C were unchanged. No concurrency, no cloud, no leaf other than that one was measured.
