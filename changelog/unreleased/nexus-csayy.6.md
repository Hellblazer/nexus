### Added

- **The engine restores a tenant export into an empty tenant as a session of short requests** (nexus-csayy.6, RDR-248 Step 5, engine half; the client verb `nx backup restore` follows). `POST /v1/tenant/import` takes the file's header (format version, `header_sha256`, the declared `row_bytes`, every table's columns and types, the `embedding_models` rows) and refuses, each naming what failed and each before any upload: a tenant that is not empty (409 `tenant_not_empty` with the table; the rows the engine itself writes for a tenant, the ghost-sweep `catalog_meta` row and a local default tenant's boot-written `embedding_profile` rows, are listed per table in the registry as `seededKeys` and do not count), a format version the engine does not read, a data table or column the engine neither has nor lists as retired (422 `file_not_loadable` naming it), a missing `embedding_models` row, a file past `NX_IMPORT_MAX_BYTES` (default 8 GiB), a tenant that already has an import or export session (409 with the open session's id, which `DELETE` closes), the engine's session cap (shared with export; 503 with `Retry-After`), and an engine that does not report the singleton lock held (503 `singleton_lock_not_held`). A newer file loads when its columns match; the changeset-count difference is shown, not refused. A `derived` table whose columns do not match, or that the target already holds rows for, is skipped and reported with every table that refers to it; a table or column in the registry's retired list is skipped and reported. `PUT /v1/tenant/import/{id}/rows?table=T&part=k` takes a part (a complete binary COPY stream, at most 8 MiB, its SHA-256 in `X-Nexus-Part-Sha256` checked before anything touches the session's transaction) into a temp table with the FILE's columns; a repeat of the last part with the same hash stages nothing, a gap or a different hash for a staged part is refused, a second part while one runs is 409 `part_in_flight`, and a malformed stream fails the session. `POST .../close?table=T&rows=N` checks the staged count against the trailer's. `POST .../commit` answers 202 and loads on the session's held connection in ONE transaction after taking the restore-load advisory lock (503 `restore_busy` with a 60 s `Retry-After` while another load runs, the upload staying staged): it re-checks emptiness, reassigns every serial id from the table's own sequence, rewrites foreign keys and the soft references (`memory_summaries.source_ids`, `nx_answer_runs.plan_id` and `run_summary` `run.plan_id`: a value whose parent was gone is negated, sentinels pass through; `taxonomy_centroids` rows whose topic is gone are dropped and counted), verifies row counts, writes the `rdr248_restore` marker and commits. `GET /v1/tenant/import/{id}` reports `staging`, `loading <table>`, `verifying`, `committed` or `failed: <reason>` with the load's counts, kept 24 hours; `DELETE` aborts (before the commit it rolls back, during the load it cancels the backend); `GET /v1/tenant/import-marker` names the file that committed, for a client that lost the session to an engine restart. Idle 10 minutes and 60 minutes in all before the first commit attempt, `NX_IMPORT_LOAD_MAX` (default 60 minutes) for a restore-wait or a load. `/version` reports `tenant_import_supported`.
- **A tenant create is never queued behind a restore load.** Liquibase `vectors-059-1` redefines `nexus.create_tenant_partitions` with a fourth parameter `p_check_restore boolean DEFAULT true`: on its slow path (the DDL path) it takes the restore-load key shared and raises `lock_not_available` at once while a load holds it, so a tenant create answers 503 `tenant_creation_busy` within about a second with `Retry-After: 30` (header and `retry_after_seconds` alike, 2 s otherwise). A create for a tenant whose partition leaves exist takes the fast path and no lock. The three-argument function is dropped.
