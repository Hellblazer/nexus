### Added

- **The six engine sender modules send the correlation id as `X-Correlation-ID` when one is bound, and no header when none is.** The id comes from `nexus.correlation` (one per `nx` invocation or MCP tool call). It rides on the vector client, the T2 stores and the catalog client, the token store, the T1 scratch store, and the cloud backup export and restore clients. The header is read on each request, so a client built before an id was bound, or under an earlier one, sends the id bound at the time of the call and nothing when none is bound. The scratch and token stores, which keep their headers on a long-lived `httpx` client, carry a request hook that sets or removes the header for the same reason. The cloud export and restore clients send the id to the managed engine too: it is a random per-invocation token that names no tenant data. The engine's health, version, status, whoami and token-mint probes, the daemon and provisioning probes, and the hooks do not send it (the census in `tests/test_z0o2p24_client_version_header.py` names them), and a worker thread started without `copy_context` sends none. The engine does not read the header yet. RDR-167, Phase 1.
