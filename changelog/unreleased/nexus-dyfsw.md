### Fixed

- **The storage-service stop no longer signals a process whose command line it cannot read** (nexus-dyfsw follow-up). Before signalling a recorded or matched pid, the stop re-reads its command line, because the pid may have been reused. Three re-reads treated an empty read as a match: the legacy-lease branch of `nx daemon service stop`, the process-table sweep after it, and the upgrade's survivor sweep before it restarts the service. On Linux `/proc/<pid>/cmdline` reads empty while a just-started process is still in `execve`, so under load the stop could terminate an unrelated process that had taken the pid. An empty re-read is now never grounds to signal. The pid is left running and named: `nx daemon service stop` prints it in its warning about pids it could not identify, the upgrade's replace step names it in its unverified-stop warning, and the upgrade's restart prints an `UNVERIFIED` note for it. The legacy lease is still released, because a process of the same user can read its own command line except mid-`execve`, so one that stays unreadable is not this service. A pid that the later sweep does stop is reported as stopped only. The re-check is one helper in `service_registry.py`, `holder_identity`, shared with the teardown stop (`stop_tier_holders`), which already treated an empty command line as not ours.
