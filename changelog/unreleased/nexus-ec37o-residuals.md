### Security

- **The version and health probes of the service take their proxy and CA from `config.yml`, not the environment, and `nx` ignores a project's `SSLKEYLOGFILE` and `OPENSSL_CONF`.** Two leftovers of the token host-binding fix. First, the requests `nx` makes to the service with no token, whose answers it trusts (the T3 client's `/version` compatibility probe, which supplies `embedding_mode` and the engine floor; the serving-engine version check; the upgrade ladder's version and Voyage checks; the schema fingerprint; the `/version` and `/health` checks of `nx doctor`, the daemon commands and the supervisor; the `nx setup` check), still read `HTTPS_PROXY`, `HTTP_PROXY` and `SSL_CERT_FILE` from the environment, so a project's `.claude/settings.json` could answer them through a proxy of its own. They now use the same transport as a request that carries a token: a proxy (`https` only) and extra CA roots from `network.https_proxy` and `network.ca_bundle` in your own `config.yml`, and nothing from the environment; a plain-`http` loopback probe never uses a proxy and follows no redirect. If you reach the managed service through a corporate proxy or private CA and had only set `HTTPS_PROXY` or `SSL_CERT_FILE`, `nx doctor` and the compatibility probe now need the two `config.yml` keys too (`nx config set network.https_proxy=...`, `nx config set network.ca_bundle=...`). A collection's recorded embedding model already decides its Voyage distance threshold, whatever the engine's `embedding_mode` says (pinned by a test); the engine-wide `onnx-local` mode still sets the upsert batch cap and lifts the Voyage byte budget, by design. The tokenless checks of `nx setup` take the same transport, while its two token-carrying requests take no proxy and no redirect. Second, `nx` and every script the plugin's `hooks.json` launches drop `SSLKEYLOGFILE` and `OPENSSL_CONF` from their environment before their first import, and the telemetry child is started without them: on Windows a project-set `SSLKEYLOGFILE` stopped any process that made a default TLS context (`no OPENSSL_Applink`), elsewhere it wrote the session's TLS secrets to a path the project chose, and `OPENSSL_CONF` can load an OpenSSL engine. A TLS debugging setup that relies on `SSLKEYLOGFILE` for `nx` no longer works, and neither does an `OPENSSL_CONF` you export yourself (a FIPS or custom-provider configuration is ignored by `nx` and the hooks). Still open: an env `NX_SERVICE_URL` with no credential lets a project choose the host of these probes, and a project that plants its own config directory (`NEXUS_CONFIG_DIR`, `HOME`) can supply the `network.*` settings they read.
