### Added

- **A red recall canary run on an index already recorded `red_unfixed` now logs, per sample query, the verdict's own recall and the recall at ef 1000.** The serving side is the run's own HNSW pages at the serving floor ef (600 unless `NX_HNSW_EF_SEARCH` raises it), scored at the verdict's five k; the wide side is one page-1000 statement per query, scored the same way, with the rows returned and the exact ranks it missed at k=120. Each statement's ef is the one the engine's settings batch set, not a computed one: a reading whose observed ef is not the intended one (the router's index set held no valid index, so the statement walked at 1000), or whose plan does not name the index, is logged as `event=pci_canary_ef_diag_failed` and records no recall. Lines: `event=pci_canary_ef_diag` (one per query, with the query id, whether it reads red and whether `red_unfixed` names it), `event=pci_canary_ef_diag_summary`, and `event=pci_canary_ef_diag_skipped` for a red run that is not diagnosed. It appears on the builder-lock holder's next red run of an index already `red_unfixed` (a boot, a daily or a vacuum run), not at the red-canary REINDEX's own re-measure; a green run clears `red_unfixed`. Diagnostic only: the verdict, the red-canary REINDEX policy and the serving path are unchanged (nexus-enew7, step 1).
