### Added

- **Two read-only routes for `nx doctor`'s chash and PDF-metadata rows** (nexus-f3yqd; engine change, ships in engine-service-v0.1.189). `GET /v1/schema/chash-conformance` (any authenticated token, a tenant data token included, so a managed user's doctor can read it; a missing or unknown credential is a 401, and a mint-scoped credential is refused 403 by the auth filter as on every route but the mint) answers `{constraints: [{table, name, present, validated, definition_matches}], all_validated}`; the root token also gets `partitions` and `partitions_not_validated` on each entry (the copies of the CHECK on `nexus.chunks`' partitions and how many are not valid), which are withheld from every other caller because each leaf is a model and tenant and the count would reveal how many tenants share the engine. The body of a non-root call carries nothing tenant-specific from `pg_constraint.convalidated` in one catalog statement, with no table scan and no tenant predicate. It reads the validated state of the two poison tables' width CHECKs only (`chunks_chash_octet_check` on `nexus.chunks` and `catalog_document_chunks_chash_octet_check` on `nexus.catalog_document_chunks`, both `octet_length(chash) = 32`). The legacy-debt legs of the doctor's chash row (`topic_assignments`, `frecency`, `relevance_log`, which carry no width CHECK) are not covered and are unchanged. The migrations add both CHECKs NOT VALID until the chash re-key rung validates them, so a fresh or never-validated store answers `all_validated: false` and the route saves nothing there; its payoff begins where a store has been validated, which the engine-side VALIDATE job of 0.1.190 is meant to make common. `validated` for the partitioned `nexus.chunks` is true only when the parent's own row and every partition's copy are valid, so a parent valid over a copy that is not valid reads not validated. A constraint is identified by its definition as well as its name: the statement reads `pg_get_constraintdef` for the table's constraint and every partition copy and each must deparse to the check the migrations add (PostgreSQL's own rendering of `octet_length(chash) = 32`, a trailing `NOT VALID` aside), so a hand-recreated same-named constraint with a weaker expression reads `present: true, validated: false, definition_matches: false` and `all_validated` false; the definition text is never returned to any caller. A constraint that is missing is `present: false, validated: false, definition_matches: false`, never a vacuous true, and a same-named constraint on another table (the retired `chunks_retired_225` has one) is not read. `GET /v1/catalog/stub-metadata?limit=N` answers `{collections: [{collection, stub_chunks, capped, examples} | {collection, timed_out: true}], limit}` for the tenant's knowledge and docs collections (the registry's content type decides which): the PDF chunks that still carry the pre-RDR-236 upload placeholder (the chunk row holds a document, position or legacy metadata key and no truthy `title`, and its live owning document is a PDF by `nexus.catalog_source_format` whose catalog metadata records no truthy `extraction_method`), counted per collection up to `limit` (1 to 10,000, default 1,000, per collection). `capped: true` means there are more than `limit`, so `stub_chunks` is "at least" that. Each collection is read by a statement of its own, stopping at `limit + 1` stub rows, under a 10 second statement bound and inside a 25 second budget for the whole call: a collection that outlasts its bound, or that the spent budget never reached, is `{collection, timed_out: true}` with no count (cannot say, never zero), the others answer, and the status stays 200; only a failure to list the collections is a 503 (`reason: statement_timeout`, no partial body). A collection with no stub is listed with 0, and up to ten owning-document names (`source_uri`, else `file_path`, else `content_hash <first 12 characters>`) come with each count, the documents with the most stub chunks first. On a test database shaped like the local tenant (244 method-less PDF documents holding about 24,500 chunks in three collections) the whole route answered in about 50 to 90 ms. The rule is the client's `_is_pdf_stub_metadata` as `nx doctor` applies it; the shared case table (`service/src/test/resources/pdf-stub-metadata-cases.json`) pins, for both the Java SQL and the Python client function, the key classes, the falsy title, the PDF test, the extraction method, the naming, the owning-document choice, a chunk held by two documents, a chunk listed at two positions and a manifest row at another collection; the limit, tombstones, tenants, which collections are examined and the examples' order are pinned by Java tests only. `/version` gains `chash_conformance_constraints_supported` and `catalog_stub_metadata_supported`. The client halves are a separate change; until they land the routes have no caller, and the public edge's `/version` allowlist must add the two flags before a cloud client can read them.
