### Added

- **The engine is not started on a store whose legacy-width chash rows its first boot would delete, until you take a backup** (nexus-f3yqd). An engine since 0.1.91 deletes chunk rows (and the manifest rows that point at them) whose chash is not 32 bytes when its `hygiene-001-5` and `hygiene-001-8` migrations run; a store that last ran an older engine can still hold them, in `nexus.chunks` or, before 0.1.75, in `chunks_384/768/1024`. Managed and bring-your-own Postgres installs are exempt, because their operator owns backups: the guard does not run there, and the supervisor log records the skip (`legacy_chash_guard_skipped`). Before the supervisor starts an engine on the bundled Postgres it counts those rows (as the cluster superuser, because the chunk table enforces row-level security even for its owner), each table gated on its own migration. If any exist the start is refused with exit 75: the message gives the counts and says to run `nx backup`, and Postgres is left running so the backup can read it. The refusal creates an empty marker schema, `nx_legacy_guard_<token>`, in your database, and a backup clears the refusal only if `pg_restore -l` lists that schema, so a dump of another store or an older one is not accepted; it must also list the chunk and manifest data. The next `nx daemon service start` or `nx upgrade` goes on once such a dump is in `~/nexus-backups/`; a dump written elsewhere is named with `nx daemon service start --legacy-backup PATH`, on `--foreground` too. Nothing runs the backup for you. The refusal and the backup that cleared it are kept in `legacy-chash-guard.json` in the config directory; the marker schema is dropped after the clear. `nx upgrade` reports the refusal by name and tells you to run `nx backup`. A backup is accepted only when it is a complete dump (`pg_restore` reads all of its data), so a truncated or half-written dump does not clear the refusal. A refusal recorded for a different database (a store wiped or re-initialised under the same config directory), or one whose rows are gone, is retired at the next start instead of blocking it. If Postgres is not running when you start (after a reboot, or `nx daemon service stop --with-pg`), the start brings it up so `nx backup` can run, and the engine stays stopped until a backup clears the refusal. `nx upgrade` reports a start that was held by the guard as the guard, not as "still starting"; for a large backup run `nx daemon service start` itself, which has no time limit (reading a dump to its end can take minutes, and a dump it timed out on is named in the refusal).
