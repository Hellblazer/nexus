### Added

- **The engine is not started on a store whose legacy-width chash rows its first boot would delete, until you take a backup** (nexus-f3yqd). An engine since 0.1.100 deletes chunk rows (and the manifest rows that point at them) whose chash is not 32 bytes when its `hygiene-001-5` and `hygiene-001-8` migrations run; a store that last ran an older engine can still hold them, in `nexus.chunks` or, before 0.1.75, in `chunks_384/768/1024`. Before the supervisor starts an engine on the bundled Postgres it counts those rows (as the cluster superuser, because the chunk table enforces row-level security even for its owner), each table gated on its own migration. If any exist the start is refused with exit 75: the message gives the counts and says to run `nx backup`, and Postgres is left running so the backup can read it. The refusal creates an empty marker schema, `nx_legacy_guard_<token>`, in your database, and a backup clears the refusal only if `pg_restore -l` lists that schema, so a dump of another store or an older one is not accepted; it must also list the chunk and manifest data. The next `nx daemon service start` or `nx upgrade` goes on once such a dump is in `~/nexus-backups/`; a dump written elsewhere is named with `nx daemon service start --legacy-backup PATH`, on `--foreground` too. Nothing runs the backup for you. The refusal and the backup that cleared it are kept in `legacy-chash-guard.json` in the config directory; the marker schema is dropped after the clear. `nx upgrade` reports the refusal by name and tells you to run `nx backup`.
