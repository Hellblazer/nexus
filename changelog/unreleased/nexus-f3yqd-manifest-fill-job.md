### Added

- **The engine fills the manifest section labels and spans itself, as a background job, so the upgrade ladder stops reading chunk metadata a batch at a time** (nexus-f3yqd; engine change, ships in engine-service-v0.1.188). `POST /v1/catalog/manifest/fill` with `{kind: "labels"|"spans", dry_run?: bool, batch_rows?: int}` (default 1000, at most 5000) answers 202 `{job_id, created}`, and `GET /v1/catalog/manifest/fill/{job_id}` reads it: `state`, `stage`, `elapsed_ms`, `done_rows`, `total_rows` (null when the start-of-job count was capped or timed out), `filled`, `cursor` (`{doc_id, position}`, the last manifest key scanned), `counts` (`fillable`, `edge` when known, `skipped_changed`), `safe_to_stop: true` and `on_stop: "resumes from the last committed batch"`, and `http_status`, `error` and `reason` once it has failed. The job fills exactly the rows `GET /v1/catalog/manifest/fillable` counts as `fillable`, with the same guards (one predicate, read by both), so after a completed job that count answers `fillable` 0 for the kind; the `edge` rows (an unreadable chunk stamp, a label or page value SQL cannot decide) are never written and stay reported. Each batch is one transaction: the next window of manifest rows after a keyset cursor, then one `UPDATE ... FROM` over that key range whose own WHERE re-checks the target row, so a row a concurrent writer changed first is skipped and never overwritten. Labels take the chunk's `section_title` and `section_type` (the empty label for an absent key or a JSON null) and its `page_number` (NULL for 0), and set `labels_written`; spans fill each NULL column the chunk records, per column, leaving every other column as it is. It writes nothing on the document or the chunk rows: `catalog_documents.indexed_at` is not restamped and no chunk is stamped as orphaned, so the client's restore step is not needed. A dry run counts and writes nothing, with the counts a real run would report. One job runs per tenant and kind: a second start with the same request is handed the running job (`created: false`), so a later box joins it, one with the other `dry_run` is a 409 naming the running job, and a job of another tenant is neither joined nor visible. The job is fill-only, so a restart, a stop or a failure is resumed by starting it again; it is held in memory and a poll for an id the engine lost is a 404. `/version` gains `catalog_manifest_fill_job_supported`. The client half (starting it, and the policy for an unattended run against a managed service) is a separate change; until it lands the routes have no caller, and the public edge's `/version` allowlist must add the flag, and the two routes, before a cloud client can use them.
