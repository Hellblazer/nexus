### Added

- **The engine fills the manifest section labels and spans itself, as a background job, so the upgrade ladder stops reading chunk metadata a batch at a time** (nexus-f3yqd; engine change, ships in engine-service-v0.1.188). `POST /v1/catalog/manifest/fill` with `{kind: "labels"|"spans", dry_run?: bool, batch_rows?: int, after?: {doc_id, position}}` (`batch_rows` default 1000, at most 5000; `after` is the `cursor` a poll showed, and the walk begins after that manifest key) answers 202 `{job_id, created}`, and `GET /v1/catalog/manifest/fill/{job_id}` reads it: `state`, `stage`, `elapsed_ms`, `done_rows`, `total_rows` (null when the start-of-job count was capped or timed out), `scanned_rows` and `manifest_rows_estimate` (progress is `scanned_rows / manifest_rows_estimate`: a window holds only the manifest rows the kind's prefilter admits, so the estimate is the count of exactly those rows past the start cursor, taken once at the start under the fillable count's 10 s bound and null past it; writers change the manifest meanwhile, so the fraction can pass 1), `filled`, `cursor` (`{doc_id, position}`, the last manifest key scanned), `counts` (`fillable`, `edge` when known, `skipped_changed`, never below 0), `safe_to_stop: true` and `on_stop: "committed batches stay written; a new start re-reads from the beginning, or from the cursor passed as after"`, and `http_status`, `error` and `reason` once it has failed. The job fills exactly the rows `GET /v1/catalog/manifest/fillable` counts as `fillable`, with the same guards (one predicate, read by both), so after a completed job that count answers `fillable` 0 for the kind; the `edge` rows (an unreadable chunk stamp, a label or page value SQL cannot decide) are never written and stay reported. Each batch is one transaction: the next window of manifest rows after a keyset cursor, then one `UPDATE ... FROM` over that key range whose own WHERE re-checks the target row (including its `chash`), so a row a concurrent writer changed first is skipped and never overwritten. A batch costs the manifest rows its window scans to admit `batch_rows` rows, which is `batch_rows` only while the admitted rows are dense: there is no partial index (an index build on an existing store is boot-time heavy work), so a sparse admitted set scans many rows per admitted one, and for spans the converged case walks every row whose chunk records no span, on every start. The UPDATE waits at most 5 s (system property `nexus.manifest.fill.lock_timeout_ms`) for a row another writer holds; past that the batch runs again skipping the held rows (`FOR UPDATE SKIP LOCKED`), which count in `skipped_changed` and which the next start fills, so a long reconcile commit does not fail the job. The system property `nexus.manifest.fill.pause_ms` (default 0) is a pause after each batch, to slow a fill on a managed tenant. The job also stops, ending `job_stopped`, when the engine's shutdown interrupts it. Labels take the chunk's `section_title` and `section_type` (the empty label for an absent key or a JSON null) and its `page_number` (NULL for 0), and set `labels_written`; spans fill each NULL column the chunk records, per column, leaving every other column as it is. It writes nothing on the document or the chunk rows: `catalog_documents.indexed_at` is not restamped and no chunk is stamped as orphaned, so the client's restore step is not needed. A dry run counts and writes nothing, with the counts a real run would report. One job runs per tenant, whatever its kind: a second start with the same `kind` and `dry_run` is handed the running job (`created: false`; its `batch_rows` and `after` are ignored), so a later box joins it, one with the other kind or the other `dry_run` is a 409 naming the running job, and a job of another tenant is neither joined nor visible. The job is fill-only, so a restart, a stop or a failure is resumed by starting it again, which re-reads from the beginning over what is left, or from the `cursor` passed as `after`; it is held in memory and a poll for an id the engine lost is a 404. `/version` gains `catalog_manifest_fill_job_supported`. The client half (starting it, and the policy for an unattended run against a managed service) is a separate change; until it lands the routes have no caller, and the public edge's `/version` allowlist must add the flag, and the two routes, before a cloud client can use them.
