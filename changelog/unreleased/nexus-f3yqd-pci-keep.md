### Fixed

- **An engine restart no longer throws away the per-collection index build in flight** (nexus-f3yqd, engine-service v0.1.186). Two places ended the builder's `CREATE INDEX CONCURRENTLY` on every restart, so a store whose first rollout queued several large builds (per-collection indexes first shipped in v0.1.158) never finished the queue if the engine restarted often, and each restart cost a full rebuild: tens of GB of writes for 20 to 30 minutes. (1) Boot: the migration walk ended every builder session on every boot. It now does so only when it has a changeset that is not `runAlways` to run, or a partition access repair to make; with only `runAlways` changesets pending (every boot of an unchanged release) it leaves the build alone and logs `event=pci_builders_kept count=N reason=only_run_always_pending`, or `event=pci_builders_terminated count=N reason=schema_changesets_pending n=M`. The `runAlways` bodies take no lock that conflicts with a build: the grants take no relation lock, and `vectors-034-2` waits at most 5 s on a leaf and skips it. (2) Graceful shutdown no longer ends the builder's backend (`BackendReaper.terminateAtShutdown` reaps the pool's backends only). The build finishes in Postgres; its session holds the builder advisory lock, so the next engine's builder reports standby and starts no parallel build, and when the build is done that engine adopts the index (`event=pci_anchor_adopted`). This helps on every restart that leaves Postgres up (a supervisor respawning the engine, `nx daemon service stop` without `--with-pg`, the upgrade finish's restart). `--with-pg`, the Windows session-end stop, a PostgreSQL bundle replacement and a reboot stop Postgres, which ends the build; the next pass rebuilds it. A real schema changeset still ends it, so the first boot after an upgrade that carries one rebuilds. A build now runs under a 6-hour `statement_timeout` (it was 30 minutes, and a build longer than that was cancelled and rebuilt from zero after the failure backoff, which could repeat on a large collection); the bound stays finite because it is also how long an orphaned, stalled build can hold the builder lock and keep later engines in standby. Drops and comments keep 30 minutes.
- **A failed index is rebuilt in the pass that drops it** (nexus-f3yqd). The planner counted a failed (invalid) index as serving its collection, so the pass dropped it and the rebuild waited a full sweep period (600 s by default). The same pass now drops and builds, and skips the build, logging `event=pci_build_skipped reason=failed_index_not_dropped`, when the drop did not happen.
