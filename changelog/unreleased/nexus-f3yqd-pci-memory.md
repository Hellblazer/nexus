### Changed

- **The index builder's session runs under a bounded `maintenance_work_mem`, and `NX_SEARCH_PCI_BUILD_MEM_MB` overrides it** (nexus-f3yqd). pgvector builds the HNSW graph in memory while it fits and finishes the rest on disk, one WAL-logged change at a time. At Postgres's 64 MB default, a 40k-row, 768-dimension build (a 164 MB index) took 123 to 128 s and wrote about 1.0 GB to disk, and an 80k-row build (328 MB) took 340 s and wrote 3.1 to 3.3 GB; at 1 GB the same builds took 33 to 37 s and 75 to 85 s and wrote 0.6 to 1.2 GB (stock pgvector 0.8 and PostgreSQL 17, ext4 on LVM; the WAL is 136 MB and 272 MB either way). The value is `min(1 GB, one eighth of RAM)` where the JDBC URL names a loopback host or a socket (the bundled Postgres), and Postgres's own setting is kept for a Postgres elsewhere. It is set on the builder session only, not on a request session. A parallel build shares one graph area of that size, so it is the total, and the area lives in shared memory: where `/dev/shm` is smaller than the setting (a container's default is 64 MB) the build fails with SQLSTATE 53100, so the builder then drops the failed index, builds serially and starts every later build serial (`event=pci_build_shared_memory_short`). `NX_SEARCH_PCI_BUILD_MEM_MB` (integer MB, 16 to 2047, refused at boot outside that; PostgreSQL on Windows rejects a `maintenance_work_mem` above 2047 MB, which would fail every build) wins in either case. The value in effect is logged at boot as `event=pci_build_memory`.
