### Added

- **The engine validates the chash width CHECKs itself, as a job a user starts** (nexus-f3yqd; engine change, ships in engine-service-v0.1.190). `POST /v1/admin/validate-constraints` with `{dry_run?: bool}` (root token only; any other credential is a 403) answers 202 `{job_id, created}`, and `GET /v1/admin/validate-constraints/{job_id}` reads it: `state`, `stage`, `elapsed_ms`, `tables_done` / `tables_total`, `current` (`{table, bytes}` for the table being validated, since `VALIDATE CONSTRAINT` gives no row progress), `validated`, `refused` (`[{table, constraint, reason, bad_rows, bad_rows_capped, example_chashes}]`), `deferred` (`[{table, constraint, reason}]`), their counts, `would_validate` on a dry run, `all_validated` (the conformance route's answer after the last step), `safe_to_stop` (always true) and `on_stop`. **It never runs at boot and nothing in the engine starts it**: a user's `nx` command (or `nx doctor --fix`) sends the POST, because a VALIDATE scans a whole table and a boot-time VALIDATE crash-loops an install whose rows differ from the measured one. One job runs on the whole engine (the constraints are table-wide): a second POST with the same `dry_run` is handed the running job (`created: false`), the other `dry_run` is a 409 naming it. The job validates exactly the constraints the conformance route lists (`chunks_chash_octet_check` on `nexus.chunks`, `catalog_document_chunks_chash_octet_check` on `nexus.catalog_document_chunks`), deepest first: each leaf partition's copy of the chunks CHECK as a step of its own on its own connection, then the model partitions, then the parent, which is cheap once every copy is valid. A constraint that is already valid is skipped, and that is the whole of resume: a rerun after a refusal, a stop or a restart does the steps that are left, and a validated constraint stays validated. A constraint whose definition is not the expected `octet_length(chash) = 32` (a same-named weaker one) is refused as `definition_mismatch`, never validated, and so is every table above it, because validating a partitioned parent recurses into its copies. Each leaf first gets a bounded pre-check, a count of the rows whose chash is not 32 bytes (capped at 1,000, under a 60 second statement timeout, holding only an ACCESS SHARE lock) read as every tenant's rows. **The job never lifts FORCE row-level security and never takes an ACCESS EXCLUSIVE lock on any table**, so search and indexing go on while it runs. The admin role is the schema owner, not a superuser, so the pre-check reads a table only where the role already sees every row (the `nexus.chunks` leaves, through the migrating role's owner policy); where it does not (production's `nexus.catalog_document_chunks`) the pre-check is `unavailable`: the VALIDATE decides, a `check_violation` is the refusal, and only then (a clean VALIDATE pays nothing) the bad rows are counted per known tenant through that tenant's own scoped session (ACCESS SHARE only, within a 30 second budget and the 1,000 cap; `bad_rows` is the count, `tenants` lists `{tenant, bad_rows}`, up to three `example_chashes`, `bad_rows_capped` true when the cap, the budget or an unreadable tenant cut it short; a tenant with rows and no token is not counted, so it is a floor, and `bad_rows` is null when nothing was counted), with `precheck` still `unavailable`. A dry run reports `precheck: unavailable` for that table instead of saying it would validate. Each refused or deferred entry carries `precheck` (`clean`, `bad_rows`, `unavailable`, `timeout`, or null for a table with copies below it). A table with a counted bad row is refused naming it, with the count and up to three example chashes in hex, its constraint stays NOT VALID, and the job goes on to the next table; a table above a refused one is `deferred` as `descendant_not_validated`. The `ALTER TABLE ... VALIDATE CONSTRAINT` runs under a 5 second `lock_timeout` with a bounded retry and backoff on `55P03` (`SHARE UPDATE EXCLUSIVE`: searches and writes continue while it scans), and a step that gives up on the lock or the statement timeout is `deferred` (`lock_timeout`, `statement_timeout`), not refused, since nothing is wrong with the data and a rerun tries it again. A dry run runs every pre-check and alters nothing. The job's bounds are properties: `nexus.validate.lock_timeout_ms` (5000), `.lock_attempts` (5), `.retry_backoff_ms` (1000), `.statement_timeout_ms` (30 minutes), `.precheck_timeout_ms` (60000), `.precheck_cap` (1000) and `.pause_ms` (0, between steps). `/version` gains `chash_constraints_validate_job_supported`; until the client halves land the route has no caller, and the public edge's `/version` allowlist must add the flag before a cloud client can read it. The job survives its own restarts: the engine's shutdown cancels a VALIDATE in flight, and the schema migration walk ends any `nexus-chash-validate*` backend (as it ends the index builders) when it has schema work, so an orphaned VALIDATE never makes a walk queue behind it; a VALIDATE is atomic, so nothing is lost and the next job resumes. A database error in one step (a dropped partition, a deadlock, an unreadable state) defers or retries that step, never fails the job, and `all_validated` is null when the final read of the constraints could not run. The three timeout properties are clamped under the admin connection's socket timeout; `nexus.validate.pause_ms` defaults to 100 ms between steps to spread the IO, and `nexus.validate.tenant_count_budget_ms` (30000) bounds the per-tenant count. A POST body of `null` is a 400. The chash width CHECKs stay validated as the store grows: a leaf or model partition created afterwards copies the valid parent constraint valid (pinned by a test), and a changelog lint fails when a later changeset adds a `*chash_octet_check` NOT VALID without a named exemption.
