### Added

- **The engine works registered data moves in the background (RDR-246).** After the HTTP listener binds, a `DataMoveWorker` thread takes the open rows of `nexus.data_moves`, oldest first, one at a time. Each pass grants `dml_utils_owner` read access to the driving table and its leaves, checks that dml_utils is installed, that the admin connection reads every row and that a `max_worker_processes` slot is free, then runs dml_utils' committing entry point once per tenant on a dedicated autocommit connection under that tenant's `nexus.tenant` setting; a list-partitioned (model, tenant) table such as `nexus.chunks` is run once per leaf of the tenant, never partition-wise. A run an engine stop interrupted resumes at its next chunk. A move that cannot proceed is held with the reason and retried; `NX_DATA_MOVE_SLEEP_MS` (clamped to 0 to 60000) overrides each move's pause between chunks. No move is registered yet, so nothing changes for an existing install (nexus-f3yqd.2.13).
