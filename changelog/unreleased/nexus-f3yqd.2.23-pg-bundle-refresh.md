### Fixed

- **`nx upgrade` now replaces an old PostgreSQL bundle that lacks pg_background.** An install keeps the bundle it was first set up with, and pg_background first shipped in the bundle at engine-service-v0.1.190 (conexus 8.2.1), so an install first set up on 8.2.0 or earlier reached a newer engine without it and every background data move stayed blocked. A plain `nx upgrade` (not `--auto`, not an MCP start) now takes the pinned release's bundle and swaps it in, in two cases: the engine version changes, or the engine is already the pinned one but the extracted bundle has no `pg_background.control` (under `pg-bundle/bundle/share/postgresql/extension/`); `nx upgrade --dry-run` lists the second as pending, and `nx doctor` warns on a `PostgreSQL bundle` row for as long as it holds. The bundle is downloaded and staged with the stack running; the engine and the bundle are then replaced under one stop and one start of PostgreSQL and the storage service. The swap restarts PostgreSQL, which an engine replacement alone does not and which stops an index build in flight, so it needs an attended `nx upgrade` and an idle engine (background work other than a data move that is only blocked, failed or paused, and index builds and vacuums, count as busy): an unattended run or a busy engine on an engine change still installs the engine and leaves the bundle, and on a converged engine it waits and says so, naming `nx daemon service install-binary <tag>` as the explicit route; the unattended passes only say it is pending. The client creates the extension the next time the service starts. This is a binary swap, not a data migration: no user data is rewritten, and a data directory made by PostgreSQL 17 starts under any other 17 bundle. A bundle with the same bytes swaps nothing and stops nothing; cloud mode and an install on its own PostgreSQL are untouched; a download, verification or extraction failure leaves the old bundle in place and the stack running, is reported as a note, and the next `nx upgrade` tries again. A swap that would change the PostgreSQL major version (read from the data directory's `PG_VERSION`) or drop pg_background from a bundle that has it is refused before anything is stopped; the first needs pg_upgrade or a dump and restore. A pinned bundle that itself lacks pg_background is reported and not downloaded again.
