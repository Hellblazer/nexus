### Fixed

- **`nx upgrade` now replaces an old PostgreSQL bundle that lacks pg_background.** An install keeps the bundle it was first set up with, and pg_background first shipped in the bundle at engine-service-v0.1.190 (conexus 8.2.1), so an install first set up on 8.2.0 or earlier reached a newer engine without it and every background data move stayed blocked. Engine convergence now also takes the pinned release's bundle and swaps it in, in two cases: the engine version changes, or the engine is already the pinned one but the extracted bundle has no `pg_background.control` (under `pg-bundle/bundle/share/postgresql/extension/`). The engine and the bundle are replaced under one stop and one start of the stack, through the same function `nx daemon service install-binary` uses. The client creates the extension the next time the service starts. This is a binary swap, not a data migration: no user data is rewritten, and a data directory made by PostgreSQL 17 starts under any other 17 bundle. A bundle with the same bytes swaps nothing and stops nothing; cloud mode and an install on its own PostgreSQL are untouched; a download, verification or extraction failure leaves the old bundle in place and the stack running, is reported as a note, and the next `nx upgrade` tries again. A swap that would change the PostgreSQL major version is refused before anything is stopped (a data directory belongs to the major that made it; that needs pg_upgrade or a dump and restore). `nx upgrade --auto` and an MCP start only report a bundle without pg_background, as they do for the engine.
