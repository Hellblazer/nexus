### Fixed

- **A background job now repairs catalog collections whose `model_version` is empty.** Some collection rows carry an empty `model_version` although their name says it (`code__1-2__voyage-code-3__v1` is `v1`). The engine registers one data move, `repair-catalog-collection-model-version`, which sets the version from the name for each tenant's rows where it is empty and the name has the `<type>__<owner>__<model>__v<N>` form. It runs in batches after the engine serves and resumes from the last committed batch after a restart; a row already set and a name that is not in that form are left as found; a `quarantine-` sibling of a conformant name is repaired with its origin. While it runs it shows under `boot_work` on `/v1/status` and in `nx doctor`, and the upgrade boot itself writes only the one registry row. It needs the `pg_background` install that `docs/configuration.md` lists under background data moves: on a database without it the move waits, shows as a warning (not a failure) in `nx doctor` with the `nx daemon service install-binary <tag>` remedy (the bundled PostgreSQL carries pg_background; a self-managed one needs it installed), and changes nothing; the engine marks such a blocked entry with the additive `reason_class: "missing_prerequisite"` in `boot_work`, and a doctor run against an older engine still shows it red (RDR-246, RDR-229 D2, nexus-f3yqd.2.23). To list what the move leaves, run as the database's migrating role: `SELECT tenant_id, name FROM nexus.catalog_collections WHERE model_version = '' AND name !~ '^(quarantine-|)(code|docs|rdr|knowledge)__[a-zA-Z0-9-]+(_[a-zA-Z0-9-]+)*__[a-z][a-z0-9-]*__v[0-9]+$'`; `nx catalog collections-census` counts them too once RDR-229 P1.2 lands.
