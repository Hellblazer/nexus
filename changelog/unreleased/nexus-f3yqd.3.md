### Added

- **`GET /v1/status` says what heavy work the engine is doing and whether stopping it is safe** (nexus-f3yqd.3, engine half). A new `boot_work` list is always present on an engine that carries it and is empty when the engine is idle. Each entry is `{id, what, started_at, done, total, unit, safe_to_stop, on_stop, step}`: `started_at` is ISO-8601 UTC, `done` and `total` are integers or null, `step` is null or `{what, done, total, unit}` for an inner level, and the engine sends no durations (a client derives rate and time left from `started_at` and the counts). The first producer is the per-collection index reconciler: while a pass that plans builds runs, `pci-reconcile` ("building search indexes") counts index builds ended, and its `step` is read every three seconds from the builder backend's `pg_stat_progress_create_index` (blocks, or tuples when the phase counts no blocks, or null counts while it waits). `total` is null until the pass has planned its last build-capable leaf, so a progress bar built on it never goes backward and never reads 100% early; a single-leaf install gets the real total at once. `done` counts every ended build, a failed one included (the next pass retries it). Stopping the engine loses no data and, since the restart no longer ends a build (nexus-f3yqd), does not lose the work either: `on_stop` says "the build keeps running in the database and is adopted after a restart; stopping the database as well loses it and it is rebuilt from the start", and finished indexes are kept. `done` counts a planned build that the pass skips (its failed index could not be dropped) as ended, so it still reaches `total`. The route is unauthenticated, so the step names the build phase only, never a collection, tenant or index, and there is no switch that changes that. Only the engine that holds the builder lock reports the entry; a standby reports an empty list. Additive: no existing key changes, and the released readers of this body read named keys and ignore the new one.
