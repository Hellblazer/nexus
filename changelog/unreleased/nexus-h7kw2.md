### Changed

- **A short page's manifest count runs under a 1 s budget per statement, and a count that runs out re-runs the page** (nexus-h7kw2; engine only, rides the next engine tag; no wire, SQL or `/version` change). The count that decides whether a short page needs its exact re-run took 13 to 14 s on a table the planner had not analyzed when the text gate's matches all sat at the end of the manifest (measured at 220,000 chunks), and then the re-run ran anyway. Each statement of the count now runs under its own `statement_timeout`: 1 s, unless a smaller bound applies (the bound already in force, or in a fan-out arm the arm's remaining budget). A route (a) count whose first read holds repeated chunks reads twice, so it can spend the budget twice. A count that runs out answers "unknown" and the page re-runs, which is what it did before the count existed, so the budget can cost a re-run the count would have spared and never skips one a page needs. An arm whose own remaining bound is the smaller one, or equal, still fails with its deadline as before. After the count the bound in force before it is set again, which also rebinds the connection's network timeout. Each spent budget logs `vector_short_page_count_budget_spent` (info) beside the existing `vector_short_page_count_failed` (warn). `NX_SHORT_PAGE_COUNT_BUDGET_MS` (1 to 600000, validated at boot) changes the budget; the count grows with the manifest, and at 220,000 chunks its slowest useful case (a filter that admits a few chunks) measured 610 ms, so a much larger tenant may need more. The root cause, the text gate evaluated on every manifest row, is unchanged: the budget caps what that costs.
