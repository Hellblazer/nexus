### Fixed

- **`nx collection delete`, `prune` and `reindex` say why when a re-embed job holds the collection.** Engine 0.1.202 refuses to delete a collection while a re-embed job that has not ended names it as its source or target, and removes nothing. They now name the job and its state and say what to do for that state: wait for a running or cutover job (`nx collection re-embed --status JOB`), resume or cancel a paused one (`--resume JOB`, `--abort JOB`), cancel a failed one (`--abort JOB`). They exit non-zero and no longer report an unconfirmed delete.
- **`nx collection re-embed --all` no longer fails on a re-entry the engine would refuse.** A kept-tombstoned job whose target collection was retired or removed cannot be re-entered; the run now prints one line (`A: not re-entered: its target B is retired; ...`, with a command that clears it) and carries on, and does the same if the engine's refusal arrives after the check, instead of exiting 1. `nx doctor` keeps listing such a source when a restored document is live in it, with the reason.
- **`nx t3 quarantine restore` explains a restore the engine refuses for an unregistered origin, and the index walk goes on.** When quarantined chunks name an origin collection with no registry row, the engine will not re-create it from its label and restores nothing. The command says which collection and how many chunks stay quarantined (exit 5, as for other engine refusals). `nx index` logs it once for that collection, skips its prune for the pass, and continues with the next collection rather than logging a failed prune with a traceback.
- **A collection label the engine reserves is refused with one clear message.** After a collection is renamed (A to B), engine 0.1.202 keeps A reserved until a later release relabels B's rows, because they still carry the name A. Registering A again (the usual way to hit it: rename A to B, then index the repo that was A), renaming onto it, superseding to it or starting a re-embed into it answers 409 `label_reserved`; an import reaches it through registration. `nx collection rename`, `nx index ...`, `nx collection re-embed` and the other commands now say which label, why it is reserved, and what to do (pick another label where you chose it; otherwise rename the other collection back), exit non-zero, and do not retry. `nx collection reindex` says plainly that it had already deleted the collection, and `nx catalog migrate-fallback` says the documents moved but the supersession was not recorded.
- **`nx catalog rename-collection` no longer reports a successful rename as a failure on an engine that renames the registry row in place.** The engine renames the collection and keeps its id, so the old name has no registry row afterwards, and the follow-up "mark the old name superseded" call answered 404. The command took that for a failed projection update, printed the recovery warning (`backfill-collections`, re-run the rename) and exited 2 after the rename had finished. It now sees that the new name holds the old name's id, says the registry row moved, and exits 0. A real registry failure still warns and exits 2. The note about an engine that deletes the old row no longer says the engine "still" does.
- **Remedies in `nx doctor` and the reconcile commands name commands that exist.** The doctor's fix lines said `nx index <path> --force`, and `nx index` takes a subcommand: they now say `nx index repo <repo-root> --force` (or `nx index md|pdf|rdr <file>` for a document indexed that way). The ghost-note and tombstoned-collection messages named `nx catalog purge-trash --execute`; the flags are `--no-dry-run --confirm`. A rename the engine refuses until it restarts (409 `rename_refused`, `missing: restart`) now says renames open after the engine's next restart and that the operator orders it, instead of "fix the error and retry".
- **The `rdr-close` skill's legacy post-mortem migration works again.** It looked the subject collection up by column position in `nx collection list` and then renamed the legacy collection onto a collection a `store_put` had just created, which `nx catalog rename-collection` refuses (and a first write to a new subject now mints a `c<id>` label). It now renames the legacy `rdr_postmortem` collection onto `knowledge__<repo>-rdr-research__<model>__v1` before any write, so the bare subject finds it, and says when to skip.
- **`plan_search` pages past the first page, and `plan_delete` of a missing id is an error result.** The engine's plan search takes a limit and no offset, and the tool asked for `limit + 1` rows and then dropped the first `offset`, so page 2 held at most one row and any offset past the limit returned nothing. It now asks for `offset + limit + 1` and slices, and the footer names the next offset only when more rows exist. `plan_delete` answered "Not found" as a success; it is an error now, as its description says. `daemon_uninstall`'s `remove_data` text now says it deletes everything under the config directory, the bundled Postgres cluster included (every T3 chunk, T1, tuples and identities). Tool descriptions also say: `tuple_release` hands the row back to available and does not consume it, `tuple_ack` on a row rewritten by `mode=replace` while claimed returns it to available with the new body, the catalog `links` and `traverse` defaults leave out `implements-heuristic` and custom link types (name them), the `tuple_list` prefix example uses slashes, and `hook_auto_approve` allows hook tools by name only.
- **More MCP tool descriptions say what the tool does.** `search_topic_scoped` lists `contents` in its structured result and explains its per-collection cut in place of pointing at a source comment the agent cannot see; `search_aspect_scoped` does the same for its coverage note; `store_get_many` lists `source_notes`; `scratch` no longer calls its notes session-only (`scope="identity"` keeps them); `store_put` says an entity key is refused on any code collection, whatever its label; the `plan_save` scope-tag example uses prefixes; `query`'s `subtree` takes an owner name and refuses a three-segment address; `scratch_manage` says `flag` also uses `project` and `title` as its flush destination; `update`'s `alias_of` text is behaviour, not history. The `t3_collection_name` docstring now describes the catalog-row lookup and the engine-minted `c<id>` label for a new knowledge subject.
- **The `rdr-close` skill finds a subject's collection whatever its label.** Its "subject already has a collection" guard and its reuse check split the collection name on `__`, so a `c<id>`-labelled subject collection (the label the engine mints for a new knowledge subject) was invisible and a migration could rename the legacy collection onto a subject that already had one. Both now read the CONTENT_TYPE and OWNER columns of `nx collection list` and also count a live name of the form `knowledge__<subject>__...`; a retired collection does not count. A legacy collection that is not listed now says "nothing to migrate" instead of "no registered model", and the skill says how to read the current knowledge model. The migration steps moved to `conexus/skills/rdr-close/migration.md` to keep the skill within its size budget.
