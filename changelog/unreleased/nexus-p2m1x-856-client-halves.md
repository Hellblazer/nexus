### Fixed

- **`nx collection delete`, `prune` and `reindex` say why when a re-embed job holds the collection.** Engine 0.1.202 refuses to delete a collection while a re-embed job that has not ended names it as its source or target, and removes nothing. They now name the job and its state and say what to do for that state: wait for a running or cutover job (`nx collection re-embed --status JOB`), resume or cancel a paused one (`--resume JOB`, `--abort JOB`), cancel a failed one (`--abort JOB`). They exit non-zero and no longer report an unconfirmed delete.
- **`nx collection re-embed --all` no longer fails on a re-entry the engine would refuse.** A kept-tombstoned job whose target collection was retired or removed cannot be re-entered; the run now prints one line (`A: not re-entered: its target B is retired; ...`, with a command that clears it) and carries on, and does the same if the engine's refusal arrives after the check, instead of exiting 1. `nx doctor` keeps listing such a source when a restored document is live in it, with the reason.
- **`nx t3 quarantine restore` explains a restore the engine refuses for an unregistered origin, and the index walk goes on.** When quarantined chunks name an origin collection with no registry row, the engine will not re-create it from its label and restores nothing. The command says which collection and how many chunks stay quarantined (exit 5, as for other engine refusals). `nx index` logs it once for that collection, skips its prune for the pass, and continues with the next collection rather than logging a failed prune with a traceback.
- **A collection label the engine reserves is refused with one clear message.** After a collection is renamed (A to B), engine 0.1.202 keeps A reserved until a later release relabels B's rows, because they still carry the name A. Registering A again (the usual way to hit it: rename A to B, then index the repo that was A), renaming onto it, superseding to it or starting a re-embed into it answers 409 `label_reserved`; an import reaches it through registration. `nx collection rename`, `nx index ...`, `nx collection re-embed` and the other commands now say which label, why it is reserved, and what to do (pick another label where you chose it; otherwise rename the other collection back), exit non-zero, and do not retry. `nx collection reindex` says plainly that it had already deleted the collection, and `nx catalog migrate-fallback` says the documents moved but the supersession was not recorded.
- **`nx catalog rename-collection` no longer reports a successful rename as a failure on an engine that renames the registry row in place.** The engine renames the collection and keeps its id, so the old name has no registry row afterwards, and the follow-up "mark the old name superseded" call answered 404. The command took that for a failed projection update, printed the recovery warning (`backfill-collections`, re-run the rename) and exited 2 after the rename had finished. It now sees that the new name holds the old name's id, says the registry row moved, and exits 0. A real registry failure still warns and exits 2. The note about an engine that deletes the old row no longer says the engine "still" does.
