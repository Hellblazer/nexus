### Changed

- **Routing by content type reads the collection's catalog row, not its name (RDR-229 P2.9).** Aspect extractor selection and the docs opt-in gate, file-routed identity (`uri_for`, the aspect worker, `nx catalog backfill-source-uri`, the exporter's note-key stamp and import floor check), the quality boost, the search distance threshold and over-fetch, the chunk `content_type` stamped on a note, topic routing, the PDF-stub and visible-superseded doctor checks and the `note_tags_array` upgrade rung each ask the row for `content_type`. A collection with a label that carries no `code__`/`docs__`/`rdr__`/`knowledge__` prefix now routes by what its row says. A collection a write is about to create has no row yet (it holds no chunk), so a router a write reaches (`uri_for`, the identity fields, `select_config`, the docs opt-in gate, the aspect worker's attribution guard, the exporter, the recovery-bundle link re-derivation, `nx enrich aspects-backfill-uri`) re-reads the row once and then answers from the name's own `<type>__` segment, as before; a listing that cannot be read does the same and logs `routing_content_type_unreadable`. A prefix-free label with no row stays unrouted. A read-only scan (the `note-tags-array` rung) reads strictly and stops on a failed listing. The URI-string classifiers (`is_note_uri`, `canonical_note_uri`) are unchanged. The `taxonomy__` prefix tests are unchanged and are migration sources of a legacy name no row identifies (they move into `legacy_names` at RDR-229 P2.2).
- **Two doctor checks no longer read an unrowed collection as "nothing here".** `nx catalog doctor`'s visible-outside-manifest report carries a new `unrowed_collections` key (listing rows with no `content_type`), and its not-applicable reason names the count. The PDF chunk metadata check, when it finds no knowledge or docs collection, says `not applicable (no knowledge or docs collections; N collection(s) carry no catalog row and were not scanned)` where it used to stop at `no knowledge or docs collections`.
- **The local-mode taxonomy default is a content-type rule.** `taxonomy.local_exclude_collections` now defaults to `[]` and the new `taxonomy.local_exclude_content_types` defaults to `["code"]`, matched against each collection's row. Patterns in `local_exclude_collections` stay label patterns. A config that sets `local_exclude_collections` (to `[]` too) and not `local_exclude_content_types` owns the exclusion: the content-type default stands down, so the documented `local_exclude_collections: []` still turns code taxonomy on locally. Set `local_exclude_content_types` explicitly to exclude content types.
