### Fixed

- **A long-lived process no longer fails a write because another process deleted a collection it had cached as registered.** RDR-229 P3.1 makes the engine refuse a write under an unregistered collection with a typed 422 (`unregistered_collection`), where it used to write. The client's per-process registration cache could still call such a name registered, so an MCP server indexing a PDF got that 422 on the document registration. Every catalog, pipeline and T2 store write now goes through one recovery in the shared POST (`nexus/registration_retry.py`): on that 422, for a name this process itself cached, it drops the name from the cache, registers it again and sends the write once more. A second refusal surfaces, never a loop; a 422 for any other reason is not retried; a name the process never cached keeps its 422, so a writer that skipped registration, or a typo in a rename or supersede, is not papered over. The chunk, aspect, taxonomy and chash writers keep `write_with_registration_retry`, which now shares the same recovery and never stacks a second retry on it.
