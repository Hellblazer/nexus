### Changed

- **Background jobs now fill the collection id on existing rows.** Each table that names a collection has a second column for the collection's id, empty on rows written before this release. The engine registers one data move per table, `rdr229-stamp-<table>` (fifteen, and a sixteenth for the retired aspect-extraction queue where that table is kept), which sets the id from the collection registry by tenant and name, in batches after the engine serves, and resumes from the last committed batch after a restart. A row that already has its id, a row whose name is empty and a row whose name no registry row carries are left as found. A move validates its table's check constraints when it finishes. The registry's own `superseded_by_id` takes the successor's id, or the row's own id when the successor is gone. An open P2.10 residue move (`rdr229-residue-catalog-documents`, `-document-aspects`, `-document-highlights`) is superseded at the P3.1 cut by a replacement (`rdr229-p31-residue-*`) that also sets the collection id, since the new CHECKs would refuse its id-less UPDATE; a pause on the old move carries over to its replacement (resuming the replacement is enough: the satellites it registers take the replacement's own pause, which is none once resumed), and `nx doctor`'s uri-residue row names both labels. The upgrade boot registers the moves and writes no row; they need the `pg_background` install that `docs/configuration.md` lists under background data moves, and show under `boot_work` on `/v1/status` and in `nx doctor` while they run. The chunks move is the long one (about 38 hours on the production-size store at its throttle); `NX_DATA_MOVE_SLEEP_MS` overrides every move's pause, so leave it unset for these (RDR-229 P3.1, RDR-246, nexus-p2m1x.17).
