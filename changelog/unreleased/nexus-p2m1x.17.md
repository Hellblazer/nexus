### Changed

- **The engine reads, after every boot, whether the collection-id stamp has finished, and reports it in its own `/v1/status` field, `rdr229_completion`.** It reads again when a data move completes, at the end of each reconciler pass, and on a 60-second safety poll. RDR-229 P3.1's boot-time completion check (`CompletionCheck`, `CompletionBootWork`) runs after the schema walk on the admin connection, over a read-only session: it reads `nexus.data_moves`, the catalog and the CHECK constraints and writes nothing, so no boot rewrites user data. Three gates, in order: every stamp move (`rdr229-stamp-<table>`) complete, then the swap and validation moves a later release adds, then P3.4's id indexes (every collection the planner would index has a VALID id-predicate index; no release builds those yet, so gate 3 does not hold). A move is complete when it, or the move that supersedes it, has `completed_at`; a failed move on a table that no longer exists counts as complete; the retired `aspect_extraction_queue` stamp is not applicable while the table or its `collection_id` column is absent, and every other label with no row stays incomplete. A stamp is complete only with its table's CHECKs present and validated, and every gate refuses while `catalog_collections_superseded_by_id_check` is missing (nexus-p2m1x.17).
- **`nx doctor` shows the completion check.** One row for the three gates (never a warning, the gates wait by design across releases), a warning per missing CHECK (the `superseded_by` one says how many registry rows hold its changeset back and that the wait clears by itself), and a warning per table whose stamp is done and whose CHECK is still NOT VALID because orphan rows violate it: the row names the table, the orphan and unstamped counts, and the operator step (once the missing collection is registered or the orphan rows are deleted, `SELECT nexus.rdr229_restamp('<table>');` as `nexus_admin` registers the table's stamp move again, which stamps the newly resolvable rows and validates the CHECK, because registering the collection alone stamps nothing). The VALIDATE waits instead of failing a boot (nexus-p2m1x.17).
- **The roll back after RDR-229 P3.1 is the operator down-step first and the tag flip second.** A previous engine cannot write a row the new `NOT VALID` CHECKs guard (SQLSTATE 23514 on its chunk INSERT, supersede UPDATE and carrier INSERTs), so `docs/runbooks/rdr-229-p31-rollback.md` hands conexus the down-step (`DROP CONSTRAINT IF EXISTS` on every listed constraint, generated from `p31-checks.tsv` by `scripts/rdr229_p31_downstep.py` and shipped as `p31-downstep.sql`), the verification query, the window (only before a stamp completes; otherwise PITR: about a minute after the first boot wherever the moves run, and on the cloud until pg_background is installed on its PostgreSQL) and the 23514 symptom an operator sees without it. A later deploy of the P3.1 engine needs the generated re-add (`docs/runbooks/rdr-229-p31-readd.sql`) first, because the changelog records the CHECKs as run, and the 24 function bodies vectors-069 redefined stay in place after the down-step (nexus-p2m1x.44).
