### Changed

- **RDR-229 P3.3a: the registry's foreign keys gain an id twin, and a move validates each one.** Six tables (`topic_assignments`, `document_aspects`, `topics`, `taxonomy_meta`, `document_highlights`, `canary_query_ring`), and the retired `aspect_extraction_queue` where that table is kept with its `collection_id` column, get a foreign key on `(tenant_id, collection_id)` to `nexus.catalog_collections`, added `NOT VALID` beside the existing name key (which stays until P3.7) and with the same ON DELETE action. The upgrade boot scans and writes no row; the twin already refuses a new or updated row that names an id no registry row carries. One registered data move per twin, `rdr229-fkvalidate-<table>`, re-stamps rows still NULL and validates the twin after the engine serves. The completion check's gate 1 now reads these seven labels too, and a label is complete only while its twin is present and validated; `nx doctor` names a twin that is missing or `NOT VALID` (nexus-p2m1x.19).
