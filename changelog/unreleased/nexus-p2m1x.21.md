### Changed

- **RDR-229 P3.3c: the two swap moves.** The moves `rdr229-swap-chunks` and `rdr229-swap-taxonomy_centroids` that P3.3b's pass registers now carry their work. Their verification (READ ONLY, ACCESS SHARE, under `verify_statement_timeout_ms` 60000) returns a row for each leaf without a valid unique index on the id key, and for the chunks swap reads `nexus.chunks` (every leaf heap and the id-key indexes) and `nexus.catalog_collections` once with a plain scan so the completion, which keeps `statement_timeout_ms` 1400 and a `lock_timeout` of 700 ms, finds them cached. Their `on_complete` refuses when the id unique key is missing (SQLSTATE 55000, permanent). The chunks swap then adds the three child id keys `fk_catalog_chunks_chunk_id`, `topic_assignments_chunk_id_fk` and `chunk_orphaned_at_chunk_id_fk` (`NOT VALID`, `ON UPDATE CASCADE`, each with its name key's ON DELETE action; the manifest's is `DEFERRABLE INITIALLY DEFERRED`, so `purge_trash` and the collection delete, which defer only the name key and delete chunks before their manifest rows, still commit) into the chunks id key, registers the three moves `rdr229-fkvalidate-<table>-chunk-fk` that validate them, and adds and validates the RDR-225 composite `chunks_collection_id_fk` on `(tenant_id, collection_id, embedding_model)` directly (PostgreSQL takes no `NOT VALID` on a partitioned referencing table). The centroids swap adds nothing beyond the check. Nothing is dropped: the name primary keys, the three name child keys and `chunks_collection_fk` stay until P3.7 and P4.1. The boot isolation check also asks about `nexus.catalog_collections` while a swap move is registered. A lock the completion cannot get in 700 ms is a transient `blocked:` (55P03) and the move retries (nexus-p2m1x.21).
- **The chunks swap's verification warms only in its READ ONLY pass, and does not look for a null id.** The warm-up arms (the anti-join of `nexus.chunks` to the registry, and a count over a column no index holds) run only when `transaction_read_only` is on, so the completion transaction's re-check, which is read-write and runs under what is left of the 1400 ms bound, pays for the leaf-key check alone. RDR-229 item 6 says the verification also returns any row with a null id; it deliberately does not, because gate 1 requires P3.1's NOT NULL CHECK to be validated before the pass registers the swap, and the arm would cost another scan inside the re-check (nexus-p2m1x.21).
- **`nexus.chunk_orphaned_at` gains an index on `(tenant_id, chash)`, and the completion check's gate 2 reads the swap labels.** Changeset `vectors-074-1` builds `idx_chunk_orphaned_at_tenant_chash` with `CREATE INDEX CONCURRENTLY IF NOT EXISTS`, outside a transaction, so the chunk delete's cascade lookup through `chunk_orphaned_at_chunk_id_fk` does not read the whole table (the manifest and `topic_assignments` already have an index for theirs); a leftover INVALID index of that name halts the boot until the operator drops it. Gate 2 of the boot-time completion check now reads both swap labels and the three child validation labels (`ReadSet.p33c()`): a validation label counts complete only while its id key is present and validated, and the chunks swap's only while the composite is (nexus-p2m1x.21).
