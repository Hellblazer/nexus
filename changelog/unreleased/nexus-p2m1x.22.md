### Added

- **The PCI reconciler builds each collection's search index on `collection_id` beside the name index, retires the name index once gate 3 holds, and gate 3 reads the database.** RDR-229 P3.4. Once gate 2 of the boot-time completion check holds (both swaps and every validation move complete), a pass builds, one at a time with `CREATE INDEX CONCURRENTLY`, an HNSW index `WHERE collection_id = <id>` for every live, unsuperseded collection with enough rows (or, while it keeps a name index, at any count the name index is kept for: half the threshold and up, and zero, so it can reach gate 3), largest first, named from a hash of the model, tenant and id that never equals a name hash. Each id index is anchored (the same comment as a name index's) and REINDEXed by the same rules; the recall canary does not run on id indexes until readers select by id. A collection with a row whose `collection_id` is still null gets none until the stamp reaches it; the scan for such a row is skipped while both P3.1 CHECKs are validated, is bounded, and a probe that times out holds back only that id build. A killed id build is left INVALID and the next pass drops it and builds it again from the start. An INVALID leftover of a killed REINDEX of an id index (`<name>_ccnew`) is dropped the same way as a name index's, and counts as an INVALID id index in `id_index_invalid`. Until gate 3 holds the name indexes stay, so each leaf holds up to `NX_SEARCH_PCI_MAX_PER_LEAF` name indexes and as many id indexes (a stated exception to the cap). Once gate 3 has latched AND the engine's id readers are present (`IdReaders.PRESENT`, a constant the id-reader release flips; false in this release, so nothing is dropped yet), no name index is built, and each name index whose collection's id index is VALID is dropped (`replaced_by_id`); one whose id index is missing or INVALID keeps it. Gate 3's PCI clause is read from the database by every engine, a standby included: every live collection that holds a name or an id index, or that has at least the build threshold of rows and no index at all (a renamed collection, or one that just crossed it), needs a VALID id index (a backed-off or half-threshold collection holds it shut), a collection whose name index is gone still counts as covered while its id index is VALID, and a store where nothing is required passes only if the scan found no live collection at the threshold. The scan of unindexed collections is bounded (one transaction, a 60 s budget) and runs only once every indexed collection is covered; it asks for no more collections on a leaf than the planner can build there (`NX_SEARCH_PCI_MAX_PER_LEAF` less the indexes already standing), the largest first, so a leaf with more qualifying collections than the cap does not hold gate 3 shut for ever; one that cannot finish makes the clause unknown, so gate 3 waits. With `NX_SEARCH_PCI=0` the clause does not apply, and gate 3 rests on the other conditions. Gate 3 also needs the eight id unique indexes below to be VALID and implies gate 2. The first time gate 3 holds, the completion check writes it to `nexus.rdr229_gate_latch` (vectors-080, one row per gate, no tenant data, no RLS) on a write session of its own, never on its read-only one, so it stays held: a live gate 3 that goes false later (an id index rebuilding) does not send readers back, and the name indexes retire on the latched value, and only when the id readers are present in the engine. `rdr229_completion` reports `gate3_latched` and `id_index_invalid`, and `nx doctor` shows an INVALID id index as its own row. The engine reads the latch row synchronously at boot, before it serves, and retries a failed read with backoff (each attempt is bounded to 10 s, it retries for up to five minutes, and it does not serve if the database still cannot answer; it never guesses), so `gate3Latched` is right from the first request. The row records `pci_off` when gate 3 latched with `NX_SEARCH_PCI=0`; `rdr229_completion` reports it as `gate3_latch_pci_off` and `nx doctor` shows a row for it; with PCI on afterwards the reconciler builds the id indexes first, as if gate 2 held. Once latched, the coverage read repeats at most every ten minutes (`id_index_invalid` stays current within that). `gate3_why` names the changeset an id twin waits for. A database restored from before the latch reads not latched and latches again once gate 3 holds.
- **The id-keyed ON CONFLICT arbiters.** Once gate 2 holds, the engine builds eight id-keyed UNIQUE indexes at run time (`CREATE UNIQUE INDEX CONCURRENTLY`, no changeset): on document_aspects, chash_remap, taxonomy_meta, topics (`WHERE parent_id IS NULL`), chunk_orphaned_at, canary_query_ring, pdf_pipeline and reembed_jobs (its active-state predicate). They are the arbiters the id-keyed upserts need, so a one-row rename cannot make duplicate rows. A unique violation during a build means the table is corrupt, since each name maps to one id. The engine logs the duplicate keys at ERROR and keeps a `boot_work` entry (`id-unique-index-held`) saying so, also shown in `nx doctor` and `gate3_why`; it does not retry that build until the next engine start, and gate 3 stays false. An index of one of these names that stands with another definition gets the same entry and is never dropped by the engine; once the operator drops it, the next pass builds the right one. These held entries are visible and safe to stop but are not work: `nx upgrade`'s bundle-swap deferral and the boot-write harness's idle rule skip them. A twin that waits for a changeset has no `boot_work` entry; `gate3_why` names the changeset. A finished pass looks again every ten minutes, so an index lost later is rebuilt, and a build that times out or is cancelled backs off for an hour, doubling to a day.
- **RDR-229 P3.4: supporting indexes for the id-twin foreign keys.** Each of P3.3a's seven id-twin foreign keys gets a supporting index on `(tenant_id, <id column>)`, built by the engine at run time once gate 2 holds, and never in the boot walk (an upgrade boot writes at most 64 MiB). Four are plain indexes: `idx_ta_tenant_source_collection_id`, `idx_topics_tenant_collection_id`, `idx_doc_highlights_collection_id`, and `idx_aspect_queue_collection_id` where an install still has the retired queue table with its id column. A fifth plain index, `idx_catalog_chunks_collection_id` on catalog_document_chunks, is the id twin of `idx_catalog_chunks_collection` for the exact route's id path. For the other three (document_aspects, taxonomy_meta, canary_query_ring), the id-keyed arbiter below leads with the same columns and serves. Without them, deleting a registry row would scan every referencing table once the name keys' indexes went. Gate 3 requires them all. No row changes.
- **The id-key index census.** `IdKeyIndexCensus` reads `pg_constraint` and `pg_index`. It counts every foreign key on an id column as supported only when a valid, non-partial index's first two columns are both columns of the key and one of them is `tenant_id`. P3.3c's keys into the chunks id key pass through their `(tenant_id, chash)` or `(tenant_id, doc_id)` indexes, and the chunks composite passes through the chunks id unique key. P4.1 will refuse to drop the name keys while the census fails.
- **The sweep, `/v1/status` and `nx doctor` count the id indexes too.** After gate 3 latches the id-predicate indexes serve and the name indexes retire, so the name-only counts read 0. The `event=pci_sweep` line gains `valid_id=` and `invalid_id=` (after `valid=` and `invalid=`, which stay name counts), `pci_sweep_set_recovered` gains `valid_id=`, `pci_sweep_read_failed` gains `kept_valid_id=`, and `pci_sweep_set_changed` lists id indexes as `leaf:id=<id>:index`. The "no valid index" warning fires only when neither family has a valid index. `GET /v1/status` `per_collection_indexes` gains the additive keys `valid_id` and `invalid_id` (directly after `reindex_leftover`); `nx doctor`'s "Per-collection indexes" row shows them ("3 valid + 2 by id") and warns on `invalid_id` like `invalid`. An older engine omits the keys and a newer client reads 0; an older client ignores them. The canary's maintenance entries read the id index's anchor for an id target.
