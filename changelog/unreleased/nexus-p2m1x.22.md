### Added

- **The PCI reconciler builds each collection's search index on `collection_id` beside the name index, retires the name index once gate 3 holds, and gate 3 reads the database.** RDR-229 P3.4. Once gate 2 of the boot-time completion check holds (both swaps and every validation move complete), a pass builds, one at a time with `CREATE INDEX CONCURRENTLY`, an HNSW index `WHERE collection_id = <id>` for every live, unsuperseded collection with enough rows (or, while it still has a name index, at least half the build threshold, so it can reach gate 3), largest first, named from a hash of the model, tenant and id that never equals a name hash. Each id index is anchored (the same comment as a name index's) and REINDEXed by the same rules; the recall canary does not run on id indexes until readers select by id. A collection with a row whose `collection_id` is still null gets none until the stamp reaches it; the scan for such a row is skipped while both P3.1 CHECKs are validated, is bounded, and a probe that times out holds back only that id build. A killed id build is left INVALID and the next pass drops it and builds it again from the start. Until gate 3 holds the name indexes stay, so each leaf holds up to `NX_SEARCH_PCI_MAX_PER_LEAF` name indexes and as many id indexes (a stated exception to the cap). Once gate 3 holds, no name index is built, and each name index whose collection's id index is VALID is dropped (`replaced_by_id`); one whose id index is missing or INVALID keeps it. Gate 3's PCI clause is read from the database by every engine, a standby included: every live collection with a VALID name or id index needs a VALID id index (a backed-off or half-threshold collection holds it shut), a collection whose name index is gone still counts as covered while its id index is VALID, and a store with no index at all passes only if no live collection reaches the build threshold. With `NX_SEARCH_PCI=0` the clause does not apply, and gate 3 rests on the other conditions. Gate 3 also needs the eight id unique indexes below to be VALID and implies gate 2. The first time gate 3 holds, the completion check writes it to `nexus.rdr229_gate_latch` (vectors-080, one row per gate, no tenant data, no RLS) on a write session of its own, never on its read-only one, so it stays held: a live gate 3 that goes false later (an id index rebuilding) does not send readers back, and the name indexes retire on the latched value, and only when the id readers are present in the engine. `rdr229_completion` reports `gate3_latched` and `id_index_invalid`, and `nx doctor` shows an INVALID id index as its own row. A database restored from before the latch reads not latched and latches again once gate 3 holds.
- **The id-keyed ON CONFLICT arbiters.** Once gate 2 holds, the engine builds eight id-keyed UNIQUE indexes at run time (`CREATE UNIQUE INDEX CONCURRENTLY`, no changeset): on document_aspects, chash_remap, taxonomy_meta, topics (`WHERE parent_id IS NULL`), chunk_orphaned_at, canary_query_ring, pdf_pipeline and reembed_jobs (its active-state predicate). They are the arbiters the id-keyed upserts need, so a one-row rename cannot make duplicate rows. A unique violation during a build means the table is corrupt, since each name maps to one id. The engine logs the duplicate keys and keeps a `boot_work` entry saying so. It does not retry that build until the next engine start, and gate 3 stays false.

### Changed

- **RDR-229 P3.4: supporting indexes for the id-twin foreign keys.** vectors-076 builds one index on `(tenant_id, <id column>)` for each of P3.3a's seven id-twin foreign keys: `idx_ta_tenant_source_collection_id`, `idx_doc_aspects_collection_id`, `idx_topics_tenant_collection_id`, `idx_taxonomy_meta_tenant_collection_id`, `idx_doc_highlights_collection_id` and `idx_canary_query_ring_collection_id`, plus `idx_aspect_queue_collection_id` where an install still has the retired queue table with its id column. Without them, deleting a registry row scanned every referencing table once the name keys' indexes went. Six of the builds run `CONCURRENTLY` at boot and retry themselves, like vectors-074: a build that is killed or waits more than 30 s leaves the boot running and is built again at the next boot. The queue's build is guarded like vectors-072-7, so an install without the table records it and does not retry. No row changes.
- **The id-key index census.** `IdKeyIndexCensus` reads `pg_constraint` and `pg_index`. It counts every foreign key on an id column as supported only when a valid, non-partial index's first two columns are both columns of the key and one of them is `tenant_id`. P3.3c's keys into the chunks id key pass through their `(tenant_id, chash)` or `(tenant_id, doc_id)` indexes, and the chunks composite passes through the chunks id unique key. P4.1 will refuse to drop the name keys while the census fails.
