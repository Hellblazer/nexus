### Added

- **The PCI reconciler builds each collection's search index on `collection_id` beside the name index, and the completion check reads gate 3 from them.** RDR-229 P3.4. Once gate 2 of the boot-time completion check holds (both swaps and every validation move complete), a pass builds, one at a time with `CREATE INDEX CONCURRENTLY`, an HNSW index `WHERE collection_id = <id>` for every collection the planner would index (live, not superseded, enough rows, not backed off, within the cap ranking), named from a hash of the model, tenant and id that never equals a name hash. A collection with a row whose `collection_id` is still null gets none until the stamp has reached it. The name-predicate index is never dropped by this change: readers stay on the name path until gate 3 holds, so each leaf holds up to `NX_SEARCH_PCI_MAX_PER_LEAF` name indexes and as many id indexes (a stated exception to the cap). A killed id build is left INVALID and the next pass drops it and builds it again from the start; an id whose registry row is gone, superseded or below half the build threshold loses its index. Gate 3 holds when every planned collection has a VALID id index and the eight id unique indexes below are VALID; it needs the PCI reconciler to be running (`NX_SEARCH_PCI=1`, on the engine that holds the builder lock) and implies gate 2.
- **The id-keyed ON CONFLICT arbiters.** Once gate 2 holds, the same pass builds eight id-keyed UNIQUE indexes (`CREATE UNIQUE INDEX CONCURRENTLY`, no changeset): on document_aspects, chash_remap, taxonomy_meta, topics (`WHERE parent_id IS NULL`), chunk_orphaned_at, canary_query_ring, pdf_pipeline and reembed_jobs (its active-state predicate). They are the arbiters the id-keyed upserts need, so a one-row rename cannot make duplicate rows. A unique violation during a build means the table is corrupt, since each name maps to one id. The engine logs the duplicate keys and keeps a `boot_work` entry saying so. It does not retry that build until the next engine start, and gate 3 stays false.

### Changed

- **RDR-229 P3.4: supporting indexes for the id-twin foreign keys.** Each of P3.3a's seven id-twin foreign keys gets a supporting index on `(tenant_id, <id column>)`, built by the engine at run time once gate 2 holds, and never in the boot walk (an upgrade boot writes at most 64 MiB). Four are plain indexes: `idx_ta_tenant_source_collection_id`, `idx_topics_tenant_collection_id`, `idx_doc_highlights_collection_id`, and `idx_aspect_queue_collection_id` where an install still has the retired queue table with its id column. For the other three (document_aspects, taxonomy_meta, canary_query_ring), the id-keyed arbiter below leads with the same columns and serves. Without them, deleting a registry row would scan every referencing table once the name keys' indexes went. Gate 3 requires them all. No row changes.
- **The id-key index census.** `IdKeyIndexCensus` reads `pg_constraint` and `pg_index`. It counts every foreign key on an id column as supported only when a valid, non-partial index's first two columns are both columns of the key and one of them is `tenant_id`. P3.3c's keys into the chunks id key pass through their `(tenant_id, chash)` or `(tenant_id, doc_id)` indexes, and the chunks composite passes through the chunks id unique key. P4.1 will refuse to drop the name keys while the census fails.
