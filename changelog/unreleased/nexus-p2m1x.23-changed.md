### Changed

- `POST /v1/catalog/collections/set_aspects_enabled` reads the collection's registry row in its own write transaction and changes that row by its `collection_id` (RDR-229 P3.5a). A request by `collection_id` whose id was freed, with its label then registered again by another row, answers a typed 404 `unknown_collection_id` and changes nothing of the label's new holder. By label it now acts only on the row the label resolves to (the live row, else the newest tombstone); before, it updated every row bearing the name, tombstones included. The wire shape is unchanged.
- `POST /v1/catalog/collections/rehome` reads both collections' registry rows `FOR KEY SHARE` after the sweep gates and builds its scope from those locked rows (RDR-229 P3.5a). A re-home retires nothing, so it is a writer, not a retiring verb: a request by `source_id` or `target_id` whose id was freed, with its label then registered again by another row, answers a typed 404 `unknown_collection_id` and moves nothing of the label's new holder; a retired end answers 409 `collection_superseded`; and a concurrent supersede or rename of either end waits for the re-home instead of running beside it. The wire shape is unchanged.
- The four `/v1/vectors/gc` writes (`quarantine-orphans`, `restore-rereferenced`, `expire-quarantine`, `quarantine-restore`) take the sweep gate, then read the collection by id, then run, with the collection's current label (RDR-229 P3.5a). A request by id whose id names no row is a typed 404 `unknown_collection_id` and a retired one a 409 before the SQL function runs (before, the function ran first and a refused one was translated afterwards), and a collection renamed since the route resolved it is moved under the label it has now. A collection renamed repeatedly while a write waits answers 503 `rename_busy`, retryable.
- A write by `collection_id` that finds its collection renamed while it waited for the sweep gate runs again from the top under the new label's gate, instead of taking that gate while holding the registry row (RDR-229 P3.5a). No wire change; it removes a lock-order inversion with a rename or supersede.

- `POST /v1/vectors/gc/quarantine-orphans`, `restore-rereferenced` and `expire-quarantine`, in their forms that set no statement bound of their own, answer 503 `rename_busy` with `Retry-After` when a rename or supersede holds the collection's registry row for more than 25 s (RDR-229 P3.5a); before, they waited for it. `quarantine-restore` keeps its own 503 `quarantine_restore_busy`. Ingest writers keep the unbounded wait, which the engine now logs as `event=registry_wait_slow` (tenant, collection, collection id, wait in ms, route) once it runs a second or longer. The Python client resends a keyed gc sweep after a `rename_busy`, as it does after `sweep_gate_busy`.
- The collection re-home moves a collection's manifest rows, topic assignments and orphan marks itself, by chunk id and in the same transaction, instead of relying on the chunk foreign keys' cascade (RDR-229 P3.5a); with those keys gone (P3.7) a manifest row no longer keeps the source's label. An operation by a label that no row holds, such as the old name of a collection renamed in place, reaches only rows the id stamp has not reached, never the renamed collection's rows.
