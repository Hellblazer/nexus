### Fixed

- A collection delete by `collection_id` takes the re-embed start guard (shared) before it locks any registry row, and then locks the origin's row `FOR UPDATE` with its quarantine siblings' rows `FOR KEY SHARE` in one `collection_id` order (RDR-229 P3.5a). Before, it locked the origin's row first and then waited for the guard, which could close a cycle with a re-embed start (the start holds the guard and wants the row) and fail one of them with a deadlock; and a second delete of the same id could deadlock with the first. The 404, 409 retired and 409 mismatch refusals are as in the id-addressed delete before; the delete still waits for a row without a time limit.
