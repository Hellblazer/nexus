### Fixed

- A collection delete by `collection_id` takes the re-embed start guard (shared) before it locks any registry row, and then locks the origin's row `FOR UPDATE` with its quarantine siblings' rows `FOR KEY SHARE` in one `collection_id` order (RDR-229 P3.5a). Before, it locked the origin's row first and then waited for the guard, which could close a cycle with a re-embed start (the start holds the guard and wants the row) and fail one of them with a deadlock; a second delete of the same id could deadlock with the first, and a claim-fenced aspect write (which holds its task row and then wants the registry row) could deadlock with it; the delete now locks the collection's aspect task rows before any registry row. No new answer: the 404, 409 and `collection_busy` refusals are the same, and the delete still waits for a row without a time limit.
