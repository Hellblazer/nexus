### Fixed

- The taxonomy writes keyed by a topic or a label prefix read the registry rows they write under before they write (RDR-229 P3.5a). `topics/update_label`, `topics/rename`, `topics/mark_reviewed`, `topics/delete`, `topics/merge`, `topics/persist_split`, `assignments/purge_doc`, `assignments/prune_projection` and `purge_collection` read the topic's collection by the id the topic carries, and the source collection of every assignment they delete or move, `FOR KEY SHARE` in one id-ordered statement, so a rename or delete of one of those collections waits for the write. A label update, a rename or a review of a topic whose collection label was renamed in place, and its old label taken by another collection, now acts on the topic and keeps its collection id; before, it re-derived the id from the stale label (another collection's id, or NULL and a 23514 refusal when no row bore the label). A merge whose existing assignment wins a conflict keeps that row's source collection id for the same reason. `purge_doc` and `prune_projection` reach the rows of the collection the label names now, by its id, and no longer the rows a stale name column still bears. `prune_projection` in its prefix form still prunes the weak projections stamped to a retired collection whose label starts with the prefix, as it did when it matched the name column: no change from the released behaviour. `topics/persist_split` refuses (400) a topic that is not a topic of the named collection. `topics/delete` and `topics/merge` answer the topic's collection by its current label. `topics/persist_split` reads its own collection's row and the parent's assignment source collections in one `collection_id`-ordered statement after its advisory lock, so a verb that holds a lower source and then wants the split's collection no longer meets a deadlock. A topic update, and a merge's moved or conflicting assignment, is filed under the collection's current label beside the id it keeps, so a one-row rename leaves no stale name column behind these writes.
