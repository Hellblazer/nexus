### Added

- A collection's row carries its `collection_id` (RDR-229 P3.5a, first step, read-only). The engine's `GET /v1/catalog/collections/list`, `/get` and `/for_tuple` answer the registry's own id as a number on every row; `HttpCatalogClient.get_collection` and `list_collections` hand it back as an `int`, or `None` from an older engine that sends no id. No route takes an id yet, and the id is not stable across a rename until P3.7's name-key drop and R6's `ids_stable` signal, so nothing caches by it before then.
- Every engine route that takes a collection accepts its `collection_id` as well as its label (RDR-229 P3.5a, write half). A request that names a collection by id (`collection_id` in a body or query string, `collection_ids` for a list, `<field>_id` for a field such as `source` or `superseded_by`) is resolved to the collection's label at the route boundary, once, before the handler runs, so every route, and every refusal it already had, answers as it does for the label. Both a label and an id for one collection, or an id that is not an integer, is a 400; an id no row has is a typed 404 `unknown_collection_id` naming the id, and the id of a retired row (a rename's or supersede's tombstone) is a 409 `collection_superseded` on every route, the delete included, naming the successor (`superseded_by`, its current label, and `successor_collection_id`, found by the tombstone's `superseded_by_id`; a tombstone that names no live successor, such as one whose successor was deleted and its label registered again, answers 409 with neither). A write route works by the id the request named, read in the write's own transaction with `FOR KEY SHARE`, so a write by an id freed between the boundary and the handler, whose label was then registered again, is refused 404 and does not land in the label's new holder. A write by an id that a rename or supersede retires after that read can still commit into the retired row until the retiring verbs lock the old row `FOR UPDATE` (RDR-229 P3.5a slice C and P3.7). An empty label with an id in a query string, an explicit `null` id, an id of more than 18 digits and an id given twice in a query string are 400. A request that names only a label is untouched. `POST /v1/catalog/collections/delete` takes `collection_id` too (its 200 answers `collection_id` and `name`, `/version` advertises `catalog_collection_delete_by_id_supported`), deletes a retired LABEL with the 200 it always gave (from gate 3 the purge is scoped by the row's own `collection_id`, so a retired label takes its own rows and never its successor's, and a label with no registry row purges nothing; a label held by several rows resolves to the live row, else the newest tombstone), and refuses a label that more than one live row holds with a 409 `collection_label_ambiguous` listing the ids.
- A collection rename decides its path inside its own transaction from the gate 3 latch row (RDR-229 P3.5a). With no row, and the rename readiness still waiting, it is the name path as before. With the row and the name-key drop move not complete, or a P3.5b changeset not applied, it is refused with a typed 409 `rename_refused` whose `missing` names the move or the restart. With the row and everything complete (the one-row regime) the catalog rename answers a typed 409 `rename_path_mismatch` until P3.7's one-row rename is wired, and each of the five per-store `rename_collection` routes (chash, taxonomy, telemetry, aspects, highlights) changes nothing and answers 200 in its usual shape with every count 0, after checking that the registry rename happened (the new label is a live registry row and the old is not); if it did not, the route answers a typed 409 `rename_not_in_registry` and changes nothing. With no row but the readiness complete (an inconsistency, as after a partial restore) every rename is a 409 `rename_refused` whose `missing` is `latch_row_missing`, never the name path. A rename's 200 now also answers the renamed row, `name`, `collection_id`, `ids_stable` (always false until P3.7's one-row rename keeps the id) and, when the engine role can read the cluster, `catalog_epoch`.
- The routes that write or move a document take a collection id (RDR-229 P3.5a): `physical_collection_id` beside `physical_collection` on register, doc/register, doc/register_many, import/document, doc/resolve_or_register, update and update_many. The id is resolved inside the write, to its registry row; a label and an id together, or an id that is not an integer, is a 400, an unknown id is a typed 404 `unknown_collection_id`, a retired id a typed 409 `collection_superseded`. `gc_audit/record`, the remap batch's per-entry target and the pipeline reference routes take an id at the route boundary too.
- A collection re-home is keyed by id from gate 3 (RDR-229 P3.5a, `POST /v1/catalog/collections/rehome` and `/rehome/status`): the source and target labels resolve to their registry rows (the live row first, else the newest tombstone) and every read and write of the re-home (the chunk model guard, the collision check, the mover, the status counts) is scoped by `collection_id`, so after a one-row rename a re-home naming the new label moves the rows that still carry the old name instead of answering 200 "moved 0". A label with no registry row behaves as an unknown collection (the 409 for a source, zero counts for a status). Before gate 3 it is keyed by the name columns as before.
- The re-embed guard a rename or a re-home takes matches a running job by the collection's registry id (RDR-229 P3.5a), or, for a job end whose id names no live registry row, by the label the job recorded, so a job still holds a collection after a one-row rename moved its label.

### Changed

- `POST /v1/catalog/collections/set_aspects_enabled` reads the collection's registry row in its own write transaction and changes that row by its `collection_id` (RDR-229 P3.5a). A request by `collection_id` whose id was freed, with its label then registered again by another row, answers a typed 404 `unknown_collection_id` and changes nothing of the label's new holder. By label it now acts only on the row the label resolves to (the live row, else the newest tombstone); before, it updated every row bearing the name, tombstones included. The wire shape is unchanged.
