### Added

- A collection's row carries its `collection_id` (RDR-229 P3.5a, first step, read-only). The engine's `GET /v1/catalog/collections/list`, `/get` and `/for_tuple` answer the registry's own id as a number on every row; `HttpCatalogClient.get_collection` and `list_collections` hand it back as an `int`, or `None` from an older engine that sends no id. No route takes an id yet, and the id is not stable across a rename until P3.7's name-key drop and R6's `ids_stable` signal, so nothing caches by it before then.
- Every engine route that takes a collection accepts its `collection_id` as well as its label (RDR-229 P3.5a, write half). A request that names a collection by id (`collection_id` in a body or query string, `collection_ids` for a list, `<field>_id` for a field such as `source` or `superseded_by`) is resolved to the collection's label at the route boundary, once, before the handler runs, so every route, and every refusal it already had, answers as it does for the label. Both a label and an id for one collection, or an id that is not an integer, is a 400; an id no row has is a typed 404 `unknown_collection_id` naming the id, and the id of a retired row (a rename's or supersede's tombstone) is a 409 `collection_superseded` on every route, the delete included, naming the successor (`superseded_by`, its current label, and `successor_collection_id`, found by the tombstone's `superseded_by_id`; a tombstone that names no live successor, such as one whose successor was deleted and its label registered again, answers 409 with neither). A handler works by the id the request named, read in its own transaction, so a write by an id freed between the boundary and the handler is refused and lands in no other collection. An empty label with an id in a query string, an explicit `null` id, an id of more than 18 digits and an id given twice in a query string are 400. A request that names only a label is untouched. `POST /v1/catalog/collections/delete` takes `collection_id` too (its 200 answers `collection_id` and `name`, `/version` advertises `catalog_collection_delete_by_id_supported`), deletes a retired LABEL with the 200 it always gave (from gate 3 the purge is scoped by the row's own `collection_id`, so a retired label takes its own rows and never its successor's, and a label with no registry row purges nothing; a label held by several rows resolves to the live row, else the newest tombstone), and refuses a label that more than one live row holds with a 409 `collection_label_ambiguous` listing the ids.
- A collection rename is refused, with a typed 409 `rename_refused`, from gate 3 until the one-row rename can run (RDR-229 P3.5a): `missing` names the name-key drop move, or the restart that applies P3.5b's changesets. The refusal sits in the shared rename primitive, so the catalog rename and each of the five per-store `rename_collection` routes have it. A rename's 200 now also answers the renamed row, `name`, `collection_id`, `ids_stable` (always false until P3.7's one-row rename keeps the id) and, when the engine role can read the cluster, `catalog_epoch`.
