### Added

- A collection's row carries its `collection_id` (RDR-229 P3.5a, first step, read-only). The engine's `GET /v1/catalog/collections/list`, `/get` and `/for_tuple` answer the registry's own id as a number on every row; `HttpCatalogClient.get_collection` and `list_collections` hand it back as an `int`, or `None` from an older engine that sends no id. No route takes an id yet, and the id is not stable across a rename until P3.7's name-key drop and R6's `ids_stable` signal, so nothing caches by it before then.
- Every engine route that takes a collection accepts its `collection_id` as well as its label (RDR-229 P3.5a, write half). A request that names a collection by id (`collection_id` in a body or query string, `collection_ids` for a list, `<field>_id` for a field such as `source` or `superseded_by`) is resolved to the collection's label at the route boundary, once, before the handler runs, so every route, and every refusal it already had, answers as it does for the label. Both a label and an id for one collection, or an id that is not an integer, is a 400; an id no row has, or the id of a retired row (a rename's or supersede's tombstone), is a typed 404 `unknown_collection_id` naming the id. A request that names only a label is untouched. `POST /v1/catalog/collections/delete` takes `collection_id` too (its 200 answers `collection_id` and `name`, `/version` advertises `catalog_collection_delete_by_id_supported`), deletes a retired row, by its label or its id, with the 200 it always gave (from gate 3 the purge is scoped by the row's own `collection_id`, so a retired label takes its own rows and never its successor's, and a label with no registry row purges nothing), and refuses a label that more than one live row holds with a 409 `collection_label_ambiguous` listing the ids.
- A collection rename decides its path inside its own transaction from the gate 3 latch row (RDR-229 P3.5a). With no row, and the rename readiness still waiting, it is the name path as before. With the row and the name-key drop move not complete, or a P3.5b changeset not applied, it is refused with a typed 409 `rename_refused` whose `missing` names the move or the restart. With the row and everything complete (the one-row regime) the catalog rename answers a typed 409 `rename_path_mismatch` until P3.7's one-row rename is wired, and each of the five per-store `rename_collection` routes (chash, taxonomy, telemetry, aspects, highlights) changes nothing and answers 200 in its usual shape with every count 0, after checking that the registry rename happened (the new label is a live registry row and the old is not); if it did not, the route answers a typed 409 `rename_not_in_registry` and changes nothing. With no row but the readiness complete (an inconsistency, as after a partial restore) every rename is a 409 `rename_refused` whose `missing` is `latch_row_missing`, never the name path. A rename's 200 now also answers the renamed row, `name`, `collection_id`, `ids_stable` (always false until P3.7's one-row rename keeps the id) and, when the engine role can read the cluster, `catalog_epoch`.
