### Changed

- **The engine's SQL readers name a collection by its id where a row carries one.** RDR-229 P3.5b. Thirty-eight functions and views whose bodies read a chunk-family table (among them `nexus.live_chunks`, `nexus.collection_vector_stats`, `chunk_is_reapable`, `chunk_sensitive_many`, the gc, quarantine and reaper movers, and the search functions) now match a chunk to its manifest row by `collection_id` where both carry one, and by name only where either lacks one. A NULL id never falls back to an empty name. Their outputs show the registry's label for a row's id, and the two views gain a trailing `collection_id` column. Each search function has a `<name>_by_id` twin that takes collection ids; the engine calls the twins once gate 3 latches (P3.5c). Twelve readers that read no chunk-family table (the catalog-044 owner trigger and its owner functions, `collection_doc_counts`, `collection_health_meta`, `topics_with_counts`) are redefined by id behind a CONTINUE precondition, which applies them only once every stamp move is complete. On a fresh install they wait until then, and are retried at each boot. The upserts on twin-key tables retry once on a unique violation of the id twin. Nothing here reads or writes a row as it migrates.
