### Changed

- **The engine's Java readers name a collection by its id once gate 3 latches.** RDR-229 P3.5c. After the latch, every Java read that matched a chunk, a manifest row, an aspect, a highlight, a topic, an assignment, a quarantine row or a ledger row by the collection's stored name matches it by `collection_id` instead, and shows the registry's current label for it; before the latch each read is the name read it was. A one-row rename leaves a row's stored name stale, so a name match no longer finds the rows of a renamed collection or finds another collection's under the old label. The two upserts (chunks and taxonomy centroids) take the id key as their conflict target, a write by id stores the locked registry row's current label (never the label the request carried), the stored-vector mismatch check and the embed-skip read find the stored row by its id, and the document move and the owner fold lock the registry row of every collection they write in before any document row. A quarantine row with no origin id is no sibling of its label's holder after the latch, an aspect-queue row whose collection id names no registry row is skipped with a WARN, and gate 3 does not latch while a quarantine chunk lacks the `origin_collection_id` key (a dangling tag is marked with the key present and JSON null; a restore fills the key from its own registry mapping). Nothing here reads or writes a row as it migrates; the name path stays until P4.1 drops the name columns.
