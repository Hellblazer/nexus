### Changed

- **Engine: a new collection label is checked (RDR-229 P3.6).** A registration through the client route, a rename target and a re-embed target are refused with a 400, and a new row of an ETL import is refused on its own (listed in the import's `refused`, nexus-3ptnh) while the rest of the batch imports, when the label is empty (a registration with no label is P3.8's mint instead), not valid UTF-8, holds a control character (U+2028 and U+2029 included), runs over 255 UTF-8 bytes, or holds `/` (it ends a collection in a note URI and names a path). A registration, a rename target and a re-embed target are also refused when the label is `c` followed by digits, which the engine reserves for the labels it mints; an import keeps such a label, since it carries another install's. A registration whose name is present but not a string is a 400. A refusal writes nothing, and a re-embed or registration that is refused seeds no embedding profile. An existing collection keeps its label whatever it is, so it still re-registers and still imports as a no-op. No 63-character cap or charset applies at the engine.
- **Engine: a label names one live collection per tenant.** `catalog-053-1` adds a partial UNIQUE index on `catalog_collections (tenant_id, name)` over the rows that are not superseded. The name is still the primary key until the P4.1 swap, so no existing row can fail it.
- **The CLI rename verbs check the target with the same rule, and still gate non-conformant targets until P3.8.** `nx collection rename` and `nx catalog rename-collection` run `validate_collection_name` on a target that does not exist yet, before calling the engine. They keep their own gates: `nx catalog rename-collection` still refuses a non-conformant target unless `--allow-legacy`, and `nx collection rename` still refuses a change of name prefix unless `--force-prefix-change`, so a user cannot yet rename onto a label such as `My Notes` without those flags. A NEW collection must still have a conformant name on the client. `validate_collection_name` is now the label rule, replacing the ChromaDB-shaped check (3 to 63 characters, alphanumeric at both ends, 128 bytes) and its `nx catalog collection-name` overflow hint. `HttpCatalogClient.register_collection` does not check the label on the client, because it cannot tell a new label from an existing one; the engine is the authority there.
- **A label with `%`, `+`, `&` or a space reads back whole from the taxonomy and telemetry query strings.** `TaxonomyHandler` and `TelemetryHandler` decoded the query twice, so a `%` or `+` in a label was decoded again and an encoded `&` split the pair.
- **A label with `[`, `?`, `#` or a fullwidth `／` no longer crashes the `nx-note://` readers.** The collection is the text up to the first `/`, as the engine reads it, not what `urlparse` makes of it.
- **Files named after a label are safe path components.** `nx store export`'s default file name and `nx catalog` orphan-backfill CSV directories go through `safe_label_filename` (percent-encoding outside `[A-Za-z0-9._-]`, `.` and `..` and Windows device names escaped, a 255-byte label cut to about 100 bytes plus a hash). A label of a conformant collection name comes through unchanged. A legacy PDF-checkpoint cleanup skips a label that no old client could have written a checkpoint for.
