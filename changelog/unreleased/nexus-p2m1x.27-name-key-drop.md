### Added

- **Engine: the name-key drop move (`rdr229-name-key-drop`) drops the seven registry name foreign keys, and waits for running index builds instead of ending them (RDR-229 P3.7, nexus-p2m1x.27).** A pass of its own, after the engine serves and once the gate 3 latch row exists, registers the move once (the completion check stays read only, and nothing runs at boot). Its `on_complete` drops the keys to `(tenant_id, name)` on chunks, canary_query_ring, document_aspects, topics, taxonomy_meta, document_highlights and topic_assignments (and the queue's key where that table still exists), which PostgreSQL would otherwise use to refuse a one-row rename. The completion attempt defers while any `CREATE INDEX` runs (the PCI builds, a leaf's unique index, an id unique index), because ending a build throws an HNSW build away. A deferral counts no failure, raises no page and ends no build; the move tries again about every 30 seconds and completes once none runs. While it waits, `GET /v1/status` `boot_work` carries the move as a `blocked:` entry whose `what` reads "waiting for in-flight index builds to finish (N running); none is ended and no failure is counted; waiting for <age>", with the additive `reason_class` value `waiting_for_builds`, or `waiting_for_builds_overdue` once the wait passes six hours (the text then adds the builders' backend pids, the one backend id the unauthenticated status carries). `nx doctor` shows the first as an `ok` note that says to wait, and the second as a warning with the engine's age, running count and pids; neither offers the retry-count reset, which would do nothing, and an engine before this cut sends no class, so a client shows the plain red blocked row. Until the move completes a collection rename answers 409 `rename_refused` with `missing` `name_key_drop_move`, which `nx doctor` names as the thing the rename waits for. Additive both ways, see `docs/wire-contract-pending.md`.
