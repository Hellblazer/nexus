### Changed

- **Engine: a collection rename keeps the collection's id and rewrites one registry row (RDR-229 P3.7, nexus-p2m1x.27).** From gate 3 of the completion check, once the name-key drop move has completed and every P3.5b changeset has applied, `POST /v1/catalog/collections/rename` updates the registry row's label in place: the collection keeps its `collection_id`, and no chunk, manifest, taxonomy, aspect, highlight or telemetry row is rewritten. Only `nx-note://` URIs that classify as notes follow the new label (never `chroma://` residue), queued aspect tasks name the new label, and tombstones that named the old label name the new one. Before gate 3 the rename is the fourteen-table rewrite it was. From gate 3 until the one-row rename can run, a rename answers 409 `rename_refused` with `missing` set to `name_key_drop_move`, `p35b_list_missing` (the build ships no P3.5b changeset list; a restart cannot fix it) or `restart`, and `GET /v1/status` carries `rdr229_completion.rename_missing` (`none`, `name_key_drop_move`, `p35b_list_missing` or `restart`) with the same spelling. Once gate 3 has held on an install (it is latched) a rename is never the fourteen-table rewrite again, even if the live gate 3 later drops back (an id index going INVALID): it is one-row or refused. The latch is process-local until P3.4's `nexus.rdr229_gate_latch` replaces it. While every stamp move is complete and a P3.5b changeset has not applied, `boot_work` lists one restart entry (`rdr229-restart`); it is safe to stop and is not counted as work by `nx upgrade`. A child row written under a renamed collection's new label for a chunk stored under the old label takes the chunk's stored name (vectors-079, one statement-level log line when a name is replaced). None of this can occur on a real boot until P3.4's Gate3Source replaces `NOT_INSTALLED`: gate 3 never holds before that, so every rename stays the fourteen-table rewrite. Additive; an older client reads the new status field as absent. After the collection-id latch, restoring quarantined chunks whose origin collection was never registered (`POST /v1/vectors/gc/restore-rereferenced`, bounded or not, and `POST /v1/vectors/gc/quarantine-restore`) answers 409 `restore_origin_unregistered` (the body names the `label` and the number of `rows`) instead of restoring them; nothing moves and the chunks stay quarantined. A restore by a renamed collection's new label now finds its quarantined chunks by the collection's id (vectors-083). The date-range form of `quarantine-restore` finds a renamed collection's quarantined chunks by the collection's id after the latch. The reaper now also expires client-moved quarantine rows whose origin was never registered (their `origin_collection_id` is the JSON null marker) past retention, and `gc_expire_quarantine` (bounded or not) no longer deletes a former holder's marker rows when it expires a re-registered label (vectors-083).
