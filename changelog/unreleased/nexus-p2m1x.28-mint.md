### Added

- **A registration with no name mints the collection's id and label (RDR-229 P3.8, engine half).** `POST /v1/catalog/collections/upsert` with no `name` registers by attributes (`content_type`, `owner_id`, `embedding_model`, `model_version`, all required): the engine takes the next `collection_id`, names the collection `c` followed by that id, and answers the row. A second registration of the same live tuple answers the same row and mints nothing, and two first registrations racing for one tuple make one row. The mint follows the live-tuple index when it exists (one insert that does nothing on a conflict, then a read) and takes a per-tuple lock before it exists. A label of the minted form already in the way makes the mint take the next id (sixteen draws, then a 409), and a sequence left behind the data by a restore is raised to the tenant's largest id once (never lowered, since every tenant draws from the one sequence), with a `collection_id_sequence_behind_data` warning, before a second collision becomes a 409.
- **No route accepts a `collection_id`.** The registration and ETL import routes answer 400 for a body that carries one; the tenant restore ignores the file's ids, reports the column skipped, and assigns each restored collection its id from the sequence. An import row, a restore file row or a named registration of a new collection on a live tuple another collection holds is refused naming both collections, with the live-tuple index present or not (without it the tuple is locked and re-read first), so none of them makes a second live row.
- **The engine role heals the `collection_id` sequence through a definer function, not a grant.** Changeset `collections-002` creates `nexus.collection_id_seq_heal(bigint)` (SECURITY DEFINER, search path pinned, raises the sequence to a floor and never lowers it) and grants `nexus_svc` EXECUTE on it; `nexus_svc` gets no UPDATE on the sequence every tenant draws from.

### Changed

- **A tuple's winner at equal version is the lowest `collection_id`.** `GET /v1/catalog/collections/for_tuple` and the re-embed target selection order by highest `model_version`, then the lowest `collection_id`, then `created_at`, then the name (it was `created_at`, then the name). The answer's shape is unchanged; which row answers can change only where two live rows share a tuple.
