### Added

- **A registration with no name mints the collection's id and label (RDR-229 P3.8, engine half).** `POST /v1/catalog/collections/upsert` with no `name` registers by attributes (`content_type`, `owner_id`, `embedding_model`, `model_version`, all required): the engine takes the next `collection_id`, names the collection `c` followed by that id, and answers the row. A second registration of the same live tuple answers the same row and mints nothing, and two first registrations racing for one tuple make one row. The mint follows the live-tuple index when it exists (one insert that does nothing on a conflict, then a read) and, before it exists, takes the tuple's advisory lock: one of 256 striped keys from `nexus.collection_tuple_lock_key` (changeset collections-003-1), the key catalog-051's owner triggers take too, so an import or restore of thousands of collections takes at most 256 locks. A label of the minted form already in the way makes the mint take the next id (sixteen draws, then a 409), and a sequence left behind the data by a restore is drawn forward to the largest id of any tenant it can read (every tenant where D2's owner-read policy exists, else this one) once (never lowered, since every tenant draws from the one sequence), with a `collection_id_sequence_behind_data` warning, before a second collision becomes a 409. An installation whose largest id is more than 100000 above the sequence gets a 409 naming the gap and the remedy, a one-off `setval` by an operator with the engine stopped, and nothing is drawn.
- **The engine role heals the `collection_id` sequence and checks ids through definer functions, not a grant.** Changeset `collections-002` creates `nexus.collection_id_seq_heal(bigint)` and `nexus.collection_id_taken(bigint)` (SECURITY DEFINER, search path pinned) and grants `nexus_svc` EXECUTE on them. An id is meant to be unique across the installation, so both read every tenant's `collection_id` through the migration role's owner-read policy (RDR-229 D2) and return one number or one boolean, never a row; the mint refuses an id any tenant holds. That holds only where the policy exists: without it the functions read no row, and the check is the caller's own tenant's. The heal draws the sequence forward with `nextval` until it has drawn the floor (the larger of the caller's and every tenant's largest id) and never calls `setval`, so a draw by another session or tenant while it runs is never set back and no id is handed out twice; it draws at most 100000 values. `nexus_svc` gets no UPDATE on the sequence every tenant draws from.
- **A rename onto the same tuple, and its way back, work with the live-tuple index present.** The registry transaction retires the old row first, naming the new row and its id, then writes the new row, so the index never sees two live rows and P3.1's successor-id check holds. A new row whose tuple a third collection holds is refused naming both. Reviving a superseded collection through a named registration is checked the way a new row is, and clears its successor id.
- **A mint that finds its row applies a non-blank `display_name`, and the client route mints `live` collections only.**
