### Added

- **A registration with no name mints the collection's id and label (RDR-229 P3.8, engine half).** `POST /v1/catalog/collections/upsert` with no `name` registers by attributes (`content_type`, `owner_id`, `embedding_model`, `model_version`, all required): the engine takes the next `collection_id`, names the collection `c` followed by that id, and answers the row. A second registration of the same live tuple answers the same row and mints nothing, and two first registrations racing for one tuple make one row. The mint follows the live-tuple index when it exists (one insert that does nothing on a conflict, then a read) and takes a per-tuple lock before it exists. A label of the minted form already in the way makes the mint take the next id (sixteen draws, then a 409), and a sequence left behind the data by a restore is set to the largest id once, with a `collection_id_sequence_behind_data` warning, before a second collision becomes a 409.
- **No route accepts a `collection_id`.** The registration and ETL import routes answer 400 for a body that carries one; the tenant restore ignores the file's ids, reports the column skipped, and assigns each restored collection its id from the sequence. With the live-tuple index in place, an import row or restore file holding two live collections for one tuple is refused naming both.
- **The engine role may set the `collection_id` sequence.** Changeset `collections-002` grants `nexus_svc` UPDATE on that one sequence, which the heal above needs.
