### Fixed

- **Two collection deletes whose origins share a quarantine sibling no longer meet in the sibling's registry delete.** A delete takes the registry rows of the quarantine siblings it removes rows from `FOR UPDATE`, with the origin's row in one `collection_id`-ordered statement on the delete by id, so two such deletes queue on the sibling. Before, both key-shared it and could end in a 40P01 deadlock, which the delete's retry absorbed. Separately, each saw the other's rows still there, so the emptied sibling stayed registered. The delete holds each sibling's row `FOR UPDATE` for its whole transaction: a write into a shared sibling (the reaper, the gc routes, a restore) waits for a delete of any origin that shares it, and the reaper counts that wait as a `LOCK_TIMEOUT` skip. A gc mover or a rename that holds the origin while a delete holds a sibling of a lower id can deadlock with it; the movers now run again on a 40P01, as the delete and the rename already did (nexus-p2m1x.23).
- **A rename's retag of the origin's quarantine rows holds the sibling rows it reads.** It takes each sibling's registry row `FOR KEY SHARE` in id order before it reads them, so a sibling renamed or retired in that window is no longer read under a stale label (nexus-p2m1x.27).
- **The engine's five SQL functions that register or refresh a registry row from another collection's tuple refuse by name where they raised a bare 23505.** They are `gc_restore_rereferenced`, `gc_restore_rereferenced_bounded`, `gc_quarantine_orphans`, `gc_quarantine_orphans_bounded` and `reaper_quarantine_chunks` (changeset `vectors-085`). When another live collection already holds the tuple, they raise SQLSTATE 22023 and move nothing. These guards act only where the index `catalog_collections_live_tuple_uq` exists; where it does not yet, the functions behave as before. Only direct SQL reached the old error; no route did (nexus-p2m1x.28).
