### Fixed

- **Two collection deletes whose origins share a quarantine sibling no longer meet in the sibling's registry delete, and a rename's retag now holds the sibling rows it reads.** A delete takes the registry rows of the quarantine siblings it removes rows from `FOR UPDATE`, with the origin's row in one `collection_id`-ordered statement on the delete by id, so two such deletes queue on the sibling instead of both key-sharing it (the cycle PostgreSQL ended with 40P01, and the emptied sibling stayed registered). A rename's retag of the origin's quarantine rows takes each sibling's row `FOR KEY SHARE` in id order before it reads them, so a sibling renamed or retired in that window is no longer read under a stale label (nexus-p2m1x.23, nexus-p2m1x.27). The engine's five SQL functions that register or refresh a registry row from another collection's tuple (`gc_restore_rereferenced`, `gc_restore_rereferenced_bounded`, `gc_quarantine_orphans`, `gc_quarantine_orphans_bounded`, `reaper_quarantine_chunks`; changeset `vectors-085`) refuse by name (SQLSTATE 22023) and move nothing, where they raised a bare 23505 from `catalog_collections_live_tuple_uq`, when another live collection already holds the tuple. Only direct SQL reached that; no route did (nexus-p2m1x.28).
