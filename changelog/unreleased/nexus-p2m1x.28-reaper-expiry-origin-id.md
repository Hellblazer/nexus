### Fixed

- **The engine's two quarantine expiries no longer delete a chunk that a manifest row of its own origin still names.** `nexus.reaper_expire_quarantine` and `nexus.reaper_expire_client_quarantine` list rows by the origin label tag and guarded each row by the collection id resolved from that label. After a one-row rename, a quarantine move that committed after the rename's retag left a row tagged with the old label; the label then resolved to no collection (or to a new holder of it), the manifest guard missed the chunk's re-reference under the new name, and the referenced row was deleted. Each expiry now also treats a manifest row of the row's own `origin_collection_id` as naming the chunk, in the count, the select and the delete. A row whose key is the JSON null marker, or a key that is not an integer-valued number, is judged by the label guard alone, as before. Changeset `vectors-086`, two function definitions, no data change.
- **After the gate 3 latch, a quarantine row with no origin id is never expired, is not counted as protected, and is not reported; a later data move will stamp such rows.** Both expiries now leave a row whose metadata has no `origin_collection_id` key alone: it stays in quarantine instead of being deleted by a label that may now name another collection. `protected_count`, the second value each function returns, no longer counts those rows. Before the latch the behavior is unchanged.
