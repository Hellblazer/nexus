### Fixed

- **Engine: a re-embed start or plan is refused with a 409 when its source shares the lookup tuple (content type, owner, model) with another live collection, or when the live target it would use was filled by a job from another source with the same tuple.** Two sources under one curator owner (`docs__arcaneum-2ad2825c` and `docs__wow-addon-dev` on one tenant, both owner `1-40`) hold two live rows on one tuple, and the target is chosen by that tuple, so the second source's re-embed would have merged into the first source's target. The second refusal reads the job log: only a job that moved at least one document (`documents_moved`) counts, and its source must have this source's embedding model, read from its registry row or, when a default cutover deleted the row, from the model token of its conformant name (an unreadable name counts, so it refuses). Only the model is compared, never the other source's current owner: the target fixed the content type and owner it had when the job ran, and re-owning that source later does not take its documents out of the target. One owner with docs in two different models, both re-embedded into the profile model's target, is not refused. A v2 of an already-moved source is refused, as a deliberate conservative refusal: the log is keyed by name and cannot tell a v2 from a shared-curator twin. Both messages name the collections and say that a client cannot change a collection's owner in place, that an owner changes through an engine data move or a rename that re-homes the collection under another owner (RDR-229 owner-is-source), and what clears the refusal: for a live twin, re-owning or superseding one of the two; for a filled target, only re-owning this source, which gives it a different target tuple (the job log persists and the other source's documents stay in the target, so superseding or re-owning the other source does not clear it, which includes a v2). A source alone on its tuple, and a restart of a source into its own earlier target, are unchanged. **Scope: this closes same-model twins only.** Both checks key on the source's model while the target is keyed on the profile model, so two shared-curator sources on different source models can still be re-embedded into one target and merge. That is an accepted residual, not a pending one: Sam ruled "Accept, documented" (T2 `nexus/sam-ruling-reembed-guard-residual-2026-11-21`). When the name-token read of a deleted source's model retires with the name parsers (RDR-229 P4), a job whose source row is gone reads as an unknown model and refuses, so the sibling-on-another-model narrowing then holds only while the first source's row is kept.
