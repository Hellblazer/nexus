### Fixed

- **Engine: a re-embed start or plan is refused with a 409 when its source shares the lookup tuple (content type, owner, model) with another live collection, or when the live target it would use was filled by a job from another source with the same tuple.** Two sources under one curator owner (`docs__arcaneum-2ad2825c` and `docs__wow-addon-dev` on one tenant, both owner `1-40`) hold two live rows on one tuple, and the target is chosen by that tuple, so the second source's re-embed would have merged into the first source's target. The second refusal reads the job log: only a job that moved at least one document (`documents_moved`) counts, and its source must have the same content type, owner and model, read from its registry row or, when a default cutover deleted the row, from the model token of its conformant name (an unreadable name counts, so it refuses). One owner with docs in two different models, both re-embedded into the profile model's target, is not refused. A v2 of an already-moved source is refused, as a deliberate conservative refusal: the log is keyed by name and cannot tell a v2 from a shared-curator twin. Both messages name the collections and say that a client cannot change a collection's owner, that an owner changes only through an engine data move (RDR-229 owner-is-source), and that the re-embed can start once one of the twins is re-owned (or, for the shared-tuple refusal, superseded). A source alone on its tuple, and a restart of a source into its own earlier target, are unchanged.
