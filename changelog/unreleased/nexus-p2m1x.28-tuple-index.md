### Added

- **The collection registry refuses a second live collection on one tuple (RDR-229 P3.8).** A partial UNIQUE index on `(tenant_id, content_type, owner_id, embedding_model, model_version)`, over rows that are neither superseded nor quarantined, makes `for_tuple` single-valued at a model version. The engine builds it at the first start where the re-own data move (`rdr229-reown-repo-stems-from-curator`) has completed and no live tuple is shared; until then the changeset waits without halting the boot or being recorded, so every start retries it. A new install takes two starts to get the index: the first registers the move, the second applies it. The check for a shared tuple is a read: it takes no lock on the registry beyond a read, so a start in the cloud never blocks the catalog, and the index build waits at most five seconds for its lock behind an open writer (it then fails quietly and the next start retries it), and it reads every tenant through the owner-read policy of RDR-229 D2 (where that policy is absent the check reads nothing, and the index build itself refuses a real duplicate and is retried).
- **`GET /v1/status` reports `collection_tuple_index_present`.** One boolean, true once the index exists; absent on an engine that predates it. `nx doctor` names any live tuple held by more than one collection (the "Collection tuples" warning), which is what holds the index back, and warns (the "Collection tuple index" row) when the index is absent, no tuple is shared and the re-own move is neither open nor failed: the index then waits for a reason the doctor cannot name, and the row points at the engine's boot log. Neither row appears when it does not apply.
