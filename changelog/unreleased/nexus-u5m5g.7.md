### Changed

- **`nx index repo` reconciles the catalog on the engine** (RDR-193 Step 6, nexus-u5m5g.7). The catalog hook of an index run walks the files, stats and hashes them and builds one landing row per file, then stages the rows on the engine in pages of at most 1000, commits the run once and polls the commit job; the diff against the catalog, the update of changed rows, the miss-count sweep, rename detection with its link moves and the explicit deletions of a delta run are the engine's, in one transaction. A run of N files is `ceil(N/1000)` stage requests and one commit where the hook's registration used to be an owner list, a batch register, a batch update, a per-document housekeeping loop and a per-path delete. The hook's own write path is that one commit; the run still writes each document's frecency to its catalog meta afterwards (the `update_many` of `_write_frecency_meta` is unchanged and is not part of the commit). A file the walk saw but could not register (a worktree or temp-dir path the guard refuses, a row that could not be built) is staged as a `keep` row, so a row an earlier run left at that path is not counted missing and swept, as before. The job contract is the client's for every commit: a 409 waits for the named job and never resubmits (the run then raises `commit_conflict`, whatever became of the other job, since its own rows were not committed), a 404 on the poll (the engine lost the job) resubmits once, a 503 from a full job registry or a failed job with reason `transient_db_error` resubmits at most three times with backoff, a stage answered 409 raises, and any other failure raises. A failed commit fails the run: no document is registered, no chunk is written, `nx index repo` exits non-zero (also for a `--since-head` run of only deletions, which names no file), and the `--since-head` base is not advanced. The commit's renamed, swept and explicitly deleted documents are logged one event each, as housekeeping did (`housekeeping_rename_detected`, `housekeeping_orphan_deleted`, `since_head_deleted_doc`). There is no fallback to the old client path, which is deleted (`_run_housekeeping`, `_maybe_run_housekeeping`, `_delete_docs_for_paths`, `register_many`/`update_many` in the hook). Needs an engine that serves `/v1/catalog/reconcile/*` (engine-service-v0.1.185).
- **`nx index md` and `nx index pdf` resolve a document with one `resolve_or_register` request, and `nx store put` a titled note** (RDR-193 Step 6). A curator-owned document with an identity of its own is looked up by source URI and registered when absent, carrying the title, year and source mtime and born flagged when sensitive; the lookup, cross-owner probe, register and reconcile requests they made one after another are gone. A document another owner holds is reported and neither adopted nor written (`foreign_owner`). `nx store put` resolves a titled note through the same request (a ghost of the same title is reused) and, as before, updates a row it finds, another owner's included. The register-time stamp, author and corpus follow in one update. A document with a legacy relative path, a repository owner's row, or no absolute identity still takes the lookups it took before.
- **A sensitive titled put or curator register on an engine below `RESOLVE_SENSITIVE_MIN_ENGINE_VERSION` (0.1.185) is refused with `CatalogReconcileError(reason="engine_too_old")`** (nexus-u5m5g.7). Engine v0.1.184 answers a `sensitive` key on `resolve_or_register` with a 400; the client now names the floor and the remedy (upgrade the engine to 0.1.185 or later) instead of surfacing the opaque HTTP error. The floor is a release check beside the note-URI and sensitivity-exclude ones (`check_engine_release_floor.py --ledger-only` and the tag-time forms fail while `REQUIRED_ENGINE_VERSION` is below it) and every gate-jar stamp is the max of the pin and the floors; a non-sensitive call is unaffected.
