### Fixed

- **The pool key scan's filter no longer reads an empty assessment reply as a reject, and logs what it sent and got back** (nexus-w8d30, RDR-250; client-only). A filter call whose reply held no evidence record is a failed call (the assessment's own instruction says so), not a verdict that nothing supports the chunk: it keeps no pool key and the report names it `pool_reason: filter_empty_reply`, with the count in `pool_filter_empty_calls` and a warning. A reply that held records and cited none as support is still a reject. With `NX_ANSWER_POOL_KEY_SCAN` on, each filter call is also an `nx_answer_pool_filter_call` event and an entry of `pool_filter_log` (payload and evidence hashes, token counts, the `supports` item and facet ids the assessment would accept, counts of records it would not and of those the host dropped, and an outcome that agrees with the reason; a record the assessment would not accept is never a reject). Off, nothing changes. What changes for you: nothing unless you set the variable.
- A pool filter call cut by the operator timeout (`OperatorTimeoutError`) now counts as a timeout (`filter_timeout` when no call completed); before, it read `filter_failed`.
- **The pool key scan's filter asks for a stronger model** (nexus-w8d30, RDR-250; client-only). With `NX_ANSWER_POOL_KEY_SCAN` on, the filter's assessment calls go to `sonnet` (`model_tiers.POOL_FILTER_ALIAS`) instead of the check tier's `haiku`: on the cheap tier the 2026-11-17 stability probe saw the keep/reject verdict vary on identical input. The boundary's own coverage assessment keeps its tier, and `NX_OPERATOR_MODEL_TIERING=0` sends the filter bare like every operator. The filter's calls are left out of the mean cost the boundary's own calls are admitted on, and still count in what the run spent. What changes for you: nothing unless you set the variable; with it set, each filter call costs more and takes longer, against time and cost bounds that are still sized from the first (haiku) assessment.
