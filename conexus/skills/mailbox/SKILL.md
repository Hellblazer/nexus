# Mailbox

RDR-205 Phase 5/6 consumer: `mailbox/<address>` tuple-space messaging, addressed to an agent id (Phase 5) or an instance name (Phase 6, cross-instance request and ack).

## When This Skill Activates

- Sending a message to another agent's or instance's address
- Draining a mailbox before composing a hand-back
- Subscribing the instance mailbox or a board topic, or acting on what the channel pushes
- Taking, renewing, or ending a queue task or a lock claim
- Authoring or reviewing code, tests, or docs against the `mailbox/<address>`, `board/<topic>`, `queue/<name>`, or `lock/<resource>` templates

## Rules

- Address (agent): the harness id `subagent-start.sh` injects (its "Claimant id: `<id>`" line). The mailbox address is `mailbox/<id>`.
- Address (a peer's NAME, RDR-208 Phase 2): pass the exact name `ListAgents` shows (for example `nexus-23`) as `mailbox_send`'s `to`: it resolves the name through the session directory (`directory/<name>`) to whichever session currently holds it and sends `address_kind: session`. This is now the normal way to reach a named peer; you no longer construct an instance address by hand.
- Address (instance, RDR-205 Phase 6, legacy during the RDR-208 transition): the session name the harness's ListAgents tool shows, sent directly as `mailbox/<name>` with `address_kind: instance` (still a valid raw `tuple_out` target until RDR-208 Phase 3 retires it, but `mailbox_send` never uses this form itself).
- Cross-instance request and ack: send `tuple_out` to the peer's address with `dims={"from": "<your instance name>", "kind": "request", "correlation_id": "<id>", "address_kind": "instance"}`; park a `PARKED in` on YOUR OWN mailbox (`mailbox/<your instance name>`) for the ack. Each `in` parks at most the 25 s cap — LOOP the call for a wait of minutes, never rely on one park outlasting it. The peer replies by claiming the request with `tuple_in`, doing the work, then `tuple_ack(claim_id, claimant, reply={"subspace": "mailbox/<your instance name>", "keys": {"to": "<your instance name>"}, "dims": {"from": "<peer>", "kind": "ack", "correlation_id": "<same id>"}, "body": "..."})` — never a separate `tuple_out` followed by `tuple_ack`; `correlation_id` is what pairs the ack with its request.
- Renew: `mcp__plugin_conexus_nexus__tuple_renew(claim_id="<id>", claimant="<address>", lease_s=<n>)`. Renew at half the lease when the work behind a claim is still running — do not wait for the lease to lapse. A lapsed claim is retaken, `attempts` increments, and two readers act on the same message; after three lapses the message is dead-lettered while the first reader may still be working on it. `lease_s` is relative to now, refused (`LeaseTooLong`) above the mailbox template's `max_lease_seconds` of 900, and clamped to the tuple's own expiry inside that cap. A renew on an already-lapsed claim fails `ClaimNotFound` — the holder learns it lost the claim rather than resurrecting it — and a renew never counts as an attempt.
- Reply in ack, not a second call: a request that needs an answer is answered through `tuple_ack`'s `reply` argument, in the ack's own transaction — never by a separate `tuple_out` followed by `tuple_ack`. A crash between those two calls would deliver the reply and leave the request unconsumed, so the requester gets a second reply under the same correlation id; reply-in-ack makes that impossible because the reply write and the request's consumption commit together or not at all. The reply's target subspace must resolve to a `keys+nonce` template (the mailbox is; the RDR-184 ledger is not, and is refused with `SchemaViolation`); an unrecognized subspace is refused with `UnknownSubspace`. Both refusals happen before anything is consumed, so the request stays claimed and the holder corrects the reply and retries. The engine sets the reply's nonce to `hex(request tuple id)` itself — no caller supplies one, and a `nonce` key in the reply object is refused as a `SchemaViolation`. If an `ack` with a reply reports that the reply was not written (an old engine with no `/renew`/reply support), the request was still consumed as a plain ack; re-send the reply with a fresh `tuple_out`.
- Push delivery (RDR-213, amending RDR-211 nexus-rplay.14 which superseded nexus-6konb): subscribe your instance mailbox ONCE per session with the exact call the SessionStart hook injects (its `MAILBOX SUBSCRIBE` line): `mcp__plugin_conexus_nexus__tuple_subscribe("mailbox/<name>")`, with `<name>` from a `ListAgents` call made now, never from memory (a resume changes it). Your session's own `mailbox/<session id>` is already subscribed from MCP-server startup; no call is needed for it. A second subscribe of the same name is harmless. Once subscribed, your session's own nexus MCP server parks a `wait` over the subscription and pushes a reference through the Claude Code channel (`notifications/claude/channel`) — a research preview reached only when the session was launched with a channel flag: `--dangerously-load-development-channels server:nexus` (a one-keystroke confirmation dialog appears every launch, not remembered between them), or `--channels plugin:conexus@nexus-plugins` with no dialog once the plugin is on the channel allowlist (`allowedChannelPlugins` in Claude Code's managed settings; see docs/tuple-space.md). The reference names the subspace and the tuple id only, never the body or a claim: the waiter holds no claim. The notification is also the wake for the same `UserPromptSubmit` hook that runs every prompt, so with the plugin's hooks loaded the drain hook usually claims, acks and renders the body in that same prompt, before your turn. If the body is rendered with the notification, act on it and claim nothing. Otherwise (no plugin hooks in this session, or the rare race the hook loses), claim it yourself with `tuple_in` on the named subspace. Each new message is announced once; if unanswered, that same reference may repeat every 150 s up to five times. An empty `tuple_in` means the row was already delivered or taken, by the hook or another claimant: do nothing further. Otherwise act: `tuple_ack` (with `reply` for a request) or `tuple_nack`. A row you are only deferring, not failing, goes back with `tuple_release`, never `tuple_nack`: each announcement is a fresh claim decision, and the mailbox template dead-letters a message after three nacks. A board post is the same shape with no claim: subspace and tuple id; read it with `tuple_rd` on that subspace. A post is announced to your session once, from the engine's per-subscriber stamp, never re-announced. When the channel is not reached at all (no launch flag, or before you subscribe) the `UserPromptSubmit` drain hook still claims, acks and renders mail at your next prompt, unconditionally — it is the floor beneath the channel, never the other way round, and it drains your instance-name mailbox only after `tuple_subscribe` has registered that name for this session. Do NOT substitute `/loop`, `/schedule`, or a sleep-and-poll loop written in prose or in a Bash command for either mechanism.
- Follow a board topic: one `mcp__plugin_conexus_nexus__tuple_subscribe(subspace="board/<topic>")` call, the same call the instance mailbox uses, no extra argument. `tuple_unsubscribe(subspace)` drops it; `tuple_subscriptions()` lists the current set (no cursor: the engine keeps every subspace's delivery position). At most 32 board topics beyond the two mailboxes (your own and, once subscribed, your instance name) — a further subscribe is refused with `SchemaViolation`. A `/resume` restores the list; a `/clear` starts clean.
- Board posting convention: post to one topic at most once a minute (RDR-211 Scale and Limits item 2) — nothing in the engine enforces this, but a `board/<topic>` subspace refuses further `out` calls once it holds `max_live_rows` (500) live posts, and posting faster than the assumed load (50 a day) is what fills that ceiling.
- Queue and lock claims: `tuple_subscribe` refuses a queue or a lock naming `in` — both are take-enabled, so a worker or a would-be holder parks with `mcp__plugin_conexus_nexus__tuple_in` instead, which already wakes on `out` and `release`. Take with `tuple_in`, renew with `tuple_renew` while the work is still running, then end the claim: `tuple_ack` when a queue task is genuinely done, `tuple_nack` when it failed (counts one attempt toward the template's `max_attempts`), or `tuple_release` to hand it back clean without counting an attempt — the only correct way to end a lock claim, and the right call for a queue task that was not a failure. `tuple_ack` on a lock claim is refused as `SchemaViolation` naming `release`: an acked lock row would stay unobtainable until the sweep purges it, so a lock is never consumed, only released.
- Unacked-request sweep: `scripts/check_inbound_relay_acks.py` also reads every `mailbox/*` subspace for `kind=request` rows with no matching `kind=ack` row at the requester's own mailbox.
- Send: `mailbox_send`. Prefer it over raw `tuple_out`. `mcp__plugin_conexus_nexus__mailbox_send(to="<session id, agent id, or name>", body="...", kind="...", correlation_id="...")`. `to` resolves at send time: a session id or an agent id is used as is; anything else is a NAME, looked up in `directory/<name>`. When exactly one live session holds the name it resolves to that session; when NO live session holds it, or MORE THAN ONE does, `mailbox_send` writes nothing and returns an error (for the two-holder case, naming every holder's session id). `nx tuple directory NAME` shows the same thing from the CLI (each live holder's session id, `created_at`, `expires_at`) before you send, or to find the session ids to resend to after a refusal. Resend directly to one of them. `mailbox_send` mints a FRESH nonce every call: unlike raw `tuple_out`, a resend is always a new tuple, never a dedup onto an earlier one (see Resend, below, which describes the raw path). The sender's own address (`from`) defaults to this session's own id and is refused, writing nothing, when it cannot be resolved. A subagent shares its parent's MCP server and would otherwise stamp the PARENT's session id: it passes `from_address="<its own agent id>"` (the harness id from `subagent-start.sh`'s "Claimant id:" line) instead.
- Send (low-level): raw `tuple_out` to the recipient's address stays the documented path: for a caller-controlled nonce (resend-dedup, below), for `address_kind: agent`/`instance` sent directly with no directory lookup, and for the cross-instance request in the pattern above, which needs `tuple_ack`'s own reply-in-ack shape rather than a second send. `mcp__plugin_conexus_nexus__tuple_out(subspace="mailbox/<address>", keys={"to": "<address>"}, dims={"from": "<your id>"}, body="...", nonce="<sender-minted nonce>")`. The nonce is REQUIRED: `mailbox/<address>` is a `keys+nonce` template, and an `out` with no nonce is refused as a `SchemaViolation`, the same way a missing `from` is. It is an id ingredient only: reading the message back (`tuple_rd`/`tuple_in`) never echoes the nonce.
- Nonce scope: the nonce need only be unique among the SENDER's own messages. `from` is the template's `id_dims` field, so two senders' messages to the same address never collide even on the same nonce — the sender is part of the tuple's identity.
- Size limit (bead nexus-r7xao): the tuple space is a coordination and metadata store, not a value store. `body` is a short message or signal, at most 4096 bytes UTF-8; `to`/`from`/`correlation_id` values at most 256 bytes; the nonce at most 128 bytes. An over-limit `out` or reply is refused with `TooLarge`, before any write. Content longer than that goes in T2 (`memory_put`) or T3 (`store_put`), and the message carries a reference — a project/title or a document id — not the content itself.
- Drain: `tuple_in` BEFORE composing any hand-back. `mcp__plugin_conexus_nexus__tuple_in(subspace="mailbox/<address>", keys_pattern={"to": "<address>"}, claimant="<address>", lease_s=<n>)`. Ack (with or without a reply) or nack the claim once handled.
- Two messages, two rows: two sends to one address with different nonces are two tuples.
- Resend, one row: the SAME sender resending the SAME nonce to one address is ONE tuple, not a second. `expires_at` never passes `created_at` plus the template's 7-day retention, however many times it is resent.
- Missing `from`: an `out` naming no `from` is a `SchemaViolation` — `from` is the template's one required dimension.
- Dead-letter: three attempts against one message — nacks, lapsed leases, or a mix of both — park it out of every future claimant's view. It stays readable by `rd` with `claim_state="dead"`, and `subspace_stats` counts it under `dead`.
- Template (`service/src/main/resources/tuples/templates/mailbox.yaml`): keys `to`; dims `from` (required), `kind`, `correlation_id`, `address_kind` in `{agent, instance, session}` (RDR-208 Phase 1 Step 2; `instance` retired after RDR-208 Phase 3); `take.enabled=true`, `max_attempts=3`, `max_lease_seconds=900`, `retention_seconds=604800`.

## Success Criteria

- [ ] A directive sent mid-turn is drained by `tuple_in` before the hand-back is composed
- [ ] A resend of the same sender+nonce lands on the same tuple id, `expires_at` unchanged
- [ ] A mailbox `out` with no `from` is rejected as a `SchemaViolation`, never silently accepted
- [ ] A cross-instance request parks on the requester's OWN mailbox for the ack, looping at the 25 s cap rather than depending on one park to outlast it
- [ ] An unacked request (no `kind=ack` row at the requester's mailbox) is visible to `scripts/check_inbound_relay_acks.py`'s mailbox scan
- [ ] A claim held across long work is renewed at half its lease, never left to lapse
- [ ] A reply to a request is sent via `tuple_ack(reply=...)`, never via a separate `tuple_out` followed by `tuple_ack`
- [ ] The instance mailbox is subscribed once per session via `tuple_subscribe`; a reference whose body is rendered with the notification is acted on, never claimed; otherwise it is claimed with `tuple_in` and given back with `tuple_release` (never `tuple_nack`) when only deferred; no `/loop`, `/schedule` or prose poll loop stands in for the channel or the drain hook
- [ ] A board topic is followed with `tuple_subscribe` and nothing else, and posts to it stay at or under one a minute
- [ ] A queue task or a lock claim ends with `tuple_release`, not `tuple_ack`, when the work was not a failure; `tuple_ack` is never attempted on a lock
- [ ] A message or reply body over 4096 bytes goes to T2/T3 with a reference in the tuple, never as an oversized `body`
- [ ] A send to a peer's NAME goes through `mailbox_send`, never a hand-built instance address, unless the caller genuinely needs a caller-controlled resend-dedup nonce or the cross-instance request/ack shape
- [ ] A name held by more than one live session is never delivered to either silently; `mailbox_send`'s refusal (or `nx tuple directory NAME`) names the session ids, and the resend goes to one of them directly
- [ ] A subagent sending through `mailbox_send` passes `from_address` set to its own agent id, never letting the default `from` stamp its parent's session
