### Engine-service release (a SECOND lifecycle — decoupled from the PyPI release)

The Java **engine-service** binary is a separate release artifact with its own cadence. Conflating it with the PyPI/marketplace release is how the cloud engine silently drifts behind develop (2026-06-26: 22 `service/` commits / 4 days un-deployed, un-cloud-tested).

Build or test the engine through `scripts/mvnw-leased.sh` (never a bare `./mvnw`/`mvn`) — one builder at a time; a concurrent `./mvnw` invocation against the same `service/target` corrupts jOOQ codegen mid-build (nexus-c00dw, see `scripts/lib/build-lease.sh`). The lease lives in the git common dir, so every worktree shares it, and a live holder is waited for rather than refused (`NX_BUILD_LEASE_WAIT`, nexus-g6xpa): one engine build or suite per box. The exception is a hand run inside a lab-run grant: `mvnw-leased.sh` and `build-gate-jar.sh` refuse at once with 75 there, since waiting would hold the grant's cores; take the lease first with `scripts/mvnw-leased.sh --lab-run <class>` (nexus-dfg0q). `scripts/build-gate-jar.sh` caches the stamped jar on its build inputs (`service/pom.xml`, `service/src/main/**`, `service/src/build/**`, `service/mvnw`, `service/.mvn/**`), so a fresh worktree with unchanged inputs gets a hard link to the cached jar (a copy only where linking fails) instead of a nine-minute rebuild. The link is read-only: a bare `./mvnw package` or an IDE build run after `build-gate-jar.sh` fails with "jar is read-only"; remove `service/target/nexus-service-1.0-SNAPSHOT.jar` or build through `scripts/mvnw-leased.sh` / `scripts/build-gate-jar.sh`, which unlink it first (nexus-k6zxp). The Python suite reads the same lease at session start (nexus-pv93h): while a build in the same checkout holds it (the lease names the checkout that took it; another worktree's build never rewrites this jar, nexus-qt6q7), `pytest` refuses the whole run with one line and exit 75 naming the holder, and `NX_BUILD_LEASE_WAIT=<seconds>` makes it wait instead; `NX_TEST_T2_SUBSTRATE=none` runs are never gated.

  The suite takes a lease of its own, `suite`, under the same root (`tests/_suite_lease.py`), so two full runs on one box see each other. **A second run queues, and fails closed when the wait runs out** (nexus-tvt6u): a run that finds the lease held waits up to 30 minutes for the holder, printing the holder and the time waited at once and then every minute, and starts when the holder exits, waiters in arrival order (a ticket under `suite.queue`, skipped when its pid is dead or it has not been touched for 30 s; the budget is read on the monotonic and the wall clock, so a sleeping Mac does not stretch it); one still refused after the wait (or that loses the race for it) exits 75, naming the holder (or the waiter ahead in the line, when the lease itself is free), and for a held lease the directory and the recovery command (`rm -rf <lease dir>`, valid only when no pytest run is live). `NX_SUITE_LEASE_WAIT=0` refuses at once instead of queueing (`=1` is the default), `NX_SUITE_LEASE_UNGUARDED=1` runs on at once, and inside a lab-run grant (`LAB_CPUS`/`LAB_MEM_MB`) on Linux the lease is skipped because lab-run is the queue there (a macOS `lab-mac` grant is admission only, so the lease is still taken). A lease directory whose pid file is missing, empty or garbage (a run killed between its `mkdir` and its pid write) is reclaimed automatically once it is 60 seconds old, so a corpse cannot wedge the queue. **A lease this user cannot READ (EACCES on the directory or the pid file) is HELD, never reclaimed**: it may be a live peer's, so the run exits 75 naming the path once its wait is spent (`acquire` creates the directory and its files group-writable and world-readable, never world-writable, explicitly, whatever the umask, so peers can read each other's and either user in the group can clear the other's corpse). A reclaimed lease is set aside by an atomic rename and then removed best-effort, and `acquire` sweeps leftover set-aside directories (named `suite.stale.` plus the reclaimer's pid and a timestamp) older than an hour (nexus-3tx9c). Two gaps stay open: a pid write that fails after `mkdir`, and a maker stalled over 60 s between the two (`_reclaim_if_dead`'s docstring). **Fails closed is a claim about contention only**: an unwritable lease root still runs UNGUARDED, silently (`acquire` swallows it and hands back a no-op release). `NX_SUITE_LEASE_UNGUARDED=1` (exactly `1`; `true`, `off` or a typo do not count) is the explicit opt-out for a HAND run; no workflow may set it, pinned by `tests/test_suite_lease_unguarded_lint.py`.

  Both leases log contention (nexus-jqk5c): one `key=value` line per event is appended to `${XDG_STATE_HOME:-$HOME/.local/state}/nexus/lease-events.log`, so waits and refusals can be measured afterwards. **The file is per user per host**: the default path is under the calling user's home, so on chas and hellmini each user writes its own. A measurement that must see every user's events sets `NX_LEASE_EVENTS_LOG` to one path (a file either writer creates is mode 0664, so users of one group, `labhand`, can append to it; an existing file's mode is never changed). Fields, in order: `ts` (ISO-8601 UTC), `lease` (`service` or `suite`), `name`, `host`, `pid`, `waited_s`, `outcome` (`acquired_after_wait`, `refused`, `stale_reclaimed` or `gave_up`; the laptop guard adds `local_heavy`, which is not a contention: it records a run `NX_LOCAL_HEAVY=1` let start on a Mac, with `workers=N` and an optional `reason=` from `NX_LOCAL_HEAVY_REASON`, nexus-74bc6), then `holder_pid` and `holder_label` when known; a value with a space is double-quoted. `refused` is a live holder met with no wait budget; `gave_up` is a wait that ran out; a wait that ends in a stale reclaim logs the one `stale_reclaimed` line. One wait writes one line, its final outcome, with the whole `waited_s`. A suite run that went on after a refusal because `NX_SUITE_LEASE_UNGUARDED=1` carries `unguarded=1`, so its `refused` or `gave_up` line is a bypass, not a blocked run. `lease=suite` is the pytest suite's lease; the build-lease helper logs a lease named `suite` the same way. **Only contention is logged: an immediate, uncontended acquire writes nothing.** Writing is best-effort, so an unwritable log changes neither a return code nor stderr.

- **Artifact + trigger:** an `engine-service-vX.Y.Z` git tag fires `engine-service-release.yml`, which builds + cosign-signs the 3 native binaries (linux-amd64, linux-arm64, mac-arm64 — mac-arm64 now SMOKED, by a job on the hellmini persistent runner, which has Docker via colima; nexus-yd9po closed the nexus-4xf5m no-Docker-on-GH-macOS gap for the default tag-push path, a `workflow_dispatch` run that falls back to `macos-14` when hellmini is offline is still unsmoked there; mac-amd64/Intel is not a supported target). It publishes **nothing to PyPI** and is **NOT gated by the luxe6 / RDR-155-P4a develop release boundary** (the workflow header says so explicitly). **The release is a DRAFT until every asset is attached** (nexus-cl14i, after v0.1.95 published PG bundles with no binary): a final `promote-release` job flips it only when both matrices succeeded and all 30 assets are present (36 with the Windows legs on; each Linux and macOS engine also ships as `nexus-service-<arch>.txz`, the asset `nx init` downloads), so a tag is consumable roughly 35 to 65 minutes (v0.1.118 took 36, a single measurement) after push, never partially; a failed leg, mac-arm64 included, leaves a draft that `gh run rerun --failed` completes and promotes. So the engine can be refreshed in the cloud at any time, independent of the unreleasable-develop state.
- **Engine-bundle canary: a new tag's PG bundle is tested before a client release pins it.** develop CI runs the substrate on the PG bundle of the engine pin (`src/nexus/engine_version.py`), which moves at a client release, so a new engine tag's bundle used to be first exercised by the release PR (conexus 8.3.0: `engine-service-v0.1.194` bundles pgvector 0.8.7, 147 more DDL statements than 0.8.2, and `tests/ddl_ceiling.toml` `migration_ddl_per_worker` read 2578 against 2431 on the release PR). `.github/workflows/engine-bundle-canary.yml` runs once per engine tag, never per push or PR. `engine-service-release.yml` calls it from a `bundle-canary` job that `needs: promote-release` (a reusable-workflow call, resolved at the tag's commit, so it runs before main has the file; a publish made with `GITHUB_TOKEN` raises no `release` event, which is why the call is not left to the event). The same workflow also fires on `release: published` for `engine-service-v*` tags (a human publishing the draft by hand) and on `workflow_dispatch` with a `tag` input; each path has its own concurrency group, so a hand dispatch never cancels the call. It builds the gate jar on one develop sha, then `scripts/engine_bundle_canary.py` fetches two bundles through the substrate's verified install seam, the pinned tag's and the new tag's, and runs `tests/test_scenario_journeys.py` (the scoped `test_store_put_is_searchable_and_catalogued` and the other journeys) on each with `NEXUS_PG_BIN` set to it. The job summary lists each bundle's PostgreSQL and pgvector version and its `ddl: migration=N`. **Where to read it:** a call is a job inside the tag's engine release run, not a run of `engine-bundle-canary.yml`: find the run (`gh run list --workflow=engine-service-release.yml --branch=<tag> --limit 1`), then `gh run view <id> --json jobs` for the `bundle-canary` job, its summary and annotations (or the tag sha's check-runs). `gh run list --workflow=engine-bundle-canary.yml` lists only hand dispatches and hand-published releases. **Red means develop or the bundle is broken, not that the tag moved the count:** the job fails when the pinned bundle's count is above `tests/ddl_ceiling.toml` (develop drifted past its own ceiling: fix the ceiling on develop; `scripts/ddl_ratchet.py` fails only above too, so a pinned count below the ceiling is a warning naming the number to lower it to), when an engine-backed test is red on a bundle, or when nothing was measured (exit codes 1, 3, 2; 4 is a bundle that would not provision). **A tag whose count differs from the pinned one is a warning, not a red:** a `::warning::` and a summary line say "engine-service-vX's bundle changes migration DDL from P to T: the client release that pins it raises/lowers `migration_ddl_per_worker` to T with this reason". The pin cannot move early (`tests/test_engine_version.py::test_pinned_floor_is_current`), so the client release that bumps it carries that change, with the reason in its commit; do not change the engine tag. The canary runs after the release is promoted, so it never gates the publish: a red job turns the engine release run red after the fact, and the publish stands. Dispatch it by hand (Actions, Engine Bundle Canary, Run workflow, with the tag) only for a tag whose `bundle-canary` job did not run, never while that job is running.

Cloud users get whatever conexus deployed; **local-mode installs get ONLY what this constant names**, so a tag that is cut, gated, and never pinned reaches nobody. That single constant also drives `PINNED_SERVICE_TAG` (`src/nexus/daemon/binary_install.py` DERIVES it, not an independent literal), so there is nothing separate to bump there. **Sequencing — the PAIRED-RELEASE choreography (Hal directive 2026-08-02, supersedes the old "bump only after deploy, floor lags a release" reading):** when a client release carries client halves of engine features, the engine tag is cut FIRST (tag-cut is never blocked — see the "A tag gates DELIVERY, not work" bullet above), the client release gates its battery against that engine and bumps the floor to it IN the same release, and the deploy fires at client-tag push, in PARALLEL with the ~90s PyPI publish workflow — any client-release precondition is satisfied the instant the client tag exists, and the engine is live before any user can install the client that requires it. Zero refusal window (GH #1402: a floor-bumped client published with NO deploy armed makes cloud clients refuse the managed service as below-identity — the deploy must fire at tag push, not "eventually") and zero inert-window (the 7.1.0/v0.1.62 inversion: floor lagging a release ships a client whose pinned engine lacks the engine halves of its own features). `scripts/check_engine_release_floor.py` fails the release in BOTH directions. **nexus-1emxn refinement (measured twice, 2026-08-29: "fires at tag push" was a human relay, PyPI published in ~90s, and the window sat open 48+ min):** (a) when every wire-ledger `## Unshipped` entry carries the `[additive]` direction-safety token (old client + new engine safe), deploy the engine BEFORE the client tag push — `check_engine_release_floor.py --client-precondition` accepts an all-`[additive]` ledger, so the client tag can never open a window at all; (b) when any entry is not additive, the redeploy must be staged with conexus (image built, a named trigger) and that CONFIRMED back before the client tag pushes — a human confirmation, nothing mechanical checks it; (c) on a cloud-mode box, the post-release local reinstall waits for the bare floor verify to pass against the live cloud (exit 1 = the cloud is still behind = new spawns would refuse the service — wait, don't reinstall).

### Data moves: a changeset changes schema, a move moves rows (RDR-246)

The rule, from [RDR-246](../rdr/rdr-246-data-moves-are-background-jobs.md): **a changeset may change schema. It may not move rows whose count grows with user data.** A changeset runs inside the boot-time schema walk, and a walk that rewrites a table of millions of rows holds the engine down for as long as the rewrite takes. A *data move* is the replacement: a dml_utils run that the engine starts after it serves, as a background job. (dml_utils is the library of SQL routines the engine vendors under `service/src/main/resources/db/vendor`; it runs one DML template over a table in chunks, each chunk committing on its own, through pg_background worker processes.) A move that is stopped resumes at its first unfinished chunk.

Terms used below. The *registry* is the table `nexus.data_moves`, one row per move. A move is *open* while its `completed_at` and `failed_at` are NULL and no other row names it in `supersedes`. The *move worker* is `DataMoveWorker`, the engine thread that works open moves, oldest `registered_at` first. A move's *driving table* is the table whose primary key dml_utils cuts into chunks. A move's *label* is its primary key; the worker names each dml_utils run after it (`<label>/<tenant>`, `<label>/<tenant>/<leaf>` for a per-leaf run on a table partitioned one tenant per leaf, or `<label>` for a table with no tenant scope), so a label never contains `/`. A *CALL* is the one SQL statement (`dml_utils.run_migration_chunks_committing`) that the worker sends on a connection of its own to run one dml_utils run; it can last hours. A *pass* is one go at a move: the preflight, one CALL per run, then the verification and `on_complete`. The *preflight* is the checks the worker makes at the start of a pass, before any CALL: the library install and its committing entry point, the pass's grant of the driving table to `dml_utils_owner`, that the serving role holds no privilege on the registry, that the driving table exists, that the admin session reads every tenant's rows, and a free background-worker slot. An error is *recorded* when dml_utils wrote it to `migration_error` for a chunk, and *raised* when a step of the pass (the CALL, a preflight check, the verification) raised it with nothing recorded. A recorded error comes from a chunk's own statement, so apart from the host's transient states (a lock, serialization, deadlock, cancel, resource or shutdown error) it is the template's fault; a raised one may also be the environment's. `what` is the text field of a `boot_work` entry, and a *fixed class* is a fixed sentence the engine writes for a kind of failure ("a CALL raised an error") in place of the original text.

#### Registering a move

A changeset registers a move with one INSERT into `nexus.data_moves`, whatever the size of the data. The gate reads that INSERT in one form only: the columns named, then `VALUES` with the same number of values as columns and a literal for each of `label`, `driving_table` and `verification` (a list of tuples registers several moves). A `supersedes` that is not a literal names no superseded move. A registering INSERT in any other form is a finding (`r1.registering-unreadable`). The columns, with the checks that keep them coherent, are in `datamoves-001-registry.xml`:

- `template`: the DML to run per chunk. It must contain `<driving_table>` and `<chunking_clause>` exactly once each; otherwise dml_utils refuses to create the run (SQLSTATE 22023; the vendored `service/src/main/resources/db/vendor/dml_utils/changes/functions/README.md` states the rule and `render_prepared_chunk_sql.sql` enforces it). The worker renders `<driving_table>` as the driving table with the alias `t`, so the template names the table's columns as `t.<column>`, and `<chunking_clause>` as the predicate on the chunk's key range, which goes in the WHERE. A single quote in the template is doubled in the INSERT, since the template is a string value. It leaves a row already in the new shape unchanged, and it rewrites a row from that row's current values, never from values read earlier, because live writers update rows while the move runs.
- `driving_schema`, `driving_table`, `chunk_size` (1 to 1,000,000), `sleep_ms` (0 to 60,000; the pause after each chunk, which throttles the move against serving traffic), `statement_timeout_ms` (positive; one budget for the completion transaction's re-check, shared by its table-wide run and every listed tenant's warm run, and, when the re-check ends, a fresh `statement_timeout_ms` for `on_complete`, whose `lock_timeout` is half of it, at most 5 s. Size it for the sum of the tenants' warm runs: a move whose re-check does not fit times out (57014) as a transient `RECHECK` failure and loops on the retry backoff, and every retry repeats the first pass) and `verify_statement_timeout_ms` (positive, default 60,000, `datamoves-002`; the bound on the first, READ ONLY verification pass, which is also the warm-up and takes ACCESS SHARE only; a registering INSERT that names no such column takes the default).
- `verification`, NOT NULL: a SELECT that returns the rows still in the old shape. It runs when every run is complete, and the move completes only if it returns no rows. The rules for writing it are in § Writing the verification query.
- `on_complete`, NULL or the SQL that finishes the new shape once the move is verified (see § Finishing a move).
- `changeset_id` and, for a fix, `supersedes` (see § Fixing a move). A move registered at run time takes its `changeset_id` by one of two rules. A move that another move's `on_complete` registers (RDR-229 P2.10's two satellites, the chunks swap's children) takes the bare id of the changeset whose text holds the registering INSERT, a literal in that `on_complete`: the child shares its parent's `changeset_id` when one changeset ships both. A move the engine itself registers with no `on_complete` text to name a changeset (a pass registering a swap's moves, a completion check registering a drop) takes `engine:<pass>:<engine version>`. The satellite INSERT in an `on_complete` carries no `ON CONFLICT`: a label already in the registry fails the parent's `on_complete` loudly (`completed_at` rolls back with it) rather than leaving another definition under the name.

A changeset ahead of the registering one creates the new shape (an empty table, a nullable column). From the release that registers a move, every writer produces only the new shape, so the move only has to cover rows that existed before that release. Code that reads the moved data copes with a move in progress: it reads both shapes, or the feature stays off until the move's `completed_at` is set. A move whose readers cannot cope is redesigned, not run at boot. Each move's RDR or bead states which of the two applies.

Progress shows in `/v1/status` under `boot_work` (the list of long-running boot-time jobs, nexus-f3yqd.3) and in `nx doctor`: one entry per open move and per failed move that no row supersedes, id `data-move:<label>`, with done and total in chunks and `safe_to_stop: true` (a stop resumes from the last committed batch). The state is the text of `what` up to its first colon. Every statement below runs as `nexus_admin`.

The registry is read and written only as `nexus_admin`; nothing on the serving pool may read it, so a separate reporter samples the registry and the active dml_utils runs on its own admin session every five seconds and adds the worker's in-memory state.

#### A worked registration, and where the changesets go

A complete registering changeset, with a hypothetical table `nexus.widgets` that has a `tenant_id` column and a new nullable `stamp` column. It is `service/src/test/resources/datamove/owner-read-policy/register.xml` with its `${label}`, `${driving_schema}` and `${driving_table}` parameters written out as literals:

```xml
<changeSet id="widgets-stamp-register-1" author="your-bead-id">
    <comment>Register the data move widgets-stamp-1 over nexus.widgets (RDR-246): one INSERT into nexus.data_moves</comment>
    <sql splitStatements="false" stripComments="false"><![CDATA[
INSERT INTO nexus.data_moves (label, template, driving_schema, driving_table, chunk_size, sleep_ms,
                              statement_timeout_ms, verification, on_complete, changeset_id)
VALUES ('widgets-stamp-1',
        'UPDATE <driving_table> SET stamp = lower(t.name) WHERE t.stamp IS NULL AND <chunking_clause>',
        'nexus', 'widgets', 500, 20, 60000,
        'SELECT 1 FROM nexus.widgets t WHERE t.stamp IS NULL AND (t.tenant_id = $1 OR $1 IS NULL)',
        NULL, 'widgets-stamp-register-1');
    ]]></sql>
    <rollback>
        <sql>DELETE FROM nexus.data_moves WHERE label = 'widgets-stamp-1'</sql>
    </rollback>
</changeSet>
```

The template runs once per chunk with `<driving_table>` and `<chunking_clause>` filled in, and leaves a row that already has a `stamp` unchanged. The verification names the real table and gives its own alias; the worker rewrites only `$1` in it and sends the rest as written, so `<driving_table>` is not substituted there (the fixture's verification writes `FROM <driving_table>`, which is only safe because the tests that use the fixture run the worker with `MoveFinisher.RUNS_ONLY`, which ends a pass where the runs end). Where the changeset that creates the new shape goes is below.

Placement, in order:

1. The registering changeset goes in a new include file in `service/src/main/resources/db/changelog/db.changelog-master.xml`, after `taxonomy-023-coverage-counts-set-based.xml` (the frozen list's freeze point) and before the two runAlways grants includes, `grants-nexus-svc.xml` and `grants-nexus-diag.xml`, which the master's comment above them says go "LAST".
2. The registering changeset holds only the INSERT. The new shape it needs, a table or a nullable column, is a separate changeset ahead of it, in the same include or an earlier one.
3. The owner-read policy changeset, when the driving table needs one (see the next section), is alone in the next include after it.
4. The fixture files take `${label}`, `${driving_schema}` and `${driving_table}` as parameters so one file serves the test tables. Replace each with a literal; the gate reads literals.
5. `changeset_id` holds the bare changeset id (`owner-read-register-1` in the fixture, `widgets-stamp-register-1` above), not the `file::id::author` key of the frozen list.

The gate does not police a changeset added to an include that sits before the freeze point: it refuses only a frozen-list entry there, and takes no notice of a new changeset in an old include. Review does. A registering INSERT is not a finding, so placing it after the freeze point is a convention that keeps the moves together in master order, not a gate rule.

#### Fixing a move

A move's template and parameters are never edited. dml_utils keeps a run's SQL from the moment the run is created and ignores a different template on a resumed call, so an edit to the registry row would change nothing the run does. The only fields changed by hand are an operator's pause and retry-counter columns. **A fix is a superseding move**: a new changeset whose one INSERT registers a new move under a new label and names the old label in `supersedes`. `supersedes` is a foreign key and unique, so a move is replaced at most once, and the INSERT closes the old move without an UPDATE, because a row that something supersedes is no longer open. The new move runs from its first chunk. A move that failed stays `failed:` across restarts (`failed_at` is set) and is not retried; the superseding move is how it is fixed. What fails a move and what only blocks it is next.

**Blocked and failed.** Every failure is decided in one place (`DataMoveFailureHandler`, with `DataMoveFailureClassifier`) and is either transient or permanent. A *transient* failure leaves the move open and `blocked:`. It adds one to `transient_retries`, stamps `last_transient_at` and `last_transient`, and the worker waits `min(30 s * 2^(n-1), 15 min)` after the nth consecutive one: the wait doubles from 30 s and reaches the 15 minute cap at the 6th (`MoveRetryPolicy.backoff`). The worker never stops retrying. From the 20th consecutive transient failure the reason carries `; needs an operator`, and the status entry follows it with the blocked-since stamp. A pass that ends cleanly clears the count, and an operator clears it by hand to run the next pass at once (the three retry columns, as `nexus_admin`). A *permanent* failure sets `failed_at` and `failure`, and the move is not retried by this process or a later boot. If the registry cannot be written, the move is reported `blocked:`, never `failed:`, because an unrecorded failure would be retried at the next boot.

The split follows the SQLSTATE, by two lists in `DataMoveFailureClassifier`: `transientRecorded` for a chunk error dml_utils recorded, and `transientRaised` for an error the CALL raised with nothing recorded, which is the first list plus class 08, 42501 and 42883. Any other or missing SQLSTATE is permanent, so nothing loops. The exception to know: a recorded 42501, 42883 or class 08 error is permanent, because a chunk records its own statement's error, which makes it the template's fault and never the coordinator's connection. By stage:

- A preflight miss the worker names (no install, a missing role, no free worker slot, an admin session that cannot read every tenant's rows) and a connection that cannot be opened are transient. The preflight reports a missing driving schema or table as 42P01, which is permanent, and a preflight check that itself raised follows the raised list.
- A CALL that returned with its run incomplete is transient, unless a chunk recorded a non-transient error in this pass. A run recorded as cancelled is permanent.
- A verification that found old-shape rows is permanent, and so is a text the worker refuses (the `VERIFICATION_REFUSED` stage). A verification that could not finish is transient when it timed out (57014), when it carries no error, or on the raised list, and otherwise permanent. The completion transaction's re-check (the `RECHECK` stage) is classified as `on_complete`'s is, and a re-check that carries no error (the session held a tenant) is transient too; a re-check that found rows is permanent (`VERIFICATION_NONEMPTY`).
- `on_complete` is transient on its statement timeout (57014), its lock timeout (55P03), a deadlock (40P01), a serialization failure (40001), a lost connection (class 08), a shutdown (57P01 to 57P03) and a busy host (class 53); the transaction rolls back whole, so `completed_at` stays unset. Any other error, and a failure that carries no error, is permanent.

#### Finishing a move

A step that finishes a move (VALIDATE CONSTRAINT on a check added NOT VALID, dropping the old column, swapping a table in) takes one of two forms.

1. **`on_complete`**, when the move's own release knows the step. The worker runs `on_complete` and sets `completed_at` in one transaction, so a stop between them leaves neither. The UPDATE runs first, and matches only a move that is still open, not paused and not superseded, so a pause set after the last read stops the finish. It holds DDL that PostgreSQL runs inside a transaction (VALIDATE CONSTRAINT, DROP COLUMN, renames), never CREATE INDEX CONCURRENTLY or any statement that cannot run there. This is the only form on the chunk-family tables: `nexus.chunks`, its leaves, and every table with a foreign key into it (`catalog_document_chunks`, `topic_assignments`, `chunk_orphaned_at`). A later finishing step on one of them is a new move whose `on_complete` does it. Every `on_complete` runs under `SET LOCAL lock_timeout`, set with the statement bound in the completion transaction: half of `statement_timeout_ms`, at most 5 s and at least 1 ms (`VerifyingFinisher.lockTimeoutMs`). A lock it cannot get fails fast (SQLSTATE 55P03) as a retried `blocked:` state, so readers never queue behind it. On a chunk-family table the worker also ends the per-collection index builders first, as a best effort and only once that UPDATE has matched, so a pause or a superseding move never ends a build for nothing, because a DROP or ALTER there takes ACCESS EXCLUSIVE and would otherwise wait behind a `CREATE INDEX CONCURRENTLY`; ending a build discards work that can take tens of minutes, so it is done only for a chunk-family `on_complete`, and the `lock_timeout` turns a builder that starts again before the lock is taken into a retry.
2. **A later changeset with the completion precondition**, on any other table: a Liquibase precondition `onFail="CONTINUE"` whose `sqlCheck` reads `nexus.data_moves.completed_at` for that move's label. The changeset is skipped, and retried on each boot, until the move completes. On a fresh install it therefore applies at the first boot after the move completes, not the first boot. If the move it waits for is superseded, the changeset that registers the replacement also re-issues the waiting step under a new id with a precondition on the new label.

A changeset with `onFail="CONTINUE"` on a chunk-family table is refused by `tests/test_changelog_continue_precondition_chunks_lint.py`, because the migrator does not count a self-retrying changeset as schema work, and a DROP or ALTER there takes ACCESS EXCLUSIVE and would queue behind an index build the migrator was told to leave running. A VALIDATE CONSTRAINT never goes in a later changeset on a table the gate's second rule lists.

The lock timeout is on every `on_complete`.

#### Writing the verification query

The verification is text in the registry, run by the worker after the runs complete (`VerifyingFinisher`): once per tenant on a connection that carries that tenant's `nexus.tenant` setting, then once table-wide on a separate admin connection. Each run is a READ ONLY transaction under `verify_statement_timeout_ms`, and each must return no rows. The completion transaction then runs the verification again, warm, before it writes `completed_at`: table-wide with no tenant and once per listed tenant under `SET LOCAL nexus.tenant`, all sharing one `statement_timeout_ms` (the tenant list is re-read from `nexus.service_tokens` and, on a table partitioned one tenant per leaf, the leaves, so a tenant added since the first pass is run; a tenant whose first rows appear after the probe in a probe-listed table, with no token and no leaf, is not). This closes the window between the two transactions, which can be hours; it is a point-in-time check, and a write committed after the re-check's snapshot can still land before `on_complete`. A verification that reads a row-security-scoped table sees nothing without a tenant, and only the tenant's run is the check. The verification must read what `on_complete` reads (the table, and the index or foreign-key side the step will scan) for the first pass to warm it for `on_complete`; a verification that reads less warms less. A non-empty re-check is `VERIFICATION_NONEMPTY` and rolls the completion back (permanent, as in the first pass). A re-check that times out, waits out `lock_timeout` behind a lock holder (55P03) or meets a deadlock or serialization failure is a `RECHECK` failure, classified as `on_complete`'s are: retried with backoff, never failed for good. It selects `1` per old-shape row (`SELECT 1 FROM ... WHERE <old shape>`); it never reads `nexus.tenant`, so the per-tenant and table-wide runs differ only in the bound value. It names the real table, as the gate's scenarios do, not `<driving_table>`: the worker rewrites only `$1`. Every run is made, even after one finds rows, so a failure names each tenant that still holds old-shape rows; a count above 10,000 shows as `10000+`. A table that is not tenant-scoped (no `tenant_id` column, or row-level security off on it) has no tenant list and so no per-tenant runs, only the table-wide one with `$1` bound to NULL; its query cannot filter on a tenant column, and the gate and the worker both accept a verification with no `$1`. The rules that the gate and the worker enforce:

- **One parameter, `$1`, the tenant.** The worker binds the tenant id for a per-tenant run and NULL for the table-wide run, so the query filters on `tenant_id = $1 OR $1 IS NULL`. A `$1` is standalone when no word character or `$` stands on either side of it. The worker rewrites every standalone `$1` to `CAST(? AS text)` and binds the tenant to each.
- **No `?` anywhere.** The JDBC driver reads a `?` as a bind parameter and cannot be told that one inside a literal is not. A `$` followed by a digit that is not a standalone `$1` (`$2`, `$10`, `my$1`, `$1x`, `$$1`) is refused for the same reason.
- **No `$1` inside a comment, string literal, dollar-quoted body or quoted name.** The worker's rewrite sees these by text, while the driver skips them when it counts parameters, so the two counts differ and the bind goes out of range. The worker refuses a text whose standalone `$1` count differs from the driver's parameter count.
- **Not empty.** The column is NOT NULL, but an empty string is accepted by it and cannot be run.

A refused text is a permanent failure at the `VERIFICATION_REFUSED` stage: the move registers, then is `failed:` once the runs finish, and the rule it broke is in the engine log and in `failure`. The gate catches the cases it can see at registration (see § The changeset gate), and those checks are on develop. The ways through for text that needs a `?`:

- the jsonb operators `?`, `?|` and `?&` are `jsonb_exists(j, key)`, `jsonb_exists_any(j, keys)` and `jsonb_exists_all(j, keys)`;
- a `?` in a LIKE or regex pattern is written `chr(63)`, or as the escape `E'\x3f'` inside the verification text. If the INSERT's own value for the column is an E-string, the gate decodes it first and sees a real `?`, so put the escape inside the text and not in the INSERT's quoting.

The worker's side of these rules is the class `MoveSql`, the one site that runs registry text as SQL, with `countRows` and `runOnComplete` its only calls. The gate's checks of the same text (`r1.verification-empty`, `r1.verification-placeholder`) refuse a registering INSERT that the worker would refuse, so the rules are enforced at registration as well as when the move runs.

#### A non-chunks driving table: the owner-read policy changeset

The engine's tables use FORCE row-level security keyed on `nexus.tenant`, and the roles that serve and migrate are subject to it. A move over a tenant-scoped table therefore runs once per tenant. To verify and finish it, the migrating role (`nexus_admin`) must also be able to read every tenant's rows. On `nexus.chunks` vectors-029 already grants that (`chunks_gate_probe_owner_read`). Any other driving table has only its tenant policy, so the move adds a second changeset, after the registering one, that creates a permissive policy `<table>_owner_read` `FOR SELECT TO CURRENT_USER USING (true)`.

A tenant-scoped table that the move's template or verification only joins (a support table, not the driving table) needs the same policy, or the table-wide verification, which runs as the migrating role with no `nexus.tenant`, joins an empty table and reports a table with work left as clean. It also needs an entry in `DrivingTableIsolationCheck.SUPPORT_TABLES`, keyed by the move's label prefix, so the boot check asks the isolation question of it too. Nothing finds a missing entry but review. RDR-229 P2.10's `rdr229-residue-*` moves are the first case: they join `nexus.catalog_collections` for the content type, and `catalog_collections_owner_read` comes from `vectors-065`, the policy RDR-229 D2's move needed first; a second move that needs an existing support policy reuses it rather than adding its own copy, because each copy's rollback drops the one policy both rely on.

The pattern to copy is `service/src/test/resources/datamove/owner-read-policy/register.xml` (the registering changeset: one INSERT, no guard, no policy) and `service/src/test/resources/datamove/owner-read-policy/policy.xml` (the policy changeset, alone in its file). The policy changeset carries vectors-029's guard word for word: a precondition `onFail="MARK_RAN"` that skips it when `nexus_svc`, or any other login role that row-level security binds, is or inherits the migrating role, and a post-condition in the same changeset that RAISEs unless the policy names exactly the migrating role. `DataMoveOwnerReadPatternShapeTest` pins the shape: the register file is one INSERT with no precondition and no policy; the policy file has one guarded changeset, SELECT only, `TO CURRENT_USER`, with the post-condition, DDL only and no mention of `nexus.data_moves`; and the guard's predicate equals vectors-029's. That test pins the fixture files, not your copy of them: an edit to the fixtures that drifts from the shape is red before a database is involved, but nothing reads the changesets you add to the changelog against the fixtures. Review compares a real policy changeset with the fixture and with vectors-029.

The policy is never in the registering changeset, because a Liquibase precondition skips its whole changeset, and the guard would then skip the new shape and the registering INSERT as well. In the single-role posture (the migrating role is `nexus_svc` itself) the guard skips only the policy: the move is registered, the service role never gains a cross-tenant read, the admin connection cannot see every row, and the move is reported `blocked:`. A skip is decided once; an install that later moves to two roles keeps the move blocked until a new changeset adds the policy.

A membership granted after the policy exists is caught at boot by `DrivingTableIsolationCheck`, which refuses boot when a permissive policy other than `tenant_isolation` on any driving table named in `nexus.data_moves` applies to the role serving traffic. It covers every driving table named in `nexus.data_moves`, in any state of the move, until a changeset drops the policy, except `nexus.chunks`, which `ChunksIsolationCheck` covers. A move over `nexus.taxonomy_centroids` still gets this check's question of its parent.

**The pattern does not apply to a table partitioned one tenant per leaf** (`nexus.chunks` and `nexus.taxonomy_centroids`). Each leaf there carries its own copy of the policies, which needs `nexus.partition_sync_access` and a walk of the leaves, and `ChunksIsolationCheck` walks those two trees. A non-chunks table partitioned another way gets its policy on the parent only, because the worker runs its move per tenant over the parent.

#### The changeset gate: `DataMoveChangesetGateTest`

`DataMoveChangesetGateTest` (`service/src/test/java/dev/nexus/service/db/`, with its rules in `DataMoveChangesetRules`) is an engine test that reads every changeset in `service/src/main/resources/db/changelog` in master order and starts no database. It reads the `<sql>` of each changeset with comments, string literals and dollar-quoted bodies masked, and refuses:

Run it through the leased wrapper, as any engine test (if another build holds the lease, the in-grant run exits 75 at once; run it again): `scripts/mvnw-leased.sh --lab-run lab-s -B test -Dtest=DataMoveChangesetGateTest` on a pool host (from the laptop, ssh to chas and run that form there; never through `lab-remote`, which wraps an engine build in `lab-run`). It prints one line beginning `data-move changeset gate:`, with `examined` (the changesets it read) and `declared` (the `<changeSet>` elements the files hold), and fails unless the two are equal.

1. **Row DML.** UPDATE, DELETE, MERGE, INSERT ... SELECT, ALTER COLUMN TYPE, a generated column added, CREATE TABLE AS, a data-modifying WITH and SELECT INTO. One INSERT into `nexus.data_moves` passes: its template, verification and `on_complete` are string values.
2. **Boot scans on a table that grows.** ADD CONSTRAINT without NOT VALID, VALIDATE CONSTRAINT and SET NOT NULL on `nexus.chunks` and its per-model tables (`chunks_*`), `catalog_document_chunks`, `catalog_documents`, `catalog_links` and `topic_assignments`. ADD CONSTRAINT ... NOT VALID passes.
3. **A destructive statement on a registered move's table without waiting.** DROP COLUMN, DROP TABLE or a rename of a table or column, on a table a registered move drives, needs a precondition `onFail="CONTINUE"` that reads `nexus.data_moves.completed_at` for one of that table's moves. A move counts as driving the table of every move it supersedes, so the old label and the new one both satisfy it. A move counts as registered when an INSERT for it sits in the same or an earlier changeset. The registering changeset is held to this rule too. The test matches by table name, so it cannot tell whether the label in the precondition is the right one; the review checks that.

A changeset that Liquibase would run through a native change type (`update`, `modifyDataType`, `customChange` and the like) is a finding too (`opaque.native-change`), because the rules cannot read it; write the change as `<sql>`. A `sqlFile` child passes unread, as do a function body and a DO block's dynamic SQL, and so does a non-concurrent CREATE INDEX. The gate is a static check of changelog text. nexus-f3yqd.1's write gate, which measures the WAL an upgrade boot writes, is the backstop for DML the static check cannot see.

**The exemption line.** A line `data-move-exempt: <table>: <reason>` in the changeset's `<comment>` names a table the changeset touches whose size does not grow with user data. It lifts only the findings on that table: a finding on any other table stays, and so does one whose statement also names a table that grows or that a registered move drives, even in a subquery or a FROM. A changeset that touches two small tables carries one line for each. A line is itself a finding, and lifts nothing, when it names a table that grows, a table a registered move drives, or a table the changeset's statements never name. The line is checked for form, not for truth: that the table does not grow is the review's.

**The frozen list.** `service/src/test/resources/data-move-gate/frozen-changesets.txt` holds the shipped changesets the rules find, as `file::id::author`, derived when the gate landed. They ran in earlier releases and are exempt. The test fails on an entry that names no changeset, on an entry whose changeset no rule finds any more (the list is the offenders and no more), and on an entry in the `freeze-point` include (`taxonomy-023-coverage-counts-set-based.xml`) or after it, so a changeset in a newer include cannot be frozen. The list only shrinks and a new changeset is never added to it. The test does not refuse a new changeset added to an include that sits before the freeze point; review does.

The gate must read as many changesets as the files declare, the frozen list must be non-empty, and each of nine kinds of finding must appear at least once in the shipped tree (`r1.update`, `r1.delete`, `r1.insert-select`, `r1.alter-type`, `r1.generated`, `r1.ctas`, `r2.add-constraint`, `r2.validate` and `r2.set-not-null`); a rule that stopped matching would otherwise freeze nothing and pass. Rule 3 sees one registered move in the shipped tree, `rdr229-residue-catalog-documents` (`catalog-049-2`, RDR-229 P2.10; its `on_complete` registers two satellite moves at run time, with the same `changeset_id`), and no destructive statement waits on it yet, so its cases are the fixture scenarios under `service/src/test/resources/data-move-gate/scenarios`.

The gate also reads a registering INSERT's `verification`, in the form § Registering a move describes. An empty verification is a finding (`r1.verification-empty`). A verification with a `?`, a `$`-digit other than a standalone `$1`, or a standalone `$1` in a comment, string literal, dollar quote or quoted name is a finding (`r1.verification-placeholder`); the last case is found by comparing the count of standalone `$1` in the raw text with the count left after the masking. The gate checks only this boundary. It does not parse the verification as SQL.

#### When a change needs a boot-time rewrite

Do not add DML to a changeset. Register a move (one INSERT), add the owner-read policy changeset if the driving table needs it, write the readers to cope with a move in progress, and write the finishing step as `on_complete` or a later changeset with the completion precondition. If a changeset touches only a table that does not grow, give it the exemption line. The frozen list is closed.
