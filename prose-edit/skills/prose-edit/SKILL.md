# Prose edit

Arguments: $ARGUMENTS

Run every command from the directory this session started in. Never run `cd`, and put nothing in front of a command and nothing after it: no `;`, `&&`, `||`, `|` or `echo` joined to it. The exit code comes back with the result, and a command with anything joined to it no longer matches the permission rule, so it is refused. Write the command prefix of the table below exactly as it is shown: unquoted, with no `./` and no `cd` before it. The skill's permission rule matches that text, and a quoted or `./`-prefixed script path, or a `cd '<dir>' &&` in front, does not match it. Pass each argument as its own argv token. Never build a shell string from the arguments. Only the arguments after the prefix go in single quotes (a single quote inside one is written `'\''`): a path with a space or a `;` is author input, and so is every token. In a command below, the names of the first column (BRIEF, MEMORY, REVIEW) stand for the prefix text of their row, typed as it is shown, and a `<placeholder>` stands for one argument in single quotes.

| Name | Command prefix |
| --- | --- |
| BRIEF | `python3 ${CLAUDE_PLUGIN_ROOT}/skills/prose-edit/scripts/brief.py` |
| MEMORY | `python3 ${CLAUDE_PLUGIN_ROOT}/skills/prose-edit/scripts/memory.py` |
| REVIEW | `python3 ${CLAUDE_PLUGIN_ROOT}/skills/prose-edit/scripts/review.py` |

A document in another checkout (a git worktree, say) is named by its absolute path: the scripts take the repository from the path, so the edit lands in that checkout.

## Invocation

| Form | Meaning |
| --- | --- |
| `<path>[:<start>-<end>] [--genre G] [--budget N]` | Edit run. Budget defaults to 10. A range limits proposals to those lines. |
| `<path>[:<start>-<end>] --mode cut-only --voice-card F --word-budget N [--genre G] [--budget N]` | Cut-only run. Not run here: the site-page review gate runs it through the `conexus-prose-edit:prose-cut` skill, which a model can invoke and this command cannot. |
| `- --genre G [--budget N]` | Stdin run. The flags are the first line. The text is everything after the first newline. Nothing is applied. |
| `rejections <path> [--remove N]` | List a document's stored rejections, or remove number N. |
| `exemplar <genre> <path>:<start>-<end>` | Store that passage as an exemplar of the genre. |
| `setup` | Check and finish what runs in this repository need. Run it once per machine and once per repository. |
| `-- <path>` or `./<path>` | A file named `rejections`, `exemplar`, `setup`, `decide` or `count`. |

## Steps

1. Run `BRIEF parse <token>...` with the arguments as tokens. For a stdin run pass only `-` and the flags to `parse`. Never pass the text. On exit 1, show stderr to the author and stop, except a stdin run whose stderr says `needs --genre`: ask the genre question of step 4's `no genre` row with `reference-doc` suggested and no remember question (a stdin run has no folder), then run `parse` again with `--genre`. A null `genre` in the output only means the flag was not given for a path run. Never ask the author for a genre because of it: a null `genre` after `parse` is not a reason to ask, at this step or at any step before step 4. Go on to step 2: step 4 finds the genre from the path and reports when none exists, and only that report (`build` exits 1 with `no genre` in stderr) is a reason to ask. On any failure, show stderr and stop.
2. Branch on `mode` in the JSON.

   | mode | Do |
   | --- | --- |
   | `rejections` | Run `MEMORY <memory_argv...>`. Show the numbered rejections. Stop. |
   | `exemplar` | Run `MEMORY <memory_argv...>`. Show the stored passage and `duplicate`. Stop. |
   | `setup` | Follow the Setup run section below. Stop. |
   | `cut-only` | Not run here. Tell the author that cut-only runs through the `conexus-prose-edit:prose-cut` skill, which the site-page review gate calls, and stop. |
   | `decide`, `count` | The same: they belong to the `conexus-prose-edit:prose-cut` skill. Tell the author and stop. |
   | `edit` | Continue. |

   If a `MEMORY` command fails, show stderr and stop.
3. Fix the input.

   | `stdin` | Do |
   | --- | --- |
   | false | Use `target` from step 1. |
   | true | Take the text after the first newline of the message. If there is none, ask the author to paste it and end your turn: no WORK exists yet. Otherwise run `BRIEF tmpdir --ready`. It prints eight lines, `WORK=`, `INPUT=`, `REPLY=`, `FILTERED=`, `REASONS=`, `ANSWERS=`, `ENTRY=` and `CARD=`, each a full path. Write the text with the Write tool to the `INPUT=` path. Use `-` as the target and `--file '<input>'`. |

4. Build the brief. Both runs print a header, a blank line, and then the brief.

   | `stdin` | Run |
   | --- | --- |
   | false | `BRIEF build <target> --budget <budget> [--genre <genre>] --work`. The header is nine lines: `WORK=<dir>`, `DISPATCH=<prompt>`, `REPLY=<path>`, `FILTERED=<path>`, `REASONS=<path>` and `ANSWERS=<path>`, then `BLOCKS=<path>`, `PROPOSED=<path>` and `STATUSES=<path>` for the MarkupEditor review. The brief is everything after the blank line. |
   | true | `BRIEF build - --budget <budget> --genre <genre> --file '<input>'`. The header is one line, `DISPATCH=<prompt>`. The brief is everything after the blank line. |

   Either way `build` has written the brief to `brief.md` in the work directory, which ends with the line `Brief id: <id>`. The line-editor reads that file and echoes the id. The id is in the file and nowhere else: never put one in the prompt. The `DISPATCH=` line is the whole prompt for step 7, with the full path of that file already in it. The brief printed here is for you to check step 6.

   | Result | Do |
   | --- | --- |
   | exit 0 | Continue. |
   | exit 1, stderr contains `no genre` | Never choose a genre yourself. Run `BRIEF suggest-genre '<path>'` (the `path` from step 1, without a range). It prints `folder_key`, `suggested`, `ranked` and `descriptions`. Ask the author which genre applies with one `AskUserQuestion` call of two questions. End your turn with that question and do nothing else. Genre question (header `Genre`): the options are `suggested` with `(Recommended)` and the next two of `ranked`, each described by its line in `descriptions`; the question text names the document and the three genres left out, which "Other" accepts. Only an exact genre name is a genre: an "Other" answer that is not exactly one of `rdr`, `reference-doc`, `how-to`, `exploration-essay`, `changelog` or `commit-message` is never passed as `--genre` or stored; say so and ask the genre question again. Remember question (header `Remember`): "Remember this for `<folder_key>`?" with "Yes, remember (Recommended)" and "Just this run". Run this step again with `--genre` only after the author answers. For "Yes, remember", also store `<folder_key>=<genre>` as one `genre_map` entry the way step 4 of the Setup run does (a fresh work directory made as step 3 of the Steps list does, `MEMORY add-entry --level repo --from-stdin`, then `BRIEF rmtmp '<work>'`). |
   | any other non-zero exit | On any failure, show stderr and stop. |

5. WORK is the directory on the `WORK=` line of step 3 or 4. It holds the saved proposal and, for a path run, the app's replies until step 12 deletes it. Every path in the steps below comes from a header line of step 3 or 4 and is used exactly as printed: `<work>` is the `WORK=` path, `<input>` the `INPUT=` path, `<reply>` the `REPLY=` path, `<filtered>` the `FILTERED=` path, `<reasons>` the `REASONS=` path, `<answers>` the `ANSWERS=` path, `<blocks>` the `BLOCKS=` path, `<proposed>` the `PROPOSED=` path, `<statuses>` the `STATUSES=` path (the `ENTRY=` and `CARD=` paths are for step 13). Never type the word WORK as a path and never build a path yourself. Never create a directory named WORK, in the repository or anywhere else: Write makes a missing directory without a word, and the stray one shows in the author's `git status`. A path that is not on a header line is not yours to invent: stop and tell the author. The one exception is step 10's page files for a long document, which sit beside `<blocks>` as `<work>/blocks-2.json`, `<work>/blocks-3.json` and so on. On every stop after WORK exists and before step 12, delete WORK first with `BRIEF rmtmp '<work>'`. Step 11, the answer route and a retry in step 12, and a retry of step 9 or step 10 after exit 3 are the exceptions: the turn ends there with WORK in place. So does a path run's turn at the end of step 10, while the author decides in the app.
6. If the brief contains `No exemplars are stored`, tell the author the genre has no exemplars yet and the editor runs without them. If it contains `all come from this document`, tell the author the genre's only exemplars are from this document, so the editor runs without them.

   6b. Path run only, before the dispatch: open the document in the MarkupEditor app, so a missing or silent app is found before the editor is paid for. First, when the document's path ends in `.html` or `.htm`, delete WORK with `BRIEF rmtmp '<work>'`, tell the author that reviewing an html page in the MarkupEditor app is not supported yet, so prose-edit cannot edit this file, and stop. Find the MarkupEditor tools by what they do: the open_document, app_state, get_document, propose_edits, list_suggestions and undo tools (search for them with ToolSearch when they are not loaded). Take every one of them from the one MCP server that offers propose_edits. More than one MarkupEditor server can be registered, and a document loaded through one is never seen by an app_state poll through another, which reads as "the app is not listening". When two servers offer open_document or undo, take that server's. If the open_document or propose_edits tool is missing, delete WORK with `BRIEF rmtmp '<work>'`, tell the author that prose-edit reviews a path run in the MarkupEditor app and needs a build with suggestions, say to start the app, turn on Assistants in its settings with read-write access, and allow this program, and stop. Call the open_document tool with the document's absolute path (the `path` of step 1, made absolute against the directory this session started in). It answers before the load finishes and while a save prompt may still be showing, so call the app_state tool, up to 30 times, until its `url` is that file (a `/private` prefix or a symbolic link is the same file) and its `modalWindow` is empty. Whatever stops the run from here to step 7, delete WORK first. If the call fails, or the app does not answer, tell the author what the app said (the app is not listening) and how to start it as above, and stop. When `modalWindow` is not empty, at any poll and also when the polls end, the app is asking about unsaved changes: tell the author that changes left by an earlier prose-edit review are to be discarded by choosing "Don't Save", never "Save" (Save rewrites the whole file, and the file on disk already holds every edit apply wrote), and that changes that are the author's own work are the author's to decide first; then stop. If the polls end with the state not reached and `modalWindow` empty, tell the author the last state app_state reported and offer to retry (a slow load of a large document can outlast 30 calls), and stop. If `hasChanges` is true there, the app holds unsaved changes to this very file, which are the author's own (a review ends by discarding its own): tell the author plainly that "Don't Save" discards them, so they are lost, and that the author may save them first, knowing the app rewrites the file's layout (paragraphs unwrapped, table rules and list markers rewritten), then let the author choose and run again; stop. Go on to step 7 only with the document showing, and then tell the author in one line, naming the server the tools came from (name that server to the author): do not type in the app until the review ends, and do not undo or save there.
7. Dispatch the `line-editor` agent with the Agent tool (`subagent_type` `conexus-prose-edit:line-editor`, `run_in_background` false). The prompt is the text after `DISPATCH=` on the header line of step 4, exactly as printed: copy it whole, change nothing, add nothing, and never type a path yourself. It already holds the full path of the brief and the instruction for the id; `<id>` stays as shown, because you do not know it. Do not paste the brief into the prompt. If the line-editor says it cannot read the brief, stop and show the author its error and tell the author to run `/prose-edit setup`: do not create a directory or a link in the repository and do not list the work directory. Wait for its reply. The harness may run the agent in the background even so: then the tool result only says the agent started, and the reply comes later as a message from the agent (its report). Wait for that message and do nothing else meanwhile.
8. Write the agent's whole reply, once, with the Write tool to the `REPLY=` path: the tool result, or the report text of the agent's message. Keep its indentation and its ```json fence as they are: the filter reads both. Never copy the reply with Bash (a heredoc or `echo`): a quote or the delimiter inside the reply breaks the copy.
9. Run `BRIEF filter <target> --budget <budget> --save '<filtered>' [--file '<input>'] < '<reply>'` (`<filtered>` is the `FILTERED=` path, `<reply>` the `REPLY=` path). Its output is the filtered proposal and the saved file holds the same text. A `warnings` entry about `brief_sha` means the editor's reply does not carry the id on the last line of `brief.md` in the work directory, so it did not read the file to its end. A `warnings` entry about `voice_card` means the editor's card is not the author-approved card the brief gave it. Show each to the author with the others in step 10. On exit 3 (a T2 outage; the `REPLY=` file holds the editor's work): show stderr, keep WORK, tell the author, end your turn, and run this step again when the author says to retry. On any failure, show stderr and stop.
10. Run `REVIEW render <target> --work '<work>' [--file '<input>'] [--genre <genre>]`. A stdin run passes `--file '<input>'` and the genre it was given. A path run passes `--genre` only when the author gave one. If `REVIEW render` fails with exit 3 (T2 became unavailable after the editor ran), keep WORK: show stderr, tell the author, end your turn, and run the same command again when the author says to retry. Any other failure: show stderr and stop. Show each filter `warnings` entry and each `unplaced` edit with its cause. Then show the filtered proposal:

    | Part | Show |
    | --- | --- |
    | `note` | The editor's note. |
    | `voice_card` | The voice card. |
    | `paragraphs` | Each as `[P<n>] <action>: <paragraphs>. <advice>`. |
    | `edits` | Each as `<n>. <old> -> <new> (<reason>)`. A path run shows only the edits the app will not show, below. |
    | `queries` | Each as `[Q<n>] <anchor>: <text>`. |
    | `dropped` | Each as `<n> <old> -> <new> (<cause>)`. The author cannot see these edits otherwise. |
    | `dropped_queries`, `dropped_paragraphs` | Each as `<n> <anchor or paragraphs> (<cause>)`. |

    A stdin run goes on to step 11. A path run has no edits to send when the proposal has no `edits`: go on to step 11. Otherwise the author decides in the MarkupEditor app, and the script does the translating. Do these in order.

    1. Call the MarkupEditor get_document tool with `from` 0 and no `limit`: `limit` is the most characters of block Markdown a reply holds (the default is 100000), not blocks, so a small one cuts the reply to a block or two. Call it again with `from` set to the reply's `next` until a reply has no `next`. Each reply is one page, and each page goes to its own file, as the reply came back: page 1 to the `BLOCKS=` path, page 2 to `<work>/blocks-2.json`, page 3 to `<work>/blocks-3.json`, and so on. When the harness saves a reply to a file instead of showing it (a long document's pages), that file is the page: copy it with `cp '<saved file>' '<blocks>'` for page 1 and `cp '<saved file>' '<work>/blocks-2.json'` for page 2 (a file copy, so no text is retyped; Claude Code asks the author to allow it). A reply that stays inline is a short one: Write it with the Write tool to the page's path. Never join pages into one file and never retype one. If a reply says `hasChanges` is true, tell the author the app holds unsaved changes ("Don't Save" clears them) and end your turn; read again when the author says to. If its `url` is not the document, call the open_document tool on the document again, poll app_state as in step 6b, and read again from `from` 0; when the app still shows another file, tell the author and end your turn.
    2. Run `REVIEW translate --work '<work>' --blocks-file '<blocks>'`, with one `--blocks-file` for each further page after it, in order (`--blocks-file '<work>/blocks-2.json'`, and so on). On exit 1 show stderr, which says what to read again, and end your turn (a page missing, out of order or given twice is one of the causes). It prints `edits`, `sent` and `refused`.
    3. When `sent` is 0 skip the next two items: every edit goes to the chat in step 11. Otherwise call the MarkupEditor propose_edits tool with the `edits` list from the `translate` output as its `edits` argument, copied whole and unchanged, then Write the tool's reply as it came back to the `PROPOSED=` path. If the call itself fails, show what the app said (a refusal about access means Assistants must be set to read-write access in the app's settings), keep WORK and end your turn: when the author says to retry, start again at the get_document call of item 1 (suggestions the app already shows for the first call stay there, and a second call sends them to the chat as overlaps).
    4. Run `REVIEW proposed --work '<work>' --from-file '<proposed>'`. On exit 1 show stderr and end your turn as in item 3. It prints `suggested` and `refused`.
    5. Show the edits that are not in the app: each `refused` entry of `translate` and of `proposed` as `<n>. <old> -> <new> (<reason>): <cause>, <detail>`, with `old`, `new` and `reason` from the filtered proposal.
    6. Tell the author to accept or reject each suggestion in the app and to say done in the chat. Say that a Reject in the app is stored for this document, so the editor does not propose that edit again, and that a suggestion left pending is held: the text stays and nothing is stored. Say that text typed in the app is not kept, so the author must not type in the document, must not use Undo (an undone Accept still counts as accepted) and must not save. Never call the MarkupEditor save or replace tools. End your turn.

11. If the filtered proposal has no `edits` (the editor proposed none, or the filter dropped every one), there is nothing to accept or reject: do not ask for numbers. Show the note, the paragraph proposals, the queries, each filter `warnings` entry and each `dropped` edit with its cause (so the author sees why no edit is left). If there is a query or a paragraph proposal, ask the author with `AskUserQuestion` whether to answer any of them with a change, in the query question below (with the voice card, as that question says), and end your turn; a change goes through the answer route of step 12. With no query, no paragraph proposal, or an answer that asks for no change, go to step 12 with `--accept none` and no other spec. Run its dry run and then, without asking, the same command without `--dry-run`: it changes no file, logs the session and deletes WORK. Otherwise ask the author with `AskUserQuestion`, one call at a time and in this order; a path run reads the app's decisions first, as the next paragraph says. Each call ends your work for the step until the author answers. Never choose the numbers yourself.

    Path run, before any question: when the author says done, call the MarkupEditor list_suggestions tool, Write its reply as it came back to the `STATUSES=` path, and run `REVIEW decisions --work '<work>' --from-file '<statuses>'`. When step 10 sent nothing, run it without `--from-file`. On exit 1 show stderr and do what it says. It changes nothing. It prints `accept`, `reject` and `hold`, the author's decisions in the app for this run's suggestions only, `warnings` (a suggestion the app no longer lists, whose edit is held), `leftover` (the edits the app never showed, each with its cause) and `undecided` (the edits nobody has decided, the author's answers to queries among them). Tell the author which edit numbers were accepted, rejected and left pending in the app, and show each `warnings` entry. A pending or stale suggestion is held, and an edit the app holds is decided only there: never offer it in a question. The questions below cover the `undecided` edits and the queries and paragraph proposals only. Then take exactly one of these two branches:
    - Branch A, `undecided` is empty. If the proposal has a query or a paragraph proposal, ask question 1 below (with the voice card, as question 1 says) and end your turn; on "No", or with no query and no paragraph proposal, ask nothing more here and go to step 12 with the `apply_args` just printed. Step 12 decides there whether the run is App-decided; on "Yes", take the answer route of step 12, and the added edits make it Branch B.
    - Branch B, `undecided` is not empty. Ask questions 1 (only with a query or a paragraph proposal, and only when it was not already asked in this step), 2 and 3 below in that order, each its own call, then run `REVIEW decisions --work '<work>' --from-file '<statuses>' --accept <spec> [--reject <spec>] [--hold <spec>]` again with the author's explicit numbers (each spec as one argv token; leave out the ones the author did not give), and use the `apply_args` it prints in step 12.

    First say, in two sentences at most, what the answers do. Accept puts the edit's new text in the document. Reject keeps the document's text as it is and stores the edit, so the editor does not propose it again for this document (a stdin run stores none). An edit the author neither accepts nor rejects is left undecided: the text stays as it is and nothing is stored for it. Offer only the edits that were placed (a path run: only the `undecided` ones): an edit listed as one that cannot be placed is not offered, and `reject the rest` leaves it alone.

    1. Queries and paragraph proposals, only when the proposal has any. One question, header `Answer`: "Answer a query or paragraph proposal with a change?" with "No (Recommended)" and "Yes". Put what it asks about in the question text: the text of the query when there is one, or the count and the first one (`[Q1] <anchor>: <text>`) when there are several; likewise a paragraph proposal. On a path run, first run step 13's sub-step 1 (`MEMORY voice-card <path>`); when it finds no card stored and the filtered proposal has a `voice_card`, put step 13's voice-card question (header `Voice card`) in the same call as this one, two questions in that call and nothing else. On "Yes", ask in plain words which one and what the change is, end your turn, and take the answer through the answer route of step 12; then return here for the edits, new ones included. A change the author makes this way is the author's own edit: it can be accepted or held, never rejected.
    2. Accept. Split the placed edits (a path run: the `undecided` ones), in order, into groups of 2 to 4 that are as even as possible: 2 to 4 edits are one group, 5 edits are 3 + 2, 6 are 3 + 3, 7 are 4 + 3, 9 are 3 + 3 + 3, 13 are 4 + 3 + 3 + 3. One multi-select question per group, up to four questions in one call (sixteen edits), with the text "Which edits do you accept?". The header names the group's own edit numbers, its first and its last, as in `Edits 3-6` (edit numbers have gaps when an edit was unplaced or dropped; the options name each edit exactly), at most 12 characters. Each option is one edit: label `Edit <n>`, description the reason first and then the words that change, `<reason>: <old words> -> <new words>`. Show the changed words with a few words of context, not the whole sentence cut off where it happens to end, and shorten the reason before you shorten the change. The author ticks none, some or all; a submission with nothing ticked means none accepted from that group. A single placed edit is one single-select question with the header `Edit <n>` and the options "Accept it" and "Leave it undecided". If more than 16 placed edits remain, offer the first 16 this way and ask for the rest in plain words as step 12's free-text route describes, naming the numbers left.
    3. The rest. When any edit offered in the accept questions went unticked, one question, header `Others`: "What about the edits you did not accept?" with "Leave undecided (Recommended)" (they are held: the text stays and nothing is stored), "Reject them all" (declines every edit you showed in the accept questions and did not get ticked; on a file run each is stored as a rejection for this document, on a stdin run none is stored; the text stays as it is) and "Choose which to reject". "Reject them all" covers only the editor's own edits the accept questions offered, never an overflow edit the author was not asked about and never an edit the author added through the answer route: those stay held. For "Choose which to reject", ask a follow-up multi-select call in groups made as the accept question makes them (header `Reject 3-6`; a single edit is one single-select question with the options "Reject it" and "Leave it undecided"), offering only the edits that were not accepted and are the editor's own; the ones the author does not tick are held. Rejection reasons are optional. Take one only from words the author wrote (the "Other" text of any of these questions, or the author's notes in conversation), never invent one, and write it through `REASONS=` as step 12 says. An "Other" answer that names explicit edit numbers is a spec of the free-text route; one that names none is asked again.

12. When the author answers a query (`Q<n>`) or a paragraph proposal (`P<n>`) with a change, never edit the document yourself. Write each change as exact text: `old` copied word for word from the document, `new` the text the author asked for, `answers` the `Q<n>` or `P<n>` it answers. Write them all as one JSON list `[{"answers": "Q4", "old": "...", "new": "..."}]` with the Write tool to the `ANSWERS=` path and run `REVIEW answer --work '<work>' --from-file '<answers>'`. It prints the new edit numbers, or on exit 1 says which `old` it cannot place (not found, ambiguous, protected): fix that entry (quote more of the text) and run it again; nothing is added until every entry places. Then run step 10's `REVIEW render` again (a path run: it only refreshes the session; do not read the app again), show each added edit as `<n>. <old> -> <new> (answers Q<n>)`, and go back to the edit questions of step 11, the added edits among them. An added edit is the author's own: it can be accepted or held, never rejected, and nothing is stored for it.

    A path run uses the `apply_args` that `REVIEW decisions` printed in step 11, as they are. The rest of this paragraph is how a stdin run builds them. Build the specs from the author's picks in step 11 as explicit numbers: `--accept` the numbers ticked in the accept questions, `--reject` the numbers of the rejected edits (every edit the accept questions offered and the author did not tick for "Reject them all", leaving out the author's own added edits, the ticked ones for "Choose which to reject"; none for "Leave undecided"), `--hold` every placed edit that is in neither, so nothing is rejected that the author did not pick. Write the reasons the author gave as step 11 says. When the author answers in words instead (the overflow past sixteen edits, or "Other" text that names numbers), turn the answer into an accept spec, a reject spec when the author rejects anything, and a hold spec when the author names edits to hold. A spec is explicit numbers and ranges (`1, 3-5`), `all` or `none`, in the author's own words. The reject spec may also be `rest`, only when the author says "reject the rest" or "reject everything else". Never reject an edit the author did not name: an edit the author leaves out is held, and so is every edit when the answer is "accept 1" or "none". For each reason the author gives, write all of them as one JSON object `{"<n>": "<the author's words>"}` (one key per rejected edit) with the Write tool to the `REASONS=` path, and pass `--reasons-file '<reasons>'`. Never put the author's words on the Bash line. If the answer names no explicit numbers (for example "all but 2", "the cuts", "looks good", "edit one", "no"), or `REVIEW` refuses it, ask the author again for explicit numbers and end your turn; never compute, infer or choose the set yourself.

    Run `REVIEW apply --work '<work>' --accept <spec> [--reject <spec>] [--hold <spec>] [--reasons-file '<reasons>'] --dry-run`, each spec as one argv token. `--accept` may be left out when the author accepts nothing: it defaults to `none`. On any other failure, delete WORK, show stderr, run the paragraph below that returns the app to the file when suggestions were sent, and stop. A successful apply has already deleted WORK (unless it reports `log_error`, below); do not delete it again. Show the author:

    A path run returns the app to the file at three points: after a successful apply, after "Cancel", and before every other stop that comes after suggestions were sent (any other failure, `expired`). Take the tools from the one MCP server that offers propose_edits, as in step 6b. On "Cancel" and at those stops the app still holds the accepted suggestions as unsaved changes, and the author must not save them: saving would rewrite the whole file. Undo them first, as the paragraph "Before the real apply" does (its url check, its bound, and only when suggestions were sent). After a successful apply the buffer is already clean, so there is nothing to undo. After any real apply, reopen the file whether or not suggestions were sent (`sent` 0 from `translate`, every edit refused by the app, or only chat decisions): apply wrote the file, and the app may still show the old text. First call the app_state tool. If its `url` is not the document (a `/private` prefix or a symbolic link is the same file, as in step 6b; the author switched the app to another file meanwhile), do not call the open_document tool, because the reopen would discard that file's unsaved state; tell the author the app shows another file and that the document is as apply left it. Otherwise call the open_document tool on the document again. If `hasChanges` did not clear, the app now asks about unsaved changes: tell the author to choose "Don't Save", never "Save". Call the app_state tool as in step 6b until its `url` is the document and `modalWindow` is empty, and tell the author the app shows the file as it is now. If the app_state call fails with the error "Resource temporarily unavailable" or the connection to the app closes, the app is showing its changed-on-disk dialog, which the app_state tool does not report: tell the author to choose "Reload from Disk", never "Keep My Changes" (the file on disk holds every applied edit), then call the app_state tool again when the author says it is done.

## Rules

| Rule |
| --- |
| Never change the document except through `REVIEW apply`. |
| Never write to T2 except through MEMORY and REVIEW. |
| Never call the MarkupEditor save or replace tools, and never type in the document there. The only MarkupEditor tools a run calls are open_document, app_state, get_document, propose_edits, list_suggestions and undo, all taken from the one MCP server that offers propose_edits. |
| Never pass the author's text in a shell string. |
| On any failure, show stderr and stop. |

## Asking the author

Every question to the author goes through the `AskUserQuestion` tool, so the author picks from a short list instead of writing prose. The steps say what to ask. A question ends the turn's work until the author answers: call the tool, then stop, and never answer for the author. The tool's limits:

| Limit | Rule |
| --- | --- |
| Questions per call | 1 to 4. |
| Options per question | 2 to 4. The tool adds an "Other" choice with free text to every question, so never list one yourself. |
| Option label | At most five words. The description beside it says what choosing it does. |
| Header | A short chip of at most 12 characters. |
| Recommended option | List it first and end its label with `(Recommended)`. |
| Several answers | `multiSelect: true`, for a question where the author may pick more than one. `preview` goes only on a single-select question. |

When `AskUserQuestion` is not available (a headless `claude -p` session) or the call fails, ask the same question in plain text: the question, then its options as a numbered list with each description, the recommended one first. End your turn and read the author's reply as the choice. Never pick for the author because the tool is missing.

What the author must read to choose (a stored passage, an entry, an edit) goes in the question text or an option's description, not only in your reply. The author's pick is the decision; text typed into "Other" is the author's own words.

## Setup run
