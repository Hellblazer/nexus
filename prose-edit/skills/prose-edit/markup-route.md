# MarkupEditor route for a path run

SKILL.md sends a path run here. Read this file in full once, at the start of the run: its sections are the path-run text of steps 6b, 10, 11, 12 and 13, and each is named after its step. BRIEF, MEMORY and REVIEW, `<work>` and the other header paths, and the step numbers are those of SKILL.md. A stdin run never reads this file.

## Step 6b

Path run only, before the dispatch: open the document in the MarkupEditor app, so a missing or silent app is found before the editor is paid for. First, when the document's path ends in `.html` or `.htm`, delete WORK with `BRIEF rmtmp '<work>'`, tell the author that reviewing an html page in the MarkupEditor app is not supported yet, so prose-edit cannot edit this file, and stop. Find the MarkupEditor tools by what they do: the open_document, get_document, propose_edits, list_suggestions and undo tools (search for them with ToolSearch when they are not loaded). Take every one of them from the one MCP server that offers propose_edits. More than one MarkupEditor server can be registered, and a document loaded through one is never seen by a get_document read through another, which reads as "the app is not listening". When two servers offer open_document or undo, take that server's. Do not call the app_state tool: the released app does not serve it (only a Debug build does). If the open_document or propose_edits tool is missing, delete WORK with `BRIEF rmtmp '<work>'`, tell the author that prose-edit reviews a path run in the MarkupEditor app and needs a build with suggestions, say to start the app, turn on Assistants in its settings with read-write access, and allow this program, and stop. Whatever stops the run from here to step 7, delete WORK first. Before opening, call the get_document tool with `limit` 1: the reply holds one block plus `url` and `hasChanges`, so it is a cheap read of the app's state. When it shows a document with `hasChanges` true, do not open the file: tell the author that the app holds unsaved changes and will ask about them when a file opens, that changes left by an earlier prose-edit review are discarded by choosing "Don't Save", never "Save" (Save rewrites the whole file, and the file on disk already holds every edit apply wrote), and that changes that are the author's own work are the author's to decide first: "Don't Save" loses them, and saving them in the app rewrites the file's layout (paragraphs unwrapped, table rules and list markers rewritten). Ask the author to settle those changes in the app and run again; stop. A read that fails here is no stop: the polls below find a silent app. Call the open_document tool with the document's absolute path (the `path` of step 1, made absolute against the directory this session started in). It answers before the load finishes, so call the get_document tool with `limit` 1, up to 30 times, until its `url` is that file (a `/private` prefix or a symbolic link is the same file). A call that ends with the error "read: Resource temporarily unavailable" was waiting on a dialog that has now been answered: the error comes back only once the dialog is gone, the app has closed its connection, and its document tools can drop out of the session, with only open_document left. Ask the author which answer the dialog got, and end your turn. After "Don't Save", search for the tools again with ToolSearch when they are not listed, call the open_document tool on the document again, and poll as above. After "Cancel", the author kept the app's changes: delete WORK and stop. After "Save", the app rewrote the whole file in its own layout: delete WORK, tell the author the file on disk changed, and to run again, and stop. Whichever it was, an unsaved-changes prompt is settled by choosing "Don't Save" only for changes an earlier prose-edit review left, never "Save": "Don't Save" loses changes that are the author's own work, so those are the author's to decide first. If a call fails in any other way, or does not answer, the app is either not listening or waiting on a dialog: tell the author both, say that a prompt about unsaved changes is settled by choosing "Don't Save" only for changes an earlier prose-edit review left, never "Save" ("Don't Save" loses changes that are the author's own work, so those are the author's to decide first), and say how to start the app as above, and stop. If the polls end with `url` still another file, tell the author the last `url` get_document reported and offer to retry (a slow load of a large document can outlast 30 calls), and stop. Go on to step 7 only with the document showing, and then tell the author in one line, naming the server the tools came from (name that server to the author): do not type in the app until the review ends, and do not undo or save there.

## Step 10 path run

A path run has no edits to send when the proposal has no `edits`: go on to step 11. Otherwise the author decides in the MarkupEditor app, and the script does the translating. Do these in order.

1. Call the MarkupEditor get_document tool with `from` 0 and no `limit`: `limit` is the most characters of block Markdown a reply holds (the default is 100000), not blocks, so a small one cuts the reply to a block or two. Call it again with `from` set to the reply's `next` until a reply has no `next`. Each reply is one page, and each page goes to its own file, as the reply came back: page 1 to the `BLOCKS=` path, page 2 to `<work>/blocks-2.json`, page 3 to `<work>/blocks-3.json`, and so on. When the harness saves a reply to a file instead of showing it (a long document's pages), that file is the page: copy it with `cp '<saved file>' '<blocks>'` for page 1 and `cp '<saved file>' '<work>/blocks-2.json'` for page 2 (a file copy, so no text is retyped; Claude Code asks the author to allow it). A reply that stays inline is a short one: Write it with the Write tool to the page's path. Never join pages into one file and never retype one. If a reply says `hasChanges` is true, tell the author the app holds unsaved changes ("Don't Save" clears them) and end your turn; read again when the author says to. If its `url` is not the document, call the open_document tool on the document again, poll the get_document tool with `limit` 1 as in step 6b, and read again from `from` 0; when the app still shows another file, tell the author and end your turn.
2. Run `REVIEW translate --work '<work>' --blocks-file '<blocks>'`, with one `--blocks-file` for each further page after it, in order (`--blocks-file '<work>/blocks-2.json'`, and so on). On exit 1 show stderr, which says what to read again, and end your turn (a page missing, out of order or given twice is one of the causes). It prints `edits`, `sent` and `refused`.
3. When `sent` is 0 skip the next two items: every edit goes to the chat in step 11. Otherwise call the MarkupEditor propose_edits tool with the `edits` list from the `translate` output as its `edits` argument, copied whole and unchanged, then Write the tool's reply as it came back to the `PROPOSED=` path. If the call itself fails, show what the app said (a refusal about access means Assistants must be set to read-write access in the app's settings), keep WORK and end your turn: when the author says to retry, start again at the get_document call of item 1 (suggestions the app already shows for the first call stay there, and a second call sends them to the chat as overlaps).
4. Run `REVIEW proposed --work '<work>' --from-file '<proposed>'`. On exit 1 show stderr and end your turn as in item 3. It prints `suggested` and `refused`.
5. Show the edits that are not in the app: each `refused` entry of `translate` and of `proposed` as `<n>. <old> -> <new> (<reason>): <cause>, <detail>`, with `old`, `new` and `reason` from the filtered proposal.
6. Tell the author to accept or reject each suggestion in the app and to say done in the chat. Say that a Reject in the app is stored for this document, so the editor does not propose that edit again, and that a suggestion left pending is held: the text stays and nothing is stored. Say that text typed in the app is not kept, so the author must not type in the document, must not use Undo (an undone Accept still counts as accepted) and must not save. Never call the MarkupEditor save or replace tools. End your turn.

## Step 11 path run

Path run, before any question: when the author says done, call the MarkupEditor list_suggestions tool, Write its reply as it came back to the `STATUSES=` path, and run `REVIEW decisions --work '<work>' --from-file '<statuses>'`. When step 10 sent nothing, run it without `--from-file`. On exit 1 show stderr and do what it says. It changes nothing. It prints `accept`, `reject` and `hold`, the author's decisions in the app for this run's suggestions only, `warnings` (a suggestion the app no longer lists, whose edit is held), `leftover` (the edits the app never showed, each with its cause) and `undecided` (the edits nobody has decided, the author's answers to queries among them). Tell the author which edit numbers were accepted, rejected and left pending in the app, and show each `warnings` entry. A pending or stale suggestion is held, and an edit the app holds is decided only there: never offer it in a question. The questions below cover the `undecided` edits and the queries and paragraph proposals only. Then take exactly one of these two branches:
- Branch A, `undecided` is empty. If the proposal has a query or a paragraph proposal, ask question 1 of step 11 in SKILL.md (with the voice card, as question 1 says) and end your turn; on "No", or with no query and no paragraph proposal, ask nothing more here and go to step 12 with the `apply_args` just printed. Step 12 decides there whether the run is App-decided; on "Yes", take the answer route of step 12, and the added edits make it Branch B.
  A reply that only says to apply (Branch A only, after you asked question 1, and the voice-card question with it): when the author's next message tells you to apply and carries no change text, no edit number and no other instruction (for example "Yes, apply."), and picks no option of either question, do not ask again which question it answers, and do not stop. Read it this way and say so in one sentence. It counts as No on question 1: a query is not an edit, so no text changes on it, and a Yes needs the author's words for the change. It does not answer the voice-card question: that one stays open, nothing is stored for it, and step 13 asks it once more after the apply. It is the author's go-ahead for the apply: go to step 12 with the `apply_args` already printed, run the dry run, show it, and then, in the same turn, do what the section "Step 12 before the real apply" says and run the same command without `--dry-run`, with no `Apply` question. This overrides, on purpose, the hold condition of the App-decided run: the edits the author left pending in the app stay held, which is what the author told you to apply, and the app drops its pending suggestions when it reloads the file, so asking `Apply` would not bring them back. The one exception: when the dry run shows `unplaced` or `would_skip` entries, ask `Apply` as step 12 of SKILL.md says, because the author has not seen what would be left out. Never read such a reply as Yes on question 1, and never as Keep it on the voice-card question. A message that carries any change text, edit number or other instruction is an ordinary answer: when it is unclear, ask what is unclear. In Branch B a bare apply decides none of the undecided edits: ask questions 2 and 3 as usual.
- Branch B, `undecided` is not empty. Ask questions 1 (only with a query or a paragraph proposal, and only when it was not already asked in this step), 2 and 3 of step 11 in SKILL.md in that order, each its own call, then run `REVIEW decisions --work '<work>' --from-file '<statuses>' --accept <spec> [--reject <spec>] [--hold <spec>]` again with the author's explicit numbers (each spec as one argv token; leave out the ones the author did not give), and use the `apply_args` it prints in step 12.

## Step 12 App-decided run

App-decided run: a path run that took Branch A of step 11 (no edit question was asked in chat), where `REVIEW decisions` printed `undecided`, `hold` and `warnings` all empty (the author accepted or rejected every suggestion in the app), and the dry run shows `hold`, `unplaced` and `would_skip` all empty. Then do not ask `Apply` (step 12): the author already decided in the app. A held, pending, stale or missing suggestion, a warning, or an edit the dry run would skip or could not place is not App-decided, because the author may want to go back to the app or cancel: ask `Apply` as in step 12 of SKILL.md. In an App-decided run, run the dry run, show it as step 12 of SKILL.md says, then do what the section "Step 12 before the real apply" says and run the same command without `--dry-run` in the same turn. An answer to a query that added edits makes them undecided, so that run goes back to the edit questions and is not app-decided. When any edit was decided in chat, the run asks `Apply` as in step 12 of SKILL.md. Either way, never skip the dry run.

## Step 12 before the real apply

Before the real apply (a path run that sent suggestions; a run that sent none has nothing to undo): the author's decisions are already read by `REVIEW decisions`, so return the app to a clean buffer now. The app holds the accepted suggestions as unsaved changes. When `apply` writes the file under them, the app raises its own dialog, "<file> changed on disk. This document has unsaved changes. Reloading will discard them.", with "Reload from Disk" and "Keep My Changes"; while it is up a get_document read still answers and shows the old text, so the skill cannot see the dialog. With a clean buffer the app reloads the file quietly. The dry run hashed the file and undo in the app does not touch the file, so the dry run still holds. Take the tools from the one MCP server that offers propose_edits, as in step 6b. First call the get_document tool with `limit` 1 and read its `url` and `hasChanges`. If its `url` is not the document (a `/private` prefix or a symbolic link is the same file, as in step 6b; the author switched the app to another file meanwhile), do not call the undo tool, because undo would revert the author's own work in that file; tell the author the app shows another file and go on. Otherwise, when `hasChanges` is true, call the MarkupEditor undo tool, then the get_document tool with `limit` 1 again, and repeat until `hasChanges` is false, at most accepted + rejected + 3 times (accepted and rejected in the app, from the latest `decisions` output; the number of suggestions sent plus 3 when there is none); when `hasChanges` is already false there is nothing to undo. If `hasChanges` did not clear (an undo restores an accepted suggestion's text, but the app can keep its unsaved-changes mark, and undo then reports nothing to undo), go on all the same and expect the dialog: tell the author first, in one sentence, that the app is about to say the file changed on disk and that the answer is "Reload from Disk", never "Keep My Changes". Only then run the same command without `--dry-run`.

## Step 12 return the app to the file

A path run returns the app to the file at three points: after a successful apply, after "Cancel", and before every other stop that comes after suggestions were sent (any other failure, `expired`). Take the tools from the one MCP server that offers propose_edits, as in step 6b. On "Cancel" and at those stops the app still holds the accepted suggestions as unsaved changes, and the author must not save them: saving would rewrite the whole file. Undo them first, as the section "Step 12 before the real apply" does (its url check, its bound, and only when suggestions were sent). After a successful apply the buffer is already clean, so there is nothing to undo. After any real apply, reopen the file whether or not suggestions were sent (`sent` 0 from `translate`, every edit refused by the app, or only chat decisions): apply wrote the file, and the app may still show the old text. First call the get_document tool with `limit` 1 and read its `url` and `hasChanges`. If its `url` is not the document (a `/private` prefix or a symbolic link is the same file, as in step 6b; the author switched the app to another file meanwhile), do not call the open_document tool, because the reopen would discard that file's unsaved state; tell the author the app shows another file and that the document is as apply left it. Otherwise, when `hasChanges` is true, the app can raise a dialog that the skill cannot see, so tell the author before the reopen which answer to give: "Reload from Disk" when the app says the file changed on disk, never "Keep My Changes" (the file on disk holds every applied edit), and "Don't Save" when it asks about unsaved changes, never "Save". Then call the open_document tool on the document again. Call the get_document tool with `limit` 1 as in step 6b until its `url` is the document, and tell the author the app shows the file as it is now. If a call fails or does not answer (the error "read: Resource temporarily unavailable" is this case), the app is waiting on one of those dialogs: tell the author to answer it as above. The app closes its connection after that error and its document tools can drop out of the session, so when the author says the dialog is answered, call the open_document tool on the document again (search for the tools with ToolSearch when they are not listed) before the next get_document call.

## Step 12 expired

On exit 1 with `expired` in stderr: suggestions sent before it may still sit in the app: run the section "Step 12 return the app to the file", tell the author, and say that any unsaved changes this review left in the app are to be discarded by choosing "Don't Save", never "Save" (Save rewrites the whole file).

## Step 13 voice card

The voice card the editor returned (`voice_card` in the filtered proposal, step 10). A path run only: a stdin run has no document, so it stores no card.
1. Run `MEMORY voice-card <path>`. When `voice_card` is not null, a card is already stored and this run's brief used it as the anchor: offer nothing, unless the author asks to replace it, and stop here. When it is null (none is stored), go on.
2. When the voice-card question was already answered in step 11 (it went in one call with the query question, and the author picked an option of it; a reply that only said to apply, as the section "Step 11 path run" describes, did not answer it, so ask it here), do not ask it again: take that answer and go to sub-step 3 on "Keep it", or stop here on "Not now"; on a change typed in "Other", show the card with that change and ask the question below once more, here, after the apply. Otherwise offer to keep the card as this document's author-approved voice card: later runs start from it instead of rebuilding it from text the editor has already edited. Ask one question, header `Voice card`, with a plain sentence saying what a voice card is (the editor's short description of how this document sounds, kept so later runs hold that voice) and the card text in the question: "Keep this voice card for this document?" with "Keep it (Recommended)" and "Not now". Put the card text whole in this reply, even when an earlier message of the run showed it: the author must see the card in the message that asks to keep it, never "the card is in my earlier message". When the author types a change in "Other", show the card with that change and ask once more. End your turn with that question.
3. When the author says yes by choosing "Keep it", make a fresh work directory as step 3 of the Steps list does and write `{"voice_card": "<the card text>"}` with the Write tool to its `CARD=` path. Store the text as the author left it after any change.
4. Run `MEMORY voice-card <path> --from-stdin < '<card>'`, then `BRIEF rmtmp '<work>'`.
5. In your reply, show the stored card back verbatim: copy the `voice_card` text that the command of sub-step 4 printed, whole, into the reply. Do not summarize it, do not paraphrase it, and do not reply "Done" or "Stored" without the text: the author has not seen the card that is now stored until you show it.

## Rules

Never call the MarkupEditor save or replace tools, and never type in the document there. The only MarkupEditor tools a run calls are open_document, get_document, propose_edits, list_suggestions and undo, all taken from the one MCP server that offers propose_edits.

## Setup step 3b

3b. The MarkupEditor check. A path run reviews its edits as suggestions in the MarkupEditor app, so look for the MarkupEditor propose_edits tool (search for it with ToolSearch when it is not loaded). When it is missing, say in plain words that prose-edit's path runs need the MarkupEditor app with suggestions and Assistants turned on: MarkupEditor 0.9.11 or later, the first release with suggestions (the Unlimited release keeps working without renewal, and so does a build from source; the Evaluation build stops after two weeks), running, with Assistants on in its settings at read-write access and this program allowed. Use every MarkupEditor tool from the one MCP server that offers propose_edits (a machine can register two MarkupEditor servers), and name that server to the author. Go on: setup does not stop for it, and a stdin run does not need the app. Whether it is present or missing, tell the author to choose "always allow" for the MarkupEditor tools the first time each asks permission. Report the result in step 6 of the Setup run as a requirement of path runs.
