# `nexus.daemon` — AGENTS.md

The shared daemon-lifecycle substrate. **One** leased/fenced/atomic service-registry primitive backs the discover / single-writer / self-heal / version-skew lifecycle for every tier it supervises. The interesting policy is the standing gate below: there is no longer a per-tier lifecycle copy, and there must never be one again.

The tier roster has SHRUNK since RDR-149 collapsed it — the T2 and T3 daemons are both retired — but the gate is unchanged, and applies to whatever tiers `TIERS` currently names. Historical references to "all three storage tiers (T1, T2, T3)" below are heritage, not current state.

## The standing gate (RDR-149, the load-bearing rule)

**Any future lifecycle fix lands in the shared primitive (`service_registry.py`) plus the cross-tier conformance suite (`tests/daemon/test_rdr149_lifecycle_conformance.py`) — NEVER in one tier's copy.**

This is the stop-the-bleeding gate. RDR-149 was created because the same lifecycle bug class (discovery loss, single-writer races, missing self-heal, stale-after-upgrade) was the target of ~10 RDRs and 156 commits in 90 days — each incident teaching exactly one tier a lesson the other two never received, because T1 (`session.py`), T2 (`t2_daemon.py`), and T3 (`t3_daemon.py`) each had a bespoke copy with no shared code. The fix collapsed all three onto one primitive. The gate keeps them collapsed.

Concretely, when you touch lifecycle behaviour (how an owner is published, discovered, reaped, fenced, restarted, self-healed, or version-cycled):

1. The change goes in `service_registry.py` (`ServiceRegistry` / `ServiceSupervisor`) — **not** in a single tier's daemon/consumer. (The shared-helper module `discovery.py` was the other home for this; it is deleted.)
2. Add or extend a property in the conformance suite's `EXPECTATIONS` matrix so the new behaviour is asserted for **every** tier in its `TIERS` tuple — currently `storage_service`, `aspect_worker` — not just the one you were debugging. **Read `TIERS` rather than trusting this list**; `t2` was removed in sub-stage B, `t3` at nexus-pmag3 (phantom tier after RDR-155 P4b), and `t1` at nexus-8zfwv (phantom tier after `T1LeasePublisher`'s retirement, 2026-08-07 — see below), and a stale cell is rejected by the matrix's own non-vacuity meta-test. A tier that legitimately cannot satisfy a property records a documented `GAP`/`SPEC` cell with a reason, never a silent omission.
3. If a property is genuinely tier-specific, it still lives in the conformance file alongside the shared battery, with a non-vacuity meta-test guarding it. (T1's transient-key → session-id re-key, CA-3, used to be the example here — it was `T1LeasePublisher`-only behavior; the publisher retired first at nexus-yfh5x, then the read-path + module it left behind retired fully at nexus-8zfwv; no surviving tier re-keys a scope in-place.)

A reviewer seeing a lifecycle change that edits one tier's file without a corresponding `service_registry.py` + conformance change should treat it as a defect: it is the exact pattern that produced the recurring bug class.

## Modules

| File | Purpose |
|---|---|
| `service_registry.py` | **The primitive.** `LeaseRecord`, `ServiceRegistry` (publish / heartbeat / discover / mark_shutting_down / relinquish, per-scope election flock, generation fencing), `ServiceSupervisor` (heartbeat cadence + version-skew cycle), `mint_owner_token`. Tier-parameterized by `tier=` + per-call `scope_key`, and **directory-scoped first**: leases live at `<dir>/<tier>_addr.<scope_key>` where `dir=nexus_config_dir()` — a `NEXUS_CONFIG_DIR` sandbox gets an independent lease from `~/.config/nexus` for the same uid (the nexus-tmsnz confusion). |

| `session_end.py` | Windows session-end stop (RDR-224, nexus-f9bgu.51): a `SetConsoleCtrlHandler` callback for `CTRL_CLOSE/LOGOFF/SHUTDOWN` (CPython maps none of them to a signal) that writes the launcher's stop marker, sets the supervisor's stop flag, stops the engine (`CTRL_BREAK`, <=2 s, job-object kill after) then `pg_ctl stop -m fast -w`, all inside a 4 s budget, and returns TRUE. Idempotent, every OS touchpoint injected. Wired by `storage_service_daemon._install_session_end_handler` (Windows only; POSIX untouched). Do not "simplify" it to `nx ... --foreground` as the task action: the supervisor would sit in the task's own group and `CTRL_BREAK` could not reach it. ## The two flocks (do NOT conflate) — HISTORICAL as of sub-stage B

The **spawn-lock** was the RDR-128 single-writer guarantee: exactly one daemon opens
the SQLite WAL, and it WAS T2/T3's election. Both spawn paths are gone (T3 at RDR-155
P4b, T2 at nexus-i711w Stage 2 sub-stage B), so no surviving tier has a spawn-lock.

What remains for every tier is the primitive's **per-scope election flock**
(`<tier>_elect.<scope>.lock`, taken briefly inside publish/heartbeat), which serializes
the generation read-increment-write so the fencing token is monotonic. It never
replaced the spawn-lock; it now has nothing to be distinguished from.

Kept as heritage because the distinction explains why the primitive's flock is scoped
the way it is — do not re-derive a spawn-lock from it.

## Adding a lifecycle fix (the checklist)

1. Reproduce the behaviour as a **red** conformance property first (cross-tier where applicable). Red-first against current code is the CA-1 discipline.
2. Implement the fix in `service_registry.py` (the shared substrate), not a tier copy.
3. Flip the conformance cell(s) to `pass`; update the matching non-vacuity meta-test from "reproduces the bug" to "fix landed".
4. Run `tests/daemon/` (the full lifecycle + supervisor + contention + version-skew + fairness suites) green.
5. Run BOTH stacked reviewers at the boundary (see root `CLAUDE.md` § Review Discipline) — the substantive-critic specifically catches the surface this gate exists to protect (a fix that quietly edits one tier).

## Hot rules

- **No per-tier lifecycle copy.** Discovery, liveness, reap, election, self-heal, version-skew all live in the primitive. If you find yourself writing a pid-keyed sweep or a bespoke discovery walk in a tier file, stop — it belongs in the substrate. This is mechanically enforced by `tests/daemon/test_lifecycle_gate.py` (the deleted bespoke addr-file functions stay deleted; `LeaseRecord` + the election flock live only in the primitive). Reintroducing one fails CI.
- **Liveness is lease freshness, not pid.** A dead owner's lease ages out via TTL; never add a new `os.kill(pid, 0)` **orphan sweep** in a tier-consumer file (pid reuse is the bug that causes). This bans the orphan-sweep *shape*, not all pid use. **The exemption list that used to sit here named `discovery.py`, `t2_daemon.py` and `t3_daemon.py` — all three now deleted.** An exemption naming a deleted file never matches, so it silently grants permission to whatever lands there next; that is the same silent-degradation class sub-stage B fixed in four code allowlists, and it is why this list is now empty rather than trimmed. `ServiceRegistry` reaches liveness through its own `pid_alive` (`os.kill(pid, 0)` on POSIX, kernel32 `OpenProcess` + a zero-timeout wait on Windows, where signal 0 is `CTRL_C_EVENT`; defined once in this module, and `tests/test_pid_alive_single_probe_lint.py` fails on a raw `os.kill(<pid>, 0)` anywhere else in `src/nexus`, nexus-f9bgu.25) — not through `nexus.session._is_pid_alive`, which this line used to name; that seam belongs to the T1 lease-publisher era this module no longer carries (see `t1_lease.py`'s retirement above), and the test harness's own `_AliveSet` injection point patches `nexus.session._is_pid_alive` for its OWN generic-harness vocabulary, not for this primitive.
  **Documented exception (nexus-oyo2g):** `service_registry.sweep_matching_processes` (+ `all_process_rows`/`process_command`/`terminate_pids`/`storage_service_stack_matcher`) IS a process-table, pid-based mechanism — but it does not change `discover()`'s liveness contract above. It answers a narrower, different question: on a lease *MISS*, is the miss a genuinely stopped service, or a discovery gap (a TTL-expired lease on a stalled-but-alive owner — the lz3f2/f9y78 stall signature)? `discover()` still never consults a pid; this fallback fires only inside the idempotent `stop` verb, only after a lease miss, purely to avoid a false "already stopped" and to make `stop` signal the whole discovered process tree (a supervisor's engine child can survive the supervisor's own SIGTERM). It generalizes the mechanism `upgrade_finish.py`'s convergence path already carried for this exact gap (`service_stack_pids` / `_sweep_surviving_stack`, nexus-cfgo9) into the primitive so no tier grows a second copy. Any future use of this exception outside `stop`-shaped idempotent-cleanup semantics needs its own justification here.
  **Second documented exception (nexus-cd1k0.17):** `service_registry.reclaim_lease_if_dead_owner` is ALSO a pid-based mechanism, materially different from the one above — it answers a question on top of a lease *HIT*, never a miss: is a TTL-fresh lease's `supervisor_pid` payload actually still running, so a self-healing spawner (both `commands/daemon.py.ensure_storage_supervisor` and `storage_service_daemon._start_locked` call the SAME function) can decide to reclaim and respawn instead of honoring a hard-crashed predecessor's stale lease. Uses `pid_running` (zombie-aware), with no cmdline/identity check against the pid — a kernel-recycled pid within the lease's TTL window reads as "alive" and the heal simply does not fire that tick; this FAILS SAFE (bounded delay until the lease's own TTL reap takes over, never double-ownership, since CA-4 fencing is unconditional) and is stated explicitly in the function's own docstring, not left implicit.
  **Third documented exception (nexus-wo6sc half one, Sam DECIDED 2026-09-24):** `ServiceRegistry.discover()`'s own `_stale_lease_still_live` IS a pid-based mechanism, and unlike the two above it changes `discover()`'s contract itself — but only for tiers in `TIER_READER_GRACE` (`storage_service` only today) and only ever by WIDENING a miss into a hit, never the reverse. It answers: a lease has just gone TTL-stale — is that a genuinely dead owner, or the 2026-09-12 stall shape (the owner alive and healthy, its own heartbeat stamp write simply overran the TTL)? Both the recorded `payload["supervisor_pid"]` (via `pid_alive`, no identity/cmdline check — the same recycled-pid trade-off `reclaim_lease_if_dead_owner` accepts) AND a bounded, loopback-only `/health` probe verifying the expected service's response shape (not bare port liveness — pid reuse and port reuse are both real) must succeed, bounded further by `STALE_LEASE_GRACE_MAX_TTL_MULTIPLE` past the lease's own TTL. The supervisor's own missed-TTL ERROR log is untouched by this — report, never masked. Any future tier that wants this same grace adds itself to `TIER_READER_GRACE`, once, rather than growing a tier-local copy. NOT a guarantee that grace resolves every stall shape: under SYSTEM-WIDE CPU contention (the whole box starved, not just the writer), the reader's own `/health` probe can starve the identical way the heartbeat stamp did, and its bounded timeout simply times it out to "down" — the same answer a caller got before this exception existed. Fails safe, never worse than the pre-existing behavior, but not a fix for that specific condition.
- **Generation is the fencing token.** `publish` only ever increments; `heartbeat` raises `StaleOwnerError` when superseded. A delayed predecessor must never clobber a higher-generation successor (CA-4).
- **Stop before relinquish.** Cancel a tier's heartbeat/reassert task BEFORE relinquishing its lease so it cannot resurrect a mid-shutdown record (RDR-129 early-stop ordering).
- **Local engine builds are guarded by a separate, unrelated lease (nexus-c00dw) — do not confuse it with the primitive above.** `service/target` (the Maven build output — jOOQ codegen, the shaded jar) is single-writer state, same hazard class as the shared git tree, but it has nothing to do with `ServiceRegistry`'s per-scope election flock: it is a plain flat-file lease (`<git common dir>/nexus-build-lease/<name>`, shared by every worktree of the repo since nexus-g6xpa; no T1/T2/T3 involvement, no engine dependency — the engine is often the thing being rebuilt) implemented in `scripts/lib/build-lease.sh` and taken by `scripts/build-gate-jar.sh` and `scripts/mvnw-leased.sh`. One engine build or suite per box at a time; a second caller waits (`NX_BUILD_LEASE_WAIT`) rather than running beside it. Never run `./mvnw` directly against any checkout of this repo while another agent might also be building — go through `scripts/mvnw-leased.sh` instead, or let `build-gate-jar.sh` take the lease for you.
- **No daemon child is ever silent (nexus-ovbr7).** Never spawn a long-lived daemon or daemon child with `stdout/stderr -> DEVNULL`. Supervisor entry points call `configure_logging(<mode>, config_dir=...)` (rotating file at `<config>/logs/<mode>.log`); child processes (jar, chroma) get `nexus.logging_setup.open_child_log(...)` as stdout/stderr; detached spawns route to `<mode>.crash.log` so pre-configure failures are captured; child exits are logged WITH returncode. Four storage-service supervisor deaths (2026-06) were undiagnosable because all of this went to DEVNULL. Pinned by `tests/daemon/test_storage_service_observability.py`. (Short-lived utility subprocesses handled via returncode may still DEVNULL.)
- **One graceful-stop send, in the primitive (RDR-224, nexus-f9bgu.17).** Any stop that signals a supervisor or engine pid goes through `service_registry.request_graceful_stop` (`SIGTERM` on POSIX; on Windows `CTRL_BREAK` after attaching to the target's console, `nexus.util.win_console`), never a bare `os.kill(pid, SIGTERM)`, which is `TerminateProcess` there. The Windows send runs in a short-lived HELPER process (`python -m nexus.util.win_console <pid>`, `DETACHED_PROCESS`, one JSON line on stdout), so the CLI's own console is never detached (`win_console.send_ctrl_break_via_helper`; an injected `console_api` still runs the sequence in-process, for tests). `GenerateConsoleCtrlEvent` is addressed with the lease's `supervisor_pid`, which behind the venv trampoline is NOT the process-group root (the trampoline `python.exe` is); measured 3 of 3 on Windows 11, the break still reaches the supervisor and it exits in about one second, and the lease path, not the process-table sweep, delivered it (T2 `nexus_rdr/224-review-p3-fixes-a`). A stop is confirmed by the target's EXIT (`pid_alive`), never by the send's return (it can return TRUE and deliver nothing). A target in another Windows session is REFUSED (`GracefulStopSend.refused`): never signalled and never hard-killed, and so is a target whose helper could not answer (spawn failure, timeout, no JSON) unless it is KNOWN to share this session (`win_console._unanswered`, `GracefulStopSend.stage == "helper"`; test review m7); `terminate_pids` leaves it alone and counts it among the survivors, and `nx daemon service stop` exits non-zero naming the owning session. The supervisor's own side: `SIGBREAK` sets the same stop event as `SIGTERM`; the engine is spawned `CREATE_NEW_PROCESS_GROUP` and put in a Job Object (`KILL_ON_JOB_CLOSE`) that holds the engine and nothing else, terminated if the engine ignores the break past `_GRACEFUL_STOP_TIMEOUT`; PostgreSQL is never in that job and is stopped only by `--with-pg`. A CPython `SIGBREAK` handler never runs inside one long wait, so any wait on the supervisor's main thread must be a loop of waits no longer than `DEFAULT_HEARTBEAT_INTERVAL` (T2 `nexus_rdr/224-research-22`). Tests: `tests/daemon/test_storage_service_stop_channel.py`, `test_storage_service_stop_cli.py`, `TestGracefulStopChannel` in the conformance suite.
- **A deliberate stop beats the Windows launcher (RDR-224, nexus-f9bgu.33).** `stop_storage_service` writes `<config_dir>/storage_service_stop.<identity>` (Windows only, owner-only, `service_registry.write_stop_marker`) BEFORE it signals anything, and even when it finds nothing to stop; a stop that was refused (another session) or left a survivor DELETES it again, because the service is still running and the launcher must stay free to respawn it when it later exits (test review S2, nexus-f9bgu.35). `windows_autostart.run_launcher` neither spawns nor respawns while that marker is not older than its last spawn (a marker older than the launcher's own start is a previous session's stop and is ignored), and a start (`ensure_storage_supervisor`) clears it. That covers the three stops that are not an exit 0: the hard-kill fallback (exit 1), a break landing before the supervisor's handler exists (`0xC000013A`), and a stop during the launcher's 30 s throttle. Measured against the real Task Scheduler launcher: without the marker a supervisor hard-killed at 20:31:17 was back under the same launcher within 45 s; with it nothing came back. `_SUPERVISOR_STOP_GRACE` is per platform: Windows adds `_STOP_LEASE_RETRIED_OPS` (4) sharing-violation retry budgets to the inner worst case (20 s against POSIX's 12 s), pinned by `tests/daemon/test_supervisor_stop_grace.py`, which MEASURES the count of four.
- **Replacing the engine or the PostgreSQL bundle on Windows stops what holds it first (RDR-224, nexus-f9bgu.20).** Windows will not overwrite a running `nexus-service.exe` (or its DLLs) or rename a bundle directory a running `postgres.exe` holds. Every replacement site runs inside `replace_quiesce.quiesced(config_dir, replacing="engine"|"pg_bundle")`: it stops the service with `stop_storage_service` (the f9bgu.17 stop), stops PostgreSQL only for a bundle swap and only when a cluster is up, and afterwards starts PostgreSQL then the service, only what it stopped, on failure as well as success (`restart_after=False` leaves the success restart to a caller that verifies it, as `converge_engine` does). A cross-session or surviving service raises `ReplaceBlockedError` naming the session before anything is replaced; it is never hard-killed. The files go in through `replace_guard`: `replace_with_retry` (Windows only, bounded, then `ReplaceBlockedError`) and `place_set_with_rollback` (each file one atomic replace, previous content kept until the whole set is in, DLLs first and the exe last, any failure restores every file, and a success sweeps the stale `.nx_old_*` keep directories that blocked upgrades left behind). `install_binary` wraps only the placement, `extract_bundle` only the swap, so the download and the extraction into the staging tree run with the service up. POSIX is a no-op. Tests: `tests/daemon/test_windows_upgrade_replace.py`, `tests/test_upgrade_finish_windows_stop.py`. The engine directory and its stage directory are granted the user's own SID (`_grant_user_ace`) before anything is staged, and the config directory is made with `nexus._winsec.make_user_dir`: an elevated install otherwise leaves them owner-only (Administrators), and a normal token could neither list them nor run the engine (nexus-f9bgu.33, measured).
- **Windows lifecycle conformance (RDR-224, nexus-f9bgu.19).** Three properties live in the conformance suite and run on every host with the platform injected, plus on native Windows: (1) a hard kill of a gone pid is not an error (`hard_kill_pid`: on Windows `os.kill` of an exited pid raises `OSError` WinError 87, not `ProcessLookupError`), and no stop site sends a raw `os.kill` (`TestHardKillOfAGonePid`); (2) `stop_storage_service` returns only after the supervisor and the engine have exited, including after a hard kill, which is confirmed by `wait_for_exit` and never by the kill's return (`TestStopReturnsAfterBothProcessesExit`); (3) the lease file is replaced and unlinked under concurrent readers, every read returns a whole lease, and on Windows a `PermissionError` from the read, the `os.replace` or the `unlink` is retried for up to `_WINDOWS_SHARING_RETRY_BUDGET_S` (Python opens without `FILE_SHARE_DELETE`; measured: without the retry the writer's replace fails with WinError 5 inside a second, and a reader's open fails about 1 read in 70) (`TestLeaseReplaceUnderConcurrentReaders`). A test that sends a REAL `CTRL_BREAK` must spawn its child with `CREATE_NEW_PROCESS_GROUP` (`_OWN_GROUP`) or the break reaches the pytest process (exit 0xC000013A). Every platform skip in the suite goes through `_posix_only` / `_windows_only` and `TestWindowsRunIsNotVacuous` pins the counts, so a Windows run that skipped most of the suite fails. `tests/daemon/_watchdog.py` bounds every test in the stop-channel and conformance files (an `ITIMER_REAL` alarm where it exists, `faulthandler` on Windows): an unbounded retry or a lock that ignores a stop request used to HANG the run instead of failing it. The test harness itself imports cleanly on Windows: `tests/conftest.py` imports `tests/_engine_substrate.py` at collection, which must not call `os.getuid()` (`tests/test_service_identity_lint.py` sweeps `conftest.py` and `tests/_*.py`).
