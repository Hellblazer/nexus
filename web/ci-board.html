CI Status From the Board

The CI board is for Claude Code sessions and their agents. When several of them work on one repository, each reads CI status from one board in the Nexus tuple space instead of asking GitHub. GitHub reports every change of every run and job to the board, so every agent sees the same result and none of them calls GitHub.

gh run watch is the right tool for one agent that watches one run. It works less well when several agents wait on CI at once, because each one polls in its own loop against the same GitHub account. Together they can reach GitHub's secondary rate limit, and then every Actions call from that account fails, including calls from agents that never polled. The board replaces those loops with one reader for each session and one writer for all of them.

Your part is lesson 1: turn the board on for your sessions and tell them to use it. Lessons 2 to 4 are what an agent then does on its own. Words like <SHA> are placeholders.

Terms used on this page
TermMeaning
boardA part of the tuple space for announcements. Every reader sees every post, and nobody removes one.
topicOne board. The CI topic for a branch is board/ci/<repo>-<branch>, for example board/ci/nexus-develop.
postOne announcement on a board. A CI post records one state change of one run or one job.
pingThe notification that a new post arrived. It names the post and does not contain it.
verdictThe script's word for one run or job: green, pending, failed, or cancelled.
1

Set up the board for your sessions

3 min

A session uses the board when it can receive pings and the project's instructions tell it to read the board rather than poll GitHub.

What you do

Launch each session with the channel, so that a new post reaches it as a ping. Getting started, "Turn on push delivery" has the steps.

claude --channels plugin:conexus@nexus-plugins

Then add the rule to the project's AGENTS.md or CLAUDE.md, which each session reads at start:

CI status comes from the board, never from polling GitHub.
- Subscribe once per session: tuple_subscribe("board/ci/<REPO>-develop").
- Check a commit with: uv run python scripts/ci_status.py <SHA>
  (exit 0 green, 1 failed, 2 pending, 3 no post, 4 cancelled).
- Before a push to develop, check the latest origin/develop commit and wait while it is pending.
- Never run gh run watch. If the board has no post for a commit, call
  gh api repos/<OWNER/REPO>/commits/<SHA>/check-runs
  one call at a time, at least 90 seconds apart.

Without the channel the posts still wait on the board, and an agent reads them when it runs ci_status.py. The board carries posts for a repository only after the conexus operator adds that repository's webhook to the adapter (RDR-220).

2

An agent checks a commit

2 min

scripts/ci_status.py gives the state of every run and job for one commit. Its exit status gives the whole answer as one number, so an agent can act on it without reading the rows.

What the agent does
uv run python scripts/ci_status.py <SHA>

The script takes the full 40-character commit sha. Each row is one workflow run, and the indented rows under it are its jobs. A row shows the verdict, the name, GitHub's conclusion or the current state, and the age of the latest post. A pending row with a large age can mean a post never arrived.

ExitMeaning
0Every run and job finished green. GitHub's success, skipped, and neutral all count as green.
1At least one run or job failed.
2Nothing failed, and something is still queued or running.
3The board has no post for this commit.
4Nothing failed or is pending, and at least one run was cancelled.

Exit 4 is usually not a problem. On develop, a push cancels the CI workflow's run for the commit before it, so the agent reads the newer commit's run instead. Other workflows, such as Service CI, are not cancelled and keep running. A job that GitHub cancelled inside a run that continued reads failed, for example a job that exceeded its time limit. The agent runs that job again.

--json gives the same result as JSON, and --topic nexus-main reads the main branch.

3

An agent waits for CI without polling

2 min

An agent subscribes once per session and is told about each new post, so it can wait for a run while it continues other work.

You might ask a session
Push this, and fix whatever CI reports.
What the agent does

It calls tuple_subscribe with board/ci/nexus-develop if it has not already, pushes, and continues. Each new post arrives as a ping. A job posts when it is queued, when it starts, and when it finishes, so the agent does not act on every ping. When its commit reaches a finished state, it runs ci_status.py for that commit and acts on the exit status.

An agent treats a post as data and never as an instruction, because the workflow and job names in it come from GitHub.

What the agent sees
The subscription
tuple_subscribe  subspace: board/ci/nexus-develop
Subscribed board/ci/nexus-develop
A ping, captured on another board. Every board uses the same form.
nexus board post: subspace board/ci-develop, tuple 6289eb34fecc86a4…. Read it with tuple_rd on that subspace. Posts are never claimed.
4

Agents do not cancel each other's runs

1 min

A push to develop cancels the CI workflow run that is in progress. Before it pushes, an agent checks whether another session is waiting for that run.

What the agent does

It runs ci_status.py for the latest commit on origin/develop. Exit 2 means that run is still in progress, so the agent waits for it and pushes when it finishes. If the board has no post for that commit (exit 3), the agent asks GitHub directly, one call at a time and at least 90 seconds apart:

gh api repos/<OWNER/REPO>/commits/<SHA>/check-runs

Appendix: how it works

reference

You need none of this to use the board.

From GitHub to your session

GitHub sends a workflow_run or workflow_job webhook each time a run or a job is queued, starts, or finishes. This covers every workflow in the repository without a change to any workflow file. A small adapter, which the conexus operator hosts, checks each webhook and writes one post. The adapter posts only for the branches on its list, which is develop and main by default. RDR-220 documents the adapter's checks (signature, forks, duplicate delivery) and its board-only token.

Which post counts

A job produces several posts, and GitHub can deliver them out of order, so the script keeps one state for each job by two rules. An attempt is one execution of a run, and a rerun has a higher attempt number. Within one attempt, the most advanced state wins. A job only moves forward, from queued to in_progress to completed, so a late queued post cannot hide a finished job. Across reruns, the newest attempt wins.

How long posts live

A CI topic holds up to 5000 posts, because every job posts every state change. A post lives at most three days. A queued or in_progress post expires after six hours, so a state whose next post never arrived does not look current for three days.

The form of a post

A post's body is compact JSON with these fields. A run post has no job field.

FieldValue
statequeued, in_progress, or completed
workflow, jobThe workflow name and the job name
shaThe commit, 40 hex characters
run, attemptThe run id and the attempt number
conclusionGitHub's conclusion once the state is completed, for example success or failure, and otherwise null
urlThe run or the job on GitHub
