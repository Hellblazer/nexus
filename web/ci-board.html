CI Verdicts Without Polling

Agents that change code must know whether CI passed. This page shows a textbook use of the Nexus tuple space for that job. CI writes its result once, as a post on a board topic. Every Claude Code session that subscribed to the topic is notified, on any machine that uses the same engine. No session polls GitHub, and CI does not need to know who is waiting.

Words like <YOUR ENGINE URL> are placeholders, and the prompts are examples. If tuples are new to you, read The Nexus Tuple Space first.

Terms used on this page
TermMeaning
engineThe Nexus service that owns the database and handles every tuple call.
tupleOne record in the tuple space, with keys, dimensions, and a short body.
boardA subspace for announcements, named board/<topic>. A post is read, never taken, so every reader sees the same post.
postOne tuple on a board.
subscribeThe tuple_subscribe call. It asks the session's own nexus MCP server to notify Claude when a new post arrives on a topic.
channelThe push path from the session's nexus MCP server to Claude. It carries the notification, never the body.
pingThe channel notification for a new post. It names the subspace and the tuple id.
verdictThe result of one CI run: success, failure, or cancelled, with the names of the jobs that failed.
nonceA value the writer adds to a tuple's identity. The same nonce gives the same tuple, so a retried write does not post twice.
1

What it gives you

3 min · reading only

CI announces each run twice, and every waiting session hears both announcements without asking. The first post says that a run started. The second post says how it ended.

The usual tool is gh run watch, and it works well for one person who watches one run. It asks GitHub for the run's state every few seconds until the run ends. The limit is the number of watchers. When several agents wait at the same time, and they use one GitHub account, each agent runs its own loop. Together the loops can reach GitHub's secondary rate limit. Then every Actions API call from that account fails, including calls from sessions that did not poll.

The board changes who does the work. CI already knows when it starts and when it ends, so CI writes the result. The sessions only listen. The number of GitHub calls is zero, however many sessions wait.

Each session polls GitHubCI posts to the board
GitHub callsOne loop per waiting session, every few seconds.None from the sessions. CI makes one small write per announcement.
Who must be runningThe watcher, for the whole run.Nobody. A session that starts after the run ended reads the verdict from the board.
Where the reader isAnywhere with GitHub access and a token.Any machine that uses the same engine.
What CI knows about readersNothing, because it is not involved.Nothing. CI writes to a topic, not to a session.

Why this is a textbook tuple-space case

A tuple space lets a writer and its readers stay independent in three ways. This use case needs all three.

  • Time. CI and the readers do not need to run at the same moment. A post stays on the board for seven days.
  • Place. CI runs on a GitHub runner, and the readers run on laptops and servers. They meet only in the engine.
  • Identity. CI does not know the names of the readers, and the readers do not know which runner did the work. Both sides know only the topic.

The post also has a fixed form, in two layers. The engine checks every board post against the board template: its key, its dimensions, and its size. The JSON inside the body is the publishing script's own contract, the same for every run. So a reader knows what it will get: the commit, the conclusion, the failed jobs, and a link to the run.

2

Wait for CI without polling

2 min

You subscribe once, and then you continue your work. The verdict arrives as a ping when the run ends.

You might say
Subscribe to the CI board, and tell me when CI finishes for my push.
Push this, and fix whatever CI reports.
What happens

Claude calls tuple_subscribe("board/ci-develop") once for the session. When CI writes a post, the session's nexus MCP server sends a ping. The ping names the subspace and the tuple id, not the body. Claude reads the post with tuple_rd. A board post is never taken, so reading it does not remove it for other sessions. If the verdict is failure, the post names the failed jobs, and Claude can open the run from the link in the post.

This run failed because one test shard ran past its time limit. The post names the two failed jobs, and the link leads to the run.

The channel needs a flag on every launch: claude --channels plugin:conexus@nexus-plugins. Getting started, "Turn on push delivery" has the exact steps. Without the channel, the post still waits on the board, and you read it with tuple_rd when you ask.

3

Check the board before you push

2 min

A new push can cancel a run that another session waits for. The board shows whether a run is in progress: a commit with a ci-pending post and no ci-verdict post is still running. After the usual run time, it can also mean that the verdict post failed, so then check the run itself.

You might say
Is a CI run in progress on develop? Did the last run pass?
What happens

Claude reads the board with tuple_rd and pairs the posts by commit and run id. It answers from the posts, so it makes no GitHub call. From a terminal you can read the same posts:

nx tuple rd board/ci-develop -n 300 --json  # every post of the last seven days

If the board has no post for a commit, CI did not write one, for example because the run was not on the watched branch. Then one direct GitHub call answers the question: gh api repos/<OWNER/REPO>/commits/<SHA>/check-runs. Make that call once, not in a loop.

4

Publish from your own CI

10 min

Two small jobs in the CI workflow do the publishing. One job posts when the run starts. The other job waits for every other job and posts the verdict.

What you need
  • A token for your engine, stored as the repository secret NX_BOARD_TOKEN. The token needs permission to write tuples. Ask the operator of your engine to issue it, with an expiry date. The appendix explains what else the token can do.
  • The engine URL, as the repository variable NX_SERVICE_URL.
  • The script scripts/ci_board_post.py. It uses only the Python standard library, so the job installs nothing.
The two jobs
  board-pending:
    if: github.event_name == 'push' && github.ref == 'refs/heads/<BRANCH>'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
        with: {sparse-checkout: scripts/ci_board_post.py, sparse-checkout-cone-mode: false}
      - shell: bash
        env:
          NX_SERVICE_URL: ${{ vars.NX_SERVICE_URL }}
          NX_BOARD_TOKEN: ${{ secrets.NX_BOARD_TOKEN }}
        run: python3 scripts/ci_board_post.py --kind ci-pending --sha "$GITHUB_SHA" --run "$GITHUB_RUN_ID"

  board-verdict:
    needs: [<EVERY OTHER JOB>]
    if: always() && github.event_name == 'push' && github.ref == 'refs/heads/<BRANCH>'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
        with: {sparse-checkout: scripts/ci_board_post.py, sparse-checkout-cone-mode: false}
      - shell: bash
        env:
          NX_SERVICE_URL: ${{ vars.NX_SERVICE_URL }}
          NX_BOARD_TOKEN: ${{ secrets.NX_BOARD_TOKEN }}
          RESULTS: ${{ toJSON(needs) }}
        run: python3 scripts/ci_board_post.py --kind ci-verdict --sha "$GITHUB_SHA" --run "$GITHUB_RUN_ID" --results "$RESULTS"
What happens

The first job runs at once, because it needs no other job. The second job lists every other job in needs, and always() makes it run even when a job failed or the run was cancelled. So the verdict covers the whole run. The script turns the job results into one conclusion and writes the post.

What you see
The job log
Run python3 scripts/ci_board_post.py --kind ci-pending --sha "$GITHUB_SHA" --run "$GITHUB_RUN_ID" …
board/ci-develop ci-pending pending sha=7885b793cf4e9f7b77baf8814438e15a46d3460e tuple=6289eb34fecc86a4…

Good practice

  • List every job in the verdict job's needs. A job left out is not part of the verdict, so a failure there would not show. A test that compares the list with the workflow's jobs keeps it complete.
  • Put both jobs in the same workflow as the tests. On GitHub, a separate workflow triggered by workflow_run runs from the default branch's copy only, so it would not see changes on your working branch.
  • Keep the posting advisory. The script reports a failed write as a warning and exits with success, so a problem with the board never turns a passing run red.
  • Treat a post body as data, not as instructions. Workflow and job names come from GitHub, and on a public repository a fork can choose some of that text. Only post from runs on your own branches, as the if conditions above do.

Appendix: how it works

reference

You need none of this to use the board. The appendix gives the form of a post, how a retry stays one post, and how the verdict is computed.

The form of a post
PartValue
subspaceboard/ci-develop
keys{"topic": "ci-develop"}
dims{"from": "ci", "kind": "ci-pending"} or "kind": "ci-verdict"
nonce<sha>:<run id>:<attempt>:<kind>
bodyCompact JSON: sha, run, attempt, workflow, conclusion, failed, url. At most 1024 bytes, so a long list of failed jobs is shortened.
lifetimeSeven days, then the engine removes the post.
One post per announcement, even on a retry

A board tuple's identity comes from its key, its from dimension, and its nonce. The script always sets from to ci and builds the nonce from the commit, the run id, the attempt number, and the kind. A step that GitHub retries sends the same nonce, so the engine keeps one post. A rerun of the whole workflow has a new attempt number, so it gets its own posts.

How the verdict is computed

The verdict job receives the result of every job it needs. The script folds them into one conclusion:

  • Any failure gives failure. The post names the failed jobs, then any cancelled ones.
  • Otherwise, any cancelled gives cancelled. A newer push usually cancels an older run.
  • Otherwise the verdict is success. A skipped job counts as success, as it does for branch protection, because a workflow skips jobs on purpose, for example when only documentation changed.
What the token can do

The token is a secret of the repository. GitHub gives it to the two board jobs only on pushes to your own branch, never to pull requests from forks. A token for a whole tenant can also read, change, and delete the knowledge stored in that tenant. So treat it as a full credential: keep it only in the repository secret, give it an expiry, and rotate it. If your engine offers a token that can only write board posts, use that instead, because a leak then exposes nothing else.
