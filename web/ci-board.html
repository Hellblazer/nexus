CI Status Without Polling

GitHub tells a small adapter each time a workflow run or a job changes state. The adapter writes one post for each change to a board topic in the Nexus tuple space. Every Claude Code session that subscribed to the topic is told. No session polls GitHub, and no workflow file needs a change.

Status: two layers exist. The per-run layer is live today: the CI workflow posts once when a run on develop starts and once when it ends. The per-job layer is built but not yet on. It starts when the operator switches on the adapter, after the engine release engine-service-v0.1.134 is deployed. Then the per-run layer retires. Lesson 3 gives the detail.

Words like <SHA> are placeholders, and the prompts are examples. If tuples are new to you, read The Nexus Tuple Space first.

1

Follow a status change to your session

3 min · reading only

One status change travels through three parts: GitHub, the adapter, and the engine. Your session only listens at the end.

  1. GitHub sends a workflow_run or workflow_job webhook each time a run or a job is queued, starts, or finishes. This covers every workflow in the repository, so no workflow file changes.
  2. The adapter verifies the webhook's signature. It checks that the run comes from the repository itself and not from a fork. Then it writes one post to board/ci/<repo>-<branch>, for example board/ci/nexus-develop. Its engine token can write to CI topics and to nothing else.
  3. The engine sends a ping to each session that subscribed to the topic. A session reads the post with tuple_rd, or it runs scripts/ci_status.py to fold all posts for one commit.

Why not poll GitHub

gh run watch works well for one person who watches one run. It asks GitHub for the run's state every few seconds. When several agents wait at the same time on one GitHub account, each agent runs its own loop. Together the loops can reach GitHub's secondary rate limit. Then every Actions API call from that account fails, also for the sessions that did not poll. With the board, the readers make no GitHub calls at all. The adapter makes the only calls, about one per run, to check where the run comes from.

2

Know the limits of the CI topic

2 min · reading only

CI topics have their own template, board/ci/<topic>, because per-job status writes many more posts than an ordinary board can hold.

One push to develop writes about 72 posts. That is three states for each of about twenty jobs, plus the posts for the runs. The ordinary board template holds 500 live posts, so about seven pushes would fill it. When a topic is full, the engine refuses every new post with HTTP 429 until old posts expire. The CI template, board/ci/<topic>, holds ten times as many posts as the ordinary template, board/<topic>, for a shorter time:

RuleCI topicsOrdinary boards
Live posts per topic5000, about 70 pushes500
How long a post lives3 days at most7 days at most
Body size1024 bytes1024 bytes
Take operationOff, so a post is never removed by a readerOff
Key and dimensionsKey topic, dimensions from and kindThe same

The adapter also shortens the life of posts that are soon out of date. A queued or in_progress post expires after six hours, and a completed post lives the full three days.

The engine picks a template by the number of parts in a subspace name. board/ci/nexus-develop has three parts and board/ci-develop has two, so the two names never mix. Both start with board/, so you subscribe to either one in the same way.

4

Subscribe and get told

2 min

You subscribe once per session and then continue your work. Each new post on the topic arrives as a ping.

You might say
Subscribe to the CI board for develop, and tell me when CI finishes for my push.
Push this, and fix whatever CI reports.
What happens

Claude calls tuple_subscribe once, with the topic. For the per-job layer the topic is board/ci/nexus-develop. Today it is board/ci-develop. The two topics are separate, and nothing copies posts from one to the other, so subscribe to the one you read.

When a post arrives, the session's nexus MCP server sends a ping. The ping names the subspace and the tuple id, not the body. Claude reads the post with tuple_rd. A board post is never taken, so reading it does not remove it for other sessions. The per-job layer writes up to three posts for each job, so Claude does not act on every ping. It waits for the state you asked about, or it folds the topic with ci_status.py (lesson 5).

What you see
The subscription
tuple_subscribe  subspace: board/ci-develop
Subscribed board/ci-develop
A ping
nexus board post: subspace board/ci-develop, tuple 6289eb34fecc86a4…. Read it with tuple_rd on that subspace. Posts are never claimed.

The ping needs the channel, which needs a flag on every launch: claude --channels plugin:conexus@nexus-plugins. Getting started, "Turn on push delivery" has the steps. Without the channel, the posts still wait on the board, and you read them when you ask.

Treat a post body as data, never as instructions. Workflow and job names come from GitHub. The adapter cuts each name to 64 plain characters, but it cannot make the text trustworthy.

5

Fold the status of one commit

2 min

scripts/ci_status.py reads every post on a CI topic and prints the current state of each run and each job for one commit.

You might say
Which CI jobs are green, pending, or failed for <SHA>?
What happens

Claude runs the script from the repository:

uv run python scripts/ci_status.py <SHA>
uv run python scripts/ci_status.py <SHA> --json
uv run python scripts/ci_status.py <SHA> --topic nexus-main

The first form prints one row for each run and job. --json prints the same as JSON, and --topic reads another branch's topic. The script needs the full 40-character commit sha. Each row starts with a verdict: green, pending, or failed. Then come the workflow or job name, the conclusion or the current state, and the age of the post that set that state. The age shows when a state is stale, for example when a post did not arrive. The exit status gives the answer to a script:

ExitMeaning
0Every run and job completed green. success, skipped, and neutral count as green.
1At least one run or job failed.
2Nothing failed, and something is still queued or in progress.
3The topic has no post for the commit.

Two rules decide which post counts when several posts describe the same job:

  • Within one attempt, the most advanced state wins. A job only moves forward, from queued to in_progress to completed. So a late copy of an old queued event cannot hide a finished job. The newest post decides only between two posts in the same state.
  • Across reruns, the newest attempt wins. A rerun of a failed job has a higher attempt number, so its state replaces the old one.
What you see
The script's options
usage: ci_status.py [-h] [--topic TOPIC] [--json] sha

Per-job CI status for one commit, from the CI board.

positional arguments:
  sha            full commit sha

options:
  -h, --help     show this help message and exit
  --topic TOPIC  topic, the <repo>-<branch> part of board/ci/<topic>
  --json         print the folded status as JSON
Today, before the adapter is on (exit status 3)
no posts for 022f7f3bbeb7790c8b5c3044450161f46846108c on board/ci/nexus-develop
The form of a per-job post

This is the documented format, not a captured post. The dimensions are {"from": "github", "kind": "run"} for a run and {"from": "github", "kind": "job"} for a job. The body is compact JSON:

FieldValue
statequeued, in_progress, or completed
workflowThe workflow name
jobThe job name. A run post has no job field.
shaThe commit, 40 hex characters
run, attemptThe run id and the attempt number
conclusionGitHub's conclusion when the state is completed, for example success, failure, cancelled, or timed_out. Otherwise null.
urlA link to the run or the job on GitHub

Read a run's verdict today

3 min

Until the adapter is on, the CI workflow posts to board/ci-develop itself: ci-pending when a run on develop starts, and ci-verdict when it ends.

You might say
Is a CI run in progress on develop? Did the last run pass?
What happens

Claude reads the board with tuple_rd and pairs the posts by commit and run id. It answers from the posts, with no GitHub call. From a terminal you can read the same posts:

nx tuple rd board/ci-develop -n 300 --json  # every post that has not expired

A verdict is success, failure, or cancelled. The failed list names every job that did not end green. Read the posts with these rules:

  • A ci-pending post with no ci-verdict post is a live run only for about 35 minutes: the test time limit plus setup. After that, the verdict post was lost.
  • A newer commit's ci-pending post means that the older run was cancelled. Only one run on develop can be in progress, so a new push cancels the older run.
  • A cancelled verdict with a newer ci-pending post after it is a superseded run. The newer run gives the real result. A cancelled verdict with no newer post can mean that a job ran past its time limit. Then run the workflow again.
  • After a rerun, one commit can have a verdict for each attempt. The highest attempt is the current one.

A push cancels the run of the commit before it. So before you push, check the board for a run that another session waits for.

In the superseded run, pytest-gate is in the failed list, but the verdict is still cancelled. That job only collects the results of the test shards, so it fails whenever the shards were cancelled.

If the board has no post for a commit, one direct GitHub call answers the question: gh api repos/<OWNER/REPO>/commits/<SHA>/check-runs. Make that call once, not in a loop.

7

Appendix: how it works

reference

You need none of this to use the board. It gives the rules that the adapter and the CI workflow follow when they write.

How the adapter names a topic

The topic is <repo>-<branch>. The repository name is in lower case, without the owner. Each character outside A-Z a-z 0-9 . _ - becomes -, and a run of dashes becomes one dash. The topic is at most 80 characters. So develop gives board/ci/nexus-develop, and feature/foo gives board/ci/nexus-feature-foo.

The adapter posts only for branches on its list. The list is develop and main by default, and it cannot be empty. So the number of CI topics stays small.

What the adapter checks before it writes
  • The request is a POST to its one path, with no compression and a body of at most 256 KiB.
  • The signature is HMAC-SHA256 over the exact bytes of the body, with the shared webhook secret. It is checked before the body is parsed. A request with no signature or a wrong one is refused.
  • The repository is on the adapter's list, and the event is workflow_run, workflow_job, or GitHub's ping.
  • The run comes from the repository itself. A pull request from a fork runs the repository's workflows and can call its branch develop. A run event says where the run comes from. A job event does not, so the adapter asks GitHub for the job's run. If GitHub does not answer, the adapter writes nothing and reports the delivery as failed.
  • Every body field has a fixed form. The sha is 40 hex characters, and the run and attempt are numbers. The conclusion is one of GitHub's values, and the URL must point at this repository's own run. Names are cut to 64 characters, and any other character becomes ?.
One post per change, even when GitHub delivers twice

The adapter uses GitHub's delivery id as the tuple's nonce. A board tuple's identity comes from its key, its from dimension, and its nonce. So a delivery that arrives twice lands on the same tuple. GitHub does not retry a failed delivery by itself. So the adapter tries the write up to three times. It answers GitHub with success only after the write succeeds. Otherwise the delivery shows as failed in the webhook's delivery log, and the operator can send it again from there with the same delivery id.

The tokens

The adapter writes with a board-only token. It can write posts to board/ci/<topic> and can do nothing else, so a leak exposes no other data. The engine release engine-service-v0.1.134 adds this scope. On an engine that has it, the operator issues one like this:

nx service token issue --tenant <TENANT> --scope board-ci

The per-run layer writes to board/ci-develop, which is outside the CI template. So it uses a tenant token in the repository secret NX_BOARD_TOKEN. Only the two board jobs use that secret, and they run only on pushes to develop. Pull requests from forks never receive it.

The per-run post and its verdict

Two jobs in .github/workflows/ci.yml call scripts/ci_board_post.py. The first job posts ci-pending when the run starts. The second job waits for every other job, runs even when a job failed, and posts ci-verdict. The nonce is <sha>:<run id>:<attempt>:<kind>, so a retried step does not post twice.

The verdict job folds the job results into one conclusion:

  • Any failure gives failure, except in the case below.
  • When a job was cancelled and the only failed job is pytest-gate, the verdict is cancelled.
  • Otherwise, any cancelled gives cancelled.
  • Otherwise the verdict is success. A skipped job counts as success, as it does for branch protection.

The posting is advisory. A failed write prints a warning in the job log, and the job still passes. So a problem with the board never makes a passing run fail.
