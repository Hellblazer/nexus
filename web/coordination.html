Coordination Between Sessions and Agents

Your Claude Code sessions and their agents can send each other work, replies, and reports through the Nexus engine. You ask in plain words, and hooks and a background watcher do the delivery. This page explains what that gives you, how to watch and steer the delivery, and what happens at each step. Every example comes from a real session.

In the tables, hook, watcher, and engine steps are automatic. Claude and agent steps are tool calls that the model makes. The Nexus Tuple Space explains the operations themselves.

Terms used on this page
TermMeaning
engineThe Nexus service that owns the database and handles every tuple call.
session idThe id of one Claude Code conversation, a UUID. It is the session's mailbox address.
nameThe short label the harness shows for a session, such as nexus-4a. It can change when a session resumes.
agent idThe id the harness gives an agent: the letter a and 16 hexadecimal digits. It is the agent's mailbox address.
tupleOne record in the tuple space. A message, a directory entry, and a ledger record are each one tuple.
messageOne tuple in a mailbox. It has a sender, a kind, a correlation id, and a short body.
mailboxThe part of the tuple space that holds the messages for one address.
directoryThe part of the tuple space that maps each name to the session id that holds it.
ledgerThe part of the tuple space where hooks record that an agent started and that it reported. Any session can read it.
dispatch fileA local file for each session, outside the tuple space. Hooks add a row when an agent is expected, when it starts, and when it reports.
hookA script that Claude Code runs at a fixed point: session start, each prompt, and agent start and stop.
watcherThe command nx tuple watch. It runs in the background and prints one line for each new message.
take operationA tuple_in call. It gives a message to one reader only, for a limited time called the lease.
ack, nacktuple_ack removes a message that the reader took. tuple_nack returns the message to the mailbox.
dead letterA message that failed three times. Anybody can read it, and nobody can take it.
correlation idAn id that a request carries and its reply repeats, so that the two can be paired.
1

What it gives you

2 min

Your sessions and agents can hand work to each other and reply without you in the middle. Every message stays in the engine until one reader takes it and confirms it, and you can see what is waiting at any time.

Claude Code already starts agents and returns their reports, and its messages reach agents and sessions that are running. Nexus memory already holds long content that every session can read. Coordination builds on both. It adds a tuple in the engine that waits for its reader, goes to exactly one reader, and tells that reader that the tuple arrived.

What you getHow it works
Sessions ask each other for workYou say "Ask <PEER NAME> to …". The request goes to the peer's mailbox, and the reply returns with the same correlation id. You do not copy text between terminals.
No lost messagesA message stays in the engine until a reader takes it and acks it. If the reader stops before the ack, the message stays claimed until its lease ends. After that, the next take operation can take it, or the sweep every six hours releases it. After three failed attempts, the message tuple becomes a dead letter that anybody can read.
Agents that you can correctYou can send a correction to an agent while it works. The agent reads the correction the next time it reads its mailbox. The agent's instructions tell it to read the mailbox before it reports.
A view of the work in progressMessages and names are rows in the engine that any session can read. You can list what waits and what nobody took. A file for each session shows which agents did not report. Lesson 7 shows how.
Other machinesIn cloud mode, sessions on other machines use the same engine, so the same request reaches them.

Lessons 2 to 6 show what happens at each step. Lesson 7 shows how to watch the delivery, and lesson 8 shows when to use it.

2

A session gets its address

3 min

The session id is the session's address. The session-start hook gives Claude that id and an instruction to start a watcher. The watcher then puts the session's name in the directory, so other sessions can find it.

ByWhat happens
hookWhen the session starts, resumes, clears, or compacts, nx hook session-start reads the session id. The hook writes a marker file for the watcher and adds two things to Claude's context: Nexus ready (session: <id>) and a MAILBOX WATCH instruction.
ClaudeCalls ListAgents to learn the session's name. The harness gives the name. Nexus does not choose the name.
ClaudeStarts the watcher with the Monitor tool, as the instruction says: nx tuple watch --instance <name>.
watcherWatches two mailboxes: mailbox/<session id> and mailbox/<name>. The watcher writes directory/<name> with the session id. The entry lasts five minutes, and the watcher writes it again every minute.
What Claude sees at session start
Nexus ready (session: 5b354c36-d317-4a00-aa15-f567e65a7209).
…
MAILBOX WATCH: arm once, now.
Monitor({
  command: "nx tuple watch --instance <name>",
  description: "mailbox watch 5b354c36-d317-4a00-aa15-f567e65a7209",
  timeout_ms: 3600000
})

ListAgents
This session is nexus-4a [102a61] — the name other sessions use to message it
The directory entry the watcher writes
tuple_rd  subspace: directory/nexus-4a
{
  "keys": {"name": "nexus-4a"},
  "dims": {"session_id": "5b354c36-d317-4a00-aa15-f567e65a7209"},

The Monitor tool ends a watch after 30 minutes. Claude starts the watcher again when the expiry notice arrives. If Claude does not, the drain hook in lesson 3 shows the instruction again.

3

A message arrives

4 min

A message waits in the mailbox until one reader takes it. The watcher tells Claude at once. If Claude does not take the message, the drain hook takes the message at the next prompt and shows it to Claude.

ByWhat happens
engineStores the message as one tuple in the mailbox. The message tuple waits there for at most seven days.
watcherReads the mailbox every three seconds and prints one ping line for each new message. The line names the sender, the kind, and the correlation id. The line does not contain the message body.
ClaudeCalls tuple_in on the mailbox. This take operation gives the message to Claude with a lease of at most fifteen minutes.
ClaudeDoes the work, then calls tuple_ack. For a request, the reply is part of the same call. The engine removes the request and writes the reply in one transaction, so a crash cannot send the reply twice. If Claude cannot do the work, tuple_nack gives the message back.
hookAt each prompt, the drain hook takes up to ten waiting messages, acks them, and shows each body in Claude's context. This path also works when no watcher runs.
hookIf no watcher holds the session's mailbox, the drain hook shows the MAILBOX WATCH instruction again, at most once every ten minutes. If that attempt fails, the hook tries again after one minute.
The ping line

4

An agent starts, works, and reports

5 min

An agent has its own mailbox, addressed by its agent id. Hooks record each agent in two places. The dispatch file lets the session check that every agent it started reported. The ledger in the tuple space lets any session see the same starts and reports.

ByWhat happens
hookBefore the Agent tool runs, a hook writes an EXPECT row for the agent type to the session's dispatch file.
hookWhen the agent starts, a hook adds the agent's id and mailbox address to its context. A second hook writes a START row to the dispatch file.
ClaudeTo correct the agent while it works, calls mailbox_send with the agent id. An agent id needs no directory lookup.
agentCalls tuple_in on its own mailbox before it writes its report. The mailbox skill tells the agent to do this. No hook reads the mailbox for the agent, so the agent reads a message only when it calls tuple_in.
hookWhen a background agent stops without a report, the stop hook stops the agent one time and writes a BLOCKED row. The agent then sends its report, and the hook writes a REPORTED row. The harness gives the report to the session.
hookAt start and at stop, other hooks also write a start record and a report record to ledger/<session id> in the tuple space. The report record copies any VERIFY: line from the report. These writes are best effort: a failure is logged and does not stop the agent.
ClaudeRuns expectations_census. The census reads the dispatch file and compares the agents that the session expected, the agents that started, and the agents that reported.
What the agent sees when it starts
Claimant id: a4873be6337bcac8c — mailbox: mailbox/a4873be6337bcac8c

5

A request to a peer session

4 min

Claude sends to a peer session by name. mailbox_send finds the name in the directory and writes to the mailbox of the session that holds it. The call is the same for a session on another machine that uses the same engine.

ByWhat happens
ClaudeWrites long content to project memory with memory_put. A message body is at most 4096 bytes, so the message carries only the memory title.
ClaudeCalls mailbox_send with the peer's name, the kind request, and a new correlation id. The tool looks up directory/<name>. When exactly one live session holds the name, the tool writes to that session's mailbox. When no session or two sessions hold the name, the tool writes nothing and names the holders.
watcherThe peer's watcher prints a ping line in the peer session.
ClaudeThe peer takes the request, does the work, and calls tuple_ack with a reply to the sender's mailbox. The reply has the same correlation id.
watcherThe sender's watcher prints a ping line for the reply, and Claude takes the reply as in lesson 3.
A send to a peer on the same machine
mailbox_send  to: nexus-8c   kind: request   correlation_id: r-41
→ {"to": "cdeb12b5-…", "address_kind": "session", "from": "5b354c36-…"}

Other machines

Two machines share one tuple space when both use the same engine. In cloud mode, every machine connects to one managed engine, so the directory and the mailboxes are the same on every machine. In local mode, each machine runs its own engine, so a session on another machine cannot receive the message. Every call carries the tenant's credentials, so only sessions of one tenant share a space.

6

The session changes

3 min

A /clear or a /resume gives the conversation a new session id. The old watcher stops by itself, and a message sent to the old id still reaches the conversation.

ByWhat happens
hookOn /clear, the session-start hook writes a record that names the old session id. Then the hook writes the watcher marker for the new id.
watcherThe old watcher compares the marker with its own session id on each cycle. When they differ, the old watcher removes its directory entry, prints a STOP line, and exits.
ClaudeStarts a new watcher with the same Monitor call. Claude calls ListAgents again first, because the name can change.
hookAt each prompt, the drain hook also reads the old session's mailbox. So a message sent to the old id reaches the new session.
hook/branch runs no session-start hook. At the branch's first prompt, the drain hook moves the marker to the new session id. The watcher for the old id then stops.
The STOP line
nx-tuple-watch: STOP: this conversation is now session 427e57b4-d9c4-474b-8626-215eb6aa80cf, not 643e36a6-b061-4ae4-ae5a-e2a29491fcf8 -- the watch for the old session is stopping. Re-arm per the SessionStart instruction, with the name from a fresh ListAgents call.
7

Watch it and steer it

4 min

Ask Claude in plain words, or read the engine yourself from a terminal. A read never takes a message, so watching cannot change what is delivered.

You might say
Is your mailbox watch armed?
What is waiting in your mailbox?
Did every agent you started report?
Tell the agent that works on <THE TASK> that <THE CHANGE>.
What happens
You askWhat Claude does
Is the watch armed?Looks for its running watcher. If there is none, Claude starts one as in lesson 2.
What is waiting?Calls tuple_rd on its own mailbox. This reads the messages and does not take them.
Did every agent report?Runs expectations_census and gives you the counts, as in lesson 4.
Tell the agent …Calls mailbox_send with the agent id, as in lesson 4.
From a terminal
nx tuple list --prefix mailbox/  # every mailbox, with counts
nx tuple stats mailbox/<SESSION-ID>  # one mailbox
nx tuple rd mailbox/<SESSION-ID> -n 20  # read without taking
nx tuple directory <NAME>  # who holds a name
nx doctor  # includes four tuple rows

The terminal command prints the same counts as one line of text for each mailbox. Add --json for JSON.

CountMeaning
availableThe message waits. No reader took it yet.
claimedA reader took the message and did not ack it yet. A message whose lease ended also counts here, until the next take operation or the sweep.
deadA dead letter: the message failed three times.
consumedDelivered and acked.
expired_unpurgedThe message is past its time limit. The next sweep removes it.
What Claude sees: three mailboxes from one tuple_list call
tuple_list
{"subspace": "mailbox/5b354c36-…",         "available": 0, "claimed": 0, "dead": 0, "consumed": 24}
{"subspace": "mailbox/nexus-e0",           "available": 2, "claimed": 0, "dead": 0, "consumed": 0, "oldest_created_at": "2026-09-14T15:19:38Z"}
{"subspace": "mailbox/shakeout-741-10236", "available": 0, "claimed": 0, "dead": 1, "consumed": 4}

The first mailbox delivered all 24 of its messages. The second has two messages that nobody took for more than a day. The third has one dead letter, which stays readable, so you can see which message failed.

nx doctor includes four tuple rows:

  • the age of the oldest message that nobody took
  • the database cleanup state of the tuple tables
  • the time since the last sweep
  • whether your Claude Code permission settings allow nx tuple watch

If the last row warns, add Bash(nx tuple watch:*) to permissions.allow in your Claude Code settings. The row names the settings file.

8

When to use it

4 min

Use coordination when work spans more than one session, or when a job takes longer than you want to wait. Use it also when many agents must all report.

SituationYou might sayWhat you get
One session in each of two repositories"Ask <PEER NAME> to <DEPLOY THE SERVICE>. The details are in memory <PROJECT>/<TITLE>. Wait for the reply."The peer does the work in its own repository. The peer's reply names the place where the peer wrote the result.
A long job on another machine, in cloud mode"Ask <REMOTE NAME> to run <THE FULL TEST SUITE> and send me the result."Your session continues with other work. Your session's watcher prints a line when the reply arrives.
Many background agents"Start one agent for each <MODULE>, and check that every one reported."The census counts the agents that the session expected, the agents that started, and the agents that reported, so a missing report is visible.
A change of plan during agent work"Tell the agent that works on <THE TASK> to <SKIP THE PARSER>."The agent reads the change the next time it reads its mailbox. The agent's instructions tell it to read the mailbox before its report.
A note for a busy session"Send <PEER NAME> a note that <THE RELEASE IS PUBLISHED>."The note waits in the peer's mailbox until the peer takes it, for at most seven days.

Good practice

  • Put long content in memory and send its title. A message body is at most 4096 bytes.
  • Give every request a new correlation id, so that its reply pairs with it.
  • Send to a name when one live session holds it. When two sessions hold a name, send to one session id.
  • Put what the reader must do into the kind. The sessions in these examples use request for a message that needs a reply and notice for one that needs none. The engine does not check the kind, so agree on the values with the sessions that read them.
9

Appendix: limits and rules

reference

You need none of this to use the system. This appendix gives the numbers behind the steps above.

Limits and rules
  • Lease. A take operation gives a message to one reader for at most fifteen minutes. A reader that needs more time calls tuple_renew.
  • Dead letter. A nack counts as one failed attempt. A lease that ends without an ack also counts as one. After three attempts, the message becomes a dead letter. The drain hook shows a dead letter once, as UNDELIVERABLE.
  • Retention. A message lasts at most seven days. Ledger records last 90 days, and nobody can take them.
  • Size. A message body is at most 4096 bytes. Each key or dimension value is at most 256 bytes.
  • Wait. One tuple_in call waits at most 25 seconds. For a longer wait, call tuple_in again.
  • Directory. An entry lasts five minutes, and the watcher writes it again every minute. mailbox_send refuses a name with no live holder or with two holders. nx tuple directory <name> shows the holders.
  • Watcher. The watcher reads every three seconds. It prints a ping for a message again after ten minutes, at most three times.
  • Drain hook. The drain hook takes at most ten messages at one prompt and uses at most six seconds.
  • Sweep. Every six hours, the engine returns claims whose lease ended and removes expired rows.
  • Health. nx doctor shows four tuple rows. Lesson 7 lists them.

Source: Hellblazer/nexus, the RDR-208 design record for session addressing, and The Nexus Tuple Space for the operations.
