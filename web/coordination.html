Coordination Between Sessions and Agents

Your Claude Code sessions and agents send each other work, replies, and reports through the Nexus engine. A sender writes a message and continues. The reader takes it when ready. This page shows what that gives you, how each step works, and how to watch it. The examples are real.

In the tables, hook, watcher, engine, and harness steps run by themselves. Claude, agent, and peer steps are tool calls that a model makes. The Nexus Tuple Space explains the operations.

Terms used on this page
TermMeaning
engineThe Nexus service that owns the database and handles every tuple call.
session idThe id of one Claude Code conversation, a UUID. It is the session's mailbox address.
nameThe short label the harness shows for a session, such as nexus-4a. It can change when a session resumes.
agent idThe id the harness gives an agent: the letter a and 16 hexadecimal digits. It is the agent's mailbox address.
tupleOne record in the tuple space. A message, a directory entry, and a ledger record are each one tuple.
messageOne tuple in a mailbox. It has a sender, a kind, a correlation id, and a short body.
mailboxThe part of the tuple space that holds the messages for one address.
directoryThe part of the tuple space that maps each name to the session id that holds it.
ledgerThe part of the tuple space where hooks record that an agent started and that it reported. Any session can read it.
dispatch fileA local file for each session, outside the tuple space. Hooks add a row when an agent is expected, when it starts, and when it reports.
hookA script that Claude Code runs at a fixed point: session start, each prompt, and agent start and stop.
watcherThe command nx tuple watch. It runs in the background and prints one line for each new message.
take operationA tuple_in call. It gives a message to one reader only, for a limited time called the lease.
ack, nacktuple_ack removes a message that the reader took. tuple_nack returns the message to the mailbox.
dead letterA message that failed three times. Anybody can read it, and nobody can take it.
correlation idAn id that a request carries and its reply repeats, so that the two can be paired.
1

What it gives you

2 min

Sessions and agents hand work to each other without you in the middle. None of them stops to wait. The message tuple waits in the engine instead.

Claude Code already returns agent reports and delivers messages to running sessions. Nexus memory already holds long content. Coordination adds a tuple that waits for its reader. Every exchange has three steps: send, continue, react. The two sides never need to run at the same time, or know where the other runs.

What you getHow it works
Sessions ask each other for workSay "Ask <PEER NAME> to …". Your session continues, and the reply arrives later. Nobody copies text between terminals.
No lost messagesThe engine keeps each message until a reader acks it. If a reader stops, its lease ends, and the next take operation or the six-hourly sweep frees the message. Three failures make it a dead letter.
Agents you can correctSend a correction while the agent works. Its instructions require a mailbox read before it reports, so it sees the correction then.
A view of the workList the waiting messages and names in the engine. A local file shows which agents did not report.
Other machinesIn cloud mode every machine uses one engine, so the same request reaches them.

A session gets its address

3 min

The session id is the session's address. The watcher publishes the session's name, so peers can find it.

ByWhat happens
hookGives Claude the session id and a MAILBOX WATCH instruction at every start, resume, clear, and compact. Writes a marker file for the watcher.
ClaudeCalls ListAgents to learn the session's name. The harness chooses it.
ClaudeStarts the watcher with the Monitor tool: nx tuple watch --instance <name>.
watcherWatches mailbox/<session id> and mailbox/<name>. Publishes directory/<name> with the session id, and renews it every minute. An entry lasts five minutes.
What Claude sees at session start
Nexus ready (session: 5b354c36-d317-4a00-aa15-f567e65a7209).
…
MAILBOX WATCH: arm once, now.
Monitor({
  command: "nx tuple watch --instance <name>",
  description: "mailbox watch 5b354c36-d317-4a00-aa15-f567e65a7209",
  timeout_ms: 3600000
})

ListAgents
This session is nexus-4a [102a61] — the name other sessions use to message it

tuple_rd  subspace: directory/nexus-4a
{
  "keys": {"name": "nexus-4a"},
  "dims": {"session_id": "5b354c36-d317-4a00-aa15-f567e65a7209"},

The Monitor tool ends a watch after 30 minutes. Claude restarts it at the expiry notice. If Claude does not, the drain hook repeats the instruction (lesson 3).

3

A message arrives

4 min

A message arrives while Claude works on something else. The watcher pings, and Claude takes the message at its next step. If Claude does not react, the drain hook delivers the message at the next prompt.

ByWhat happens
engineKeeps the message tuple in the mailbox for up to seven days.
watcherRuns beside Claude's work. Reads the mailbox every three seconds and prints one ping line per new message: sender, kind, and correlation id, without the body.
ClaudeCalls tuple_in after the ping. The take operation usually returns at once, with a lease of up to fifteen minutes. If the drain hook took the message first, the take operation finds nothing.
ClaudeDoes the work and calls tuple_ack, with the reply in the same call. The engine removes the request and writes the reply in one transaction. tuple_nack returns the message instead.
hookTakes up to ten waiting messages at each prompt, acks them, and shows their bodies to Claude. Works without a watcher.
hookRepeats the MAILBOX WATCH instruction when no watcher runs: at most every ten minutes, or every minute after a failed attempt.
The ping line

An agent starts, works, and reports

5 min

A background agent works while the session continues. Every agent has a mailbox at its agent id. Hooks record each agent in a local dispatch file and in the tuple-space ledger.

ByWhat happens
hookWrites an EXPECT row to the dispatch file before the Agent tool runs.
hookGives the starting agent its id and mailbox address, and writes a START row.
ClaudeSends a correction to the agent id with mailbox_send, and continues. The correction waits in the agent's mailbox.
agentCalls tuple_in on its own mailbox before it reports, as the mailbox skill instructs. No hook does this for the agent.
hookStops a background agent once if it tries to stop without a report, and writes BLOCKED. The agent then reports, and the hook writes REPORTED.
harnessDelivers a background agent's report as a notification while the session does other work.
hookAlso writes start and report records to ledger/<session id>, with any VERIFY: line. A failed write never stops the agent.
ClaudeRuns expectations_census to compare expected, started, and reported agents from the dispatch file.
What the agent sees when it starts

5

A request to a peer session

4 min

Claude sends a request to a peer by name and continues. The reply arrives later as a ping. The call is the same for a peer on another machine that uses the same engine.

ByWhat happens
ClaudeStores long content with memory_put and sends only its title. A message body holds at most 4096 bytes.
ClaudeCalls mailbox_send with the peer's name, kind request, and a new correlation id, then continues. The tool finds the peer in the directory, or refuses and names the holders.
watcherPings the peer. The request waits in the peer's mailbox until the peer is ready.
peerTakes the request, does the work, and acks with a reply to the sender. The reply keeps the correlation id.
watcherPings the sender when the reply arrives, minutes or days later. Claude takes it as in lesson 3.
A send to a peer on the same machine
mailbox_send  to: nexus-8c   kind: request   correlation_id: r-41
→ {"to": "cdeb12b5-…", "address_kind": "session", "from": "5b354c36-…"}

Other machines

Machines share one tuple space when they use one engine. Cloud mode does this. In local mode each machine runs its own engine, so only its own sessions reach each other. Only sessions of one tenant share a space.

The session changes

3 min

/clear and /resume give the conversation a new session id. The old watcher stops itself, and mail for the old id still arrives.

ByWhat happens
hookOn /clear, records the old session id, then writes the watcher marker for the new id.
watcherSees the new marker, removes its directory entry, prints STOP, and exits.
ClaudeCalls ListAgents for the current name and starts a new watcher.
hookDrains the old session's mailbox into the new session at each prompt.
hookOn /branch, which runs no session-start hook, moves the marker at the first prompt. The old watcher stops.
The STOP line
nx-tuple-watch: STOP: this conversation is now session 427e57b4-d9c4-474b-8626-215eb6aa80cf, not 643e36a6-b061-4ae4-ae5a-e2a29491fcf8 -- the watch for the old session is stopping. Re-arm per the SessionStart instruction, with the name from a fresh ListAgents call.

Watch it and steer it

4 min

Ask Claude, or read the engine from a terminal. A read never takes a message.

You might say
Is your mailbox watch armed?
What is waiting in your mailbox?
Did every agent you started report?
Tell the agent that works on <THE TASK> that <THE CHANGE>.
What happens
You askWhat Claude does
Is the watch armed?Checks for its watcher, and starts one if none runs.
What is waiting?Reads its mailbox with tuple_rd, and takes nothing.
Did every agent report?Runs expectations_census.
Tell the agent …Sends the correction with mailbox_send.
From a terminal
nx tuple list --prefix mailbox/  # every mailbox, with counts
nx tuple stats mailbox/<SESSION-ID>  # one mailbox
nx tuple rd mailbox/<SESSION-ID> -n 20  # read without taking
nx tuple directory <NAME>  # who holds a name
nx doctor  # includes four tuple rows

nx tuple list prints one line of counts per mailbox. --json prints JSON.

CountMeaning
availableWaiting. Nobody took it.
claimedTaken, not yet acked. Also counts a message whose lease ended, until the next take operation or the sweep.
deadFailed three times.
consumedDelivered and acked.
expired_unpurgedPast its time limit. The next sweep removes it.
What Claude sees: three mailboxes from one tuple_list call
tuple_list
{"subspace": "mailbox/5b354c36-…",         "available": 0, "claimed": 0, "dead": 0, "consumed": 24}
{"subspace": "mailbox/nexus-e0",           "available": 2, "claimed": 0, "dead": 0, "consumed": 0, "oldest_created_at": "2026-09-14T15:19:38Z"}
{"subspace": "mailbox/shakeout-741-10236", "available": 0, "claimed": 0, "dead": 1, "consumed": 4}

The first mailbox delivered all 24 messages. The second holds two that nobody took for a day. The third holds one readable dead letter.

nx doctor adds four tuple rows: the oldest untaken message, tuple-table cleanup, time since the last sweep, and the watcher permission. If the permission row warns, add Bash(nx tuple watch:*) to permissions.allow in the settings file that the row names.

8

When to use it

4 min

Use coordination when work spans sessions, when a job runs longer than you want to watch, or when many agents must all report.

SituationYou might sayWhat you get
One session in each of two repositories"Ask <PEER NAME> to <DEPLOY THE SERVICE>. The details are in memory <PROJECT>/<TITLE>. Tell me when the reply arrives."The peer works in its own repository while yours continues. Its reply names where it wrote the result.
A long job on another machine, in cloud mode"Ask <REMOTE NAME> to run <THE FULL TEST SUITE> and send me the result."Your session keeps working. A ping announces the reply.
Many background agents"Start one agent for each <MODULE>, and check that every one reported."The census shows any agent that did not report.
A change of plan during agent work"Tell the agent that works on <THE TASK> to <SKIP THE PARSER>."The agent reads the change at its next mailbox read.
A note for a busy session"Send <PEER NAME> a note that <THE RELEASE IS PUBLISHED>."The note waits in the peer's mailbox, for up to seven days.

Good practice

  • Send, then continue. The watcher tells you when the reply arrives.
  • Put long content in memory and send its title.
  • Use a new correlation id for every request.
  • Send to a name that one live session holds. Otherwise, send to a session id.
  • Use the kind to tell the reader what to do. These sessions use request for a reply and notice for none. The engine does not check kinds.

Appendix: limits and rules

reference

You need none of this to use the system. This appendix gives the numbers behind the steps above.

Limits and rules
  • Lease. A take operation gives a message to one reader for at most fifteen minutes. A reader that needs more time calls tuple_renew.
  • Dead letter. A nack counts as one failed attempt. A lease that ends without an ack also counts as one. After three attempts, the message becomes a dead letter. The drain hook shows a dead letter once, as UNDELIVERABLE.
  • Retention. A message lasts at most seven days. Ledger records last 90 days, and nobody can take them.
  • Size. A message body is at most 4096 bytes. Each key or dimension value is at most 256 bytes.
  • Parking. A take operation on an empty mailbox can park for up to 25 seconds. A watched session seldom needs this.
  • Directory. An entry lasts five minutes, and the watcher writes it again every minute. mailbox_send refuses a name with no live holder or with two holders. nx tuple directory <name> shows the holders.
  • Watcher. The watcher reads every three seconds. It prints a ping for a message again after ten minutes, at most three times.
  • Drain hook. The drain hook takes at most ten messages at one prompt and uses at most six seconds.
  • Sweep. Every six hours, the engine returns claims whose lease ended and removes expired rows.
  • Health. nx doctor shows four tuple rows. Lesson 7 lists them.

Source: Hellblazer/nexus, the RDR-208 design record for session addressing, and The Nexus Tuple Space for the operations.
