Coordination Between Sessions and Agents

This page follows one Claude Code session through its work with agents and with other sessions. For each step, it shows which part does the work. Hooks, the watcher, and the engine do their steps without a request. Claude does its steps with tool calls. Every example comes from a real session.

In the tables, hook, watcher, and engine steps are automatic. Claude and agent steps are tool calls that the model makes. The Nexus Tuple Space explains the operations themselves.

Terms used on this page
TermMeaning
engineThe Nexus service that owns the database and handles every tuple call.
session idThe id of one Claude Code conversation, a UUID. It is the session's mailbox address.
nameThe short label the harness shows for a session, such as nexus-4a. It can change when a session resumes.
agent idThe id the harness gives an agent: the letter a and 16 hexadecimal digits. It is the agent's mailbox address.
mailboxThe part of the tuple space that holds messages for one address.
directoryThe part of the tuple space that maps each name to the session id that holds it.
ledgerThe part of the tuple space where hooks record that an agent started and that it reported. Any session can read it.
dispatch fileA local file for each session, outside the tuple space. Hooks add a row when an agent is expected, when it starts, and when it reports.
hookA script that Claude Code runs at a fixed point: session start, each prompt, and agent start and stop.
watcherThe command nx tuple watch. It runs in the background and prints one line for each new message.
take operationA tuple_in call. It gives a message to one reader only, for a limited time called the lease.
ack, nacktuple_ack removes a message that the reader took. tuple_nack returns it to the mailbox.
dead letterA message that failed three times. Anybody can read it, and nobody can take it.
correlation idAn id that a request carries and its reply repeats, so that the two can be paired.
1

A session gets its address

3 min

The session id is the session's address. The session-start hook gives Claude that id and an instruction to start a watcher. The watcher then puts the session's name in the directory, so other sessions can find it.

ByWhat happens
hookWhen the session starts, resumes, clears, or compacts, nx hook session-start reads the session id. It writes a marker file for the watcher and adds two things to Claude's context: Nexus ready (session: <id>) and a MAILBOX WATCH instruction.
ClaudeCalls ListAgents to learn the session's name. The harness gives the name. Nexus does not choose it.
ClaudeStarts the watcher with the Monitor tool, as the instruction says: nx tuple watch --instance <name>.
watcherWatches two mailboxes: mailbox/<session id> and mailbox/<name>. It writes directory/<name> with the session id. The entry lasts five minutes, and the watcher writes it again every minute.
What Claude sees at session start

The Monitor tool ends a watch after 30 minutes. Claude starts the watcher again when the expiry notice arrives. If Claude does not, the drain hook in lesson 2 shows the instruction again.

2

A message arrives

4 min

A message waits in the mailbox until one reader takes it. The watcher tells Claude at once. If Claude does not take the message, the drain hook takes it at the next prompt and shows it to Claude.

ByWhat happens
engineStores the message in the mailbox. It waits there for at most seven days.
watcherReads the mailbox every three seconds and prints one ping line for each new message. The line names the sender, the kind, and the correlation id. It does not contain the message body.
ClaudeCalls tuple_in on the mailbox. This take operation gives the message to Claude with a lease of at most fifteen minutes.
ClaudeDoes the work, then calls tuple_ack. For a request, the reply is part of the same call. The engine removes the request and writes the reply in one transaction, so a crash cannot send the reply twice. If Claude cannot do the work, tuple_nack gives the message back.
hookAt each prompt, the drain hook takes up to ten waiting messages, acks them, and shows each body in Claude's context. This path also works when no watcher runs.
hookIf no watcher holds the session's mailbox, the drain hook shows the MAILBOX WATCH instruction again, at most once every ten minutes. If that attempt fails, the hook tries again after one minute.

3

An agent starts, works, and reports

5 min

An agent has its own mailbox, addressed by its agent id. Hooks record each agent in two places. The dispatch file lets the session check that every agent it started reported. The ledger in the tuple space lets any session see the same starts and reports.

ByWhat happens
hookBefore the Agent tool runs, a hook writes an EXPECT row for the agent type to the session's dispatch file.
hookWhen the agent starts, a hook adds the agent's id and mailbox address to its context. A second hook writes a START row to the dispatch file.
ClaudeTo correct the agent while it works, calls mailbox_send with the agent id. An agent id needs no directory lookup.
agentCalls tuple_in on its own mailbox before it writes its report. The mailbox skill tells the agent to do this. No hook does it for the agent, so the agent reads a message only when it calls tuple_in.
hookWhen a background agent stops without a report, the stop hook stops it one time and writes a BLOCKED row. The agent then sends its report, and the hook writes a REPORTED row. The harness gives the report to the session.
hookAt start and at stop, other hooks also write a start record and a report record to ledger/<session id> in the tuple space. The report record copies any VERIFY: line from the report. These writes are best effort: a failure is logged and does not stop the agent.
ClaudeRuns expectations_census. It reads the dispatch file and compares the agents that the session expected, the agents that started, and the agents that reported.

A request to a peer session

4 min

Claude sends to a peer session by name. mailbox_send finds the name in the directory and writes to the mailbox of the session that holds it. The call is the same for a session on another machine that uses the same engine.

ByWhat happens
ClaudeWrites long content to project memory with memory_put. A message body is at most 4096 bytes, so the message carries only the memory title.
ClaudeCalls mailbox_send with the peer's name, the kind request, and a new correlation id. The tool looks up directory/<name>. When exactly one live session holds the name, it writes to that session's mailbox. When no session or two sessions hold the name, it writes nothing and names the holders.
watcherThe peer's watcher prints a ping line in the peer session.
ClaudeThe peer takes the request, does the work, and calls tuple_ack with a reply to the sender's mailbox. The reply has the same correlation id.
watcherThe sender's watcher prints a ping line for the reply, and Claude takes it as in lesson 2.
A send to a peer on the same machine
mailbox_send  to: nexus-8c   kind: request   correlation_id: r-41
→ {"to": "cdeb12b5-…", "address_kind": "session", "from": "5b354c36-…"}

Other machines

Two machines share one tuple space when both use the same engine. In cloud mode, every machine connects to one managed engine, so the directory and the mailboxes are the same on every machine. In local mode, each machine runs its own engine, so a session on another machine cannot receive the message. Every call carries the tenant's credentials, so only sessions of one tenant share a space.

5

The session changes

3 min

A /clear or a /resume gives the conversation a new session id. The old watcher stops by itself, and a message sent to the old id still reaches the conversation.

ByWhat happens
hookOn /clear, the session-start hook writes a record that names the old session id. Then it writes the watcher marker for the new id.
watcherThe old watcher compares the marker with its own session id on each cycle. When they differ, it removes its directory entry, prints a STOP line, and exits.
ClaudeStarts a new watcher with the same Monitor call. It calls ListAgents again first, because the name can change.
hookAt each prompt, the drain hook also reads the old session's mailbox. So a message sent to the old id reaches the new session.
hook/branch runs no session-start hook. At the branch's first prompt, the drain hook moves the marker to the new session id. The watcher for the old id then stops.
The STOP line
nx-tuple-watch: STOP: this conversation is now session 427e57b4-d9c4-474b-8626-215eb6aa80cf, not 643e36a6-b061-4ae4-ae5a-e2a29491fcf8 -- the watch for the old session is stopping. Re-arm per the SessionStart instruction, with the name from a fresh ListAgents call.
6

Appendix: limits and rules

reference

You need none of this to use the system. It gives the numbers behind the steps above.

Limits and rules
  • Lease. A take operation gives a message to one reader for at most fifteen minutes. A reader that needs more time calls tuple_renew.
  • Dead letter. A nack counts as one failed attempt. A lease that ends without an ack also counts as one. After three attempts, the message becomes a dead letter. The drain hook shows a dead letter once, as UNDELIVERABLE.
  • Retention. A message lasts at most seven days. Ledger records last 90 days, and nobody can take them.
  • Size. A message body is at most 4096 bytes. Each key or dimension value is at most 256 bytes.
  • Wait. One tuple_in call waits at most 25 seconds. For a longer wait, call it again.
  • Directory. An entry lasts five minutes, and the watcher writes it again every minute. mailbox_send refuses a name with no live holder or with two holders. nx tuple directory <name> shows the holders.
  • Watcher. It reads every three seconds. It prints a ping for a message again after ten minutes, at most three times.
  • Drain hook. It takes at most ten messages at one prompt and uses at most six seconds.
  • Sweep. Every six hours, the engine returns claims whose lease ended and removes expired rows.
  • Health. nx doctor shows four tuple rows. They report the oldest message that nobody took, the database cleanup state of the tuple tables, the time since the last sweep, and whether the watcher can run.

Source: Hellblazer/nexus, the RDR-208 design record for session addressing, and The Nexus Tuple Space for the operations.
