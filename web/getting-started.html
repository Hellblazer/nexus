Nexus · getting started

Nexus Getting Started

You do all of this inside Claude Code. You give Claude a short instruction. Claude uses Nexus for you. Each lesson shows the instruction to give, what Claude does, and what you see. Eight lessons, about one hour.

Before you start: install Nexus and the plugin with the install guide. Then open a terminal in a project of yours and run claude. Every lesson happens in that Claude Code session.

The lessons use a few words with one fixed meaning. Open a group to read them.

Where data lives
StoreA place where Nexus keeps data. There are three stores: scratch, memory, and knowledge.
EntryOne item in the scratch store or the memory store.
DocumentOne item in the knowledge store: a file from a repository, a note, or a PDF.
CollectionA named group of documents in the knowledge store, for example distributed-systems.
CatalogThe list of all documents and the links between them.
TTLTime to live. How long an entry stays before Nexus deletes it.
PromoteTo copy an entry from one store to the next store. Scratch to memory, or memory to knowledge.
Finding things
ChunkA piece of a document. Nexus cuts each document into chunks before it indexes them.
IndexTo read documents, cut them into chunks, and add the chunks to the knowledge store.
Semantic searchSearch by meaning. The question and the chunks are compared as meanings, not as exact words.
Claude Code
ToolAn action that Claude can take. Nexus adds tools to Claude Code. When Claude uses one, Claude Code shows the tool name.
SkillA named procedure that Claude follows. You start one with a command such as /conexus:query.
SessionOne run of Claude Code. The scratch store belongs to one session.
RDRResearch, Design, Review. A short document that records a decision before the code is written.
nxThe Nexus terminal command. Claude runs it for you when needed. You can also run it yourself.
1

Start a session

5 min

When Claude Code starts with the Nexus plugin, Nexus gives Claude some context before you type anything. You do not see this context. This lesson shows what it contains, and introduces the three stores that all later lessons use.

What Claude receives when the session starts

Run claude in your project. Before your first message, the plugin gives Claude several blocks of text. Claude Code does not show them to you. To see them, ask Claude:

What context did the Nexus plugin give you at the start of this session?

Claude repeats the blocks. The important ones are:

BlockContent
T2 MemoryThe memory entries for this project. Empty in a new project. Lesson 3 adds the first one.
Ready BeadsOpen tasks from the bd task tracker, if the project uses it.
nx CapabilitiesA short list of the Nexus tools that Claude can use.
Knowledge MapThe main subjects in the knowledge store, with the number of chunks for each.

If Claude reports a block with the heading "nx Preflight: FAILED", a part of the install is missing. Type /conexus:nx-preflight. It tells you which part.

The three stores

Every Nexus tool works on one of three stores. The stores differ in one way: how long the data lives.

T1 · lives for one sessionScratch

Notes for the current session. Nexus deletes them when the session ends, unless you promote them.

T2 · lives for one projectMemory

Facts and decisions about a project. Each entry has a project name and a title. An entry lives 30 days by default. Each read makes it live longer. You can also make it permanent.

T3 · lives permanentlyKnowledge

Indexed code, documents, PDFs, and notes. Claude finds them with semantic search.

Data moves in one direction only: scratch to memory, then memory to knowledge.

How to choose a store: ask how long the data must live. Only this session: scratch. This project, and you will look it up by name: memory. Permanently, and you will look it up by meaning: knowledge.

You do not need to name the store when you talk to Claude. Say what you want to keep and for how long. Claude chooses the store. The lessons below show the words that make the choice clear.

Investigate further

  • Ask Claude: "Which Nexus tools do you have, and what does each one do?"
  • Storage tiers: how the three stores work, and how the TTL grows with each read.
2

Index your repository, then search it

10 min

Indexing reads your repository and adds its chunks to the knowledge store. After that, Claude can answer "where is retry handled" by searching for meaning, instead of reading many files. This is the step that makes all later searches possible.

Index

Say to Claude
Index this repository into Nexus.
What Claude does

Claude runs the terminal command nx index repo . for you. Claude Code shows a Bash tool call with that command. The command reads every file, cuts it into chunks, and stores the chunks. On a large repository this takes a few minutes. At the end the output shows Done. and, after the first index, the topics that Nexus found.

If you index the same repository again later, Nexus skips files that did not change. The output then shows skipped: index fresh for them.

Search

Say to Claude
Use Nexus search: how are retries handled in this codebase?
What you see

Claude Code shows a tool call named search on the nexus server. The tool returns the best matching chunks, grouped by topic, with the file path and the line number of each chunk. Claude then answers your question from those chunks and names the files.

If Claude uses grep instead, say: "Use Nexus search, not grep." Grep finds exact words. Nexus search finds meaning, so it also finds code that does not contain the word "retry".

From the terminal, the same search is nx search "how are retries handled".

Investigate further

  • Ask Claude: "Search only the documentation, not the code, for how configuration is loaded." Claude limits the search to the docs group.
  • Ask Claude: "Which topics did Nexus find in this repository?" Claude runs nx taxonomy list.
  • Repo indexing: how files are classified and cut into chunks.
3

Memory: facts about your project

5 min

The memory store holds facts and decisions about a project. When a new session starts, Claude receives these entries first. This is how a decision from today is still known next month, in a new session, without you repeating it.

Say to Claude
Remember this in Nexus memory for this project, permanently, with the title "auth-tokens":
Auth uses JWT. Tokens expire after 24 hours. The refresh endpoint is /v2/refresh.
What you see

A tool call named memory_put on the nexus server, with the project name, the title auth-tokens, and the text. Claude confirms that the entry is stored.

Say to Claude, later or in a new session
What does Nexus memory say about authentication in this project?
What you see

A tool call named memory_search or memory_get. Claude answers with the stored text. In a new session, Claude also receives the entry in the "T2 Memory" block from lesson 1, before you ask.

Three rules for good entries: Put one fact in each entry. Give it a title that describes it, for example auth-tokens, not notes-3. Say "permanently" for facts that must stay. Without that word, the entry lives 30 days, and each read makes it live longer.

If you store an entry with the same title again, the new text replaces the old text. To change a fact, store it again. From the terminal: nx memory put "…" -p PROJECT -t TITLE --ttl permanent.

Investigate further

  • Ask Claude: "List all Nexus memory entries for this project."
  • Ask Claude: "Delete the memory entry auth-tokens." Then store it again to practice.
  • Configuration: heat-weighted T2 expiry: the exact rule for how reads extend the TTL.
4

Scratch: notes for this session only

5 min

The scratch store belongs to the current session. Nexus deletes it when the session ends. Claude and every helper agent that Claude starts share the same scratch store. It is the place for ideas and partial results while you work on a problem.

Say to Claude
Note in Nexus scratch: hypothesis, the unstable test is caused by clock skew between the two containers.
What you see

A tool call named scratch on the nexus server, with the action put. Claude confirms the entry. When Claude later starts a helper agent to investigate, that agent can read the same note and add its own findings.

Say to Claude, when the idea proves true
Promote that scratch note to Nexus memory for this project, with the title "flaky-test-cause".
What you see

A tool call named scratch_manage with the action promote. The note is now a memory entry and survives the session. If the memory store already has a similar entry with a different title, the tool reports overlap_detected. Then Claude, or you, can merge the two.

Scratch notes that you do not promote disappear when the session ends. This is the purpose of the store. From the terminal: nx scratch put "…" and nx scratch promote ID -p PROJECT -t TITLE.

Investigate further

  • Ask Claude: "Show all Nexus scratch notes from this session."
  • Storage tiers: T1: how a session is identified, and how helper agents share the store.
5

Knowledge: notes, documents, and the catalog

10 min

The knowledge store is permanent, and Claude searches it by meaning. In lesson 2 you added a repository. In this lesson you add a written note and a document. You also meet the catalog, which lists every document and the links between them.

A note in a subject collection

Say to Claude
Store this in Nexus knowledge, in the collection "distributed-systems", with the title "idempotency-keys-per-tenant":
Idempotency keys must be scoped per tenant. A global key space let two tenants collide in production (2026-03).
What you see

A tool call named store_put on the nexus server, with the collection, the title, and the text. Claude confirms the document ID. From now on, a search for "idempotency key collision" finds this note.

A collection is a subject. Name it after a subject that will exist for years: distributed-systems, postgres, team-process. Do not name it after a session, a task, or a program. Nexus refuses the names knowledge, notes, default, tmp, and test. If you do not know the existing collections, ask Claude: "List the Nexus collections."

Documents

Say to Claude
Index docs/design-notes.md and papers/replication-protocol.pdf into Nexus.
What Claude does

Claude runs nx index md for the Markdown file and nx index pdf for the PDF. Nexus chooses the correct PDF reader automatically, also for scanned PDFs. Both documents are now in the knowledge store and in the catalog.

The catalog

Nexus adds every repository, note, and document to the catalog. The catalog also records links between documents. A link has a type, for example cites, implements, or supersedes. Search finds text inside documents. The catalog answers two other questions: what documents exist, and how they are connected.

Say to Claude
Which documents in the Nexus catalog are linked to the replication protocol paper?
What you see

Tool calls on the nexus-catalog server: show or links. Claude lists the linked documents and the type of each link. In a new install there are few links yet. Links appear when Nexus enriches documents and when an RDR cites a source.

From the terminal: nx store put, nx index md, nx index pdf, and nx catalog links "TITLE".

Investigate further

  • Collections: the rules for collection names.
  • Document catalog: all link types, and how to add a link yourself.
  • Ask Claude: "Export the distributed-systems collection to a backup file." Claude runs nx store export.
6

Questions that need many documents

10 min

A normal question makes one or two searches. Some questions need more: compare what the documentation says with what the code does, or collect a pattern from many files. For these, the plugin has a skill that plans several steps and combines the results.

Say to Claude
/conexus:query Compare what the architecture docs say about caching with what the code actually does.
What you see

A tool call named nx_answer. It searches the documentation and the code, extracts the relevant facts from each, compares them, and returns one answer with sources. This takes longer than a normal search, usually 5 to 15 seconds and sometimes more.

Use /conexus:query when one search cannot hold the answer. For a simple question, a normal sentence to Claude is faster.

Other commands to know

TaskCommand
Understand a codebase that is new to you/conexus:analyze-code
Plan a feature before you write code/conexus:brainstorming-gate, then /conexus:create-plan
Review code before you commit it/conexus:review-code
Debug a problem after two failed tries/conexus:debug
Prepare the next session/conexus:continuation
Not sure which oneAsk Claude: "Read the using-nx-skills skill and tell me which skill fits my task."

At the end of a session, run /conexus:continuation. It writes a short text with the branch, the open work, and the active memory. Paste this text as the first message of the next session. The next session then continues where this one stopped.

7

Record a decision with an RDR

15 min

An RDR is a short document that you write before you write code. It records the problem, what you found out, the options, and the option you chose. When you close an RDR, Nexus indexes it into the knowledge store. Later, when you or Claude work on a similar decision, the old RDR appears in search.

When to write one

  • The problem has more than one good solution.
  • A bug needs a real cause, not a quick fix.
  • The change affects something that other people depend on.

Do not write one when the reason is clear from the code.

The steps

Say to Claude
/conexus:rdr-create             # create the document, status Draft
/conexus:rdr-research add 12    # add a finding, with a tag that says how sure you are
/conexus:rdr-gate 12            # optional: automatic checks and a critique
/conexus:rdr-accept 12          # lock the decision

Replace 12 with the number that rdr-create gives you. Make the RDR as long as the decision needs. For a bug fix, three sections are enough: Problem, Root Cause, Fix. Use the full template only for large design decisions with real options.

Accepting locks the record. While the RDR is a draft, change it as often as you want. After you accept it, it says what was decided. If the code later shows that the decision was wrong, do not edit the accepted RDR. Mark it as abandoned and write a new RDR with what you learned.

Investigate further

  • /conexus:rdr-list and /conexus:rdr-show: read the RDRs that already exist in a project.
  • RDR: the full template, the sections, and the status values.
  • The Nexus RDR directory: more than 200 real examples.
8

Maintenance

5 min

Three things keep Nexus working: a health check, the correct way to update, and a current index.

Health check

Say to Claude
Run nx doctor and tell me if anything is wrong.

Every line must show ✓. One line may say "credentials not set". This is normal for a local install. Inside Claude Code, /conexus:nx-preflight checks the plugin in the same way.

Update

Say to Claude
/conexus:upgrade

The skill shows what an update would change, then runs it. From the terminal, the same update is two commands: nx self install, then nx upgrade. Always run both.

Never update with uv tool install conexus. That command removes the local search model, and search then returns nothing. If this happened, nx self install repairs it.

Keep the index current

Say to Claude
Install the Nexus git hooks in this repository.

Claude runs nx hooks install. After that, git indexes the changed files after each commit. Without the hooks, say "Index this repository into Nexus" again after the code changes. Only changed files are indexed.

Investigate further

  • Ask Claude: "Show what nx upgrade would change, without running it." Claude runs nx upgrade --dry-run.
  • Getting started: troubleshooting: more problems and their fixes.

Complete

You know the three stores and how to choose one. You can ask Claude to index a repository and search it. You can keep facts in memory and working notes in scratch. You can store notes and documents in knowledge and find their links in the catalog. You know the commands for large questions, for RDRs, and for maintenance. Search results and session context get better as you index and record more.
