Nexus · getting started

Nexus Getting Started

Eight lessons, in dependency order, about an hour in total. Each gives the reason a command exists, the command, and the output it produces. Prerequisite: nx doctor reports no failures.

Not installed: see the install guide. Everything here runs locally and needs no API key.

1

Where things live

5 min · no typing

Every Nexus command operates on one of three stores. They differ by lifetime. Knowing the lifetime determines the command.

T1 · this sessionScratch

Working notes for the current session. Deleted at session end unless promoted.

nx scratch

T2 · this projectMemory

Project decisions and facts. Keyed by project and title. Default expiry 30 days, extended on read; permanent on request.

nx memory

T3 · foreverKnowledge

Indexed code, docs, PDFs, and durable notes. Retrieved by semantic search.

nx index · nx store · nx search

Entries move in one direction: scratch → memory with nx scratch promote, memory → knowledge with nx memory promote.

Selection rule: required lifetime. This session: scratch. This project, retrievable by name: memory. Indefinite, retrievable by meaning: knowledge.

Exercise: select the tier

Select T1, T2 or T3 for each case. The correct answer is shown after a selection.

A hypothesis formed during debugging: the flaky test is a clock-skew problem.
T1. Useful only for the current session. Promote it if confirmed.
Auth tokens expire after 24 h; the refresh endpoint is /v2/refresh. Needed by the team for months.
T2. A project fact retrieved by name. Use --ttl permanent.
A 40-page design paper on the replication protocol.
T3. Passages are retrieved by meaning. nx index pdf.
A source repository.
T3. nx index repo ., lesson 2.
Check: why does memory (T2) expire entries by default?
To keep the tier limited to facts still in use. Each read extends an entry's TTL (effective TTL = base × (1 + ln(reads + 1))), so consulted facts persist and unread ones expire. Facts that must persist regardless take --ttl permanent.
2

Index a repository and search it

10 min

Indexing populates the knowledge tier (T3) from a repository. Search then ranks chunks by semantic similarity to a natural-language query, so a question such as "where is retry handled" resolves without knowing identifiers.

Index

cd your-project
nx index repo .
What you should see
Registered /Users/you/your-project.
Indexing /Users/you/your-project…
  [1/412] retry.py — 6 chunks  (0.4s)        ← one line per file with --monitor; a progress bar otherwise
  …
Tip: run `nx hooks install` to auto-index this repo on every commit.
Done.

Files are chunked by structure (functions, classes, sections) before embedding. Topic discovery runs after the first index. On re-run, unchanged files are skipped and reported as skipped: index fresh.

Search

nx search "how are retries handled"
nx search "how are retries handled" --files       # just the file paths
nx search "config loading" --corpus docs          # only prose, not code
nx search "RetryPolicy" --hybrid                  # meaning + exact text (needs ripgrep)
What you should see
src/net/retry.py:41:class RetryPolicy:
src/net/retry.py:42:    """Exponential backoff with a jittered cap."""
src/net/retry.py:43:    def backoff(self, attempt: int) -> float:
…
src/net/client.py:88:def _send_with_retry(req, policy):

Each matching chunk prints as path:line:text, best match first, in grep's shape; --vimgrep emits path:line:col:text for editor quickfix lists. Queries are natural-language and ranked by meaning, not by keyword match.

Topics

nx taxonomy status
nx taxonomy list
What you should see
Taxonomy Status

  code__your-project…
    9 topics, 1 812 docs assigned (9 accepted)

Topics feed search ranking and are the grouping the MCP search tools present. Labels are generated when the claude CLI is on PATH.

Check: when is --hybrid appropriate?
When the query contains an exact identifier (class name, error string) and semantically related chunks are also wanted. Hybrid merges ripgrep matches with the embedding search. Plain search for questions; hybrid for identifiers.
3

Memory: project facts

5 min

Memory (T2) holds project decisions and facts. Every entry is keyed by project and title, so it is retrievable by name, and the Claude Code plugin loads the project's entries at session start.

nx memory put "Auth uses JWT; tokens expire after 24h; refresh at /v2/refresh" \
  -p myproject -t auth-tokens --ttl permanent
nx memory search "JWT" -p myproject
nx memory get -p myproject -t auth-tokens
nx memory list -p myproject
What you should see
Stored: myproject/auth-tokens (id=4471)
[4471] myproject/auth-tokens  (permanent, 2026-09-10T17:19:39Z)
  Auth uses JWT; tokens expire after 24h; refresh at /v2/refresh
Auth uses JWT; tokens expire after 24h; refresh at /v2/refresh

The confirmation, the search hit, then get, which prints content only and is suitable for piping.

Conventions: one fact per entry; a descriptive title (auth-tokens, not notes-3); one spelling of the project name. Writing the same project and title again replaces the entry.

Default TTL is 30 days, extended on each read. Use --ttl permanent for durable facts; leave the default for working context.

Check: an entry was written under the wrong title. How is it corrected?
Write it under the correct title, then nx memory delete the old one. There is no rename; upsert is keyed on project plus title.
4

Scratch: session notes

5 min

Scratch (T1) is scoped to the current session and deleted at its end. It holds hypotheses and intermediate findings that are not yet worth recording.

nx scratch put "working hypothesis: the cache TTL is too short" --tags cache
nx scratch list
nx scratch search "cache"
What you should see
Stored: 7b09cc46-0d91-4921-8353-dabb574f232f
[7b09cc46] cache  flagged=False
  working hypothesis: the cache TTL is too short

Promotion

nx scratch promote 7b09cc46 -p myproject -t cache-ttl-finding   # copy to memory now
nx scratch put "…" --persist -p myproject -t some-title        # or: flush to memory at session end

An ID prefix from nx scratch list suffices. Promotion reports overlap_detected when a similar memory entry exists under another title.

Check: what happens to unpromoted scratch at session end?
It is deleted. Promote entries worth keeping; the rest is discarded by design.
5

Knowledge: notes, documents, catalog

10 min

Knowledge (T3) is the permanent, semantically searched tier. Lesson 2 added a repository. This lesson adds written notes and documents, and introduces the catalog that registers all three.

A note under a subject collection

echo "Idempotency keys must be scoped per tenant; a global key space let two tenants collide in prod (2026-03)." \
  | nx store put - --collection distributed-systems --title "idempotency-keys-per-tenant" --tags "incident,design"
nx search "idempotency key collision"
What you should see
Stored: 9f2c…e41a  →  knowledge__distributed-systems…

The search returns the note near the top in the path:line:text shape of lesson 2, with the title in the path position.

Collections are subjects. A collection names a durable subject area: distributed-systems, postgres, team-process. Not a session, task, source application, or placeholder. The CLI refuses knowledge, notes, default, tmp and test. Check nx collection list before creating a new one.

Documents

nx index md ./docs/design-notes.md --corpus myproject
nx index pdf ./papers/replication-protocol.pdf --corpus papers
nx search "leader election under partition" --corpus papers -c

PDFs are routed to the appropriate extractor automatically, including scanned ones. --corpus names the document group; the docs collection is derived from it.

Catalog

Every repository, note and document is registered in the catalog, which records typed links between documents (cites, implements, supersedes). Search retrieves passages; the catalog answers inventory and relationship questions.

nx catalog search replication         # by title, author or path
nx catalog show "replication-protocol" # full entry with every link in and out
nx catalog links "replication-protocol"

Registration happens at index and store time. Links are added by enrichment and by RDR citations; the MCP query tool follows them.

Check: search or catalog for "which documents cite the replication paper"?
Catalog. The question is about relationships between documents, not passages within them. nx catalog links "replication-protocol", or /conexus:query, which traverses the same links.
Check: memory (T2) or knowledge (T3) for "the Postgres connection pool is sized at 40"?
Memory. A project fact retrieved by name, subject to change. A write-up of the sizing rationale with measurements belongs in knowledge under postgres.
6

The Claude Code plugin

10 min · Claude Code plugin

The plugin gives Claude Code the same three tiers through MCP tools. A session starts with the project's memory loaded, and agents retrieve from the store rather than crawling files.

Session start

Run claude in the indexed project. Session-start hooks surface the project's T2 memory, list ready beads, and check tooling. The fact stored in lesson 3 should appear in the opening context.

Scratch (lesson 4) is shared within the session: the operator and every agent Claude spawns read and write the same T1.

A retrieval question

Where do we handle retries, and what does our memory say about the auth tokens?

Expected tool calls: search and memory_get on the nexus MCP server. If Claude greps the tree instead, instruct it to use nexus search.

Entry points

TaskCommand
Analyze an unfamiliar codebase/conexus:analyze-code
Answer a question spanning many documents/conexus:query Compare what the docs say about caching with what the code does
Plan a feature before implementation/conexus:brainstorming-gate then /conexus:create-plan
Review code before committing/conexus:review-code
Debug after two failed attempts/conexus:debug
Write a handoff for the next session/conexus:continuation
Routing between theseThe using-nx-skills skill

Direct questions and /conexus:query cover most retrieval. The others apply when the task has a defined shape: a plan, a review, a persistent bug.

Session close: /conexus:continuation writes a handoff (branch, open work, active memory) that the next session takes as its first message.

Check: a direct question versus /conexus:query?
A direct question performs one or two lookups. /conexus:query plans a multi-step retrieval (search several corpora, extract, compare, synthesize) for answers that must be reduced from many documents.

RDR: recording a decision

15 min

An RDR (Research, Design, Review) is a specification written before implementation. It records the problem, research, alternatives and chosen approach, and is indexed into knowledge on close, so prior decisions surface during later design work.

Criteria

Write one when the problem has more than one viable solution, when a bug needs root-cause analysis rather than a patch, or when the change affects something others depend on. Skip it when the rationale is evident from the code.

Lifecycle, in Claude Code

/conexus:rdr-create             # scaffold with metadata, status Draft
/conexus:rdr-research add 12    # append a finding with an evidence tag, as you learn
/conexus:rdr-gate 12            # optional: structure check, assumption audit, critique
/conexus:rdr-accept 12          # lock the decision

Depth matches the decision. A bug fix: Problem, Root Cause, Fix. The full template is for architectural decisions with real alternatives.

Acceptance locks the record. Iterate freely while drafting. After acceptance the RDR states what was decided. If implementation invalidates it, mark it abandoned and write a successor; do not edit it to match what shipped.

Retrieval

Closed RDRs are indexed into knowledge. Research on a similar decision later, by an operator or by Claude, retrieves the prior record.

Check: implementation shows the accepted design does not work. What changes in the RDR?
Its status only: abandoned. A new RDR records what was learned. Rewriting an accepted RDR to match the outcome destroys the record it exists to keep.
8

Maintenance

5 min

Three diagnostic commands, the update procedure, and re-indexing.

nx doctor              # every row ✓; the first diagnostic in every case
nx taxonomy status     # topics per collection; empty topics mean discovery never ran
nx collection list     # what is actually indexed, and how big

Updating

nx self install
nx upgrade

Both commands, every time. Never upgrade with uv tool install conexus: it resets the environment and drops the local embedder, after which search returns nothing. nx self install repairs that state.

Re-indexing

nx index repo . re-indexes changed files only. nx hooks install adds a git hook that runs it on commit.

Check: search returns nothing. First two diagnostics?
nx doctor, then whether the last upgrade was a bare uv tool install. nx self install repairs the second.
