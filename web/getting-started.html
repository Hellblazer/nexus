Nexus Getting Started

You do all of this inside Claude Code. You describe what you want. Claude chooses the Nexus tools and skills for you. Each lesson shows the instruction to give, what Claude does, and what you see. Eleven lessons, about ninety minutes.

Words in <ORANGE CAPITALS IN ANGLE BRACKETS> are placeholders. Replace them with something from your own project before you send the instruction.

Before you start: install Nexus and the plugin with the install guide. Then open a terminal in a project of yours and run claude. Every lesson happens in that Claude Code session.

The lessons use a few words with one fixed meaning. Open a group to read them.

Where data lives
StoreA place where Nexus keeps data. There are three stores: scratch, memory, and knowledge.
EntryOne item in the scratch store or the memory store.
DocumentOne item in the knowledge store: a file from a repository, a note, or a PDF.
CollectionA named group of documents in the knowledge store, for example distributed-systems.
CatalogThe list of all documents and the links between them.
TTLTime to live. How long an entry stays before Nexus deletes it.
PromoteTo copy an entry from one store to the next store. Scratch to memory, or memory to knowledge.
Finding things
ChunkA piece of a document. Nexus cuts each document into chunks before it indexes them.
IndexTo read documents, cut them into chunks, and add the chunks to the knowledge store.
Semantic searchSearch by meaning. The question and the chunks are compared as meanings, not as exact words.
Claude Code
ToolAn action that Claude can take. Nexus adds tools to Claude Code. When Claude uses one, Claude Code shows the tool name.
SkillA named procedure that Claude follows for one kind of situation. Claude chooses it from what you say. A command such as /conexus:query starts it directly.
SessionOne run of Claude Code. The scratch store belongs to one session.
RenderingA readable document, in Markdown or as a web page, that Claude writes from what is in the stores at that moment.
RDRResearch, Design, Review. A short document that records a decision before the code is written.
nxThe Nexus terminal command. Claude runs it for you when needed. You can also run it yourself.
1

Start a session

10 min

When Claude Code starts with the Nexus plugin, Nexus gives Claude some context before you type anything. You do not see this context. This lesson shows what it contains, and introduces the three stores that all later lessons use.

What Claude receives when the session starts

Run claude in your project. Before your first message, the plugin gives Claude several blocks of text. Claude Code does not show them to you. To see them, ask Claude:

What context did the Nexus plugin give you at the start of this session?

Claude repeats the blocks. The important ones are:

BlockContent
T2 MemoryThe memory entries for this project. Empty in a new project. Claude fills it as it works. Lesson 4 explains.
Ready BeadsOpen tasks from the bd task tracker, if the project uses it.
nx CapabilitiesA short list of the Nexus tools that Claude can use.
Knowledge MapThe main subjects in the knowledge store, with the number of chunks for each.

Not every project has every block. A project without the bd task tracker has no Ready Beads block. A project without RDRs has no RDR block. A new install has an empty T2 Memory block and a short Knowledge Map. This is normal.

If Claude reports a block with the heading "nx Preflight: FAILED", a part of the install is missing. Type /conexus:nx-preflight. It tells you which part.

Why Claude receives this context

The context is how Nexus works. Claude does not follow a fixed script. It reads the situation and chooses what to do. The blocks above give it what it needs to choose well:

  • The memory block tells Claude what was decided before, so it does not decide again from zero.
  • The capabilities block tells Claude which tools exist, so it searches the store instead of reading every file.
  • A guidance block describes situations, not commands: "something is broken", "a plan needs a check", "an answer must come from many documents". For each situation it names the skill that fits. Claude matches your request to a situation and uses the skill by itself.

What this means for you: describe what you want in your own words. You do not need to learn a command for each task. If you say "this test fails and I do not know why", Claude recognizes a debugging situation and follows the debugging skill. If you say "is what the docs say about caching true in the code", Claude recognizes a question that needs many documents and plans a search. The /conexus:… commands in later lessons are shortcuts. They are never required. The language model does the routing.

This also means Claude adapts to how you work. A person who writes short instructions and a person who thinks aloud in long paragraphs get the same tools, chosen from what they said. The prompts in these lessons are examples of phrasing, not scripts. Your own words work the same.

The three stores

Every Nexus tool works on one of three stores. The stores differ in one way: how long the data lives.

T1 · lives for one sessionScratch

Notes for the current session. Nexus deletes them when the session ends, unless you promote them.

T2 · lives for one projectMemory

Facts and decisions about a project. Each entry has a project name and a title. An entry lives 30 days by default. Each read makes it live longer. You can also make it permanent.

T3 · lives permanentlyKnowledge

Indexed code, documents, PDFs, and notes. Claude finds them with semantic search.

Data moves in one direction only: scratch to memory, then memory to knowledge.

How to choose a store: ask how long the data must live. Only this session: scratch. This project, and you will look it up by name: memory. Permanently, and you will look it up by meaning: knowledge.

You rarely choose a store yourself. Claude does it as it works, following the plugin's guidance. The rule above is so you can read what Claude did and see whether it was right.

Investigate further

  • Ask Claude: "Which Nexus tools do you have, and what does each one do?"
  • Storage tiers: how the three stores work, and how the TTL grows with each read.
2

End a session, start the next one

15 min

Work with Nexus happens in many sessions, not one. What connects them is a small habit at the end of each session. Learn it now, before the first real work, because every later lesson ends with it.

A Claude Code session has a limited memory of the conversation. When it gets long, Claude Code compresses it, and detail is lost. When you close the session or type /clear, the conversation is gone. Memory (lesson 3) keeps the facts and decisions. It does not keep "where was I": which branch, what was half done, what to do first tomorrow. That is what /conexus:continuation is for.

You might say, when you are about to stop
/conexus:continuation
What Claude does

Claude writes one file under /tmp with the state of the work. The file has a fixed set of sections:

  • What was finished in this session: commits, closed tasks, memory entries written.
  • Where the state lives: the branch, the files, the memory entries, the task IDs.
  • The first actions for the next session, as commands that can be run as they are.
  • Open work, and what blocks it.
  • Decisions from this session that the next session must keep.
  • Things the next session must not do.
  • What went wrong in this session, so the next one avoids it.

Then Claude answers with three lines only. The third line is a command of the form cat /tmp/…. Copy that line.

In the next session

Type /clear, or start a new session. Paste the copied line as the first message. Claude reads the file, runs the first actions, and continues where the last session stopped. It also receives the memory block from lesson 1, so it has both the facts and the position.

When to run it

Three moments. In each one, run /conexus:continuation first, and then do the thing.

MomentHow you notice itThen
You are about to stop workingEnd of the day, a meeting, lunch. Anything where the terminal will sit for more than an hour.Run it. Then close the terminal or leave the session open. Either is fine.
You finished a task, or are about to change subjectThe task is committed, or the next task has nothing to do with the current one: a different branch, a different part of the system.Run it. Then /clear. Start the next task in the empty session. Paste the handoff only when you return to the old subject.
The context window is filling/context shows it well used, or Claude Code shows its warning, or Claude asks about things you told it an hour ago.Run it. Then /clear and paste the handoff. You lose nothing, and the session is fast again. Details below.

The context window, concretely

Claude works from a fixed amount of text called the context window. Everything in the session goes into it: your messages, Claude's answers, every file Claude read, every command output, every search result, and the blocks the plugin added at the start. Nothing leaves by itself. So the window fills, and a full window has two costs. Claude reasons less well when the useful part of the window is buried in old tool output. And when the window is full, Claude Code compresses the conversation without asking. The compressed version keeps the outline and loses the detail: exact file names, the reason for a decision, what was tried and did not work.

See how full it is
/context

Claude Code shows how much of the window is used and by what. Look at it when a session has run for a while, or when an answer feels off. When the window is close to full, Claude Code also shows a warning above the input line. The warning is the last call. Run the continuation when you see it, not after.

Keep it lean on purpose. Do not wait for the warning. The habit that works: one unit of work per session. Finish the task, run /conexus:continuation, /clear, and start the next task in an empty window with only the handoff and the plugin's context in it. A session that stays lean answers faster, costs less, and does not lose detail to compression. The continuation is what makes clearing free: nothing you need is in the window that is not also in the file or in memory.

What fills the window fastest: reading large files, long command outputs, and wide searches. If Claude is about to read a big file, ask for the part you need. If a command prints thousands of lines, ask Claude to summarize it instead of showing it. This is not fussiness. It is the difference between a session that lasts an afternoon and one that compresses before lunch.

Compression by hand, /compact, exists too. It is better than the automatic one because you choose the moment, but it still loses detail. Continuation and /clear lose nothing. Prefer them.

If you forget: nothing is lost that was in memory (lesson 4). Start the new session and ask "What do you know about this project, and what was I working on?" Claude answers from memory. The last continuation file, if there was one, is still in /tmp until the next reboot. Ask Claude to find it.

What it looks like, end to end

An example. The project is a small web service. The session fixed one bug and started on a second.

End of the first session
You:    /conexus:continuation

Claude: Paste this in the next session after /clear:

        cat /tmp/nexus-continuation-orders-api-2026-09-10.md

You copy the third line. Then you type /clear, or you close the terminal and come back the next day.

Start of the next session
You:    cat /tmp/nexus-continuation-orders-api-2026-09-10.md

Claude: Reading the handoff.
        Finished yesterday: the timeout bug in the order endpoint (commit 4f2a91c,
        task orders-17 closed). Open: the duplicate-webhook bug, task orders-18,
        with the cause found (retries are not idempotent) and the fix not yet written.
        First actions from the handoff: I am on branch fix/orders-18, the tree is
        clean, and the memory entry webhook-idempotency has the analysis.
        Continuing with the fix. Starting with the test for the duplicate case.

Claude ran the first actions from the file (checked the branch, checked that the tree was clean, read the memory entry it named) and continued the open work. You typed one line. The names in this example are made up. The shape is what you will see.

Two stores, two jobs. Memory holds what is true about the project, for weeks. The continuation file holds where the work stands, for the next session only. Use /conexus:continuation at the three moments above. It costs a few seconds. Without it, the next session spends its first minutes finding out what this one already knew.

You can give a topic: /conexus:continuation <TOPIC>. The file is then named after the topic, which helps when you work on several things in parallel. The files live in /tmp and disappear at the next reboot. They are a handoff, not a record. The record is memory.

Investigate further

  • Read one continuation file after Claude writes it. The sections are plain text. If a section is empty or wrong, tell Claude before you close.
  • The continuation skill: the exact list of sections Claude writes, and why the answer is three lines.
3

Index your repository, then search it

10 min

Indexing reads your repository and adds its chunks to the knowledge store. After that, Claude can answer questions about the code by searching for meaning, instead of reading many files. This is the step that makes all later searches possible.

Index

You might say
Index this repository into Nexus.
What Claude does

Claude runs the terminal command nx index repo . for you. Claude Code shows a Bash tool call with that command. The command reads every file, cuts it into chunks, and stores the chunks. On a large repository this takes a few minutes. At the end the output shows Done. and, after the first index, the topics that Nexus found.

If you index the same repository again later, Nexus skips files that did not change. The output then shows skipped: index fresh for them.

Find out what is in the index

You know your repository. The lessons do not. So the first question after indexing is one that works for every repository: what did Nexus find?

You might say
Which topics did Nexus find in this repository? List them with a short description of each.
What you see

Claude runs nx taxonomy list and describes each topic. The topics are groups of related code that Nexus found by itself. They are a map of your repository. Pick one topic that interests you for the next step.

Search one topic

You might say
Use Nexus search to show me the main files for the topic "<TOPIC>", and explain in a few sentences what they do.

Replace <TOPIC> with a topic from the list.

What you see

Claude Code shows a tool call named search on the nexus server. The tool returns the best matching chunks, with the file path and the line number of each. Claude answers from those chunks and names the files. Open one of the files to check that the answer is correct.

If Claude uses grep instead, say: "Use Nexus search, not grep." Grep finds exact words. Nexus search finds meaning, so it also finds code that uses different words for the same idea.

Now ask your own questions

Search works best with a question in normal language, not with a keyword. Three forms that work for any repository:

Where in this codebase is <SOMETHING YOU KNOW EXISTS> handled?
Is there any code in this repository that <DOES SOMETHING YOU ARE NOT SURE ABOUT>?
Which files deal with <A CONCEPT>, and how are they connected?

Start with something you know exists. Check that Nexus finds it. Then ask about something you are not sure about. The second kind of question is where semantic search helps most. It finds code that you did not know the name of.

From the terminal, a search is nx search "your question". Add --corpus docs to search only documentation, or --files to list only file paths.

Investigate further

  • Ask Claude: "Search only the documentation, not the code, for <A CONCEPT>." Claude limits the search to the docs group.
  • Ask Claude: "Search for <AN EXACT CLASS OR FUNCTION NAME> with hybrid search." Hybrid search combines exact text matches with semantic matches.
  • Repo indexing: how files are classified and cut into chunks.
4

Memory: what Claude keeps between sessions

5 min

The memory store holds facts and decisions about a project. Claude writes to it by itself while it works: a decision it made, a finding from an investigation, the state of the work at the end of a session. When a new session starts, Claude receives these entries first. Memory is not a to-do list or a place for your own notes. Claude fills it, and Claude reads it. You do not manage this store. You work, and it fills.

How it fills

Nothing to do here except work. Spend a session with Claude on a real task: fix a bug, add a feature, investigate a question. As it works, Claude records what it decided and what it found. At the end, if you close the session with /conexus:continuation (lesson 2), the state of the work is recorded too. Helper agents that Claude starts write their results to the same store.

Each entry has a project name and a title. An entry lives 30 days by default. Each time Claude reads it, it lives longer. So facts that stay useful stay, and facts that nobody reads expire.

How you notice it

Start a new session on the same project the next day. Claude already knows what was decided. You see this in how it answers: it refers to yesterday's decision without you repeating it. If you want to check directly, ask in any words you like. Something like:

What do you already know about this project from earlier sessions?

Claude answers from the memory block it received at session start, and may call memory_search or memory_get for details. In a brand-new project the answer is "nothing yet".

When you correct it

Sometimes Claude remembers something that is wrong or out of date, or does not know a fact that is not in the code, for example a decision made in a meeting. Then tell it, in conversation, the way you would tell a colleague: "that was changed last week, we use X now" or "for the record, the team decided Y". Claude updates the store. You see a memory_put tool call. You do not need a special phrase.

From the terminal: nx memory list -p PROJECT shows every entry for a project.

Investigate further

  • After a week of sessions, ask Claude to list what it remembers about the project, with the age of each entry. Delete what is stale.
  • Storage tiers: T2: how the TTL grows with each read, and how entries move on to knowledge.
5

Scratch: how Claude and its agents share notes

5 min

The scratch store belongs to the current session. Claude uses it as a shared notepad. When Claude starts helper agents to investigate a problem, each agent reads and writes the same scratch store. That is how the agents coordinate. Nexus deletes the store when the session ends. You do not write to it. It is useful to know that it exists, and what it looks like while it is in use.

Where you see it

Give Claude a task that takes several steps, for example an investigation of a bug that has more than one possible cause, or /conexus:analyze-code on a part of the codebase. Watch the tool calls. Between the searches and file reads you see calls named scratch on the nexus server: Claude and its agents writing hypotheses and partial results for each other. When the task ends, the notes have served their purpose.

If you are curious what is in there at some moment, ask. Any phrasing works: "what have you noted so far", "what are the agents finding". Claude lists the notes.

What survives the session

Most scratch notes disappear at the end. That is the purpose of the store. A hypothesis that proved true does not stay a scratch note: Claude promotes it to memory during the session, or marks it, and the plugin copies it to memory at session end. You see this as a scratch_manage call with the action promote. If you think a finding is worth keeping and Claude has not kept it, say so in passing. "Keep that" is enough.

From the terminal: nx scratch list shows the notes of the current session.

Investigate further

  • Storage tiers: T1: how a session is identified, and how agents share the store.
6

Knowledge: notes, documents, and the catalog

10 min

The knowledge store is permanent, and Claude searches it by meaning. In lesson 3 you added a repository. In this lesson you add a written note and a document. You also meet the catalog, which lists every document and the links between them.

A note in a subject collection

You might say
Store this in Nexus knowledge, in the collection "<SUBJECT>", with the title "<SHORT-TITLE>":
<A LESSON YOU LEARNED THAT IS TRUE BEYOND THIS PROJECT>

Example: collection distributed-systems, title idempotency-keys-per-tenant, text "Idempotency keys must be scoped per tenant. A global key space let two tenants collide in production."

What you see

A tool call named store_put on the nexus server, with the collection, the title, and the text. Claude confirms the document ID. From now on, a search about that subject finds this note, in any project.

A collection is a subject. Name it after a subject that will exist for years: distributed-systems, postgres, team-process. Do not name it after a session, a task, or a program. Nexus refuses the names knowledge, notes, default, tmp, and test. If you do not know the existing collections, ask Claude: "List the Nexus collections."

Documents

You might say
Index <PATH/TO/A-MARKDOWN-FILE.md> and <PATH/TO/A-PAPER.pdf> into Nexus.
What Claude does

Claude runs nx index md for the Markdown file and nx index pdf for the PDF. Nexus chooses the correct PDF reader automatically, also for scanned PDFs. Both documents are now in the knowledge store and in the catalog.

The catalog

Nexus adds every repository, note, and document to the catalog. The catalog also records links between documents. A link has a type, for example cites, implements, or supersedes. Search finds text inside documents. The catalog answers two other questions: what documents exist, and how they are connected.

You might say
Which documents in the Nexus catalog are linked to <THE TITLE OF THE PAPER>?
What you see

Tool calls on the nexus-catalog server: show or links. Claude lists the linked documents and the type of each link. In a new install there are few links yet. Links appear when Nexus enriches documents and when an RDR cites a source.

From the terminal: nx store put, nx index md, nx index pdf, and nx catalog links "TITLE".

Investigate further

  • Collections: the rules for collection names.
  • Document catalog: all link types, and how to add a link yourself.
  • Ask Claude: "Export the <SUBJECT> collection to a backup file." Claude runs nx store export.
7

Explore: research, links, and the topic map

20 min

The lessons so far put things into Nexus and took them out again. This lesson is the loop that Nexus is built for: you ask, Claude searches, you follow what it finds, you connect it to other things, and the store gets better each time. Every step here is a conversation, not a command.

Research a subject

You might say
/conexus:research <A SUBJECT THAT YOUR PROJECT DEPENDS ON>
What you see

Claude starts a research agent. The agent searches the knowledge store first, then the web, then your code. Claude Code shows the agent's tool calls: search, query, web searches, and at the end store_put. The result is a summary with sources, and the findings are saved in the knowledge store. The next search on that subject finds them.

Example subjects: the consensus protocol your database uses, the retry rules of an API you call, a library your build depends on. Pick something you want to understand better, not something you already know.

Follow what you found

A research result names documents and files. Each of them is a place to continue. Ask about one:

Open <ONE DOCUMENT OR FILE FROM THE RESULT> and tell me what else in the store is related to it.
What you see

Claude calls show and links on the nexus-catalog server, and search for related chunks. It tells you what the document is, what links to it, and what is similar. Then ask about one of those. This is how you move through the store: from one document to its neighbours, without knowing the names in advance.

Connect a document to code

The catalog records links between documents. Most links appear by themselves: an indexed paper cites other papers, an RDR cites its sources. You can also add one when you know a connection that Nexus does not.

You might say
Link <THE PAPER OR DESIGN DOCUMENT> to <THE FILE OR MODULE THAT IMPLEMENTS IT> with an "implements" link.
What you see

A tool call named link on the nexus-catalog server, with the two documents and the type implements. From now on, a question about the design finds the code, and a question about the code finds the design. Ask: "What implements <THE DESIGN DOCUMENT>?" Claude follows the link.

Link types: cites, implements, supersedes, relates, and others. If you index papers, ask Claude to "enrich the <COLLECTION> collection with bibliographic data". Claude runs nx enrich bib, which looks up each paper and adds cites links automatically.

Shape the topic map

In lesson 3 you saw the topics that Nexus found in your repository. Topics are not fixed. You can look at them, question them, and change them.

You might say
Show me the topic map for this project. Which topics appear in both the code and the documentation?
What you see

Claude runs nx taxonomy list and nx taxonomy hubs. The hubs are topics that connect several collections. They are often the most important ideas in the project. Then narrow a search to one topic: "Search for <A QUESTION> inside the topic <TOPIC> only." Claude passes the topic to the search tool, and results outside that topic are excluded.

When a topic is wrong, say so: "The topic <TOPIC> should be called <BETTER NAME>." or "Assign <DOCUMENT> to the topic <TOPIC>." Claude runs nx taxonomy assign. For a full review of every topic, nx taxonomy review in the terminal walks through them one by one and lets you accept, rename, or merge each.

The loop: ask a question. Look at what Claude found. Ask about one of the results. Connect what belongs together. Repeat. Each search, link, and topic you touch makes the next answer better, for you and for Claude.

Investigate further

  • Document catalog: all link types, and how links change search ranking.
  • Topic taxonomy: how topics are found, labelled, and reviewed.
  • Ask Claude: "Which topics have documents from more than one collection, and what connects them?"
  • Querying guide: how the query tool follows links while it searches.
8

Render and iterate

15 min

After some sessions, the stores hold a lot about a subject: findings in knowledge, decisions in memory, links in the catalog. It is spread over many entries, and Claude manages them. When you want to see the whole picture, you ask for a rendering: one readable document written from the current state of the stores. Then you change it, Claude carries the changes back into the stores, and you ask again. The document and the stores stay in agreement. This is how most design work with Nexus is done.

Ask for a rendering

You might say
Render everything we have on <A SUBJECT YOU HAVE WORKED ON> as a Markdown document: what we know, what we decided, and what is still open.
What you see

Claude collects the material: memory_search and memory_get for the decisions, search and query for the findings, links on the catalog for what is connected. Then it writes one file. The result is not a copy of the entries. It is a document with a structure, written for a reader, from what the entries say.

Ask for the form that suits you. A Markdown file in the repository is easy to edit and to commit. A web page (Claude Code can publish one as an artifact) is easier to read and to share. Both are renderings of the same state.

Change it

Read the rendering. Where it is wrong or incomplete, change it in the way that is natural for you:

  • Edit the file directly, then tell Claude: "I changed the section on <TOPIC>, update the stores."
  • Or say what is wrong in conversation: "the second decision is out of date, we dropped that in March", "add the constraint about <X>", "this section is too long".
  • Or, on a web page, leave comments on the parts you disagree with and ask Claude to work through them.
What you see

Claude changes the document, and then writes the change back to where it belongs: a corrected decision goes to memory with memory_put, a new finding goes to knowledge with store_put, a new connection becomes a catalog link. You see those calls after the file edit. This step is what keeps the stores true. Without it, the document and the stores drift apart, and the next session works from the old state.

Ask again

Later, after more work, ask for the rendering again. Claude writes it from the current state, so it includes what changed since the last one: what you edited, what the sessions in between decided, what the research found. Compare it with the previous rendering if you want to see the movement.

The rhythm: work, and the stores fill. Render, and you see the whole. Change the rendering, and the stores follow. Render again. An RDR (lesson 10) is a rendering of one decision, with a fixed form and a lifecycle. This lesson is the general case.

Investigate further

  • Ask for two renderings of the same subject a week apart. Ask Claude to show the differences.
  • Ask for a rendering aimed at a reader who is not you: "write this for a new team member". The material is the same. The document is not.
  • Plan-centric retrieval: how Claude collects material from several stores for one document.
9

Questions that need many documents

10 min

A normal question makes one or two searches. Some questions need more: compare what the documentation says with what the code does, or collect a pattern from many files. For these, the plugin has a skill that plans several steps and combines the results.

You might say
/conexus:query Compare what the documentation says about <A CONCEPT FROM LESSON 2> with what the code actually does.
What you see

A tool call named nx_answer. It searches the documentation and the code, extracts the relevant facts from each, compares them, and returns one answer with sources. This takes longer than a normal search, usually 5 to 15 seconds and sometimes more.

Use /conexus:query when one search cannot hold the answer. For a simple question, a normal sentence to Claude is faster. You can also ask the large question in plain words. Claude recognizes it and plans the search without the command.

Other commands to know

Each command below starts one skill directly. You can also describe the task in your own words, and Claude picks the same skill. The commands are useful when you want to be certain which skill runs.

Plan a feature before you write code/conexus:brainstorming-gate, then /conexus:create-plan
Review code before you commit it/conexus:review-code
Debug a problem after two failed tries/conexus:debug
Hand the work to the next session/conexus:continuation, lesson 2
Not sure which oneAsk Claude: "Read the using-nx-skills skill and tell me which skill fits my task."

10

Record a decision with an RDR

15 min

This lesson is the short version. The full working practice, from the first conversation to the close across many sessions, is its own page: Working with RDRs.

An RDR is a short document that you write before you write code. It records the problem, what you found out, the options, and the option you chose. When you close an RDR, Nexus indexes it into the knowledge store. Later, when you or Claude work on a similar decision, the old RDR appears in search.

When to write one

  • The problem has more than one good solution.
  • A bug needs a real cause, not a quick fix.
  • The change affects something that other people depend on.

Do not write one when the reason is clear from the code.

The steps

You might say
/conexus:rdr-create             # create the document, status Draft
/conexus:rdr-research add 12    # add a finding, with a tag that says how sure you are
/conexus:rdr-gate 12            # optional: automatic checks and a critique
/conexus:rdr-accept 12          # lock the decision

Replace 12 with the number that rdr-create gives you. Make the RDR as long as the decision needs. For a bug fix, three sections are enough: Problem, Root Cause, Fix. Use the full template only for large design decisions with real options.

Accepting locks the record. While the RDR is a draft, change it as often as you want. After you accept it, it says what was decided. If the code later shows that the decision was wrong, do not edit the accepted RDR. Mark it as abandoned and write a new RDR with what you learned.

  • /conexus:rdr-list and /conexus:rdr-show: read the RDRs that already exist in a project.

11

Maintenance

5 min

Three things keep Nexus working: a health check, the correct way to update, and a current index.

Health check

You might say
Run nx doctor and tell me if anything is wrong.

Every line must show ✓. One line may say "credentials not set". This is normal for a local install. Inside Claude Code, /conexus:nx-preflight checks the plugin in the same way.

Update

You might say
/conexus:upgrade

The skill shows what an update would change, then runs it. From the terminal, the same update is two commands: nx self install, then nx upgrade. Always run both.

Never update with uv tool install conexus. That command removes the local search model, and search then returns nothing. If this happened, nx self install repairs it.

Keep the index current

You might say
Install the Nexus git hooks in this repository.

Claude runs nx hooks install. After that, git indexes the changed files after each commit. Without the hooks, say "Index this repository into Nexus" again after the code changes. Only changed files are indexed.

Investigate further

  • Ask Claude: "Show what nx upgrade would change, without running it." Claude runs nx upgrade --dry-run.
  • Getting started: troubleshooting: more problems and their fixes.

You know the three stores and how to choose one. You can ask Claude to index a repository and search it. You know what Claude keeps in memory and scratch, and how to look inside. You can store notes and documents in knowledge, research a subject, follow and add links, and shape the topic map. You can ask for a rendering of a subject, change it, and have the stores follow. You know the commands for large questions, for RDRs, and for maintenance. Search results and session context get better as you index and record more.
