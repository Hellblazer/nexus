Nexus · getting started

Your First Hour with Nexus

You have nx doctor showing all ticks. This is the hour that turns that into a habit: eight short lessons, in the order the pieces depend on each other, each one a thing you type and a thing you should see. Tick a lesson off when it clicks.

Not installed yet? Start with the install guide. Everything here runs fully local and needs no API key.

1

Where things live

5 min · no typing

Everything else in Nexus is a verb on one of three places. Learn the three by lifetime and you will never wonder which command to reach for.

T1 · this sessionScratch

Working notes while you debug or explore. Gone when the session ends unless you promote them.

nx scratch

T2 · this projectMemory

Decisions and facts that must survive restarts. Keyed by project and title. Expire after 30 days unless read or made permanent.

nx memory

T3 · foreverKnowledge

Indexed code, docs, PDFs, and durable notes. Searched by meaning, grouped by topic.

nx index · nx store · nx search

Ideas move rightwards as they prove out: scratch → memory with nx scratch promote, memory → knowledge with nx memory promote. Nothing moves left.

The one rule: ask "how long does this need to live?" Today: scratch. This project, for a while: memory. Anyone, any time, found by meaning: knowledge.

Try it: which tier?

Click T1, T2 or T3 for each. Wrong picks fade so you can see the right one.

"Hypothesis: the flaky test is a clock-skew problem." You are mid-debug.
T1. It is only useful for the next hour. If it turns out true, promote it.
"Auth tokens expire after 24 h; the refresh endpoint is /v2/refresh." Your teammates will need this next month.
T2. A project fact, looked up by name. Make it permanent with --ttl permanent.
The team's 40-page design paper on the replication protocol.
T3. You will want to find passages in it by meaning, not remember a title. nx index pdf.
Your own repository.
T3. nx index repo . is the first thing most people do, and lesson 2.
Self-check: why does memory (T2) have a 30-day default expiry at all?
So the tier stays a record of what is still true. Entries that get read live longer automatically (heat-weighted TTL), so a fact people rely on never expires on its own, while stale notes clear themselves. Anything you know must persist, mark --ttl permanent.
2

Index a repo, then search it by meaning

10 min

This is the first real win, and the one everything else builds on. After this, "where is the code that handles retries" is a one-line question instead of a grep expedition.

Index

cd your-project
nx index repo .
What you should see
Registered /Users/you/your-project.
Indexing /Users/you/your-project…
  [1/412] retry.py — 6 chunks  (0.4s)        ← one line per file with --monitor; a progress bar otherwise
  …
Tip: run `nx hooks install` to auto-index this repo on every commit.
Done.

Files are split by structure (functions, classes, sections) before embedding, so results land on the unit you meant. Topic discovery runs at the end of the first index. On a re-run unchanged files are skipped and reported as skipped: index fresh, so re-indexing is cheap.

Search

nx search "how are retries handled"
nx search "how are retries handled" --files       # just the file paths
nx search "config loading" --corpus docs          # only prose, not code
nx search "RetryPolicy" --hybrid                  # meaning + exact text (needs ripgrep)
What you should see
src/net/retry.py:41:class RetryPolicy:
src/net/retry.py:42:    """Exponential backoff with a jittered cap."""
src/net/retry.py:43:    def backoff(self, attempt: int) -> float:
…
src/net/client.py:88:def _send_with_retry(req, policy):

Each matching chunk prints as path:line:text, best match first, the same shape grep gives you, so it drops straight into an editor's quickfix list (--vimgrep) or a pipe. Type a question the way you would ask a colleague; this is not a keyword box, and the ranking is by meaning.

See the topic map

nx taxonomy status
nx taxonomy list
What you should see
Taxonomy Status

  code__your-project…
    9 topics, 1 812 docs assigned (9 accepted)

Topics boost search ranking and are what Claude's search tools group results under. If you have the claude CLI, they are auto-labelled in plain English.

Self-check: when do you add --hybrid?
When you know an exact identifier (a class name, an error string) and also want the semantic neighbours. Hybrid merges ripgrep's exact hits with the embedding search. Plain nx search is right for questions; hybrid is right for names.
3

A note that outlives the session

5 min

Memory (T2) is where a project's decisions go so they stop living in chat scrollback. Every entry has a project and a title, so you can ask for it by name later, and so Claude can be handed it at the start of a session.

nx memory put "Auth uses JWT; tokens expire after 24h; refresh at /v2/refresh" \
  -p myproject -t auth-tokens --ttl permanent
nx memory search "JWT" -p myproject
nx memory get -p myproject -t auth-tokens
nx memory list -p myproject
What you should see
Stored: myproject/auth-tokens (id=4471)
[4471] myproject/auth-tokens  (permanent, 2026-09-10T17:19:39Z)
  Auth uses JWT; tokens expire after 24h; refresh at /v2/refresh
Auth uses JWT; tokens expire after 24h; refresh at /v2/refresh

Four commands, four lines: the store confirmation, the search hit, then get prints only the content, which is what you want when piping it somewhere.

Habits that pay off: one fact per entry, a title you would type from memory (auth-tokens, not notes-3), and the project name spelled the same way every time. Writing the same project and title again replaces the entry, which is what you want for a fact that changed.

Default TTL is 30 days, extended every time an entry is read. Use --ttl permanent for facts, leave the default for working context.

Self-check: you wrote a fact with the wrong title. How do you fix it?
Write it again under the right title, then nx memory delete the wrong one. Upsert is keyed on project plus title, so there is no edit command to look for.
4

Scratch while you work

5 min

Scratch (T1) is a pad for the current session only. It is the right place for a hypothesis you are not ready to commit to: you can think out loud without leaving anything behind.

nx scratch put "working hypothesis: the cache TTL is too short" --tags cache
nx scratch list
nx scratch search "cache"
What you should see
Stored: 7b09cc46-0d91-4921-8353-dabb574f232f
[7b09cc46] cache  flagged=False
  working hypothesis: the cache TTL is too short

When the hypothesis turns out true

nx scratch promote 7b09cc46 -p myproject -t cache-ttl-finding   # copy to memory now
nx scratch put "…" --persist -p myproject -t some-title        # or: flush to memory at session end

The ID prefix from nx scratch list is enough. Promotion tells you if a similar memory entry already exists under another title, so you can merge instead of duplicating.

Self-check: what happens to un-promoted scratch when the session ends?
It is gone. That is the point of the tier: it lets you think out loud without polluting memory. Promote what proved out; let the rest go.
5

Knowledge that stays

10 min

Knowledge (T3) is where things go to be found by meaning, forever. You already put a repo there. Now add the other two kinds: your own written notes, and documents.

A note, filed under a subject

echo "Idempotency keys must be scoped per tenant; a global key space let two tenants collide in prod (2026-03)." \
  | nx store put - --collection distributed-systems --title "idempotency-keys-per-tenant" --tags "incident,design"
nx search "idempotency key collision"
What you should see
Stored: 9f2c…e41a  →  knowledge__distributed-systems…

Then the search prints your sentence back near the top, in the same path:line:text shape as lesson 2, with the note's title where a file path would be.

Collections are subjects, not containers. A collection is a durable area someone would browse: distributed-systems, postgres, team-process. Never a session, a task, a source app, or a placeholder. The CLI refuses knowledge, notes, default, tmp and test on purpose. Reuse a subject before inventing one: nx collection list.

Documents

nx index md ./docs/design-notes.md --corpus myproject
nx index pdf ./papers/replication-protocol.pdf --corpus papers
nx search "leader election under partition" --corpus papers -c

PDFs are routed to the right extractor automatically, including scanned ones. --corpus names the group the document belongs to; the docs collection is minted from it.

The catalog: what is in there, and how it connects

Every repo, note and document you add is also registered in the catalog, a registry with typed links between documents (cites, implements, supersedes). Search finds passages; the catalog answers "what do I have, and what relates to it".

nx catalog search replication         # by title, author or path
nx catalog show "replication-protocol" # full entry with every link in and out
nx catalog links "replication-protocol"

Nothing to set up: registration happens at index and store time. Links accrue as you enrich documents and as RDRs cite sources; Claude's query tool follows them.

Self-check: search or catalog for "which of our documents cite the replication paper"?
Catalog. That is a question about relationships between documents, not about passages inside them. nx catalog links "replication-protocol", or in Claude, /conexus:query, which walks the same links.
Self-check: memory (T2) or knowledge (T3) for "our Postgres connection pool is sized at 40"?
Memory. It is a project fact you look up by name, and it will change. Knowledge is for material you find by meaning and expect to be true for a long time. If you later write up why 40, with the measurements, that write-up belongs in knowledge under postgres.
6

Let Claude use it

10 min · Claude Code plugin

Everything you just did, Claude can do too, through the same store. With the plugin installed, a session opens already knowing your project's memory, and the agents reach for search instead of guessing. Your job is mostly to know what to ask for.

What happens at session start

Open claude in your indexed project. The plugin's hooks surface your T2 memory for that project, list ready beads, and check the tooling. Nothing to run. If a fact you stored in lesson 3 shows up in the session's opening context, the loop is closed.

The scratch pad from lesson 4 is shared too: you and every agent Claude spawns in the session read and write the same T1, so a hypothesis you jot down is visible to them and theirs to you.

Ask a question the store can answer

Where do we handle retries, and what does our memory say about the auth tokens?

Watch the tool calls: search and memory_get from the nexus MCP server, not a file crawl. If Claude greps instead, say "use nexus search".

The entry points worth knowing on day one

You want toType
Understand an unfamiliar codebase/conexus:analyze-code
Answer a question that spans many documents/conexus:query Compare what the docs say about caching with what the code does
Plan a feature before writing code/conexus:brainstorming-gate then /conexus:create-plan
Get a review before committing/conexus:review-code
Debug after two failed attempts/conexus:debug
Hand the next session everything it needs/conexus:continuation
Not sure which of theseAsk Claude to read using-nx-skills

The plain question and /conexus:query cover most days. The rest are there when the task has a shape: a plan, a review, a bug that resists.

End every session with /conexus:continuation. It writes a paste-ready handoff (branch, open work, active memory) so the next session starts where this one stopped instead of re-deriving it.

Self-check: what is the difference between asking a question and /conexus:query?
A plain question makes one or two lookups and answers from them. /conexus:query plans a multi-step retrieval (search several corpora, extract, compare, synthesise) and is for questions where the answer has to be reduced from many documents. Reach for it when a single search could not possibly hold the answer.
7

Your first RDR

15 min

RDR is Research, Design, Review: a short spec written before the code, so the decision is captured while the thinking is fresh and is searchable forever after. It is the habit that stops "why did we do it this way?" from ever being unanswerable.

When to write one

When the problem has more than one viable solution, when a bug needs a root cause rather than a patch, or when you are about to change something others depend on. If the rationale is obvious from the code, skip it. The test: if you would be three hours in wondering why you went this way, that is the RDR to write first.

The loop, in Claude Code

/conexus:rdr-create             # scaffold with metadata, status Draft
/conexus:rdr-research add 12    # append a finding with an evidence tag, as you learn
/conexus:rdr-gate 12            # optional: structure check, assumption audit, critique
/conexus:rdr-accept 12          # lock the decision

Right-size it. A bug fix wants Problem, Root Cause, Fix and nothing else. The full template is for architecture with real alternatives.

The rule is about timing. Iterate freely while drafting. Once accepted, the RDR is the record of what was decided. If implementation proves it wrong, do not edit it to match what shipped: abandon it and write the next one with what you learned. The chain of RDRs is the history.

Why it compounds

Accepted and closed RDRs are indexed into knowledge, so the next time you or Claude research a similar decision, the prior one surfaces in search. That is the difference between a team that repeats its mistakes and one that does not.

Self-check: implementation showed the accepted design will not work. What do you do to the RDR?
Nothing to that one. Mark it abandoned and create a new RDR that records what was learned. Rewriting an accepted RDR to match the outcome destroys the very record it exists to keep.
8

Keeping it healthy

5 min

Three commands cover almost every "something feels off" moment, and one rule keeps upgrades from breaking search.

nx doctor              # every row should be ✓; this is always the first move
nx taxonomy status     # topics per collection; empty topics mean discovery never ran
nx collection list     # what is actually indexed, and how big

Updating

nx self install
nx upgrade

Both, every time, and never uv tool install conexus to upgrade. That resets the environment, drops the local embedder, and search returns nothing. If it already happened, nx self install repairs it.

Re-indexing

Re-run nx index repo . whenever the code has moved on; it only touches changed files. To keep it automatic, nx hooks install adds a git hook that re-indexes on commit.

Self-check: search suddenly returns nothing. First two moves?
nx doctor, then check whether the last upgrade was a bare uv tool install. Those two explain nearly every empty-results report; nx self install fixes the second.

That is the hour.

You can put things in the right place by lifetime, get them back by meaning, let Claude work from the same store, and write down a decision before it evaporates. From here the tool rewards use: the more you index and record, the better every search and every session start gets.
