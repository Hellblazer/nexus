How Agents Build and Ship Nexus

Several Claude Code sessions build, test, review, and release Nexus, and one more session runs the managed cloud. They work on the same repository and the same engine at the same time. They do not collide, because each claim, push, and deploy is a record that the others see as soon as it is written. The owner decides what the agents do not: every release tag, every cloud deploy, and every change of direction.

Two parts of this setup ship to users: the tuple space, and the agents, skills, and hooks of the conexus plugin. The name conexus also belongs to the product on PyPI. The rest is this project's own: the lab pool, the managed cloud, the GitHub adapter, and the release checks.

The system at a glance

  • Sessions and subagents. Each working session is a Claude Code session with its own worktree and branch on the laptop. It dispatches subagents: developers to implement, and two standing reviewers, a code reviewer and a critic.
  • The cloud session. A separate Claude Code session, in a separate repository, runs the managed engine, which hosts the tuple space that all the sessions share. It also hosts the adapter that turns GitHub events into CI board posts, deploys each engine release, and runs the cloud checks. It is a peer of the other sessions: it receives requests in its mailbox and answers there.
  • GitHub runs CI on every push to develop and on every pull request, and it runs the release workflows on tags. It sends the Python test shards, the engine's Java tests, and a macOS test job to the lab pool, and runs its other jobs on its own runners.
  • The lab pool is a set of machines on the local network that CI and the sessions' own heavy runs share. A scheduler gives each run a share of cores and memory, so the machines do not run out of memory. One pool machine also runs Windows natively, for hand runs of the Windows tests and for the win-release runner, and one is a Mac. The pool also builds the macOS release binaries, and the win-release runner builds the Windows ones. A session named labrun runs the pool.

Agents, skills and tools

The conexus plugin gives every session the same agents, skills, and hooks, so the sessions work the same way without instructing each other. A session hands most work to background subagents: developers, the two reviewers, a debugger, planners. Skills carry checklists, such as the two release procedures, and hooks enforce what nobody should have to remember. Hooks brief each subagent when it starts. They stop a subagent from running git write commands in the shared checkout, and they stop a command from printing a credential. Before Claude Code compacts a session's context, a hook saves the session's working state as a checkpoint. After the compaction, a second hook puts the checkpoint back into the session. Review is a rule, not a hook, and the build step below describes it.

One change, end to end

Design

A change that needs a design decision starts as an RDR, a design record in the repository. A critic agent checks the record in a gate before anyone plans from it, and the owner accepts it. The strategic-planner agent then splits the accepted design into beads. Working with RDRs describes the record and the gate.

Claim and announce

A session claims a bead with bd update --claim, so other sessions do not start the same work. A session subscribes to the boards it cares about. It also holds a short name in a directory in the tuple space, so a message addressed to that name reaches its mailbox. Each subagent has a mailbox of its own. Sessions do not poll in a loop, because pings announce new records, whether a session waits for CI, for a peer, or for a reply. A post or a message carries a short signal and names a Nexus memory entry for anything longer, such as a measurement.

Each session also keeps one thread entry, a Nexus memory entry with one block for each open thread of work. A block has one line each for what the work refers to, where it stands, what it waits on, and what it needs from the owner. The session rewrites the entry at each phase boundary: when a thread starts, at a push, at a wait, and when the work is done. The Threads tab of nx console shows the entries of all sessions in one place.

Build and review

The session creates a worktree on a feature branch and dispatches a developer subagent, which writes the failing test and then the fix. Before review, the session states the acceptance bar as a line that begins "Ship when", for example "Ship when the local-upgrade path cannot wedge". Both reviewers read the change against that bar. The session triages each finding as a ship-blocker or as a new bead, never both, and fixes only the ship-blockers. A second round confirms those fixes. When both reviewers are clean, the session commits the change by explicit path and closes the bead.

Test

Test selections and full suites go to the lab pool, not the laptop. The lab-remote command copies the worktree to a pool machine and runs the command there under lab-run. A run that a session starts itself is a hand run. Each hand run asks for a class, a fixed share of cores and memory, and waits until the scheduler grants it. The scheduler gives the next free share to a waiting hand run before a CI job. On the Linux machines it also stops a run that uses more memory than its share. Engine builds in the worktrees of one clone take a lease, so they run one at a time. The lease ends by itself if its holder stops. Before a full suite, the session tells the labrun session why it needs the run. A tree that already has a green full run is not run again. After the push, the CI run of the commit is the verdict.

A session starts a lab-remote run as a background command, so it keeps working and is woken when the run exits. If another run already holds the worktree's copy on the pool machine, lab-remote exits with code 98, and the session waits and tries again instead of running the command on the laptop. The first run from a new worktree takes longest, because the pool machine builds the Python environment for it. On the Mac the scheduler admits and records each run but does not cap its memory. Its larger class books nearly all of the Mac, so CI and release jobs wait behind it. A session tells the labrun session before such a run and keeps it away from the times when a release is built.

The default test run leaves out the lint tests. These tests scan the whole repository for structure problems. A session that changes the plugin's files, RDR frontmatter, or a hook or storage rule runs them with -m lint. A change to files that the Windows tests in CI watch is tested on the pool's Windows side before the push. scripts/windows_hand_test.py --check says whether the change needs this, and the same script runs the tests there the way CI does.

Push

Before it pushes, the session asks whether a CI run that someone is waiting on is in flight. Each push starts a CI run on the shared pool, so green commits are held and pushed together. One goes out alone only for a failure on develop or for a waiting peer. The push script, scripts/git-push-develop.sh, sends only the commits that the session names, so a peer's work never goes out with the push. It holds the push lock only while it pushes. The session then fast-forwards the primary checkout, which stays on develop as the shared reference and which nobody edits.

Check CI

GitHub sends a webhook to the adapter for each state change of each run and job on develop. The adapter verifies it and writes one post to the CI board. The board only wakes the session with a ping. The session reads the verdict for its commit with one call, gh api repos/<owner>/<repo>/commits/<sha>/check-runs. A red commit gets its fix as a new commit.

The CI jobs
  • A predicate job decides whether a change touches code. A documentation-only change skips the tests.
  • One job builds the engine's service jar once for all test jobs, and caches it on the service source.
  • The unit suite runs in parallel shards against a real engine on the lab pool. A pull request from a fork runs on GitHub's own runners instead. Separate jobs run the repository-structure tests and further checks over the whole suite.
  • A change under the engine source also builds the engine's native image, and a separate workflow runs the Java tests on the lab pool.
  • A pull request to main also checks the wire-contract ledger.
  • One required check collects every result, and it fails on any failed, cancelled, or missing part.
  • A newer push to a pull request cancels the older CI run. On develop a running CI run is never cancelled, and a push replaces only a run that is still waiting.
  • A release workflow publishes what CI already tested, without testing it again.

Release the client

A session creates a release worktree, because the primary checkout moves with every push to develop. A tree that moves would change what the checks build. It bumps the version and runs the release checks, which live in tests/e2e/release-battery.sh. A serial preflight runs first. Then the end-to-end legs run in parallel, and one table prints the verdict of each leg. One leg checks the plugins as a user runs them, from a project outside any Nexus checkout. A file reference in a plugin that opens only inside the repository fails that leg. A leg that finishes without its verdict line counts as missing, never as passed. The session opens a pull request to main. The owner merges it, then pushes the release tag or authorizes a session to push that one tag. The release workflow checks the tag against the version and the tagged commit's CI results. It then publishes the package to PyPI and creates the GitHub release. Each client release pins exactly one engine version.

Release and deploy the engine

Before an engine tag, the Java suite and the native build must be green on the exact tree to be tagged. Three more checks run first. One confirms that no held changeset, none that scripts/release-holds.txt lists, is in the tagged tree. One confirms that every new field in the engine's /version answer has a paired change to the public edge's allowlist, because the edge passes only listed fields. The third applies to a cut that must carry Windows. That cut needs the repository switch NX_WINDOWS_RELEASE_LEGS on, the win-release runner online, and a green trial run of the release workflow. The owner pushes the engine tag, or authorizes a session to push that one tag. The engine workflow builds and signs the native binaries for Linux and macOS, and for Windows when the switch is on. It publishes the GitHub release only when every asset is present. A failed build job leaves the release as a draft until a rerun completes it. A check then installs the published binary on a bare machine and tests it.

A deploy request carries the tag and the evidence from these checks, and no approval. A session sends it to the cloud session's mailbox. The owner types the approval in the cloud session itself, and the cloud session refuses an approval that another session relays. It then deploys the engine and runs its cloud checks. Afterwards, a session on a cloud-mode machine checks that the engine's contracts reach real client code through the public edge.

The wire-contract ledger decides the order. It lists each engine change whose client half has not shipped, and it marks whether an old client still works against the new engine. When every entry is safe for old clients, the engine deploys before the client release. Otherwise, the cloud session must have the redeploy staged, and must confirm that back, before the client tag. A person confirms this, because no script checks it, and the releaser waits for the confirmation.

Who decides what

The owner gives the sessions standing grants: kinds of step that a session takes without asking first. The session acts, then writes one line in its thread entry that names the grant and what it did. A question that a rule in the owner's instruction files already answers is not put to the owner. The session acts on the rule and records it in the same way.

A decision that only the owner can make goes into the thread entry as an ask. The ask states the question, where the work stands, and what happens if the owner waits. It lists two or more options and marks each option that cannot be undone. It can carry a recommendation, and it says whether every option can be undone cheaply and whether the work is blocked until the answer. The thread also carries a needs_sam line that points at the ask, so the Threads tab flags the ask beside the session's work. When the decision is also tracked as a bead, that bead carries the needs-sam label.

The owner supervises the sessions from one tmux window. Claude Code hooks mark each session as working, waiting for the owner's next message, needing an answer, or held while it waits on something else, such as background work. One key after the tmux prefix jumps to the session that has waited longest, and sessions that need an answer come first.
