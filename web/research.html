Research with Nexus

Nexus is a curated retrieval store. Retrieval-augmented generation (RAG) means that Claude reads from a store of documents before it answers. Curated means that what is in the store was chosen, described, and linked, not collected automatically. The store holds the papers you read, the code you write, the design records (RDRs) that connect the two, and the reports, briefings, and documentation you produce from them, so a finding from a paper, the decision it led to, the code that implements the decision, and the report that explains it are in one place and linked. The store keeps its contents when a Claude session ends, so the reading, notes and findings of one session are available to every later session. Research is the main use of Nexus.

The store is more than text chunks. Every document is registered in a catalog, and the catalog holds typed links between documents (cites, implements, supersedes, relates), which form a knowledge graph. Every collection has a topic map, found by clustering and named. Papers can carry structured fields: problem, method, datasets, baselines, result. For a question that needs many documents, nx_answer plans several steps over these structures and returns one answer with sources. The sections on asking and coupling, and the appendix, describe each of these. Grounding describes what the store does for the truth of an answer.

Research has the same steps it always had: collect sources, read them, keep notes, ask questions about the material, combine the findings, connect them, check them, and write the result. This page describes what Nexus does for each of these steps.

Words in <ORANGE CAPITALS IN ANGLE BRACKETS> are placeholders. The prompts are examples. Your own words work. Read Getting started first. This page uses these ideas from it: the three stores, the catalog, continuations, and renderings.

What the system does

5 min · reading only

The practices happen in the order that the work needs. The table gives one sentence for each. The sections below give the details.

PracticeWhat Nexus does for it
CuratingExtracts the text, cuts it into chunks, embeds them, and registers the source in the catalog. Enrichment adds the DOI, the authors, and citation links. Collections group sources by subject.
ReadingTwo agents read at the same time: one reads the full text, one reads about the field around it. Both write to memory, with a source for every claim.
ChroniclingEach piece of work is stored while it happens: as a document in the knowledge store, as a memory entry, or as a catalog link.
CouplingTyped links between documents. Many are created automatically. The important ones you add. The links can be followed, and they affect ranking.
Asking and analyzingA question that needs many documents runs as a saved plan over a collection: search, extract, compare, and one answer with sources.
Synthesizing and extractingAgents write mappings and proposals from the store, the code, and the RDRs. Structured fields from many documents are extracted into one table.
VerifyingA critic agent with access to the code and documents checks a plan. A second critic recomputes a result from its raw data.
RenderingOne document for a reader, written from the current content of the stores: a report, a briefing, a precis, system documentation, or a test design. Your changes go back to the stores. Ask again later and the document is current.

Three rules apply in every practice.

  • Everything is written down and linked. A reading, a mapping, a synthesis, a critique, a result, a report: each becomes a document in the knowledge store, registered in the catalog, linked to its source and to the work before it.
  • Agents read and check. You choose the direction. The research agent reads and collects. The critic agent checks claims against the code and the earlier decisions. You decide what to look at next and when to stop.
  • Every result is checked. A critic checks each synthesis. Each experiment is checked against its own raw data. When a tool reports "nothing found", the thing it counted is checked directly.

Grounding

5 min · reading only

A grounded answer is one that rests on a document you can open. Without a store, Claude answers from what it learned in training, and it can produce a confident sentence with no source behind it. With Nexus, Claude reads from the store before it answers, and each claim in the answer points at the chunk, the document, or the memory entry it came from.

Grounding in Nexus works at four levels.

  • The answer is limited to the store. Retrieval runs before generation. A question about a paper that is not in the store gets "not found", not an invented summary. This is why curating comes first: the store can only ground what it holds.
  • Every source is addressable. A chunk has a content hash, a document has a catalog entry, a memory entry has a project and a title. A citation in an answer names one of these, and you can open it. nx doc cite "<A CLAIM>" finds the chunk that grounds a sentence and returns a link to it, or reports that nothing in the collection does.
  • Claims carry their evidence. A reading marks each claim with a source or with "could not verify". An analytical answer from nx_answer returns a source for each claim. A check across several documents returns, for each document, whether it supports or contradicts the claim, with the passage.
  • The evidence is checked, not only cited. A citation can point at a passage that does not say what the answer says. The critic reads the cited artifact and the claim together (Verifying). A recompute goes past the report to the raw data.

What grounding does not do: it does not make a source true. A paper in the store can be wrong. Grounding tells you where a claim came from, so that you can judge the source. The second reading in Reading, which looks outside the paper, is how the source itself is judged.

You might say
For each claim in that answer, show me the passage it came from. Mark any claim that has no passage.

Claude opens each cited chunk and quotes it under the claim. A claim with no passage is the one to question first.

Curating

10 min

Collecting sources and keeping them in order. In Nexus this means: the text is extracted, cut into chunks, embedded, and registered in the catalog together with what is known about it. With enrichment on, the system also finds related documents in the store before anyone reads the source.

A paper

You might say
Index <PATH-TO-THE-PDF> into the <SUBJECT> collection, with bibliographic enrichment, and show me what it links to.
What Claude does

Claude runs nx index pdf with --enrich. The text extractor is chosen from the content: a paper with many formulas goes to a different extractor automatically. A scanned paper needs the OCR extractor named with --extractor mineru. Enrichment looks the paper up by title and adds the DOI, the authors, the venue, and the citation count to the catalog entry. If the paper cites other papers that are already in the store, cites links are created. When the paper arrives through DEVONthink and you pass --link-semantic, documents with similar content also get relates links.

On macOS with DEVONthink, nx dt capture takes a URL or a DOI, stores the PDF in DEVONthink, and indexes it, in one step. Papers that are already in DEVONthink can be indexed by selection, by group, or by tag. The catalog keeps the DEVONthink identity, so the same paper is never indexed twice.

Collections are subjects

Papers go into collections named for the subject, not for the project or the date: distributed-systems, semantic-operators, agent-memory, interpretability. Later questions are limited to a subject collection. The question "What do the semantic-operator papers say about batching" can be answered because those papers are in one collection.

Watch it go in

Indexing has several stages, and each stage writes to the log. Ask Claude to read the log instead of waiting for the summary line. If a paper was indexed with no aspects, or if the citation lookup returned nothing, that is a fact about the pipeline, not about the paper. If you find it now, it costs one minute.

From the record

A six-page position paper on ingest-time compilation for retrieval was indexed with enrichment on. Reading the log while it ran found three defects in the indexing pipeline that the summary line did not show. The catalog entry received a DOI, an OpenAlex identifier, and relates links to similar papers from the DEVONthink path. After a first reading, links were added by hand to the parts of the codebase that the paper was about.

Investigate further

  • Ask Claude: "Show the catalog entry for <THE PAPER>, with its links."
  • nx index pdf --help: the extractor choice, --enrich, --dir for a folder of papers.
  • Repo indexing and Document catalog.

Reading

15 min

Search results are not reading. A paper's chunks and a summary can give the impression that you have read it, and they hide what kind of document it is. A six-page position paper whose protocol is in an unpublished second paper looks like a full study when you see only its chunks. The method that works is two readings by two agents at the same time.

You might say
Two agents on <THE PAPER>, at the same time. One reads the full text and reconstructs the paper: claims, method, numbers, and what the paper does not say. The other researches everything outside the paper: the authors, independent evaluations, earlier work, and the opinion of the field. Both write to memory.
What Claude does

Two agents start. The first reads the full text and writes a technical reconstruction: what is claimed, with what evidence, and what is missing. The second is the research agent, working outward: authors, venue, independent evaluations, the literature around the paper. It marks every claim with a source or with "could not verify". Both write memory entries. Read the two entries together. Where they disagree, you have your first finding.

Read the full source before you design anything on it. Everything built on a reading inherits the errors of that reading. A reading that says "the protocol is in a second paper that is not published" changes what can be tested later. Search results do not contain that sentence.

From the record

A vendor's technical report claimed a false-positive rate of one in twenty-four thousand. The first agent recorded the claim, the evaluation set, and the tables for other languages, which showed much worse numbers outside English. The second agent found three things. No third party had evaluated the new version. The strongest independent study had a sample far too small to confirm a rate that low. The vendor was not present on the one leaderboard that a vendor does not run. Every line in both entries has a source or the words "could not verify".

Investigate further

  • Ask Claude, after the two readings: "Where do the two readings disagree, and which one has the source?"
  • The research agent: its steps, and why it checks the catalog before it searches.

Chronicling

10 min

Keeping the record while you work: what was read, what was found, what was decided, and when. This practice carries the work from one session to the next. When a conversation ends, its contents are gone. What was written to the stores remains. Every other practice on this page produces something that belongs in the record. The system keeps three kinds of record, and Claude writes to them as it works.

WhatWhereWritten by
A reading, a mapping, a synthesis, a critique, a result, a reportThe knowledge store, as a document, registered in the catalog and linked to its sourceThe agent that produced it, when its work ends
A decision, a finding, the state of the workMemory, by project and titleClaude, as it works, and at the end of a session
A connection between two documentsThe catalog, as a typed linkIndexing and enrichment, automatically. Claude or you, by hand

You do not keep this record yourself. You check that it is kept. At the end of a piece of work, ask: "What did you write to the stores today, and what does it link to?" If the answer is "nothing", the work exists only in this conversation, and the next session starts without it.

Write after each piece of work, not once a day. It takes a few minutes each time. The test is simple: a person who was not present can follow the links from the source through everything that was done with it.

From the record

The catalog entry of one paper, after one day of work, held these things.

  • The bibliographic fields from enrichment.
  • Outgoing relates links to similar papers, added by the DEVONthink path at index time.
  • Outgoing links to the code and the RDRs it concerns, added during reading.
  • Incoming cites links from the documents written that day: a mapping, a synthesis, a critique, a verdict, and an experiment result.
  • comments links from the documents that took a position on it.

From the catalog entry alone, a reader can find every document written about the paper that day.

Coupling

10 min

Connecting things that belong together: a paper to the code that implements its idea, a finding to the decision it changed, a design to the paper it came from. The catalog stores these as typed links. Most are created automatically. The links with the most meaning are the ones you add.

You might say
Link <THE PAPER OR DESIGN DOCUMENT> to <THE MODULE THAT IMPLEMENTS IT> with an "implements" link.
What Claude does

A tool call named link on the nexus-catalog server, with the two documents and the link type. From then on, a question about the design finds the code, and a question about the code finds the design. Ask "What implements <THE DESIGN DOCUMENT>?" and Claude follows the link.

Following links

A research result names documents. Each one is a place to continue: "Open <ONE DOCUMENT> and tell me what else in the store is related to it." Claude uses the catalog tools show and links, and a search for similar chunks. It tells you which documents link to this one and which are similar. Then ask about one of those. In this way you move through a store without knowing the names of its documents.

Link types

cites, implements, supersedes, relates, comments, quotes, formalizes. Enrichment adds cites from a paper's bibliography. Indexing an RDR adds relates from its frontmatter to its parent and related RDRs, and the DEVONthink path adds relates between similar documents when asked. implements is added by hand or by the developer agent when code realizes a design. Every link records who created it. A search can therefore prefer links made by hand or by bibliographic enrichment over links made by heuristics. The full table is in Link types.

The link graph

A link has a type, a direction, and a creator. Together the links form a graph that you can follow: from a paper to the documents that cite it, from an RDR to the code that implements it, from a design to the design that replaced it.

  • Follow it from a document. "What links to <DOCUMENT>, and what does it link to?" Claude uses the catalog's links tool. From the terminal: nx catalog links "<TITLE>".
  • Follow it for several steps. "Start from <THE PAPER>, follow cites links for two steps, and list what you reach." Claude uses the traverse tool with a depth. The query tool can do the same during a search, with follow_links, so the results include documents that were reached through the graph.
  • It affects ranking. The query tool ranks a document higher when the document has an outgoing implements link. relates and cites links count half as much. The plain search tool does not use links. When you want the graph to affect the results, ask for a document-level query.

Two kinds of link are less reliable. implements-heuristic links were generated by matching parts of file paths with RDR titles. The generator is now off. The existing links remain, but ranking gives them no weight. Links created from an LLM suggestion are marked as such and are advisory only. When the answer matters, ask Claude to filter by creator: "Only links made by hand or by bibliographic enrichment."

Investigate further

  • Link types: what each means and who creates it.
  • Ask Claude: "Which papers in the store are cited by the most documents?" Those are the papers the project has used most.

Asking and analyzing

15 min

Asking questions about the material. With one source, the question is "what does this say". With several sources on one subject, the questions change: how do they differ on this point, which of them does our code follow, what does the literature recommend that we do not do. These questions need several searches, extraction from each result, and a comparison.

You might say
/conexus:query Compare how <PAPER A> and <PAPER B> handle <THE POINT>, and say which approach our code takes.
What Claude does

The skill compares the question with a library of saved retrieval plans. If a plan fits, it runs: search the named collections, extract the relevant passages, compare them, and write one answer with the sources. If no plan fits, Claude writes a plan, runs it, and saves it. The next similar question uses the saved plan.

What you see

A tool call named nx_answer, then the answer, with a source for each claim. This takes longer than a search: one to five minutes for a comparison across two collections is normal. If the answer surprises you, ask: "Which plan did that use, and what did each step return?"

Limit the question to one collection. "What do the semantic-operator papers say about batching" runs over the papers in that one collection. "What does the literature say about batching" runs over everything, takes longer, and mixes subjects.

From the record

The saved plans of one project include these questions.

  • How the distributed-systems papers handle membership changes.
  • What the semantic-operator papers say about batching to reduce model calls.
  • A comparison of two membership protocols by how they detect failure.
  • A comparison of the time index of one memory system with that of another.
  • Which vocabulary a vision paper introduces.

Each was asked once as a new question, and saved.

Investigate further

  • Ask Claude: "List the saved retrieval plans for this project."
  • Querying guide and Plan-centric retrieval.

Synthesizing and extracting

15 min

Combining findings into a statement of what they mean for you. Two forms are common. A mapping says where a source touches your own system. A synthesis turns a mapping into proposals. Extraction is the mechanical step under both: taking the claims, numbers, and definitions out of the text in a form that can be compared.

A mapping

You might say
Map <THE PAPER> onto our system. For each claim: does it apply to us, which module or decision does it touch, and does it agree with what we decided. Link the paper to those modules and RDRs in the catalog.

Claude reads the reconstruction, searches the code and the RDRs for each claim, and writes the mapping to the knowledge store, with links from the paper to the code it concerns and to the RDRs it touches. A mapping usually finds three kinds of result. Our module already does this. Our RDR rejected this, for a reason. This applies and nothing does it. Only the third kind leads to a proposal. The first two are still worth the links.

A synthesis

You might say
Write proposals from the mapping of <THE PAPER>. Give the agent the mapping, the linked RDRs, the code paths, and a web check. Every proposal states what it changes, the result that would show it is wrong, and a cost. Include a do-nothing option.

The research agent runs with that instruction and produces three to six proposals, each with the result that would show it is wrong (its falsifier) and its cost, plus the do-nothing case. The document goes to the knowledge store with a cites link to the paper. A proposal with no way to be wrong is an opinion. The falsifier is what makes the next experiment clear.

Extraction, on its own

When the question is about one kind of fact across many documents, ask for the extraction directly: "From every paper in <COLLECTION>, extract the dataset, the baseline, and the reported metric, as a table." Claude uses the extraction and comparison operators over the collection and returns the table with a source for each row. On collections that have structured aspects (see the appendix), this is faster.

From the record

A paper that argued for one unified database layer under retrieval systems was mapped onto a system that had just completed that migration. The mapping found that two of the paper's three failure modes were already closed, that the third matched an open task, and that the paper's remedy was the architecture the system already had. The result was a proposal document that marks the paper as a confirmation, linked to the paper and to the RDR it confirms, with the status "unresolved draft" and a decision pending.

Investigate further

  • Ask Claude, of any proposal: "What result would make this wrong, and how much would it cost to get that result?"
  • The research synthesis skill.

Verifying

30 min

Checking that a claim is true before you act on it. Two forms are common here, and they are the two with the most value: a critique of a plan by a second reader who has access to the code and documents, and a measurement whose result is recomputed from the raw data instead of read from the report.

Critique, with the artifacts

You might say
Have the critic read the synthesis on <THE PAPER> with access to the code, the schema changelogs, and the RDRs. For each proposal: survives, survives with amendment, or dies, with the artifact that decides it.

The critic agent runs (/conexus:substantive-critique) with a list of paths to check. It returns a verdict for each proposal, with the evidence: a changelog line, an RDR section, a function. Claude writes a verdict document that reduces the synthesis and the critique to what survives, and links it to both.

Proposals fail for reasons like these. A changelog shows that a table has no document identity. The alternatives section of an RDR shows that an idea was rejected, not adopted. A field contains a paraphrase, not a quote. None of this is in any paper, and semantic search over prose does not find it. Tell the critic which files to read.

Measurement

When a surviving proposal has a falsifier that can be measured, measure it. The rules that make the result reliable are the test rules of the codebase, applied to a measurement. Before you spend anything, write one paragraph and ask Claude to check the run against it. The paragraph names these things.

  • The arms of the experiment and the one variable that differs between them.
  • The known confounding factors and what fixes each one.
  • The metric and the statistic.
  • The budget.
  • The result that would falsify the hypothesis.
  • The number of cases in which the treatment can have an effect at all.
You might say
Build the harness for <THE EXPERIMENT>. Fix the random seed and the model identifiers. Retrieve once per question and cache the result. Save, for each trial, the exact text each arm received, the structured flags, and the cost of every model call. Report McNemar, Wilson intervals, and a cluster-robust paired difference.

A harness that produces only a summary table cannot be audited. A harness that keeps the input text, the reader's flags, and every cost can answer, later, why any trial failed.

Recompute

You might say
Methodology critique of <THE EXPERIMENT>. Give the critic the raw trial data, not the report. Recompute every number. Classify every outcome as correct, wrong, or no answer. Check that the generated data follows its own generation rules. Validate the grader on a sample labelled by a person.

A report that says "the treated arm mostly answered wrongly" and a raw log that shows forty-five non-answers among fifty-six failures are two different findings. Only the recompute finds the second.

A synthesis alone produces a plausible plan with false assumptions. An experiment alone produces a correct number with a wrong explanation. The critique of the plan and the recompute of the result are what make both usable.

From the record

One synthesis produced five proposals. The critic, given the changelog directory, the alternatives section of one RDR, and the field definitions of the extractor, rejected three as factually wrong about the system, amended one, and found one thing the synthesis had missed. The surviving proposal was tested with a fixed seed and paired counts. The methodology critic, working from the raw trials, still found defects in the report and in the harness. The effect was large enough to survive them.

Investigate further

  • The critic agent: its verdict vocabulary and what it is told to check.
  • Ask Claude, before any run: "Write the pre-registration paragraph. Do not run anything until I have read it."

Rendering

10 min

Writing the result. Not from nothing: the material is already in the stores, linked, put there by sessions that may be weeks apart. A rendering is one document, written from the current content of those stores, for a reader: a report on a question, a briefing for people who did not follow the work, a precis of a paper, the documentation of a system, or the design of a test. If you change it, the changes go back to the stores. If you ask again later, in another session, the document includes what happened since.

You might say
Render everything we did with <THE PAPER> as one document: what the paper claimed, what applied to us, what we proposed, what the critic removed and why, what the experiment showed, and what is still open.

Claude follows the links and writes the document from the current content. System documentation and a design document for a new component are produced in the same way: rendered from the research, the design records, and the code, and kept current in the same way (Getting started, lesson 8).

When the space is open

Sometimes there is an idea and no paper. Then the rendering comes first. A brainstorm produces the possible directions, a landscape synthesis places the idea among the systems that exist, and a short document says in which order to read them. All three go into the store as exploration. Each has a decision line: adopted, parked, or scrapped, and by whom. An exploration with no decision line is a question that waits for you.

You might say
Brainstorm the design space around <THE IDEA>: related designs, what we could merge into existing parts, what would be new. Then write where it sits among systems that do similar things. Write both as documents and index them.

From the record

A design document for a workflow engine went through this process. The architect agent returned twelve directions, among them merging one of its new stores into a store that already existed. The research agent placed the design among four neighbouring families of systems and found the area it occupies empty. A third document listed the reading order. All three are in the store as exploration, each with the owner named as the person who decides.

Where it ends up

5 min

Research work ends in a document for a reader, in a decision, or in a lesson. Which form is usually your decision. All of them are kept in the stores, so the conclusion of this session is the starting point of a later session.

OutcomeFormWhen
A report or a briefingA rendering for a named reader: what was asked, what the sources say, what was checked, and what is still openSomeone who did not follow the work needs its current state, or a question has an answer worth keeping.
An analysis or a precisOne condensed document per source or per question, with the claims, the numbers, and the sources, linked to the material it condensesThe material is large, and later readers will need the short form more often than the long one.
System documentationA rendering from the code, the design records, and the reading, re-rendered when any of them changeA part of the system is used or changed by people who did not build it.
A test designThe pre-registration paragraph and the harness plan from Verifying: arms, confounding factors, metric, budget, falsifierA claim can be measured, and the measurement costs enough to be planned first.

From the record

For one subject, one project's store holds a precis of each paper, a briefing written for a team that had not followed the reading, the documentation of the part of the system the papers concern, a test design for the one claim that could be measured, and the design record that the measurement justified. All of them were rendered from the same readings and links. A question on the subject today finds the papers and every document written from them together.

Appendix: topics, aspects, sections, projections

reference

Four kinds of structure that the store builds over a corpus, used by the practices above. This section says where each comes from and how to use it.

Topics and the taxonomy

After a collection is indexed, Nexus clusters the chunk embeddings and finds topics. Each topic gets a label from its most typical terms, and a readable name when the claude command is available. Every document is assigned to its nearest topic, and new documents are assigned when they arrive. The result is a topic map for each collection. It is kept in memory-tier tables, and you can inspect it and correct it.

  • See it. "Show the topic map for <COLLECTION>." From the terminal: nx taxonomy status, nx taxonomy list, nx taxonomy show <ID>.
  • Correct it. Rename, merge, assign, or split a topic. nx taxonomy review goes through every topic and asks what to do. In conversation, "Rename topic <X> to <Y>" or "assign <DOCUMENT> to <TOPIC>" also works.
  • Find the hubs. nx taxonomy hubs lists topics that appear in many collections. Sometimes they are the central ideas of a project. Sometimes they are generic words that need a new name.
  • It affects search. Results that share a topic with the best match are ranked closer to it, and results are grouped by topic when most of them have one. In Claude Code, a search can be limited to one topic: the search tool has a topic argument, and search_topic_scoped does only that. The terminal command has no topic option. There, use --corpus to limit the search to a collection.
  • Topics link to each other. nx taxonomy links shows relationships between topics, derived from the document link graph. A result in one topic is ranked a little closer to results in a linked topic.

Aspects

For scientific papers, Nexus can extract a fixed set of structured fields from the text, at index time or later: the problem the paper addresses, the proposed method, the datasets, the baselines, the main result, and an open field for anything else useful. These fields are stored per document, with a confidence value.

  • Extract them. "Extract aspects for every paper in <COLLECTION>." Claude runs nx enrich aspects. A background worker processes a queue, so a large collection takes some time. nx doctor --check-aspect-queue shows the queue.
  • Use them. Questions such as "which papers used dataset X", "group the papers by baseline", or "the most common method in the collection" run against the aspect table directly, instead of reading every paper again. The filter, group-by and aggregate operators use this fast path when aspects exist, and read the text when they do not.
  • Limit a search by them. The search_aspect_scoped tool applies an aspect condition in the same query as the vector search. A strict filter therefore does not lose results, unlike "search first, filter after", which can. This tool sees only documents whose aspect row is linked to a catalog entry. For notes stored by title instead of by file, that link is often missing. For those, the filter operator is the safer choice.

Sections

Every chunk has a section label. For prose from Markdown: abstract, introduction, methods, results, discussion, conclusion, references, and others. For code: class, method, or empty for module-level content, and imports for a chunk that contains only import lines. The label can be used as a filter. nx search "<QUESTION>" --where section_type!=references removes bibliography chunks from a prose search. --where section_type!=imports removes import blocks from a code search. Nothing applies the references filter by default. The analytical query drops import-only chunks on its own while it collects evidence, and nothing else.

Projections

A projection applies the topic map of one collection to another collection. For example, the topics found in a documentation collection are projected onto the code collection of the same repository, so that a code chunk can be found under the topic names of the documentation. The command nx taxonomy audit reports how well a projection fits.

Complete
