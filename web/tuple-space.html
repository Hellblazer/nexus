The Nexus Tuple Space

The tuple space is where the processes that work with you coordinate: the Claude Code session you talk to, the agents it starts, the hooks that run around every tool call, and the other sessions on the same machine. It is a shared collection of small typed records. Any process can add a record, read one, or take one, and a take is exclusive: when two processes reach for the same record, one gets it and the other does not. A read can wait for a record that has not arrived yet.

You use it for three things. You wait for an agent's report instead of polling for it. You send a message to an agent while it works, and the agent reads it before it replies. You send a request to another session on the machine and wait for its ack. Each is a few words to Claude, and the rest of this page shows them.

The harness, hooks, memory, and scratch keep doing what they do. The tuple space is built from them: hooks write its records, the ids the harness assigns are its addresses, and Claude reads it with the same kind of tools it already calls. Everything on this page is live in the current release.

The reference, with the exact parameters of every operation and every state a tuple can be in, is docs/tuple-space.md. The walkthroughs draw each use as a sequence, and RDR-205 records the design and its reasons.

What it does for you

5 min

Three situations come up in every multi-agent session, and each is one instruction.

Wait for an agent to report

You might say
Wait until <THE AGENT> reports, then continue with its result.
What happens

When the agent stops, a hook writes a report tuple to the session's ledger. Claude reads that tuple with a timeout and wakes the moment it lands. The agent does nothing to make this work, and if it never reports, the missing tuple is the evidence.

Tell an agent something while it works

You might say
Tell the agent that works on <THE TASK> that the schema changed. Put the message in its mailbox.
What happens

Claude writes a message tuple to the agent's mailbox. The agent reads its mailbox before every reply, so it acts on the message before it hands back its next result, not after. The message reaches exactly one reader.

Ask another session for something

You might say
Ask the <PEER SESSION> session to rebuild its gate jar. Wait for its ack.
What happens

Claude writes a request tuple to the other session's mailbox and waits on its own mailbox for the ack. The other session takes the request, does the work, and writes the ack. Nobody relays anything by hand, and an unanswered request stays visible with its age.

What makes these work is that a tuple is a record, not a message. It exists from the moment it is written until it expires, whoever reads it and whenever. It can be taken by exactly one reader, it can be waited for, and anyone with the tenant's credential can query it afterwards. The rest of this page explains the operations behind that and what else you can do with them.

Operations

10 min

The tuple space has three operations and one closing step, and that is the whole interface. Each operation has one exact meaning. Every use on this page is these same operations applied to a different shape of tuple.

addout

Add a tuple. The tuple's identity comes from fields that the caller supplies. If you send the same tuple twice, the space stores it once.

readrd

Read matching tuples. The tuples stay in the space. Any number of readers can read. With a timeout, the read waits until a tuple arrives.

takein

Claim one matching tuple. Exactly one caller wins. The winner holds a lease and ends it with ack, or returns the tuple with nack.

Templates

A tuple has keys, dimensions, and a body. The keys are what a take operation matches on, and the dimensions describe the tuple without being part of that match. Subspaces divide the space into named parts, and the engine registers a template for each kind of subspace. The template fixes four things: which keys are required, which dimensions are allowed, how long a tuple lives, and whether take operations are allowed. If they are allowed, it also fixes how many failed take operations turn a tuple into a dead letter. The engine checks every out against its template and refuses one that does not fit before it stores anything. Because only the engine holds the templates, every client sees the same shapes, and no client can hold an outdated copy.

Uses

Two of these uses exist today: the ledger, and the mailbox, which also carries request and reply when the address is a session instead of an agent (see Sessions and instances). The other three are in the table to show what the operations can do, not because anyone has planned them.

Small on purpose

Three operations with exact meanings are easier to build correctly, easier to analyze, and easier to combine than a larger interface would be. Each one is a short database transaction, so the space scales the way the database scales, and a busy subspace does not slow a quiet one. A take operation matches on keys alone and always ends in an ack or a nack. You can therefore say exactly what happens to any tuple under any sequence of calls, including a crash between a take operation and its ack. The uses in the table are not features of the space. They are compositions of the three operations, and a new use is a new composition rather than new code in the engine.

A tuple is metadata, not data. It says that an agent started, that a report exists, that a message is waiting, that a request needs an answer. It carries keys and a few dimensions, and its body is a pointer to whatever it is about: a document, a memory entry, a catalog link, a bead. There are no tuple documents. The documents stay in the stores built for them, and the tuple space holds only the signals about them. Keeping the two apart keeps the operations simple. An operation over a small typed record with exact keys can be specified completely. An operation over arbitrary content cannot.

The tuple space and the three stores

5 min

The tuple space is a fourth store beside the three Nexus already keeps, in the same database and behind the same engine. It holds coordination and nothing else, and points at the other three for everything else: scratch for a session, memory for a project, and knowledge for permanent documents.

StoreHoldsLifetimeReaders
Scratch (T1)Working notes of one session and its agentsThe sessionMany
Memory (T2)Decisions, findings, and the state of the work, by project and titleThe projectMany
Knowledge (T3)Documents, chunks, the catalog, and its linksPermanentMany
Tuple spaceCoordination: who is present, who owes a report, a message, a requestDays, set by the templateMany read, one takes

All four stores share one database and one tenant. A tuple can therefore name an item in any of the other three, and the reader opens it with the credential it already has. That is what decides what a tuple should contain.

References, not values

A tuple is a signal about data, so a message carries a pointer to its content, not the content itself. A chunk has a content hash, a document has a catalog address, a memory entry has a project and a title, and a scratch entry has an id. A message says "read this" with one of those pointers, and the reader opens the content where it is stored. This is a rule rather than a preference, for three reasons.

  • The content is already stored once, in the right store. A finding lives in memory and a document in the knowledge store. A copy inside a message becomes wrong the moment somebody corrects the original.
  • A tuple stays small. Tuples travel the same network path as every other call. Small tuples are what let a mailbox hold many messages and a ledger hold every dispatch of a session for ninety days.
  • A pointer can be checked. "The result is in memory under this title" can be verified by opening the entry. A message that copies the result cannot be distinguished from one that copies it incorrectly. The research page asks for the passage behind every claim for the same reason.
A message, as sent
to: <AGENT-ID>   from: <YOUR-ID>   kind: directive
body: The schema changed. Read memory <PROJECT>/<TITLE> before you write the migration.

The body names the memory entry, and the entry holds the full change. If somebody edits the entry before the agent reaches the message, the agent reads the edited version. It always reads what exists when it opens the entry, not what existed when the message was written.

Communication

10 min

A message to an agent is a tuple in the agent's mailbox. The agent reads its mailbox before it writes any reply to you. A correction you send while it works is read before that reply is written, not after.

Every agent gets an address when it starts. The hook that runs at agent start tells the agent its own id and its matching mailbox address. To send a message, you add a tuple to that mailbox with a message id that you create yourself. That id becomes the identity of the tuple. If the connection fails and you send again, the second send matches the same tuple, and the agent never sees the message twice.

You might say
Tell the agent that works on <THE TASK> that the schema changed. Put the message in its mailbox.
What Claude does

Claude makes one tuple_out call to the agent's mailbox with the message body and a message id. The agent's instructions tell it to read its mailbox before every reply, so on its next read it takes the message, acts on it, and acks it.

The body of the message is a pointer, not the content. It names the memory entry, the document, or the scratch note that holds what the agent needs, and the agent opens that item (see the three stores). A message that carried the content would be a copy, and the copy would be wrong the moment somebody corrected the original.

Each message reaches exactly one reader. When two readers take from the same mailbox, the claim statement hands each message to one of them, and the other does not receive it. A reader that takes a message and then crashes never acks it, so its lease ends, the message becomes available again, and the next reader gets it. After three failed take operations the engine marks the message as a dead letter. Nobody can take it, but anybody can read it, so a message that makes every reader crash stays visible instead of disappearing. An unclaimed or dead-lettered message survives at most seven days before the sweep removes it.

The agent never talks to the sender, and the sender never has to wait until the agent is between turns. Both talk to the tuple space. Neither has to know when the other is running. That is why a shared space works better than a direct message between two processes on different schedules.

Rendezvous

10 min

A read with a timeout lets the tuple space act as a meeting point. One process adds a tuple that means "done", and another process wakes when it arrives, whether it started waiting before or after.

The first use is waiting for an agent's report. When an agent stops, a hook adds a report tuple to the session's ledger with the agent's id as the key. Your session reads that key with a timeout. If the tuple is already there, the read returns immediately. If not, the read waits inside the engine and wakes when the tuple is written or the timeout ends. The agent does nothing to make this work, because the hook writes the tuple from the data the harness gives it.

You might say
Wait until <THE AGENT> reports. Then continue with its result.
What Claude does

Claude calls tuple_rd on the ledger with the agent's id and a timeout. Each call waits for at most twenty-five seconds and returns what it found, so a wait of minutes is a loop of these calls. The limit is deliberate. It keeps every wait shorter than every network timeout between the client and the engine, so a wait can never become a dropped connection.

The second use is waiting for the reply to a request. A session sends a request to a peer session, then calls in on its own mailbox with a timeout and wakes when the ack arrives. The request and the ack share a correlation id, which is how the reply is paired with its question.

The engine wakes a waiting read with a signal rather than by polling. When a tuple is written, the engine signals every reader waiting on that subspace once the write is committed, and readers on other subspaces are not signalled. A waiting read holds no database connection. When the engine stops for a deploy, it wakes every waiting read, and each returns what it has. A deploy therefore requires one retry, never a stall.

Queries

10 min

You can query the coordination state of the whole system, because tuples are rows with registered shapes. Before the tuple space, "who owes a report" was stored in a file that one shell function on one machine could read.

Three kinds of question have direct answers.

  • What is in a subspace. A read with an empty pattern returns every live tuple in it: for a ledger, every start and every report of the session, and for a mailbox, every waiting message. Tuples under a live claim and dead letters are included, each with its state. This read is the census, and only rd can do it. A take operation must give every key exactly, so a wide pattern can never claim a tuple by accident.
  • Which subspaces exist, and how full they are. A list by prefix returns every subspace that exists, with counts of available, claimed, dead, and consumed tuples and the oldest and newest timestamps. "Every session that started an agent in the last ninety days" is one call.
  • What happened to a tuple. Every claim, ack, nack, lease end, and dead letter writes one row to a claim log that is never edited. The history of a message is in that log, and the log is the only history. A restore from backup keeps the log, and any claim that was live at backup time ends when its lease ends.

Three rows in nx doctor watch the space as a whole. They report the age of the oldest unclaimed tuple in each subspace, the health of the database table, and the age of the last sweep. The sweep is the job that ends leases nobody renewed, removes expired tuples, and removes old claim-log rows after their own longer retention. A healthy space shows small numbers in all three. What these rows catch is a sweep that has stopped, which no single read would notice.

You might say
Which agents started in this session and did not report?
What Claude does

Claude reads the session's ledger with an empty pattern and compares the start tuples with the report tuples by agent id. The same question over the last several sessions is one list by prefix followed by that read for each session.

The tuple space has no embeddings and no similarity search. Reads match on equality only, and that is a decision rather than a gap. A lock or a mailbox must never be taken by a pattern less specific than the tuple, and a similarity match is exactly that. If similarity is ever added, it goes on rd only, where a wrong match costs a read and not a claim.

Sessions and instances

10 min

The tuple space is where sessions meet, because no single session owns it. A session's conversation is gone when it ends, and the sessions on one machine cannot see each other's context. All of them can read and write the same tuples.

Across sessions

A session that starts tomorrow can read which agents a session last week started and whether they reported, without that session's transcript. The ledger makes this possible: it is keyed on the session id and the agent id the harness assigns, and its tuples live for ninety days. Memory holds the findings of a session, and the ledger holds that session's accounting. Because hooks write the ledger rather than Claude, it is complete whether or not anyone remembered to write it.

Across instances

A mailbox addressed to a session's name is a channel between any two of the sessions on one machine. All of them share the same engine and the same tenant, and each has a name that the harness shows. One session adds a request to the other's mailbox with a correlation id, then calls in on its own mailbox and waits. The other session reads its mailbox, opens what the request names, and does the work. Then it adds an ack with the same correlation id to the first session's mailbox, and that wakes the first session. No person relays anything. An unanswered request is a tuple with an age that the census shows, not a line in a chat window that nobody reads.

You might say
Ask the <PEER SESSION> session to rebuild its gate jar. Wait for its ack.
What Claude does

Claude calls tuple_out to the peer's mailbox with kind "request" and a new correlation id. Then it calls tuple_in on this session's own mailbox in a loop, until an ack with that id arrives or you tell it to stop.

A request names its subject with a pointer, whether a bead id, a memory title, or a document address. If the work produces a result, the ack names where the result was written, and the requester opens it there.

No new addressing scheme was needed for this. Both sessions use one tenant, so the call that reaches an agent's mailbox reaches the peer session's mailbox too. A channel between two tenants is neither designed nor needed.

Implementation

10 min

One table, one log, and one handler, in the engine that already serves every other store. The design is small on purpose, and most of its value is what the database and the engine already provide.

  • One Postgres table holds the tuples. Subspace, keys, dimensions, body, expiry time, and claim state are columns, and a claim log table beside it records every claim event. The row-level security that separates one tenant's memory from another's applies to tuples unchanged.
  • A take is one statement. In one short transaction, the engine selects the oldest available row for the given keys, skipping any row another transaction holds, then locks it, marks it claimed, and logs the claim. A row someone else holds is skipped rather than waited for, so two hundred readers on one mailbox do not queue behind each other.
  • A lease bounds every failure. Every claim has an end time. A reader that crashes loses its claim when the lease ends, and a sweep on the engine's existing scheduler releases claims that nobody retook. A claim can never outlast its tuple, and after a fixed number of failed take operations the engine marks the tuple as a dead letter.
  • Every out is idempotent: sending the same one twice has no extra effect. The engine computes a tuple's identity from fields the caller supplies, never from the insert time. The same out sent twice, across a failed connection or an engine restart, is therefore one tuple. A retry needs no protocol of its own.
  • Waiting happens inside the engine. There is one engine process, so a waiting read waits on a signal for its subspace, which the engine sends after commit. The client does not poll, the wait holds no connection, and each wait is bounded so the client's own timeouts never fire first.
  • Templates are delivered with the engine. They are files the engine loads and checks at start. A bad template stops the start with the file and field named. A client can ask the engine for the templates and their digest, a short fingerprint that changes when the templates change, and detect a mismatch instead of guessing.

Building on the engine's Postgres gave the design durability, tenants, backup and restore, and a proven claim statement without designing any of them. An earlier version ran on a local database file and a vector store, and it was removed together with that storage layer. The design itself survived: registered templates, leases with ack and nack, a claim log that is never edited, and exact match for take operations. The move also removed the earlier version's bottleneck, where every operation queued behind one writer. Here each call is its own transaction, and a busy row is skipped.

Scope and status

5 min

Two uses are named, and no others. RDR-205 itself says that any third use needs a design record of its own. That rule is what keeps the earlier failure from repeating: the primitive stays small, and each use is decided on its own.

The tuple space deliberately excludes five things. The lease that protects an engine build stays out because it has to work while the engine is down. The files that hold a session's identity stay out because a reader needs a credential before it can read a tuple. The check that guards a push from a shared checkout stays out for the same reason: it must work with no engine. Scratch, memory, and plans stay out because they are read-many stores and should remain so. Rendered surfaces stay out because Nexus does not produce them.

Two limits are known and accepted for now. A claim cannot be extended, so a mailbox claim lasts at most fifteen minutes. Nothing enforces that fifteen minutes is enough. It holds only because nothing today asks for longer, and a task that needs more time loses its claim. A reply is a separate out from the take operation that claimed the request. A reader that crashes after taking the request and before sending the reply leaves the request unanswered. The request is delivered again when the lease ends, the work is repeated, and no reply is lost, because none was sent. Both limits could be removed later, with a renew operation and an ack that carries its reply in the same transaction. Neither is designed yet.

Status. The tuple space is live. The engine release that serves the tuple routes is published and deployed to the managed service. The current client release requires that engine, so a local install and a cloud install both have it. The ledger, the mailbox, and the request and ack between instances are in the released plugin. Every install class has been fully tested. A real dispatch on an installed plugin reaches the ledger, and a cloud client reads the tuples back through the public service address, not only from the engine directly.
