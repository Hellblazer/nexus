Working Together: Agents, Sessions, and Machines

Your Claude Code session, its agents, and other sessions can send work and replies to each other. The other sessions can run on your machine or on other machines. This page explains three things: who has an address, how a message reaches its reader, and what changes between machines.

Words in <ORANGE CAPITALS> are placeholders, and the prompts are examples. The Nexus Tuple Space explains the operations.

Terms used on this page
TermMeaning
engineThe Nexus service that owns the database and handles every call on this page.
tuple spaceOne shared store of small records in the engine. Any participant can add, read, or take a record.
agentA process that a session starts to do one task.
sessionOne Claude Code conversation. Its session id stays the same for the life of the conversation.
nameThe short label the harness shows for a session, such as nexus-8c. It can change when a session resumes.
mailboxThe part of the tuple space that holds messages for one address.
ledgerThe part of the tuple space where hooks record that an agent started and reported.
directoryThe part of the tuple space that maps each name to the session that holds it.
watcherA background command, nx tuple watch, that prints one line when a message arrives.
take operationA read that gives a message to one reader only. No other reader gets that message.
leaseThe time limit on a message that a take operation gave to a reader.
dead letterA message that failed three take operations. Anybody can read it, and nobody can take it.
correlation idAn id that a request carries and its reply repeats, so that the two can be paired.
1

The model in one picture

3 min

Nobody sends to anybody directly. Every participant writes to and reads from one shared space in the engine. Every participant has an address there.

ParticipantAddressGiven by
An agentits agent id, such as a3f7c2e1d09b4c551the harness, when the agent starts
A sessionits session id, a UUIDClaude Code, for the life of the conversation
A session, by nameits name, such as nexus-8cthe harness. The directory maps the name to a session id.

This means three things. A sender never needs the reader to be running, because the message waits in the reader's mailbox. Each message goes to exactly one reader. Any two sessions that use the same engine can send messages to each other, on any machine.

2

Your agents

4 min

An agent reports to your session through the ledger, and your session reaches an agent through its mailbox. Hooks do both of these steps. The agent needs no configuration.

You might say
Start an agent to <THE TASK>, and wait until it reports.
What happens

When the agent starts, a hook gives it an agent id and its mailbox address. When it stops, a hook writes a report record to your session's ledger, with that id as its key. Your session waits for the report in the ledger and continues when it arrives.

What you see
$ nx tuple rd ledger/<SESSION-ID> -n 300
  keys: {'kind': 'report', 'agent_id': 'aad95573891a57169'}
  created_at: 2026-09-15T11:53:16Z
  keys: {'kind': 'report', 'agent_id': 'a37fb0e62ffd57677'}
  created_at: 2026-09-15T11:53:48Z
You might say
Tell the agent that works on <THE TASK> that the schema changed.
What happens

Claude sends the message to the agent's mailbox, addressed by the agent id. The agent reads its mailbox before it returns its result, so it reads the message in time.

3

Sessions on your machine

5 min

You address a peer session by the name that the harness shows. mailbox_send resolves the name to a session id, and the message waits in that session's mailbox.

You might say
Ask <PEER NAME> to confirm its mailbox watcher is armed, and wait for the reply.
What happens

Claude calls mailbox_send with the name. The directory says which session holds the name, and the message goes to that session's mailbox.

What you see
$ nx tuple directory nexus-8c
'nexus-8c' resolves to session cdeb12b5-f397-478f-83cd-37b77a4f3160.

mailbox_send  to: nexus-8c   kind: request   correlation_id: r-41
→ {"to": "cdeb12b5-…", "address_kind": "session", "from": "5b354c36-…"}

How the peer receives the message

The peer's watcher prints a line as soon as the message arrives. A hook also shows any waiting message at the peer's next prompt. The reply arrives in your mailbox with the same correlation id. That id pairs the reply with your request. Your watcher prints a line for the reply.

What you see
nx-tuple-watch: new mail at mailbox/5b354c36-… from=cdeb12b5-… kind=reply correlation_id=r-41

The session's watcher sends its directory entry again every minute, and an entry ends five minutes after the last one. So a name leaves the directory at most five minutes after its session stops. mailbox_send refuses a name that no live session holds, or that two sessions hold. The refusal names the holders, so you can send to one session id directly.

4

Sessions on other machines

3 min

A session on another machine is reachable when both machines use the same engine. The directory and the mailboxes are in the engine, so the calls do not change.

In cloud mode, every machine connects to one managed engine. A session on your laptop and a session on a server then share one space. In local mode, each machine runs its own engine, and that space is private to the machine.

You might say
Send <REMOTE NAME> a note that the release is published.
What happens

Claude makes the same mailbox_send call. The name resolves in the shared directory to the remote session's id, and the remote session's watcher prints its line. A reply arrives in the same way.

What you see, from a test with a second host in cloud mode
mailbox_send  to: nexus-13
→ {"to": "5cab61d9-…", "address_kind": "session", "from": "5b354c36-…"}

# and the other direction, sent by the remote session
mailbox_send  to: nexus-b7
→ {"to": "5b354c36-…", "address_kind": "session", "from": "5cab61d9-…"}
5

Appendix: the rules that keep it safe

reference

You need none of this to use the model. It explains why a message is never lost, never read twice, and never delivered to the wrong session.

The rules
  • One reader per message. A take operation gives a message to one reader, and a second reader does not receive it.
  • A crash does not lose a message. A message that a reader took has a lease of at most fifteen minutes. If the reader does not acknowledge it before the lease ends, the message returns to the mailbox.
  • A message that fails three times stops. After three failed take operations, a message becomes a dead letter. Anybody can read it, and nobody can take it.
  • Nothing waits forever. An unread message lasts at most seven days.
  • A name is a lease. It lasts five minutes. The session's watcher sends it again every minute. mailbox_send refuses a name with no live holder or with two holders.
  • A session keeps the correct mailbox after it changes. After /clear, /resume, or /branch, the old watcher stops itself. After /branch, the new session gets its own id, and the original session keeps its mailbox.
  • A message is a pointer. A message body is at most 4096 bytes. It names where the content is, such as a memory title or a document address. It does not carry the content itself.

Source: Hellblazer/nexus, the RDR-208 design record for session addressing, and The Nexus Tuple Space for the operations.
